# Surface After Care — Регулярный раунд обслуживания опубликованного репозитория

## Когда использовать этот навык

Используйте его для репозитория, который **уже публичен** и требует планового осмотра. Это недорогой уровень: всё, что можно решить в рамках самого репозитория без инвентаризации сторонних проектов и запроса юридических заключений.

Разграничение со смежными навыками:

| Ситуация | Навык |
|---|---|
| Репозиторий публикуется впервые | `github-repo-care` |
| Репозиторий публичный, плановый раунд обслуживания | **этот навык** |
| Дополнительно юридическая проверка + перекрестные ссылки по всем орг + i18n приложения | `full-after-care` (Синоним `deep-after-care`) |
| Чистая проверка права/приватности/лицензии перед публикацией | `repo-publish-check` |
| Синхронизация языковых версий документов по содержанию | `bilingual-doc-sync` |
| Распределение этого раунда по множеству репозиториев с честной ротацией | `rotation-check` |

## Основная идея

Опубликованный репозиторий расходится в двух направлениях: **документация описывает более старую версию ПО, чем лежит в репозитории**, и **накапливаются файлы, никогда не предназначавшиеся для чужих глаз**. Ни то, ни другое обычно не катастрофично, но отпугивает ровно тех пользователей, которых вы хотите привлечь — один уходит, потому что инструкция по установке не работает, другой — потому что видит в корневой папке `AUFGABEN.txt` и `Plan.txt` и создает впечатление, будто разработчик пишет код только для себя.

Этот раунд устраняет обе проблемы. Он сознательно рассчитан на частые повторения: лучше полчаса четыре раза в год, чем одна генеральная уборка раз в год.

## Ход работы

Последовательность не произвольна. Шаг 0 стоит в начале, так как он определяет объем всех последующих шагов. Шаг 2 выполняется перед любыми действиями, отправляющими изменения — иначе вы закоммитите улучшения поверх состояния, которое еще только предстоит очистить. Шаг 1 выполняется исключительно на стороне сервера и не создает помех.

### 0. Инвентаризация площадок дистрибуции

**Перед внесением изменений: выясните, где расположен этот проект.** GitHub-репозиторий редко является единственной площадкой. Исправленный README малополезен, если страница пакета на npm продолжает показывать старую версию с неверными командами установки — а ведь большинство пользователей попадает именно туда, так как реестры пакетов часто ранжируются в поисковиках выше самих репозиториев.

```bash
# Манифесты раскрывают каналы
cat package.json pyproject.toml setup.py Cargo.toml 2>/dev/null | rg -n "name|version|keywords|repository|homepage"
rg -n "npmjs.com|pypi.org|marketplace|registry|crates.io|hub.docker|zenodo|doi" README* docs/ .github/ 2>/dev/null

# Запрос опубликованного состояния каналов (только применимые)
npm view <paket> version description keywords 2>/dev/null
pip index versions <paket> 2>/dev/null
gh release list --repo ORG/REPO --limit 5
```

Типичные площадки: npm, PyPI, Crates, Docker Hub, реестр MCP, каталоги плагинов/навыков, маркетплейсы VS Code или браузеров, магазины приложений, Zenodo/DOI, веб-сайт проекта, профиль организации, `llms.txt`, зеркала репозитория на других хостах.

Зафиксируйте найденный список в журнале выполнения. Отныне это ваша **целевая матрица**: любое изменение из следующих шагов в конце отзеркаливается на этот список (см. "Паритет по всем площадкам"). Если вы обнаружили площадку, которую никто больше не поддерживает и которая ссылается на заброшенную версию, это самостоятельное замечание — либо обновите её, либо сознательно отзовите, но не оставляйте в заброшенном виде.

### 1. Установка тегов (Topics)

Topics — важнейшая поисковая поверхность внутри GitHub, не требующая почти никаких затрат.

```bash
gh repo view ORG/REPO --json nameWithOwner,description,repositoryTopics,homepageUrl,visibility
gh repo edit ORG/REPO --add-topic <topic> --add-topic <topic>
```

Цель — примерно 5–12 тегов с трех ракурсов: **чем является** (`cli`, `mcp-server`, `python-library`), **о чем проект** (`file-management`, `tax`, `note-taking`) и **как работает** (`local-first`, `offline`, `privacy`). Ориентируйтесь на теги, реально используемые у похожих проектов — выдуманные теги не приведут пользователей. Заодно проверьте Description и Homepage, они находятся в том же представлении.

Теги имеют эквиваленты на других площадках из Шага 0: `keywords` в `package.json`, `keywords`/`classifiers` в `pyproject.toml`, категории и теги в маркетплейсах и магазинах. Держите их идентичными по содержанию — это одно и то же решение в разных местах.

### 2a. Шлюз приватности (Privacy-Gate) — выполняется всегда

Этот шаг никогда не пропускается, даже при кажущемся безобидным раунде. Поиск ведется в **отслеживаемом (tracked)** множестве файлов, а не в видимом рабочем дереве, ведь в этом и заключается разница между "выглядит чистым" и "является чистым".

```bash
git ls-files
rg -n "C:\\\\Us[e]rs\\\\|/home/[a-z]|s[k]-[A-Za-z0-9]{16}|gh[p]_|gh[o]_|AKIA[0-9A-Z]{16}|API[_-]?KEY|TO[K]EN|PASS[W]ORD|SEC[R]ET|BEGIN [A-Z ]*PRIVATE KEY" $(git ls-files)
rg -n "\x{C3}\x{83}|\x{C2}\x{A0}|\x{FFFD}" $(git ls-files -- '*.md' '*.txt' '*.json')
```

Дополните шаблоны поиска **названиями ваших собственных внутренних папок** — папки пайплайнов, тематические директории, приватные рабочие области:

```bash
rg -n "\.SOFTWARE|\.RESEARCH|_control-center|<weitere eigene Ordnernamen>" $(git ls-files)
```

Такие ссылки не являются секретами и не вызывают срабатывания сканеров безопасности, поэтому проскакивают незамеченными — но они **нерешаемы** для внешних читателей ("перенесено из пайплайна .SOFTWARE" ничего не говорит посторонним) и раскрывают внутреннюю структуру. Их следует заменять или удалять, а не терпеть. Поиск, ориентированный только на `C:\Users\…` и токены, гарантированно их не найдет.

Нашли что-то? **Характер** находки определяет порядок действий — см. раздел "Правило Force-Push". Закоммиченный секрет считается скомпрометированным: удаления из `HEAD` недостаточно, его необходимо ротировать.

### 2b. Проверка намерения публикации документов

Главное ядро этого раунда. Просмотрите отслеживаемые файлы `.md`, `.txt` и `.json` и спросите по каждому: **Предназначался ли этот файл для чужих глаз?**

```bash
git ls-files -- '*.md' '*.txt' '*.json' | sort
```

Не угадывайте по имени файла — загляните внутрь. Файл `PLAN.md` может быть публичной дорожной картой, а безобидный `notes.md` — внутренней стратегией ценообразования. Три категории:

**Остается в репозитории** — README, LICENSE, CHANGELOG, SECURITY, CONTRIBUTING, `docs/`, справочники API, примеры конфигураций, реальные дорожные карты, манифесты (`package.json`, `pyproject.toml`), lock-файлы, конфигурация CI.

**Не должно быть в репозитории, но не критично** — обычный случай этого раунда. Файлы задач и планирования (`AUFGABEN.txt`, `Plan.txt`, `TODO-intern.md`), заметки сессий и передачи дел (`HANDOFF`, `BRIEFING`, `_handoff/`), файлы состояния собственных пайплайнов, дневники разработки, `_archive/`, JSON-файлы реестров и индексов с локальными путями, промежуточные результаты и сгенерированные артефакты, рабочие файлы агентов. Такие файлы не опасны, но создают неряшливость и впечатление неразобранной стройки. Решение: обновить `.gitignore`, выполнить `git rm --cached <файл>` и **запушить как обычно**.

**Не должно быть в репозитории и конфиденциально** — учетные данные (Credentials), персональные данные, данные клиентов, внутренние финансовые расчеты, стратегии цен/переговоров, неопубликованные бизнес-планы, черновики договоров, всё, что имеет коммерческую ценность. Здесь обычного коммита недостаточно, см. Правило Force-Push.

В отношении `.json` требуется дополнительное внимание: манифесты и lock-файлы остаются, но локальные конфиги, файлы задач/реестров, дампы экспорта и все, что содержит абсолютные пути или имена хостов, являются типичными безбилетниками.

Если вы удаляете файл, который кто-то может искать (например, дорожную карту), кратко укажите в коммите или README, где теперь находятся эти сведения — иначе это выглядит как регресс.

### 3. Баннер

Баннер часто определяет, начнет ли посетитель читать страницу вообще. Проверьте, существует ли баннер и встроен ли он в README в качестве первого элемента.

Если баннер отсутствует, есть три пути (в порядке приоритета):

1. **Генератор изображений агента** (например, agy; слово "сгенерируй" там является триггером для создания реального PNG), если визуальный мотив подходит лучше типолики.
2. **Codex**, если баннер должен быть создан из кода и есть визуальный образец стиля.
3. **Самостоятельное создание SVG**, если баннер — это прежде всего текстовый логотип плюс формообразующий язык: часто это самый быстрый и управляемый вариант, а SVG легко редактировать в дальнейшем.

Соблюдайте стиль семейства, если проект входит в группу: единый базовый цвет, единая эстетика, единое оформление логотипа. Выбивающийся из стиля баннер выглядит хуже, чем его отсутствие. Стандартный размер 1200x300; PNG сохраняется в репозиторий, SVG-исходник лежит рядом.

### 4. Сверка утверждений с реальным кодом

Здесь создается максимальная ценность. README утверждает факты — проверьте их в коде, а не верьте на слово:

- **Версия** в README/Badge сверяется с `pyproject.toml`/`package.json`/`__version__` и с последним релизным тегом. Если версий несколько, проверьте все.
- **Путь установки** пройдите на практике (как минимум логически): существует ли пакет с указанным именем? Совпадают ли команды и флаги?
- **Список возможностей** сверьте с кодом: все ли описанное присутствует и не забыто ли новое?
- **Цифровые показатели** (количество инструментов, поддерживаемые форматы, покрытие тестами) пересчитайте в источнике. Цифры в README тихо устаревают.
- **Скриншоты** сверьте с текущим интерфейсом.
- **Требования** (версия Python/Node, зависимости) сверьте с манифестами.
- **Ссылки** на соседние проекты, документацию и реестры: работают ли они?

**Исправление применяются ко всем площадкам, а не только там, где была замечена ошибка.** Если утверждение оказалось ложным — особенно если его поправил владелец —, высока вероятность, что то же утверждение встречается в других местах: в профиле организации, в `llms.txt`, во второй языковой версии, в README соседнего проекта. Выполните целевой поиск перед закрытием задачи:

```bash
gh search code "<характерная фраза>" --owner ORG
```

Иначе вы исправите одну точку и оставите три — и противоречие всплывет только при обслуживании следующего репозитория. Это не только тратит время, но и подрывает доверие к документации: тот, кто находит два разных описания одного и того же, не верит ни одному.

Затем улучшите **оформление** в слабых местах: длинные списки опций лучше смотрятся в виде таблиц; блокам кода нужны языковые теги; обзор структуры или процесса в виде Mermaid-диаграммы или ASCII-дерева воспринимается быстрее текста; первый экран должен показывать назначение, установку и пример использования, а не значки и предысторию. Если README превышает ~400 строк, вынесите подробности в `docs/` и дайте ссылки.

**Правило языков для README:** Стандартом является **английский `README.md`** плюс **вторая версия на немецком**. Исключение: предметная область самого приложения является немецкоязычной (немецкое право, налоги, система субсидирования, немецкоязычная аудитория) или до сих пор существовала только немецкая версия — тогда немецкий остается основным языком. Для каждого дополнительного языка, который проект уже поддерживает в коде, должна быть соответствующая версия README. Придерживайтесь конвенции наименования, уже принятой в репозитории (`README_de.md`, `README.de.md`, `docs/README.de.md`), не выдумывая вторую. Связывайте версии перекрестными ссылками в заголовке.

### 6. Создание недостающих стандартных языков

Дополните версиями README на **стандартных языках**: немецком, английском, испанском, упрощенном китайском, японском, русском. Цель — охват аудитории, поэтому это относится прежде всего к пользовательским проектам. Для библиотеки разработчиков с чисто английской аудиторией русский README не приносит пользы, а создаёт лишь лишнюю нагрузку при обслуживании. Принимайте взвешенное решение и фиксируйте его в журнале выполнения.

Новые версии **заполняются реальным контентом, а не создаются пустыми** — заготовка с "TODO: translate" хуже отсутствия файла, так как создаёт ложную видимость полноты. Параллелизм содержания и синхронизацию обеспечивает `bilingual-doc-sync`; при наличии более двух версий имеет смысл задействовать этот навык.

### 7. Видимость и продвижение

Продумайте, какие меры реально приведут пользователей для **данного** проекта, и реализуйте их:

- **Реестры**, к которым проект относится технически: пакетные реестры (npm, PyPI), реестр MCP, каталоги плагинов/навыков, маркетплейсы.
- **Курируемые списки** (`awesome-*` и тематические подборки), если критерии приема действительно выполнены. PR в список, критериям которого проект не соответствует, портит репутацию.
- **Собственные площадки**: Профиль организации, `llms.txt`, сайт проекта, README экосистемы, ссылки из связанных собственных репозиториев.
- **Release Notes** как повод: Релиз без рассказа о новых функциях останется незамеченным.

**Шлюз одобрения (Approval Gate):** Всё, что выходит вовне — PR в сторонние репозитории, записи в сторонних списках, публикации, заявки — **сначла предлагается и выполняется только после явного одобрения**, если для этого канала нет постоянного разрешения. Изменения на собственных площадках не требуют этого шлюза. Причина проста: отозванный PR в чужом репозитории виден публично и бросает тень на проект.

### 8. Запись на страницах организаций

Сначала собственная организация: указан ли репозиторий в README профиля (`ORG/.github` → `profile/README.md`) вообще, в правильном ли разделе, с актуальным ли описанием?

```bash
gh api user/orgs --jq '.[].login'
```

Затем пройдите по **всем** организациям и ответьте на один вопрос по каждой: получит ли посетитель этой страницы организации пользу от данного репозитория? В большинстве случаев ответ «нет» — тогда «не ссылаться» является правильным результатом, а не пробелом. Где ответ «да» (тематическая близость, общие пользователи, инструмент, дополняющий тамошние проекты), установите ссылку с предложением, объясняющим пользу, а не просто названием.

Профиль живет в отдельном репозитории (`ORG/.github`). Изменения там вносятся и пушатся параллельно — по правилу грязного дерева из Шага 11.

### 10. Issues и Pull Requests

```bash
gh issue list --repo ORG/REPO --state open --limit 50
gh pr list --repo ORG/REPO --state open --limit 30
```

Проработайте их, а не просто посчитайте:

- **Исправимые баги** устраните сразу — контекст в этом раунде всё равно загружен. Компактные фиксы с тестом и ссылкой на номер Issue.
- **Уже решенные Issues** закройте с пояснением в одно предложение.
- **Неясные репорты** требуют уточняющего вопроса (версия, ОС, шаги воспроизведения).
- **PR**: внимательно прочитайте Diff, запустите тесты, затем смержите или мотивированно ответьте. PR, висящий месяцами без ответа, отнимает больше лояльности, чем вежливый отказ.
- **Зависшие (Stale) случаи** разрешите, а не тяните дальше.

**Шлюз одобрения (Approval Gate):** Публичные комментарии, закрытия с обоснованием и мерж чужих вкладов являются внешней коммуникацией — предоставляйте их до выполнения, если нет постоянного разрешения. Чистые фиксы кода в своем репозитории этим не затрагиваются.

### 11. Коммит, пуш, верификация

Раунд заканчивается не на правках, а когда они **опубликованы снаружи**. Рабочее дерево, полное незапушенных улучшений — наихудший результат: следующая сессия — возможно, другого агента или на другом устройстве — должна будет сначала разбираться в чужом полуготовом состоянии, а на публичных площадках ничего не изменилось.

Перед пушем кратко проверьте то, что поддается проверке: запустите тесты и смоук-чеки, при правках документации проверьте ссылки и скомпилированный вид. Затем сгруппируйте в **тематически разделенные коммиты**, а не сваливайте всё в один коммит-свалку — уборка, обновление документации и фиксы багов являются тремя разными вещами, и тот, кто позже захочет откатить одну из них, будет благодарен:

```bash
git add .gitignore && git rm --cached <interne dateien>
git commit -m "chore: убрать внутренние рабочие файлы из отслеживания"
git commit -am "docs: обновить README (версия, число инструментов, скриншоты)"
git commit -am "fix: <номер issue> ..."

git pull --rebase        # при разошедшейся ветке, перед пушем
git push
```

Затем верифицируйте, а не предполагайте: удаленный README в скомпилированном виде, прогон CI, состояние релизов и тегов.

```bash
gh run list --repo ORG/REPO --limit 3
gh repo view ORG/REPO --json description,repositoryTopics,url
```

**Если CI загорелся красным, хотя ваш коммит касался только документации**, причина почти никогда не в вас. Самый частый случай — в этом семействе репозиториев встреченный **трижды** за один день — это **неприкрепленный линтер без фиксированного набора правил**. Проверьте это **в первую очередь**, прежде чем подозревать свой коммит.

Механизм: если в Workflow запускается `ruff check` (или flake8, eslint …) с неприкрепленной зависимостью (`ruff>=0.12` или вообще без версии) и отсутствует явный выбор правил (`[tool.ruff.lint] select = [...]`, при отсутствии `pyproject.toml` — отдельный `ruff.toml`), то линтер следует дефолтам **заново установленной** версии. Новый релиз линтера смещает этот дефолт, и неизмененный код становится красным. Признаки:

- Коды правил, которых у проекта никогда не было (`UP045`, `UP006`, `BLE001`, `RUF100`, `DTZ005`, `N999` …), иногда сотнями.
- Сбой часто происходит **межплатформенно**: раннеры с закэшированной старой версией остаются зелеными, свежие становятся красными.
- Иногда правило ругается на неисправимое (`N999` на само имя пакета) — верный знак, что оно никогда не было стандартом.

Фикс: зафиксировать набор правил, который раньше был зеленым — `select = ["E4","E7","E9","F"]` являются классическими дефолтами ruff. Если `pyproject.toml` нет, создайте `ruff.toml`. Проверьте на **новой** версии линтера (установить, без конфига воспроизвести находки, с конфигом увидеть "passed"). Новые правила становятся **задачей** для проекта — осознанное принятие является рішенням, а не побочным эффектом обновления инструмента. Это реальная повторяющаяся проблема: без фиксации CI снова упадет при следующем релизе линтера в **каждом** аналогично настроенном репозитории.

Два случая, когда пуш **не** выполняется: если для проекта действует заморозка публикаций/сдачи, или если состояние явно не завершено. И то, и другое — исключения с обоснованием; стандартный случай: закоммитить и запушить.

При заморозке публикаций раунд не прерывается, а **перенаправляется**: закоммитить локально на отдельной ветке (`judging-hold/…`, `freeze/…`), оставить основную ветку нетронутой на сданном состоянии, отметить причину заморозки в журнале выполнения и подтянуть после снятия. Важно соблюдать последовательность: заморожен не только `git push`, но и **любые удаленно видимые изменения** — темы, описание, домашняя страница, релизы, действия с Issues и PR меняют опубликованный проект точно так же.

Если существуют другие клоны того же репозитория (второе устройство, деплой-копия, зеркало), подтяните их сразу после пуша. Клон, отставший на десять коммитов, при следующей отладке выдаст диагнозы по состоянию, которого больше нет.

#### Изменения в других репозиториях — исключение грязного дерева (Dirty Tree)

Этот раунд регулярно создает изменения **за пределами** обслуживаемого репозитория: строка в профиле организации (Шаг 8), позже в глубоком раунде — обратная ссылка в связанном репозитории. Такие изменения также коммитятся и пушатся — незапушенная обратная ссылка не является ссылкой.

Перед тем как трогать чужой репозиторий, кратко проверьте его состояние:

```bash
git -C <путь> status --porcelain
```

**Чистое рабочее дерево** → внести изменение, закоммитить в **отдельном тематическом коммите** (`docs: link <проект>`) и запушить. Не смешивать с коммитами обслуживаемого репозитория: это другой репозиторий со своей историей и читателями.

**Грязное, но чужие изменения в других файлах** → ваше изменение все равно можно сделать чисто. Застейджите и закоммитьте **строго по пути только свой файл**, чтобы чужая непроверенная работа не ушла вместе с ним:

```bash
git -C <путь> add README.md
git -C <путь> commit -m "docs: link <проект>"     # только застейдженный путь
```

Но **не пушить**. Коммит локально безвреден; пуш может быть опасен: вы не знаете, к чему ведет чужое рабочее состояние — возможно, его сейчас правят, ребейзят или режут иначе, и ваш пуш заставит других разбираться с конфликтами. Локальный коммит сохраняет работу, никому ее не навязывая; раунд, который позже займется тем репозиторием, найдет его и заберет с собой.

**Грязные изменения ровно в том файле, который нужно править** → не трогать. Здесь вам пришлось бы строить поверх чужого промежуточного состояния и коммитить его вместе; разобраться в нем сначала стоит дороже, чем одна эта ссылка.

**Активная блокировка (`LOCK*.txt`) в целевом репозитории** → **сначала прочитать блокировку, а не воспринимать ее как тотальный запрет.** Блокировка описывает свой объем, и он часто уже, чем "вообще ничего". Типичные случаи:

- **Блокировка редактирования** ("здесь сейчас кто-то работает") → ничего не трогать, даже соседние файлы.
- **Чистая блокировка публикации/пуша** (сдача, судейство, заморозка) → локальная работа остается разрешенной, заблокирован только удаленный контакт. Работать на отдельной ветке и коммитить локально; **удаленно видимые шаги опускаются** — не только пуш, но и темы, описание, домашняя страница, релизы и действия с Issues/PR.

Восприятие блокировки, запрещающей только пуш, как тотального запрета, теряет всю локальную часть раунда без выигрыша в безопасности. И наоборот, недостаточно лишь опустить пуш, продолжая менять метаданные. При сомнениях процитируйте блокировку и спросите.

#### Пожелание не должно быть потеряно

Если изменение **не** выполнено по одной из этих причин, оно переносится в список задач целевого репозитория — `AUFGABEN.txt`, `TODO.md` или `TODO.txt`, в зависимости от того, что там есть. Запись с датой, желаемым изменением и причиной:

```markdown
- [ ] [2026-07-24, after-care] Добавить обратную ссылку на <проект> в README
      (пропущено: README содержал незакоммиченные чужие изменения)
```

В этом разница между «отложено» и «забыто»: список задач находится там, куда следующий исполнитель этого репозитория все равно заглянет — надежнее, чем заметка в протоколе чужого прогона. Если списка задач нет, не создавайте его; достаточно открытого пункта в собственном журнале выполнения.

При **активной блокировке не применяется и это** — файл остается нетронутым, а заметка остается исключительно в собственном журнале выполнения. Запишите ее туда в обоих случаях, чтобы ротация знала об открытых пунктах.

В завершение обслужите площадки из Шага 0 — см. следующий раздел.

## Паритет по всем площадкам дистрибуции

В завершение раунда сверьтесь со списком из Шага 0: **Каждое изменение, которое увидел бы пользователь, должно попасть на каждую площадку, где он его ищет.** Репозиторий, страница которого на npm рассказывает другую историю, находится в худшем положении, чем проект с одной площадкой.

Решающий механизм: **Реестры пакетов показывают README последнего Publish, а не текущее состояние репозитория.** Исправление README на npm или PyPI становится видимым только с новой версией. Если исправление существенно по содержанию (неверная установка, неверная версия, устаревший список функций), к нему относится патч-релиз — иначе фикс останется неэффективным.

| Площадка | Что там обслуживается | Как туда попадает |
|---|---|---|
| npm | README, `description`, `keywords`, ссылка на репозиторий | Только через `npm publish` (патч-версия); метаданные берутся из `package.json` |
| PyPI | README (`long_description`), классификаторы, URLs проекта | Только через новую загрузку; метаданные из `pyproject.toml` |
| Реестр MCP / Каталоги плагинов | Описание, версия, список инструментов, вводная документация | В зависимости от реестра: обновление манифеста или повторная сдача |
| Маркетплейс / Магазин | Описание, скриншоты, категории, языковые версии | Через соответствующий интерфейс управления; скриншоты там стареют особенно быстро |
| Docker Hub / Реестр контейнеров | Описание, теги, пример использования | Описание репозитория плюс новый тег |
| Zenodo / DOI | Метаданные, авторы, версия | Прямое редактирование метаданных, новая версия для контента |
| Веб-сайт / Профиль орг / `llms.txt` | Краткое описание, ссылка, позиционирование | Прямое редактирование — самые дешевые площадки, никогда о них не забивайте |

При поднятии версии **все носители версии** должны обновляться одновременно: манифест, константа в коде, бейдж в README, ченджлог, релизный тег, `llms.txt`. Наполовину поднятое состояние версии диагностировать сложнее, чем сквозное старое.

Если обновление на какой-то площадке сейчас невозможно или нецелесообразно (например, релиз только ради опечатки), зафиксируйте это в журнале выполнения, чтобы следующий раунд не принял расхождение за оплошность.

## Правило Force-Push

Стандартом является **отсутствие Force-Push**. Задним числом проигнорировать внутренние файлы планирования не оправдывает переписывания истории: затраты высоки, каждый клон и форк ломается, открытые PR становятся непригодными — а выигрыш ничтожен, так как содержимое безобидно. Стандартный путь:

```bash
git rm --cached <файл>            # из отслеживания, локально сохраняется
# обновить .gitignore
git commit -m "chore: убрать внутренние рабочие файлы из отслеживания"
git push
```

Переписывание истории (и тем самым пуш с `--force-with-lease`) оправдано только при **реальных утечках (Leaks)**: учетных данных и ключей, персональных данных или данных клиентов, а также документов с реальной коммерческой ценностью — внутренних расчетов, ценовых стратегий, неопубликованных планов, условий договоров. В этом случае:

1. **Сначала ротировать утекшие секреты** — история к этому моменту уже скопирована, зафоркана и закэширована. Ротация работает; удаление — лишь косметика.
2. Очистить историю (`git filter-repo` или BFG), запушить с `--force-with-lease`.
3. Проверить форки и кэши; при необходимости связаться с поддержкой GitHub для удаления сиротских объектов.
4. Зафиксировать операцию в журнале выполнения: что, когда, какая ротация.

При сомнениях между "не критично" и "конфиденциально": обращаться как с конфиденциальным и предоставить на рассмотрение. Издержки асимметричны.

## Замечания становятся задачами, а не просто строками журнала

Раунд обслуживания регулярно находит больше, чем может или должен исправить в том же прогоне: отсутствующую языковую версию, отставание по модернизации, публикацию, которая так и не состоялась. **Такие находки в момент обнаружения становятся задачами** — иначе они останутся погребенными в протоколе завершенного прогона, куда следующий исполнитель проекта не заглянет.

Задача относится к **локальной системе задач папки проекта** — туда, куда заглянет тот, кто следующим будет работать над этим проектом. Обычно это `AUFGABEN.txt` или `TODO.md` в папке проекта, которая часто **не находится внутри Git-клона**, а в директории, где живет планирование проекта. Клон содержит код, папка проекта — управление; запись в клоне, которая исчезнет при следующем `git clean`, не является задачей.

Учитывайте три момента:

1. **Разделять внутренний список задач и публичную дорожную карту.** Файл `TODO.md` может быть ухоженной публичной дорожной картой — тогда он не место для сброса внутренней доработки. Загляните внутрь, прежде чем дополнять: если там есть заголовок вроде "Public roadmap", пишите во внутренний файл рядом (`AUFGABEN.txt`) и помечайте как внутреннее.
2. **Проверять существующие записи перед дублированием.** Часто находка уже там записана. Тогда не создается новая запись, а **обогащается** имеющаяся — эмпирическим доказательством из этого прогона ("подтверждено: `--help` выдает полностью немецкий вывод"). Известный пункт со свежим доказательством ценнее второй дублирующей записи рядом.
3. **Записывать выполненное.** То, что раунд исправил, относится к выполненным пунктам с хэшем коммита. Это объясняет следующему раунду, почему находка исчезла, и предотвращает её повторное "открытие".

Формулируйте задачу так, чтобы она была понятна без контекста этого прогона: что найдено, почему это важно, каков следующий шаг. "i18n неполный" — не задача; "Каталог содержит только `status.title`, там es/zh/ja/ru пустые — сначала перенести CLI-строки в каталог, затем заполнить все шесть языков" — задача.

## Журнал выполнения

Зафиксируйте результат в `_after-care/LOG.md` (папка относится к `.gitignore` — это материал пайплайна, а не контент репозитория, строго по Шагу 2b). На каждый прогон одна строка с датой, уровнем и осознанными решениями:

```markdown
## 2026-07-24 — surface
- Площадки: GitHub, npm (<paket>), реестр MCP, профиль орг, llms.txt
- Topics: +local-first, +mcp-server; keywords в package.json выровнены
- Удалено: AUFGABEN.txt, _handoff/ (добавлено в gitignore, force-push не нужен)
- README: Версия 0.9 -> 1.2 исправлена, число инструментов 23 -> 26 пересчитано
- Языки: EN + DE поддерживаются; ES/ZH/JA/RU сознательно пропущены (разработческая аудитория)
- Issues: #12 исправлен, #7 закрыт (решено), по #15 задан уточняющий вопрос
- Push: 3 коммита, CI зеленый; npm-републикация 1.2.1 из-за правки README
- Открыто: Скриншоты в store устарели, требуют нового билда
```

Протокол избавляет следующий раунд от повторного принятия тех же решений и является основой для ротационных раундов обслуживания по многим репозиториям (`rotation-check`).

## Частые ошибки

| Ошибка | Исправление |
|---|---|
| Смотрели только рабочее дерево, а не `git ls-files` | Всегда проверять отслеживаемое множество — там кроются проблемы |
| Шлюз приватности искал только пути и токены | Искать также имена собственных папок/пайплайнов — они не вызывают тревог и проскакивают |
| Внутренний файл удален с переписыванием истории | Для некритичных файлов достаточно `git rm --cached` + обычный пуш |
| Секрет удален из `HEAD` и процесс сочтен завершенным | Ротировать секрет; все остальное — косметика |
| Файлы классифицированы строго по имени | Кратко заглянуть внутрь — имена не передают намерение надежно |
| Цифры в README увеличены без пересчета | Считать в источнике (список инструментов, прогон тестов, манифест) |
| Новая языковая версия создана пустым шаблоном | Заполнить или опустить — пустой шаблон имитирует полноту |
| Введена вторая конвенция наименования README рядом с имеющейся | Принять конвенцию, существующую в репозитории |
| PR в сторонний список отправлен без одобрения | Внешнюю коммуникацию предоставлять до отправки; свободны только свои площадки |
| Issues посчитаны вместо обработки | Исправить, закрыть или задать уточняющий вопрос — каждый случай получает статус |
| Баннер создан самостоятельно в чужом стиле | Соблюдать дизайн-семейство экосистемы |
| README в репозитории исправлен, страница npm/PyPI показывает старый | Страницы реестров берутся из последнего Publish — сделать патч-релиз |
| Версия поднята только в манифесте | Все носители версии одновременно: манифест, код, бейдж, ченджлог, тег, `llms.txt` |
| Изменения готовы, но оставлены незапушенными | Коммит и пуш входят в раунд; только блокировки оправдывают исключение |
| Все изменения в одном коммите-свалке | Разделять уборку, документацию и фиксы — иначе ничто нельзя откатить отдельно |
| CI красный после коммита документации, подозреваете себя | Неприкрепленный линтер без `select` следует дефолту новой версии — зафиксировать набор правил |
| Неверное утверждение исправлено только там, где замечено | Искать фразу по всей организации — обычно она есть в профиле орг, `llms.txt` и во 2-й языковой версии |
| В грязном чужом репозитории работали с `commit -a` | Стейджить строго по путям и коммитить, не пушить — чужая работа остается нетронутой |
| Изменение в чистом репозитории профиля орг сделано, но не запушено | Чистые чужие репозитории получают отдельный коммит **и** отдельный пуш |
| Пропущенное изменение записано только в своем протоколе | Дополнительно записать в список задач целевого репозитория, если он есть |
| Находка записана только в журнал выполнения | Переводится в задачу в локальной системе папки — в журнал позже никто не заглянет |
| Внутренняя доработка повешена на публичную дорожную карту | Сначала заглянуть внутрь; "Public roadmap" означает: использовать внутренний файл рядом |
| Известная находка продублирована новой записью | Обогатить имеющийся пункт свежим доказательством из этого прогона |
| При блокировке редактирования записана строка TODO в заблокированный репо | Блокировка относится ко всему проекту — ни к чему там не прикасаться |
| Блокировка пуша прочитана как тотальный запрет и весь репо пропущен | Прочитать блокировку: если она запрещает только публикацию, вести локальный раунд на отдельной ветке |
| При блокировке пуша пуш опущен, но изменены темы или описание | Метаданные видны удаленно — при заморозке публикаций они опускаются тоже |

## История изменений

### 1.6.0 (2026-07-24)
- Добавлено правило: Содержательная правка применяется ко всем площадкам. Вывод из практики — уточнение пользователя было исправлено в прогоне 1 в хабе, но незамеченным оставалось еще в пяти местах в профиле организации (EN, DE, `llms.txt`) и было замечено только через девять прогонов.

### 1.5.0 (2026-07-24)
- Уточнена диагностика линтера после трехкратного проявления паттерна за день (n8n-workflow-manager ruff 0.15, clirec + swarm-ai ruff 0.16): "сначала проверить", конкретные коды правил-виновников, разделение по платформам, `ruff.toml` как фикс при отсутствии `pyproject.toml`, верификация на новой версии линтера.

### 1.4.0 (2026-07-24)
- Добавлена диагностика: Если CI стал красным после коммита чистой документации, частая причина — неприкрепленный линтер без фиксированного набора правил (новый релиз меняет дефолт и делает неизмененный код красным). Фикс: зафиксировать набор правил, новые правила как задача. Случилось дважды подряд (n8n-workflow-manager с ruff 0.15, clirec с 0.16).

### 1.3.0 (2026-07-24)
- Новый раздел "Замечания становятся задачами": То, что раунд не может исправить сам, в момент обнаружения становится записью в локальной системе задач папки проекта — там, где посмотрит следующий исполнитель, а не в протоколе завершенного прогона. Включая разделение внутреннего списка и публичной карты, обогащение вместо дублирования, выполненное с коммитом.

### 1.2.0 (2026-07-24)
- Шлюз приватности дополнительно ищет названия собственных внутренних папок. Они не являются секретами, поэтому не вызывают тревог и проходят шлюзы, ищущие только пути и токены — но остаются нерешаемыми для читателей и раскрывают внутреннюю структуру.

### 1.1.0 (2026-07-24)
- Блокировки читаются, а не воспринимаются как тотальный запрет: чистая блокировка публикации/пуша перенаправляет раунд на локальную ветку вместо отмены. Одновременно уточнено, что при такой блокировке метаданные, релизы и действия с Issues/PR опускаются тоже — они так же видны удаленно, как и пуш.

### 1.0.0 (2026-07-24)
- Первоначальная версия. Уровень 1 обслуживания репозиториев, производный от `github-repo-care`.
