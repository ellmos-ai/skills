# Load Project (Загрузка проекта)

## Назначение

Используйте этот навык в начале конкретной задачи проекта или когда контекст работы стал неясным. Цель состоит не в полном аудите репозитория, а в поиске минимального надежного контекста, с которым можно безопасно продолжать работу.

## Конфигурация

Этот навык не требует фиксированных имен каталогов. Локальные установки могут опционально определять следующие значения в своих общих правилах агента или в локальной конфигурации проекта:

- известные корни рабочих областей (workspace),
- предпочитаемые инструменты работы с файлами,
- имена дополнительных файлов загрузки или реестра,
- средства проверки блокировок (locks),
- специфические для проекта роли и приоритеты.

При отсутствии такой конфигурации навык работает исключительно с указанной целью и найденными там правилами проекта.

## Порядок действий

### 1. Определение цели

1. Взять в качестве начальной точки явный путь, имя проекта или текущую рабочую папку.
2. Определить фактический корень проекта или репозитория.
3. Ограничить неточный выбор на основе задачи, корневых документов и границ репозитория; не угадывать при существенных различиях в целях.

### 2. Загрузка иерархии правил

Читать от общего контекста к специфическому:

1. глобальные правила агента и безопасности,
2. правила рабочей области или пайплайна,
3. правила проекта и репозитория,
4. инструкции к конкретной задаче.

Более специфические правила действуют в пределах своей области; границы безопасности и авторизации более высокого уровня остаются в силе.

### 3. Чтение корневых документов по ролям

Имена файлов — это подсказки, а не жесткий стандарт. Целенаправленно ищите документы со следующими ролями:

| Роль | Типичное содержимое |
|---|---|
| Вход | Назначение, навигация, начальные инструкции |
| Правила | Метод работы, язык, безопасность, соглашения |
| Архитектура | Компоненты, поток данных, границы |
| Статус | Текущее состояние, открытые проблемы, последняя проверка |
| Задачи | Приоритетные следующие работы |
| Реестр | Канонические проекты, проверки или публикации |
| Доказательства | Тесты, протоколы проверок, заметки к проверкам |
| Передача | Текущая работа, сторонние изменения, следующий шаг |

Загружайте только те роли, которые релевантны конкретной задаче.

### 4. Отслеживание обязательных ссылок

Если прочитанное правило явно называют другие файлы обязательными к прочтению, загрузите их целенаправленно. Завершайте цепочки ссылок, как только они перестанут предоставлять дополнительный обязательный контекст для задачи.

### 5. Проверка состояния и блокировок (Locks)

- Проверять блокировки на основе локальной политики на предмет владельца, области применения, метки времени и критерия действительности; никогда не объявлять блокировку устаревшей по собственному усмотрению без определенного правила устаревания,
- Статус системы контроля версий и сторонние изменения,
- Запущенные процессы или контрольные точки, если применимо,
- Актуальность реестров, тестов и деталей статуса.

Сохраните начальное состояние затронутых областей перед внесением изменений в качестве базовой линии статуса/diff. Если существующие изменения не удается точно атрибутировать, предохранительно считайте их сторонними и оставляйте нетронутыми.

Относитесь к снимкам (snapshots) как к состояниям на определенный момент времени и повторно проверяйте их перед выполнением рискованных действий.

### 6. Составление отчета о состоянии

Кратко зафиксировать перед выполнением:

```text
Ziel:
Projekt-Root:
Geltende Regeln:
Evidenzquellen:
Snapshot-Zeitpunkt:
Relevanter Ist-Zustand:
Locks oder fremde Änderungen:
Erfolgskriterium:
Nächster sicherer Schritt:
```

Указывайте источники только с той точностью, которая необходима для проверки. Редактируйте (скрывайте) секреты, персональные данные и конфиденциальный контент и не копируйте их в отчет о состоянии.

Если задача на этом основании однозначна и авторизована, переходите непосредственно к работе.

## Ограничения

- По умолчанию не производить широкий, неограниченный поиск файлов.
- Не изобретать заново отсутствующие правила или реестры.
- Не рассматривать старые сообщения о статусе как текущее доказательство.
- Не перезаписывать сторонние изменения.
- Не проводить полный онбординг проекта, если требуется загрузить контекст только для конкретной задачи.
