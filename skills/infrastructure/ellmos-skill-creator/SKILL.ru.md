# ellmos-skill-creator

## Происхождение и решение (форк или собственная разработка)

**Решение: собственная разработка, не форк.** Обоснование, чтобы оно не было потеряно:

- `skill-creator` (Anthropic, маркетплейс `claude-plugins-official`) распространяется под лицензией **Apache-2.0**
  (текст LICENSE прочитан и проверен в клоне, 2026-08-24) — форк был бы юридически чистым
  и в репозитории уже является устоявшейся практикой (`skills/third-party/grilling`).
- Однако форк унаследовал бы всю машинерию оценки/бенчмарков оригинала (`agents/{analyzer,comparator,grader}.md`, `eval-viewer/`,
  7 скриптов, SKILL.md на 485 строк) — возможность, которая уже есть и вызывается напрямую (`Skill: skill-creator:skill-creator`).
  Согласно правилу 4 `.PLUGINS/CLAUDE.md` («проверить возможности, прежде чем строить заново») и шаблону P10
  («два переключателя, которые никто не сравнивает»), это было бы дубликатом, а не расширением.
- Реальный пробел **чисто специфичен для ellmos** и принципиально неизвестен оригиналу:
  фирменный frontmatter (`templates/SKILL.md`), `docs/CONVENTIONS.md`, нейтральность к поставщику/пользователю с
  чувствительностью к ellmos, подключение `grounding-seed`, осведомлённость о вендорах, самообновление.
- Этот навык **не содержит текста Anthropic** (сформулировано самостоятельно от начала до конца), поэтому
  не возникает обязанность атрибуции Apache-2.0 для модификаций. Он **компонует** оригинал, а не копирует его:
  это одновременно самый чистый в правовом отношении и наименее трудоёмкий в сопровождении путь.

## Когда активировать

- «создай навык для X», «построить новый навык», «используй skill-creator»
- «сделай этот навык соответствующим ellmos», «довести навык до стандарта дома»
- Всегда, когда **место назначения** — навык в `.AI/.SKILLS/skills/…` (или его канонический клон Plan-D).
  Не при общих запросах вне экосистемы («создай мне какой-нибудь навык Claude без связи с этим»).

## Порядок действий

### Шаг 1 — Делегировать интервью/черновик/оценку

Вызови официальный `Skill: skill-creator:skill-creator` для: уточнения намерения,
черновика структуры SKILL.md, тестовых случаев, цикла оценки,
оптимизации описания (`scripts/improve_description.py`). **Не изобретай заново** — эта часть
общая и в оригинале уже хорошо решена.

### Шаг 2 — Развернуть домашний каркас ellmos (обязательно, дополнительно к формату оригинала)

Дополни SKILL.md, созданный оригиналом, девятью домашними полями из
`.SKILLS/templates/SKILL.md` (либо `AGENT.md`/`WORKFLOW.md`/`PROMPT.md` в зависимости от типа),
предварительно прочитай `.SKILLS/docs/CONVENTIONS.md`: папки категорий, правило плоской структуры (<5 файлов — плоско),
соглашение о версиях (SemVer: MAJOR/MINOR/PATCH) и наборы для многоязычности (ядро: DE+EN обязательно).
**`visibility` всегда стартует с `private-only`** — публикация является более поздним,
проверенным решением пользователя (`.AI/VISIBILITY-POLICY.md`), никогда не значением по умолчанию.
Эти поля являются чисто **дополнительными** к формату Anthropic (дополнительные ключи YAML рядом с
`name`/`description`) — каждый так созданный навык остаётся полностью
`anthropic_compatible: true`.

### Шаг 3 — Соблюдать принципы: нейтральность к поставщику, к пользователю, нейтральность к ellmos, но чувствительность к ellmos

Полный текст и шаблоны кода: `references/ELLMOS-PRINCIPLES.md`. Краткая версия: созданный
навык должен **работать самостоятельно** (содержать всё необходимое) и **одновременно**
использовать компоненты ellmos, как только они доступны — он решает это сам во время выполнения,
никогда не зашивая жёстко. Именно этот шаблон уже реализует `grounding-seed`
(README: «cultivated landscape, not wildflower» / «viable alone, more productive
together») — **второй механизм распознавания не изобретается**, этот навык последовательно
направляет создаваемые навыки к `grounding_seed.detect_ecosystem()`.

### Шаг 4 — Поставить config.json + connections.json

`grounding-seed` уже импортируется как Python-пакет (проверено 2026-08-24:
`import grounding_seed` успешно разрешается в локально клонированном дереве исходников `grounding-seed`, клон Plan-D) — это
**канонический узел подключения**, новый файл не изобретается. Для каждого созданного навыка с
внешней потребностью (программы, сервисы, поставщики):

- **`config.json`** — собственные настройки навыка (шаблон: `templates/skill-config.template.json`).
  `grounding_seed.store.LocalStore(root)` по умолчанию использует это имя файла для своего хранения ролей — созданный
  навык может либо использовать свой `config.json` как бэкенд `LocalStore`, либо держать его отдельно,
  если помимо ролей ему нужны чисто поведенческие настройки (тогда — второй экземпляр `LocalStore(root, filename="connections.json")`).
- **`connections.json`** — фактически **разрешённые** внешние точки подключения
  (какая программа/какой сервис найдены, с какого времени, из какого источника) —
  шаблон: `templates/skill-connections.template.json`, схема `ellmos.source-resolver.user-config.v1`
  (идентична `source-resolver`; согласно README grounding-seed это выбрано намеренно, чтобы
  последующий перенос в настоящий `source-resolver` был без потерь — см. `migration.py` там).

Подробности, CLI и пример кода: раздел `references/ELLMOS-PRINCIPLES.md` «Docking».

### Шаг 5 — Встроить осведомлённость о поставщиках/вендорах

Полный текст: `references/VENDOR-AWARENESS.md`. Краткая версия: созданный навык получает раздел «Поставщики и альтернативы», который
(а) называет State-of-the-Art поставщика(ов) темы (например, ElevenLabs для TTS), (б) называет хотя бы один
альтернативный поставщик, (в) явно перечисляет **собственные компоненты ellmos как равноправного кандидата**,
если они покрывают тему (например, `ellmos-voice-io` вместо/наряду с ElevenLabs), и при подходящем запросе пользователя
**предлагает** установку/переход, а не предполагает их молча. Основа для проверки «что есть в системе»:
`grounding_seed.scan.scan_resources([...])` (проверяет `shutil.which`) плюс `.AI/.MCP/MCP-PROFILE-MANAGEMENT.md` для кандидатов ellmos.

### Шаг 6 — Настроить самообновление

Полный текст: `references/SELF-UPDATE.md`. Краткая версия: каждый созданный навык получает раздел «Самообновление», который
(а) периодически предлагает краткий веб-поиск, чтобы оставаться на уровне State-of-the-Art, (б) знает связанные
навыки/рабочие процессы и называет новые альтернативы, которые могут лучше подойти, (в) ведёт небольшой
JSON обучения (шаблон: `templates/skill-connections.template.json`, поле `notizen`/`gelernt`), который при наличии
компонента памяти ellmos (USMC/Gardener) может быть вынесен туда, а не расти локально —
и здесь: распознавать, а не зашивать жёстко (`grounding_seed.detect_ecosystem()`).

### Шаг 6b — Создать контракт обучения + покрытие сценариев (повторно используемый шаблон)

Полный текст: `references/LEARNING-CONTRACT-AND-COVERAGE.md`. Краткая версия: не только сам этот
навык, но **каждый созданный им навык** получает небольшой повторно используемый набор файлов обучения/покрытия —
проверенный по признанным стандартам, без параллельного стандарта:

- `evals/evals.json` — **повторно использовать**, не дублировать: это уже стандарт skill-creator
  для тестовых случаев, написанных автором.
- `user-usecases.json` — сценарии использования, которые пользователь действительно предъявил, по форме идентичные
  `evals.json` (шаблон: `templates/user-usecases.template.json`).
- `usecase-gaps.json` — сверка: какие пользовательские сценарии не протестированы/не покрыты
  (шаблон: `templates/usecase-gaps.template.json`).
- `known-providers-and-abilities.json` — пространство кандидатов известных поставщиков по ролям,
  поля по образцу A2A/`AgentSkill` (id/name/description/tags), а не изобретены (шаблон: `templates/known-providers-and-abilities.template.json`).
- `gap-closing-analysis.json` — структурные пути закрытия для каждого пробела (модуль ellmos,
  пакет ellmos, сторонний модуль, новая разработка) — не дубликат `grading.json.eval_feedback`
  (шаблон: `templates/gap-closing-analysis.template.json`).
- `config.json`, поле `lernvertrag` — кодекс поведения (выбрать лучший вариант, **пользователь как король**,
  никогда не устанавливать самостоятельно, интервал обновлений) — намеренно как расширение
  `config.json`, а не седьмой файл.

Схемы: `.SKILLS/schemas/{user-usecases,usecase-gaps,known-providers,
gap-closing-analysis}-v1.schema.json` — та же домашняя конвенция, что и `skill-v1.schema.json`.
`grounding-seed` был проверен для этого набора файлов и намеренно **не** расширялся
(обоснование в `LEARNING-CONTRACT-AND-COVERAGE.md`) — только `connections.json` остаётся его частью.

### Шаг 7 — Зарегистрировать, протестировать, закоммитить

- Выбери папку категории по `.SKILLS/CLAUDE.md`/`SKILLS-MAP.md`; при сомнениях спроси `skill-finder`
  или `controlcenter_find_skill`, существует ли уже семейство.
- Запусти `testing/` (privacy_gate + тесты метаданных) до коммита.
- Файлы реестра (`registry/components.json`, `SKILLS-MAP.md`, `llms.txt`) **не редактируй вручную** — они
  генерируются (`build_public_registry.py`, `build_skills_map.py`, `catalog.py`). Если в каноническом клоне сейчас
  идёт чужая незакоммиченная сессия, НЕ регенерируй глобально (это смешает чужие и свои изменения в одном файле) —
  вместо этого закоммить только новую папку навыка изолированно и оставь регенерацию реестра
  следующему чистому прогону (`skill-register-care`).
- `git commit -- skills/<kategorie>/<name>/` — только свои новые пути.

## Совместимость с форматом Anthropic

Все дополнительные поля — чисто расширения YAML рядом с `name`/`description`: стандартный Claude Code
без этой экосистемы по-прежнему читает только `name`/`description` и игнорирует остальное.
`config.json`/`connections.json` — необязательные сопутствующие ресурсы (как предусмотрено в
`docs/CONVENTIONS.md`), а не обязательная зависимость — навык без них работает без изменений.

## Связанные навыки

- `skill-creator:skill-creator` — общий цикл интервью/оценки (делегируется, шаг 1).
- `skill-finder` — маршрутизатор для существующих собственных навыков (ПЕРЕД созданием проверить: а вдруг уже есть?).
- `skill-explorer` — аудит ландшафта + веб-поиск новых навыков/плагинов (мета-уровень: наш *набор* навыков;
  этот навык, напротив, делает каждый *отдельный созданный* навык осведомлённым о поставщиках).
- `skill-family-care`, `skill-register-care` — сопровождение после создания.
- `grounding-seed` (модуль, `.AI/.MODULES/.CONTROL/grounding-seed`) — фактическая логика подключения/самообеспечения,
  здесь только упоминается, не дублируется.
