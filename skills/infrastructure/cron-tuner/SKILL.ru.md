# cron-tuner — самонастраивающаяся тактовая регулирующая петля

**Самонастраивающаяся** регулирующая петля для повторяющейся работы по расписанию
(cron-задачи, плановые задания, таймеры). Вместо фиксированного интервала
задание само подстраивает свой такт: оно ускоряется при наличии работы и
охлаждается при тишине. Не зависит от хоста и платформы; шаблон работает с
любым планировщиком.

## Когда применять

- Повторяющееся сканирование (наблюдение за почтовым ящиком, сканирование
  Sync-Yard, опрос очереди) должно быстро реагировать во время активного
  «совпадения» и оставаться дешёвым в периоды простоя.
- Подстройка должна быть **поддаваемой аудиту** (один файл состояния), а не
  неявно храниться в диалоге или в памяти человека.

## Концепции

- **Регулирующая петля**: измерить → решить → действовать → сохранить. Каждый
  запуск завершается записью своего состояния; каждый запуск начинается с его
  чтения.
- **Активация**: найдена новая работа → немедленный переход на самый короткий
  интервал.
- **Лестница охлаждения**: пустые запуски опускают ступень лестницы; каждая
  ступень применяется, только если интервал действительно меняется.
- **Потолок**: никогда не расслабляться сверх заданного максимального
  интервала.

## Эталонная схема

| Условие | Новый интервал |
|---|---|
| найдена новая работа | самый короткий (например, 15 мин) |
| 4 последовательных пустых запуска | 30 мин |
| 6 последовательных пустых запусков | 1 ч |
| каждый следующий пустой запуск | удвоение (2 ч, 4 ч, 8 ч) |
| Потолок | 24 ч (никогда не выше) |

Пороги согласовать с рабочей нагрузкой; удвоение держать простым, а потолок —
явным.

## Файл состояния (обязателен)

Небольшой JSON-файл на каждого воркера, например `cron-tuner-state.json`:

```json
{
  "empty_runs": 0,
  "interval_minutes": 15,
  "note": "cron-tuner state"
}
```

Правила:

1. **Файл, а не память.** Счётчик должен переживать компактирование контекста,
   перезапуски сессий и смену оператора и быть доступным для просмотра людьми
   и другими агентами. Не отслеживать такт в истории диалога.
2. **Перезаписывать только при изменении.** Состояние сохранять при каждом
   запуске, но заменять запланированное задание только тогда, когда интервал
   действительно меняется.
3. **Новое задание = новое расписание, то же состояние.** Смена такта
   означает удаление старого задания и создание нового с новым интервалом;
   счётчик продолжает работу.

## Эксплуатационные правила

- **Решает работа, а не настроение.** Такт меняют только наблюдаемые поступления
  — никогда ожидания или приближения.
- **Смещения против стадности.** Избегать отметок начала и половины часа для
  самого короткого интервала (например, минуты 7/22/37/52), чтобы флоты не
  срабатывали синхронно.
- **Страховка:** если партнёрская система замолкает, применяется обычное
  обычное правило вакансии/отсутствия (недоступности партнёра) — тюнер никогда не эскалирует до потока опросов.
- **Подтверждения:** каждая смена такта фиксируется с причиной, старым и новым
  интервалом.

## Расширяемость (реестр типов петель)

Навык служит основой для дополнительных самонастраивающихся типов петель со
временем:

- **cooldown** (эта схема: тишина → медленнее)
- **backoff** (ошибки → медленнее, успех → быстрее)
- **burst** (всплеск поступлений → временный быстрый режим с явным концом)
- **wake-assist** (внешнее сообщение пробуждения → немедленный запуск вне
  цикла)

Новые типы петель получат здесь собственный подраздел и собственную схему
файла состояния.
