# cron-tuner — স্বয়ং-সমন্বয়ী টাইমিং রেগুলেশন লুপ

পুনরাবৃত্ত, সময়সূচি-চালিত কাজের (cron জব, নির্ধারিত কাজ, টাইমার) জন্য একটি **স্বয়ং-সমন্বয়ী** রেগুলেশন লুপ। স্থির ব্যবধানের পরিবর্তে জবটি নিজের টাইমিং সামঞ্জস্য করে: কাজ থাকলে এটি শানিত হয় এবং নীরবতায় শীতল হয়। হোস্ট ও প্ল্যাটফর্ম-নিরপেক্ষ; এই প্যাটার্ন যেকোনো scheduler-এর সাথে কাজ করে।

## কখন ব্যবহার করবেন

- একটি পুনরাবৃত্ত স্ক্যান (mailbox watch, sync-yard scan, queue poll) সক্রিয় "Match"-এর সময় দ্রুত সাড়া দিতে চায় এবং অলস সময়ে সস্তা থাকতে চায়।
- সমন্বয়টি **নিরীক্ষাযোগ্য** হওয়া দরকার (একটি State ফাইল) বরং কোনো কথোপকথনে বা কোনো ব্যক্তির মাথায় অন্তর্নিহিতভাবে না থাকে।

## ধারণাসমূহ

- **রেগুলেশন লুপ**: পরিমাপ → সিদ্ধান্ত → কার্যকর → সংরক্ষণ। প্রতিটি রান তার State লেখার মাধ্যমে শেষ হয়; প্রতিটি রান তা পড়ার মাধ্যমে শুরু হয়।
- **সক্রিয়করণ**: নতুন কাজ পাওয়া গেলে → সরাসরি দ্রুততম ব্যবধানে লাফ।
- **Cooldown-সিঁড়ি**: খালি রানগুলো একটি সিঁড়ি নিচে নামায়; প্রতিটি ধাপ কেবল তখনই প্রযোজ্য যখন ব্যবধান সত্যিই বদলায়।
- **সীমা (Deckel)**: একটি নির্ধারিত সর্বোচ্চ ব্যবধানের ওপরে কখনোই শিথিল হয় না।

## রেফারেন্স স্কিমা

| শর্ত | নতুন ব্যবধান |
|---|---|
| নতুন কাজ পাওয়া গেছে | দ্রুততম (যেমন 15 মিনিট) |
| 4টি পরপর খালি রান | 30 মিনিট |
| 6টি পরপর খালি রান | 1 ঘণ্টা |
| প্রতিটি অতিরিক্ত খালি রান | দ্বিগুণ (2 ঘণ্টা, 4 ঘণ্টা, 8 ঘণ্টা) |
| সীমা | 24 ঘণ্টা (কখনোই বেশি নয়) |

থ্রেশহোল্ডগুলো কাজের চাপের সাথে মিলিয়ে ঠিক করুন; দ্বিগুণ করাটা সহজ রাখুন এবং সীমাটি স্পষ্ট রাখুন।

## State ফাইল (বাধ্যতামূলক)

প্রতি worker-এর জন্য একটি ছোট JSON ফাইল, যেমন `cron-tuner-state.json`:

```json
{
  "empty_runs": 0,
  "interval_minutes": 15,
  "note": "cron-tuner state"
}
```

নিয়মাবলি:

1. **মেমরি নয়, ফাইল।** কাউন্টারটিকে context compaction, session পুনরারম্ভ এবং অপারেটর পরিবর্তন টিকে থাকতে হবে এবং মানুষ ও অন্যান্য এজেন্টের কাছে দৃশ্যমান হতে হবে। কথোপকথনের ইতিহাসে টাইমিং ট্র্যাক করবেন না।
2. **পরিবর্তন হলেই পুনর্লেখা।** প্রতিটি রানে State সংরক্ষণ করুন, কিন্তু নির্ধারিত জবটি কেবল তখনই প্রতিস্থাপন করুন যখন ব্যবধান সত্যিই বদলায়।
3. **নতুন জব = নতুন সময়সূচি, একই State।** টাইমিং পরিবর্তনের অর্থ পুরনো জব মুছে নতুন ব্যবধানসহ একটি নতুন জব তৈরি করা; কাউন্টার চলতে থাকে।

## পরিচালনার নিয়মাবলি

- **কাজ সিদ্ধান্ত নেয়, মেজাজ নয়।** কেবল পর্যবেক্ষিত আগমনই টাইমিং বদলায় — কখনো প্রত্যাশা বা আনুমানিক ধারণায় নয়।
- **ভিড়-বিরোধী অফসেট।** দ্রুততম ব্যবধানের জন্য পূর্ণ-ঘণ্টা ও অর্ধ-ঘণ্টার চিহ্ন এড়িয়ে চলুন (যেমন মিনিট 7/22/37/52), যাতে বহরগুলো একসাথে ফায়ার না করে।
- **Fail-Safe:** কোনো partner সিস্টেম নীরব হলে স্বাভাবিক শূন্যতা/অনুপস্থিতির নিয়ম প্রযোজ্য — tuner কখনো poll-বন্যায় ঠেলে দেয় না।
- **প্রমাণ:** প্রতিটি টাইমিং পরিবর্তন কারণ, পুরনো ও নতুন ব্যবধানসহ লগ করা হয়।

## সম্প্রসারণযোগ্যতা (Loop-প্রকারের Registry)

এই skill সময়ের সাথে আরও স্বয়ং-সমন্বয়ী loop-প্রকারের আবাসস্থল:

- **cooldown** (এই স্কিমা: নীরবতা → ধীর)
- **backoff** (ব্যর্থতা → ধীর, সাফল্য → দ্রুত)
- **burst** (আগমনের শীর্ষ → একটি স্পষ্ট শেষসহ সাময়িক দ্রুত মোড)
- **wake-assist** (বাহ্যিক wake বার্তা → চক্রের বাইরে তাৎক্ষণিক রান)

নতুন loop-প্রকার এখানে একটি উপ-অধ্যায় এবং তার নিজস্ব State ফাইল স্কিমা পাবে।
