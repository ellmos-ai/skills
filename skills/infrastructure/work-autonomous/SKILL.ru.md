# work-autonomous — завершать цикл только тогда, когда доказано, что автономных задач не осталось

## Назначение

Этот навык делает две вещи одновременно:

1. **По возможности продолжать работать автономно** — обычная работа в рамках сессии, ничего особенного.
2. **Завершать цикл только тогда, когда ДОКАЗАНО**, что не существует ни одной автономно выполнимой задачи. Подозрение «сейчас ничего не могу найти» — **не** основание для прекращения. Оно является **триггером** цепочки проверок, которая сначала пытается **найти** новые задачи. Только если эта цепочка полностью остаётся безрезультатной, прекращение считается доказанным.

**Намеренно без встроенного `/goal`:** навык самостоятельно пригоден для использования (например, напрямую как вызов `/work-autonomous` внутри обычной сессии), а также как условие внутри вышестоящей конструкции цикла: `/loop` назначается обычным образом, затем в качестве цели указывается только этот навык. Цель тогда звучит примерно так: *«Заверши цикл, когда автономных задач не останется — и до этого момента по возможности продолжай работать автономно.»* Сам навык не вызывает конструкцию `/goal`; он лишь выдаёт однозначный сигнал прекращения, который такая конструкция может прочитать (см. «Сигнал прекращения» ниже).

## Операционная модель — два уровня

### Уровень 1 — обычная работа (каждый тик)

#### Шлюз приёма TICKET-MASTER (приоритет над всем остальным на этом уровне)

**Актуально только тогда, когда система тикетов (`_TICKETS/`) вообще входит в контекст** — сессии без системы тикетов пропускают этот шлюз без последствий; навык без всякой системы тикетов остаётся самостоятельно пригодным (см. «Назначение» выше). Сначала нужно проверить, полностью ли `INBOX/` — включая неформальные, ещё не приведённые к формату тикета записи — оформлен и отсортирован. Если нет, именно это считается найденной автономной работой (оформление/сортировка — канцелярская работа без решения пользователя, см. разграничение ниже): выполнить её, тик завершается, Уровень 2 не запускается, как и для любого другого источника Уровня 1.

**Пока INBOX открыт, НЕ может возникнуть `NO_WORK`, сигнал исчерпания (`exhausted`/`blind`), Guard-STOP или любой другой сигнал прекращения.** Только после полной сортировки приёма можно проверять `ACTIONABLE`, разблокированные `BLOCKED` и наступившие `WAITING` (ниже) — и уже затем, при необходимости, Уровень 2.

*Случай из практики:* цикл начал проверку исчерпания после обработки `ACTIONABLE`, в то время как непрерывно поступали новые `INBOX`-тикеты, среди них два с приоритетом P1. Без этого шлюза цикл сообщил бы `exhausted`/`blind`, хотя вход был открыт — именно это шлюз и предотвращает.

Затем в обычном порядке искать дальнейшую автономно выполнимую работу (см. разграничение ниже) и выполнять её: открытые `ACTIONABLE`-тикеты, разблокированные `BLOCKED`-тикеты, наступившие `WAITING`-тикеты, открытые `TODO.md`/`AUFGABEN.txt`-пункты в проектах без зависимости от пользователя, наступившие регулярные/гигиенические проверки по локальной политике, начатую, но не завершённую в прошлой сессии работу (USMC `working`), **наступившие `tidy-up`-запуски активного проекта** (дополнение 1.3.0, 2026-08-19 — см. навык `tidy-up`: проход Tasksolver+Writer+Maintainer по папке проекта, в которой сессия работала последний раз; наступление срока проверяет сам `tidy-up` по собственному лёгкому журналу USMC, см. соответствующий раздел «Связь с work-autonomous»).

→ **Найдено и выполнено:** кратко сообщить результат, тик завершается, цикл продолжается в обычном режиме. Уровень 2 НЕ запускается — ни один из четырёх дорогостоящих шагов проверки не нужен, пока есть видимая работа.

### Уровень 2 — проверка исчерпания (только при подозрении «нечего делать»)

Только если Уровень 1 **не** находит ничего автономного, возникает подозрение. Одного этого подозрения недостаточно. Теперь **обязательно** запускается следующая цепочка, чтобы **найти** новые задачи.

#### Самопознание (до цепочки, а не после)

Прежде чем что-либо опрашивать: навык декларирует, КАКИЕ источники ему нужны для своего суждения. Четыре потребности (`grounding_seed.self_knowledge.Need`, если `grounding-seed` установлен — иначе тот же список действует как чистая декларация без подключения библиотеки):

| Роль | Шаг цепочки | Что за этим стоит |
|---|---|---|
| `decisions.ledger` | 2 | центральный реестр решений |
| `memory.organic` | 3 | Gardener (`find()`/`put()`) |
| `memory.curated` | 3 | USMC (`facts`/`lessons`/`working`/`context`) |
| `user.model` | 4 | decision-avatar / BYUM |

**`/think` + `/decide` (шаг 1) намеренно НЕ являются декларируемым источником.** Это собственный аналитический шаг модели, а не внешняя система, которая может быть доступна или недоступна — он всегда «доступен» в смысле этого различия. Только шаги 2–4 могут стать `unavailable`.

Необязательный, тестируемый инструмент для чистого вопроса локализации (found/unavailable, ещё БЕЗ проверки содержимого): `scripts/exhaustion_check.py` в папке этого навыка. Он использует `grounding_seed.resolve()` + `status_from_resolution()` для `decisions.ledger`/`user.model` (там есть реальный провайдер `source-resolver`), а для `memory.organic`/`memory.curated` всегда проверяет доступность напрямую через CLI (`gardener`/`usmc` в PATH) — для этих двух ролей до 2026-08-15 не было зарегистрированного провайдера `source-resolver`; опрос через резолвер сообщил бы лишь `unavailable`, независимо от того, установлены ли Gardener/USMC на самом деле. Работает одинаково с установленным `grounding-seed` и без него.

**Обновление 2026-08-25 (K3=C, `T-20260825-342866657`):** пробел закрыт — `source-resolver` регистрирует `memory.organic` (Gardener) и `memory.curated` (USMC) теперь обе как роль уровня 1 с той же CLI-проверкой присутствия (`shutil.which("gardener")`/`shutil.which("usmc")`), которую этот скрипт до сих пор жёстко зашивал сам. `exhaustion_check.py` поэтому НЕ переделан сразу (потери функциональности нет, существующая проверка остаётся корректной) — при следующем проходе по уходу за навыком шаг 3 можно перевести на `source_resolver.resolve("memory.organic"/"memory.curated")`, аналогично шагу 2 (`decisions.ledger`), чтобы не поддерживать CLI-проверку дважды.

#### Четыре шага цепочки — каждый сообщает found | empty | unavailable

Каждый шаг выполняется в два этапа: сначала **локализация** (знаю ли я вообще доступное место?), затем — только при успешной локализации — **проверка содержимого** (модель действительно читает, есть ли там что-то новое, своими инструментами). Источник, который не удалось локализовать, НИКОГДА не проверяется по содержанию — он считается `unavailable`, а не `empty`.

1. **`/think` + `/decide`** применяются к вопросу: «Действительно ли не осталось автономно выполнимой работы, или я что-то упускаю?» — структурированный анализ вместо догадки. Статуса found/empty/unavailable не имеет (см. выше, это не источник).
2. **`decisions.ledger`** — локализация через `source_resolver.resolve("decisions.ledger")` / `grounding_seed.resolve(...)`, если установлены; иначе известный запасной путь (`_control-center/_CONTROL/_DECISIONS/`, цепочка `TO-DECIDE-USER*.txt`, собственный `TO-DECIDE-USER-<HOST>.txt` хоста, `DECIDED-AND-DONE.md`). Локализован → читаем содержимое: не приняты ли недавно решения, которые разблокируют ранее заблокированную или ожидающую согласования работу? Есть совпадения → `found`. Прочитано, ничего нового → `empty`. Не локализуется (резолвер отсутствует И запасного пути не существует) → `unavailable`.
3. **`memory.organic` (Gardener) + `memory.curated` (USMC)** — два отдельных источника, один шаг цепочки. Локализация: CLI в PATH (`gardener`/`usmc`), см. самопознание выше. Доступен → читаем содержимое (`find()`/`recall()` или `usmc facts|lessons|working|context`): открытые пункты рабочей памяти, уроки с невыполненным продолжением, факты, указывающие на упущенную, но выполнимую работу (именно здесь прошлые сессии оставляют незавершённые пункты — поле `RESUME:`, открытые записи `note`). Совпадения → `found`. Прочитано, ничего нового → `empty`. CLI не в PATH → `unavailable`.
4. **`user.model` (decision-avatar/BYUM)** — локализация как у `decisions.ledger` (резолвер или запасной путь `_control-center/_CONTROL/_USER-MIND/`). Локализован → проверить содержимое: есть ли подтверждённый шаблон, по которому пользователь хотел бы видеть определённое действие выполненным автономно? Засчитывается как `found` только при достаточной уверенности (🟢/🟡) — 🔴 засчитывается как `empty`, то есть не как найденная задача, а как открытый пункт для шага «остаток только для пользователя» ниже. Не локализуется → `unavailable`.

**«Exhausted» допускается сообщать только тогда, когда ВСЕ ЧЕТЫРЕ источника (шаги 2–4, три шага, четыре роли) действительно МОГЛИ быть опрошены — то есть `found` или `empty`, ни одного `unavailable`.** Это соответствует `grounding_seed.self_knowledge.GroundingReport.all_answerable()`. Если хотя бы одна роль `unavailable`, «exhausted» НЕ применяется, а выдаётся собственный сигнал «blind» (см. сигнал прекращения ниже) — цикл всё равно завершается (он всё равно ничего не может опросить), но больше не утверждает, что проверил то, что проверить не смог.

Если какой-либо шаг находит новую работу → назад на Уровень 1, работа выполняется, состояние Guard (см. ниже) ставится в «found» вместо «exhausted»/«blind».

### Особый случай: остатки, зависящие только от пользователя

Если цепочка **не** находит ни одной **автономной** задачи, но открыты `USER/*`-тикеты или нерешённые `_DECISIONS`-пункты, это всё равно СТОП для автономности — но не «нечего делать», а «нечего делать *автономно*». Эти пункты по правилу автономного цикла из `ticket-master` **объединяются** в один сводный запрос (одна сводная подача, не отдельные уведомления), а не запрашиваются по одному. Сигнал прекращения явно отличает этот случай от настоящего отсутствия работы.

## Разграничение — что считается «автономно выполнимым»?

Ссылка: категории `ticket-master` (`.AI/.MODULES/.CONTROL/ticket-master/docs/CATEGORIES.de.md`).

| Случай | Автономно? | Обоснование |
|---|---|---|
| `INBOX/`, включая неформальные записи, в TICKET-MASTER (до сортировки) | **Да, с приоритетом** | Оформление/сортировка — канцелярская работа без решения пользователя; идёт раньше `ACTIONABLE`/`BLOCKED`/`WAITING` и до этого блокирует любой сигнал прекращения (см. шлюз приёма выше). |
| Тикет `ACTIONABLE` | **Да** | Не блокер, без зависимости от пользователя — по определению. |
| `BLOCKED/*` (host-receipt, foreign-state, lock, quota, dependency) | Нет, пока блокер не снят **эмпирически** | Периодическая повторная проверка допустима (цикл автономности), «есть запись» не является доказательством — нужен подтверждённый факт. |
| `WAITING/*` (scheduled, review-due, marker) до срока/маркера | Нет | Привязано ко времени. |
| `WAITING/*` после наступления срока/маркера | **Да** | Условие выполнено → переходит в `ACTIONABLE`. |
| `USER/*` (decision, data, freigabe, hardware, session) | **Никогда автономно** | Обязательно решение/данные/согласование/оборудование/сессия пользователя. Вынести сводно, см. выше. |
| `PARKED/*` (skip, backlog, until-trigger) | Нет, кроме явного поручения/триггера | Сознательно отложено, без автоматической повторной проверки. |
| Открытые `TODO.md`/`AUFGABEN.txt`-пункты без отметки согласования/решения | **Да** | Реестр проекта, обычная работа. |
| Наступившие регулярные/гигиенические проверки (cooldown истёк, без блокировки) | **Да** | Обычные работы по обслуживанию согласно локальной политике. |
| Области, заблокированные `LOCK.user.*` | **Никогда** | Блокировка пользователя — снимает только пользователь, см. LOCK-SYSTEM. |
| Необратимые/внешне действующие шаги без разрешения политики (загрузка в Zenodo, push в проверенные/защищённые ветки, решение о серверных расходах сверх порога ноутбука, окончательное удаление без предпросмотра) | **Нет** | Нужно согласование/решение, даже если технически выполнимо. |
| Сессия, запускаемая только через GUI/вход (например, задача Claude Desktop, интерактивный вход, физическое действие с оборудованием) | **Никогда** | «Сессия, которую может запустить только пользователь» — цикл её не выполнит. |

Эмпирическое правило: автономно является то, что можно довести до конца **без** решения, согласования, данных, оборудования или сессии пользователя И что не требует необратимого/внешне действующего шага без задокументированного разрешения политики.

## Защита от бесконечных циклов (обязательно)

**Проблема:** без тормоза четырёхступенчатая цепочка при каждой повторной проверке запускалась бы полностью заново, хотя с последнего безрезультатного прохода ничего не изменилось — дорого и бессмысленно, особенно при повторных вызовах навыка (цикл, запланированная задача, повторный ручной вызов подряд).

**Состояние сохраняется в USMC** (состояние процесса в этой системе относится туда, а не в файлы Markdown):

```bash
# Zustand lesen (nach Tag work-autonomous-guard filtern)
usmc --agent <agent> working --limit 20

# Zustand nach einem Kettendurchlauf schreiben
usmc --agent <agent> note "work-autonomous-guard: result=<exhausted|blind|found> fingerprint=<FP> at=<ISO-Zeit>" \
  --type context --priority 3 --tags "work-autonomous-guard,<projekt-slug>"
```

**Отпечаток состоит из ДВУХ компонентов — состояния дел И доступности:**

1. **Компонент состояния** (как прежде): количество/ID открытых `ACTIONABLE`-тикетов, mtime цепочки `_DECISIONS` (`TO-DECIDE-USER*.txt`, `DECIDED-AND-DONE.md`), число новых записей USMC `working` с последнего прохода цепочки.
2. **Компонент доступности (новый, обязательный с 1.2.0):** отсортированный кортеж ролей, которые в данный момент `unavailable` при проверке самопознания (`exhaustion_check.availability_fingerprint_component()`), например `("memory.organic",)` или `()`.

**Почему второй компонент обязателен — «Guard наследует пробел»:** без него отпечаток (компонент 1) опирается, в частности, на mtime цепочки `_DECISIONS`. Если эта цепочка на какой-то системе вообще отсутствует, эта часть отпечатка остаётся постоянной навсегда — однажды ошибочно выставленное `exhausted`/`blind` никогда не перепроверялось бы, даже если позже установили `source-resolver` или создали `_control-center/_CONTROL/_DECISIONS/`. Компонент доступности устраняет это целенаправленно: если меняется, КАКИЕ роли недоступны (источник появился или пропал), отпечаток меняется автоматически — Guard замечает это при следующем вызове и заново запускает цепочку. Это «пересадка» в смысле метафоры заземления (T-20260815-371628859): смена окружения запускает новый поиск без того, чтобы кто-то вручную сбрасывал Guard.

**Порядок перед каждым проходом цепочки:**

```
guard = letzten "work-autonomous-guard"-Eintrag aus USMC lesen
wenn guard existiert
   und guard.result in ("exhausted", "blind")
   und (jetzt - guard.timestamp) < GUARD_INTERVAL   (Default: 15 Minuten)
   und fingerprint(jetzt) == guard.fingerprint:      # Lage- UND Verfügbarkeits-Baustein
       → Kette NICHT erneut fahren.
       → guard.result == "exhausted":
           Melden: "Weiterhin keine autonome Arbeit — unverändert seit {guard.timestamp}.
                    Kein neuer Trigger. STOP (Guard aktiv, exhausted unchanged since …)."
       → guard.result == "blind":
           Melden: "Weiterhin blind (Quellen nicht verfügbar) — unverändert seit {guard.timestamp}.
                    STOP (Guard aktiv, blind unchanged since …)."
sonst:
       → Kette vollständig fahren (Selbstkenntnis-Prüfung + alle vier Kettenschritte).
       → Neuen Guard-Zustand schreiben (timestamp=jetzt, fingerprint=fingerprint(jetzt),
         result=exhausted|blind|found).
       → alle vier Quellen befragbar UND alle empty → exhausted → STOP (belegt).
       → mindestens eine Quelle unavailable → blind → STOP (nicht belegt, nur unerreichbar).
       → mindestens eine Quelle liefert einen Treffer → found → zurück zu Ebene 1, Arbeit erledigen.
```

Один полностью выполненный проход цепочки, при котором ВСЕ ЧЕТЫРЕ источника были доступны для опроса и НИ ОДИН не дал результата, достаточен как доказательство «автономных задач больше нет» (требование тикета: «только когда ВСЕ шаги одного прохода остаются безрезультатными» — безрезультатными здесь явно означает `empty`, а не `unavailable`). Guard не препятствует самому установлению факта, а только **повторному, неизменному пересчёту** при частых последующих вызовах — и делает это раздельно для `exhausted` И для `blind`, никогда не смешивая их.

`GUARD_INTERVAL` настраивается (по умолчанию 15 минут) — при очень инертной среде (редкие новые тикеты/решения) можно выбрать больше, при очень активной — меньше.

## Сигнал прекращения

Каждый проход завершается **одной** однозначной, поддающейся grep строкой, чтобы объемлющий `/loop` или будущая конструкция `/goal` могли прочитать из неё, продолжать ли работу:

```
WORK-AUTONOMOUS: CONTINUE                                          — Ebene 1 hat Arbeit erledigt, Loop läuft weiter.
WORK-AUTONOMOUS: STOP (exhausted)                                  — alle vier Quellen befragt, alle empty. Belegt: keine Arbeit mehr.
WORK-AUTONOMOUS: STOP (blind, N/4 Quellen nicht verfuegbar: <rollen>) — mind. eine Quelle unavailable. NICHT belegt — nur nicht prüfbar.
WORK-AUTONOMOUS: STOP (guard, exhausted unchanged since …)         — Guard aktiv, weiterhin exhausted, kein neuer Trigger.
WORK-AUTONOMOUS: STOP (guard, blind unchanged since …)             — Guard aktiv, weiterhin blind, keine Quelle neu verfügbar geworden.
WORK-AUTONOMOUS: STOP (user-only)                                  — nur USER/*-Reste offen, gebündelt vorgelegt.
```

`CONTINUE` — единственный сигнал, при котором вышестоящий цикл должен запустить ещё один тик. Все варианты `STOP` означают доказанное прекращение — включая обоснование, какой случай имеет место.

**Различие между `exhausted` и `blind` существенно для пользователя, а не косметично:** `exhausted` означает «я проверил всё, что нужно было проверить — работа завершена». `blind` означает «мне не хватает инфраструктуры, чтобы вообще проверять — это не состояние работы, а пробел».
Конструкция `/loop`/`/goal`, которая обрабатывает оба случая одинаково (цикл всё равно завершается), не должна одинаково СООБЩАТЬ о них пользователю — иначе исчезнет именно та информация, которую потребовал T-20260815-205101335.

## Связь с другими навыками

- **`think`/`decide`** — дают структурированный анализ/решение в шаге 1 цепочки. Здесь вызываются как составной элемент, а не изобретаются заново.
- **`decision-avatar`** (сам этот навык, нейтральный к пользователю) — даёт шаг 4 цепочки. В системах с конкретным, авторизованным профилем это соответствует `user-model` + `build-your-users-mind`.
- **`orchestrator`** — регулирует, КАК делегировать субагентам и как проверять их сообщение о завершении. `work-autonomous` регулирует, КОГДА вообще перестать искать; оба сочетаемы (оркестратор может выступать частью работы, выполненной на Уровне 1).
- **`bugsweep`** — пример другого, самоограничивающегося протокола поиска (эскалация удвоением вместо цепочки из четырёх шагов). `work-autonomous` более общий: он проверяет не только код на ошибки, но любой источник автономной работы.
- **Категории тикетов (`ticket-master`)** — дают словарь для «автономно выполнимо» (см. таблицу разграничения) и шаблон для цикла автономности (повторная проверка BLOCKED, сводка USER, перенос WAITING по сроку, PARKED — застой).
- **`tidy-up`** (с 1.3.0) — даёт дополнительный источник Уровня 1: однократный проход Tasksolver+Writer+Maintainer для папки проекта, с которой работали последний раз. Сам проверяет свой срок (лёгкий журнал USMC, без четырёхшагового Guard, как здесь) — `work-autonomous` вызывает его лишь как один из нескольких источников Уровня 1, не дублируя его логику.

## Пример хода

```
Tick 1: ACTIONABLE-Ticket T-... gefunden → erledigt. WORK-AUTONOMOUS: CONTINUE
Tick 2: Kein ACTIONABLE-Ticket mehr, kein offener TODO-Punkt.
        → Ebene 2: Selbstkenntnis + Kette 1–4 läuft.
        → Schritt 2 (decisions.ledger): verortet, DECIDED-AND-DONE.md hat einen neuen Eintrag
          seit 10 Min. → found, daraus resultiert eine neue autonome Aufgabe.
        → Guard: result=found geschrieben. Aufgabe erledigt. WORK-AUTONOMOUS: CONTINUE
Tick 3: Wieder nichts sichtbar. Voll ausgestattetes System (Gardener, USMC, _DECISIONS, BYUM alle da).
        → Ebene 2: alle vier Quellen verortet UND befragt, alle vier empty.
        → Guard: result=exhausted, fingerprint=FP1 (Lage + Verfügbarkeit ()), timestamp=T1.
        → WORK-AUTONOMOUS: STOP (exhausted)
Tick 4 (2 Minuten später, z. B. durch erneuten Loop-Trigger):
        → Guard: result=exhausted, fingerprint(jetzt)==FP1, (jetzt-T1) < 15 Min.
        → Kette NICHT erneut gefahren.
        → WORK-AUTONOMOUS: STOP (guard, exhausted unchanged since T1)

Gegenbeispiel — System OHNE Gardener/USMC (der Kernfall aus T-20260815-205101335):
Tick 1: Nichts sichtbar. Selbstkenntnis-Prüfung: decisions.ledger verortet (leer, empty),
        memory.organic/memory.curated NICHT verortet (CLI fehlt) → unavailable,
        user.model verortet (empty).
        → nicht alle vier Quellen befragbar → KEIN exhausted.
        → Guard: result=blind, fingerprint=FP2 (Verfügbarkeit ("memory.curated","memory.organic")).
        → WORK-AUTONOMOUS: STOP (blind, 2/4 Quellen nicht verfuegbar: memory.organic, memory.curated)
Tick 2 (Nutzer installiert grounding-seed + usmc auf diesem System):
        → Selbstkenntnis-Prüfung: memory.curated jetzt verortet (CLI auf PATH) → Verfügbarkeits-
          Baustein ändert sich zu ("memory.organic",) → fingerprint(jetzt) != FP2.
        → Guard erkennt Änderung, Kette läuft neu (Verpflanzung) — ohne dass jemand den Guard
          manuell zurückgesetzt hätte.
```
