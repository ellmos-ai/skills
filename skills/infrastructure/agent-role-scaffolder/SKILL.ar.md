# agent-role-scaffolder

<!-- FAMILY-ROUTER:Agenten-Orchestrierung START -->
> **عائلة تنسيق الوكلاء — دليل الإرشاد:** اختيار النموذج وتدرجه ->
> `model-strategy`؛ اختيار نمط التنسيق -> `choose-your-orchestrator`؛
> عمليات السرب (5 أنماط أساسية + وضعان) -> `swarm-operations`؛ تقسيم المهمة وتفويضها واستلامها -> `orchestrator`؛
> الرسائل عبر المزودين والحضور والأقفال -> `agents-bridge`؛ **بناء دور جديد أو فحصه -> هذه المهارة (agent-role-scaffolder)**.
<!-- FAMILY-ROUTER:Agenten-Orchestrierung END -->

## الغرض

تملك هذه المنظومة بالفعل عائلة ناضجة من مهارات التنسيق
(`model-strategy` و`swarm-operations` و`orchestrator` و`choose-your-orchestrator` و`agents-bridge`) — لكن **لا توجد
فيها مهارة واحدة تجيب عن السؤال "كيف يُنشأ دور جديد بشكل صحيح".** تسدّ `agent-role-scaffolder` هذه الفجوة. وهي لا تكرر
المهارات المذكورة، بل **توجّه إليها** متى احتاج الأمر إلى التدرج أو نمط التنسيق أو الرسائل عبر المزودين.

**المصدر:** قرار المستخدم M5 من التذكرة `T-20260825-935905816`
(مسح شامل للسوق): الحكم (ب) — كانت المعرفة الذاتية ببناء الوكلاء موجودة، لكنها غير رسمية. خدمت الإضافة الرسمية
`agent-sdk-dev` (claude-plugins-official، رخصة Apache-2.0) كـ**نموذج بنيوي**: ملف أمر لتهيئة الهيكل مع
وكيلَي تحقق متخصصين بقائمة مراجعة وصيغة تقرير PASS/PASS-WITH-WARNINGS/FAIL. أُخذت **الصيغة** (كتالوج أسئلة الهيكلة ← البناء ← قائمة التحقق بتقرير منظّم)، لا النص ولا الموضوع — فتلك الإضافة تبني تطبيقات Claude Agent SDK الخام (Python/TypeScript)، أما هذه المهارة فتبني **أدوار وكلاء خاصة بمنظومة ellmos** (تعريفات وكلاء فرعيين وعمال مرافقة). الأصل **غير مثبّت**؛ وهو موجود للقراءة فقط في ذاكرة السوق المحلية ولم يُقرأ إلا للاطلاع (`.PLUGINS/CLAUDE.md` القاعدة 5: الأفكار حرة، والصياغات لا). مدخل السجل: `.AI/.PLUGINS/PLUGIN-REGISTER.md`، الحالة `zitiert`.

## مساران للبناء — كلاهما يندرج هنا

تنشأ الأدوار الجديدة في منظومة ellmos بطريقتين مختلفتين بنيوياً لا ينبغي الخلط بينهما (مماثلة لفصل TS/Python في الإضافة النموذجية — لكنه هنا على طول الحد الفعلي للنظام):

| | **الوكيل الفرعي الأصلي** | **عامل المرافقة** |
|---|---|---|
| ما الذي يُنشأ | تعريف دور دائم (`~/.claude/agents/<name>.md`، قابل للتشغيل عبر أداة `Agent`) | نسخة مسمّاة ارتجالياً تُعاد استخدامها عبر `SendMessage` لسلسلة مهام واحدة |
| مدة الحياة | دائمة، قابلة لإعادة الاستخدام عبر الجلسات | لمدة سلسلة تذكرة/موضوع، ثم يُستغنى عنها |
| أمثلة في المخزون | `ati-agent`، `bueroassistent`، `versicherungs-agent`، `gesundheitsassistent`، `persoenlicher-assistent`، `production`، `research-agent`، `reflection-agent`، `test-agent`، `entwickler-agent` | نموذج هذه الجلسة نفسه (مثل `skillcreator-bau`، `policyreg-decisions`، `workflowhooker-ausbau` — عمال مسمّون في نظام التذاكر) |
| طبقة دورة الحياة | سجل الوكلاء الخاص بـ Claude Code | **COMA** (`.MODULES/.ORCHESTRATION/coma`) — إذا بُدئ عبر العمليات، لا داخل الأداة فقط |
| دليل البناء هنا | `references/subagent-role-scaffold.md` | `references/companion-worker-scaffold.md` |

**قاعدة عامة:** إذا احتاجت القدرة إلى اسم دائم خاص بها يُعاد استخدامه عبر جلسات كثيرة مع وصف تشغيل ثابت (مثل "كلما تعلق الأمر بمستندات الضرائب") ← وكيل فرعي أصلي. وإذا كانت سلسلة محدودة لكنها مترابطة من المهام يفوّضها منسّق في الوقت الحالي (سلسلة تذاكر، تغيير موضوع) ← عامل مرافقة.

## السير

1. **اختر مسار البناء** (الجدول أعلاه) — وعند الشك اسأل المستخدم ولا تخمّن.
2. **اعبر أسئلة الهيكلة** (انظر `references/*.md` المناسبة) — بالتتابع كما في الإضافة النموذجية لا دفعة واحدة: الغرض/المحفّز، واحتياج الأدوات (`Tools:`)، واختيار النموذج (← **الخطوة 3**)، واحتياج التنسيق (وكيل رئيسي مع خبراء أم دور منفرد؟).
3. **لا تقرر اختيار النموذج هنا — فوّضه إلى `model-strategy`.**
   الاختيار القائم على النقاط، والتفويض بين الوكلاء، والاقتران بالمستشار، ومحفزات التصعيد محلولة هناك
   بالفعل؛ هنا الإحالة فقط. قاعدة عامة من المخزون: الوكلاء الفرعيون **لا يرثون النموذج الرئيسي تلقائياً** (انظر
   ذاكرة الملاحظات `feedback_subagenten_modellstaffelung`).
4. **افحص نمط التنسيق** إذا كان الدور الجديد سيعمل مع عدة أدوار أخرى — تختار `choose-your-orchestrator` النمط،
   وتقدم `swarm-operations` الأنماط الخمسة الأساسية + الوضعين، و`orchestrator` بروتوكول التقسيم والتفويض والاستلام.
5. **التزم بأعراف الفريق والرسائل** (`references/
   model-staffing-and-messaging.md`): `SendMessage` للتواصل بين الوكلاء،
   وحجز التذكرة باسم الملف عند تفويض التذاكر، و"الإحالة بدل التكرار" عند إسناد المهام (لا تعِد سرد القواعد المركزية في الموجّه، بل المهمة الخاصة فقط).
6. **تحقّق** — نفّذ قائمة التحقق المناسبة في ملف `references/*.md` المختار، وأعدّ التقرير بصيغة
   `PASS / PASS MIT WARNUNGEN / FAIL` (البنية أدناه).
7. **سجّل عند الحاجة** — الدور الدائم الجديد يُدرج في السجل المناسب (`~/.claude/agents/`، وربما تجميع الإضافات)؛
   عامل المرافقة لا يحتاج مدخلاً في السجل، بل تسليماً أولياً واضحاً للمهمة فقط.

## صيغة تقرير التحقق (للمسارين)

بنية أُخذت عن قصد من الإضافة النموذجية (الصيغة لا النص) — أربعة أقسام موجزة:

- **الحالة:** PASS | PASS MIT WARNUNGEN | FAIL
- **النقاط الحرجة:** ما يجعل الدور غير صالح للاستعمال (وصف محفّز مفقود، و`Tools:` واسع جداً أو ضيق جداً، ونموذج غير مبرَّر عبر `model-strategy`، وعدم فحص التمييز عن دور قائم)
- **التحذيرات:** دون المثالي لكنه عامل (مثل وراثة النموذج الرئيسي بدل التدرج، أو عدم وجود معيار تدوير لعامل مرافقة طويل الأمد)
- **الفحوص الناجحة + التوصيات:** ما يصلح، وما ينبغي فعله تالياً

## المهارات ذات الصلة

- `model-strategy` — اختيار النموذج وتدرّجه (الخطوة 3، هنا للإحالة فقط).
- `swarm-operations` — أنماط السرب للتعاون بين أدوار متعددة.
- `choose-your-orchestrator` — يختار نمط التنسيق المناسب.
- `orchestrator` — بروتوكول التقسيم والتفويض والاستلام.
- `agents-bridge` — الرسائل عبر المزودين والحضور والأقفال، إذا احتاج الدور الجديد إلى التواصل مع Codex/Gemini/Kimi خارج Claude Code.
- `skill-explorer` — يفحص إن كانت القدرة موجودة بالفعل قبل بناء دور جديد (تجنّب التكرار).
