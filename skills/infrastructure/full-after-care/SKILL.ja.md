# Full After Care — 深層ラウンド（同義語: Deep After Care）

## このスキルをいつ使用するか

公開済みリポジトリを**根本的**に見直す必要がある場合に使用します：長期間チェックされていない、メジャーリリース前、法的に関連する対象、または他の所有プロジェクトとの連携がテーマとなっている場合などです。

安価なラウンドとの違いは丁寧さではなく工数です：レベル 2 は単一のリポジトリの境界を越えます。外部リソース（法的状況）に照会し、**全**組織を棚卸しし、アプリケーション自体（言語）を調整します。そのため、実行頻度は低く、通常は 1 リポジトリにつき年 1 回、または特定の契機で行われます。

## ワークフロー

### まずレベル 1 を完全に実行

**`surface-after-care` を完全に実行**してください —— ステップ 0（配信プラットフォーム）、プライバシーゲート、公開の意图、バナー、現状と理想の比較、README の言語、公開設定、組織への登録、Issue および PR、並びにコミット、プッシュ、プラットフォームの整合性を含みます。ここではこれらを繰り返したり省略したりしません。

以下の 3 つのステップが追加で加わります。これらはドキュメントおよびコードに変更を発生させるため、レベル 1 で説明した同じリズムで、テーマごとに分割したコミットでプッシュしてください。

### 5. 年次再確認を伴う法的一次評価

#### まず：評価の期限が来ているか？

`_after-care/RECHTSCHECK.md` を確認してください（このフォルダは gitignore されています。下記参照）。そこに**1 年未満**の監査日付が記載されている場合、このステップは深層ラウンドであっても**スキップ**されます。短い期間で新たな評価を取得することは時間と費用の無駄であり、新しい知見をもたらしません。

日付が **1 年以上経過**しているか、ファイルが存在しない場合は評価を行います。再確認を行う理由は法的鑑定が劣化するためではなく、**法的状況**が変化するためです：新しい規制、変更された閾値、新しい判例、改定されたプラットフォーム利用規約。2 年前の法的鑑定は形式的には正しくても実務的には陳腐化している可能性があります。

1 年の周期外であっても、**対象物**が変更された場合は再評価が必要です：新しいデータカテゴリ、新しい配信チャネル、新しいビジネスモデル、ライセンスの変更、Copyleft を持つ新しい依存関係、別の管轄区域への拡大など。

#### リポジトリは法的に関連しているか？

すべてのプロジェクトがこれを必要とするわけではありません。トリガーとなるのは以下のような場合です：

- ローカルであっても個人データを処理している
- 外部サービス、ウェブサイト、または API にアクセスしている（利用規約、スクレイピング）
- 規制された分野（法律、医療、税務、金融）で情報や助言を提供している
- 名称、ドキュメント、または UI に第三者の商標、名前、ロゴが含まれている
- Copyleft や不明確なライセンスを持つ依存関係が含まれている、または外部コンテンツを同梱している
- 未成年者を対象としている、決済を処理している、または輸出／暗号規制の対象となっている
- 人間に関する自動決定を行っている、または AI システムとして分類されている

いずれも該当しない場合は、実行ログに**チェックを行い該当なしであった旨を記録**してください。そうしないと次のラウンドで再び同じ質問が発生します。

#### 評価の取得

法務部門（スキル `law-checker`、モジュール `law-checker`）を使用し、具体的事実を提示します：アプリが何を行うか、どのデータに触れるか、どのチャネルで配信されるか、どのライセンスが含まれるか、誰を対象としているか。事実が具体的なほど、参照条文が有用になります。結果は条文の裏付けを伴う一次評価となります —— **法的助言ではありません**。深刻なリスクがある場合、結果は弁護士による確認の推奨であり、判決そのものではありません。

#### 格納

```
_after-care/
├── LOG.md                    # 両レベルの実行ログ
└── RECHTSCHECK.md            # 日付、対象、結果、条件、再確認日
```

`_after-care/` は `.gitignore` に含める必要があります。これは秘密主義ではなく、レベル 1 のステップ 2b と同じルールです：内部作業ドキュメントはリポジトリのコンテンツではありません。法的鑑定の場合、公開されたリスク分析は権利侵害の認否と受け取られる可能性があり、攻撃者にロードマップを与えることになります。あるいは、リポジトリ外の専用フォルダに保管することもできます —— 重要なのは次回実行時に**発見可能**であることであり、そうでなければ年次ルールが機能しません。

ヘッダー行はマシン可読な形式を維持してください：

```markdown
# Legal check — <Project>
checked: 2026-07-24
subject: local file management, no cloud, no personal data of third parties
result: unproblematic
conditions: Note on MIT license of embedded library X in README
resubmission: 2027-07-24
```

評価から**公開**されるのは**結果・影響**のみです：ライセンス表記、免責事項、プライバシー通知、アプリの動作に関する詳細な説明。これらの変更はリポジトリに含まれますが、その背後にある内部論据は含まれません。

### 9. 全組織にわたる相互参照

レベル 1 ではリポジトリが組織ページに掲載されているかのみを確認します。レベル 2 はさらに一歩踏み込みます：**所有する全組織の中のどの個別リポジトリがこれと関連しており、双方がそれを認識しているか？**

```bash
gh api user/orgs --jq '.[].login'
for ORG in $(gh api user/orgs --jq '.[].login'); do
  gh repo list "$ORG" --limit 200 --json name,description,updatedAt,isArchived,primaryLanguage
done
```

成果は単なるリストアップではなく、関係性の認識によって生まれます。関連するタイプ：

- **使用している / 使用されている** — 両方向の実際の技術的依存関係
- **同一ファミリーに属する** — 共通の製品ライン、共通の接頭辞、共通のアーキテクチャ
- **同じ問題を異なる方法で解決する** — 一方に到達したユーザーはもう一方も知りたいことが多い
- **前身 / 後継** — 置き換えられたプロジェクトには案内標識が必要であり、そうしないとユーザーが永久に古いバージョンにとどまります
- **構成要素 / 複合体** — ライブラリとそれを使用するアプリケーション

参照は**双方向**に設定してください。一方通行のリンクはこのステップでの最も頻繁なミスです：メンテナンス中のリポジトリに関連プロジェクトのリストを追加しても、関連プロジェクト側には何も記載されていないケースです。そこに到達した人は二度と戻る道を見つけられません。

相手側のリポジトリでの逆参照は実際に設定します —— レベル 1 のステップ 11 にある **Dirty Tree ルール**に従ってください。簡潔に言えば：クリーンなツリー → 独立したコミットとプッシュ；他ファイルに未コミットの変更あり → パス指定でコミットし、プッシュはしない；対象ファイルに未コミットの変更ありまたはアクティブなロックあり → 触れない。参照が設定されない場合は、対象リポジトリのタスクリスト（`AUFGABEN.txt`/`TODO.md`）に、ロックされている場合は自身の実行ログにのみ記録します。これにより、他者の作業状態を危険に晒すことなく、参照を失わずにラウンドを完结させることができます。

参照は単なる名前の羅列ではなく、メリットを意識して記述してください：「**project-b** — このツールが生成したエクスポートを読み取りレポートを作成する」は有用ですが、「参照: project-b」は有用ではありません。

アーカイブされたリポジトリや明らかに放棄されたリポジトリはリンクしません —— 逆方向への明示的な後継案内を除く。

この棚卸しは本ラウンドで最もコストがかかる部分です。多くの組織やリポジトリをチェックする必要がある場合、棚卸しの結果を実行ログに保存しておくと、別のリポジトリの次の深層ラウンドでそれを活用できます。

### アプリ層での全言語の追及

レベル 1 は README の言語バージョンを担当します。ここでは**製品自体**が対象です：UI テキスト、メッセージ、ヘルプ画面、CLI 出力、エラーメッセージ、ストアおよびレジストリの説明。

まず、アプリケーションが技術的にどの言語をすでに認識しており、どのように管理しているかを特定します：

```bash
rg -l "gettext|i18n|locale|translations|LC_MESSAGES|\.po$|messages\.json" --hidden
fd -e po -e pot -e ftl . 2>/dev/null; ls locales/ i18n/ lang/ translations/ 2>/dev/null
```

次に、3 つの問いに沿って不足を埋めます：

1. **プロジェクトが備えるべき言語が不足していないか？** ユーザー向けアプリの場合、標準言語はドイツ語、英語、スペイン語、簡体字中国語、日本語、ロシア語です。開発者向けのライブラリの場合、英語のみが適切な答えであることが多いです。不要な言語は継続的なメンテナンスの負荷であり、益にはなりません。
2. **既存の言語は完全か？** 機能追加のサイクルごとに、サブ言語は遅れをとります。翻訳のない新しいキーは実行時に静かにデフォルト言語にフォールバックするため気づきにくいです —— そのため見かけに頼らず、主言語に対して明示的に diff を取ってください。
3. **言語選択はユーザーにとって到達可能か？** 誰も有効化できない完全な翻訳は、存在しないのと同じです。切り替えスイッチが存在するか、選択が永続化されるか、システム言語がデフォルトとして検出されるか？

プロジェクトで確立されている i18n メカニズムに従い、並行して第 2 の仕組みを導入しないでください。リソースファイルだけでなく、**実際の画面**で結果を確認してください：長すぎる文字列はレイアウトを崩し、フォントサポートの欠落はレンダリング時に初めて明らかになります（不足している CJK グリフは空の四角として表示されます）。

最後にレベル 1 のステップ 0 の配信プラットフォームを含めます：ストアやレジストリの説明には独自の言語フィールドがあり、アプリの翻訳と自動的には連動しません。

## よくあるミス

| ミス | 修正 |
|---|---|
| 前回の法的評価が 3 ヶ月前だったにもかかわらず再度取得した | まず `RECHTSCHECK.md` の日付を確認する — 1 年未満ならスキップ |
| 「何も変わっていない」という理由で法的評価をスキップした | 法的状況はプロジェクトとは独立して変化するため、1 年経過後は確認が必要 |
| 法的鑑定書をリポジトリにコミットした | `_after-care/` は `.gitignore` に含める；公開するのは結果・影響のみ |
| 法的関連性がないと判断したことを記録しなかった | 「関連なし」も確認結果でありログに記録が必要 |
| 相互参照をメンテナンス中のリポジトリにしか設定しなかった | 双方向に設定する。そうしないと一方通行になる |
| 自分の組織のみをチェックした | レベル 2 は全組織を意味する —— これがレベル 1 との違い |
| 参照を単なる名前のリストにした | 半文でメリットを説明する。そうでなければ誰もクリックしない |
| 新しい言語を追加したが UI からアクセスできない | 切替スイッチ、永続性、システム言語の自動検出を確認する |
| 翻訳をリソースファイル内だけで確認した | 実際の画面で確認する —— レイアウト崩れやグリフの欠落はそこでしか見えない |
| ストア/レジストリの言語フィールドを忘れた | アプリの翻訳と自動的には連動しない |
