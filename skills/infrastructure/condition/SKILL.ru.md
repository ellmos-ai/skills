# condition — Язык условий для целей и промптов

## Основная идея

Условия в сплошном тексте легко упустить из виду. Поэтому переводите каждое важное условие в именованный, проверяемый гейт (Gate):

> Щедр при чтении, непреклонен при подтверждении.

Входные данные могут быть на естественном языке и неполными. Однако внутренний перевод должен четко фиксировать:

1. какое условие должно быть выполнено,
2. какой подшаг заблокирован,
3. какой запрос к инструменту служит доказательством,
4. означает ли невыполнение задержку или запрет.

Блокируйте только затронутый подшаг. Продолжайте независимую работу.

## Языковые блоки

| Выражение | Семантика | Пример |
| --- | --- | --- |
| `/condition <Условие> -> <Шаг>` | Канонический гейт | `/condition Тесты зеленые -> Собрать релиз` |
| `/if <Условие> -> <Шаг>` | Синоним для `/condition` | `/if Ревью завершено -> слить` |
| `/when <Условие> -> <Шаг>` | Выполнить, как только условие наступит | `/when Экспорт готов -> Проверить отчет` |
| `/if-only <Условие> -> <Шаг>` | Только при выполнении; иначе не выполнять вовсе | `/if-only Бэкап подтвержден -> Удалить старые данные` |
| `/after <Длительность> -> <Шаг>` | Смещение времени от момента установки | `/after 30 minutes -> Проверить статус` |
| `/and` | Все связанные условия должны соблюдаться | `/if Тесты зеленые /and Ревью есть -> слить` |
| `/or` | Достаточно хотя бы одного условия | `/if Разрешение есть /or Аварийное правило активно -> начать` |

Используйте пронумерованные условия, такие как `/condition 1 ...` и `/condition 2 ...`, когда промпт содержит несколько гейтов. При смешивании `/and` и `/or` не придумывайте неявный приоритет операторов: используйте скобки или пронумерованные подусловия. Если значение остается двусмысленным, запросите уточнение перед выполнением рискованного шага.

Относитесь к `/if-only` как к запрету. Если условие не может быть доказано, не выполняйте шаг. В случае нечеткой формулировки и необратимых последствий выбирайте более строгую интерпретацию.

## Порядок действий

### 1. Нормализация условия

Переведите входные данные в проверяемое утверждение. При установке относительного времени преобразуйте его в абсолютную временную метку с часовым поясом.

| Входные данные | Нормализованное условие | Класс доказательства |
| --- | --- | --- |
| `time 06:00` | Системное время не менее 06:00 в согласованном часовом поясе | Инструмент часов/времени |
| `after 2 hours` | Системное время не менее момента установки плюс два часа | Инструмент часов/времени |
| `wenn Worker A fertig ist` | Артефакт приемки или статус задачи Worker A показывает завершение | Инструмент задач/файлов |
| `wenn Tests grün sind` | Предписанный прогон тестов завершается успешно | Инструмент процессов/тестов |
| `nach dem Push` | Целевой репозиторий содержит предназначенный коммит | Инструмент контроля версий |
| `wenn der User zustimmt` | Явное согласие присутствует в разговоре | Пользовательский ввод |

Если объективный способ проверки не просматривается, заявите об этом открыто. Никогда не формулируйте гейт так, чтобы его можно было закрыть только на основе предположений.

### 2. Фиксация состояния гейта

Если доступно хранилище гейтов, задач или памяти, сохраните как минимум следующие поля:

```text
id
condition
blocks
mode = wait | only
proof_method
status = open | met | dropped
created_at
evidence
```

Если постоянное хранилище отсутствует, сохраняйте состояние видимым в текущей цели, плане задач или передаточном документе. Утверждайте, что гейт сохраняется между сессиями, только если используемое хранилище действительно является постоянным.

Существующий адаптер среды выполнения может использовать другие имена команд. Функционально ему требуются: `open`, `list`, `meet` и `drop` или эквивалентные операции.

### 3. Переупорядочивание работы

Открытый гейт не блокирует весь заказ. Выполните все независимые шаги и повторно проверьте состояние гейта перед следующим зависимым шагом.

Не проводите активный опрос в коротких циклах агента. Для длительных периодов ожидания используйте планировщик, фоновую задачу или событие, которое сообщает однократно при наступлении. После сигнала пробуждения повторно проверьте фактическое условие с помощью предназначенного инструмента.

### 4. Строгая проверка и закрытие

Сначала выполните запрос инструмента, затем закройте гейт с конкретными доказательствами. Подходящие доказательства включают:

- Время: измеренная временная метка с часовым поясом,
- Файл: путь, метаданные или хэш ожидаемого артефакта,
- Тесты: выполненная команда, код выхода и соответствующая сводка,
- Репозиторий: ветка, ID коммита и сверка с удаленным репозиторием,
- Процесс или задача: стабильный ID и измеренный конечный статус,
- Согласие: однозначный ответ пользователя в текущем контексте.

Оценка, ожидаемое состояние или простое утверждение другого работника недостаточны, если должно быть доступно независимое доказательство.

Если гейт устарел из-за изменения заказа, отметьте его как `dropped` с обоснованием. Для `/or` также закройте или сбросьте ненужные альтернативы, чтобы не оставалось зомби-гейтов.

### 5. Эскалация

Когда все независимые шаги выполнены:

1. проверьте, можно ли активно выполнить блокирующую предварительную работу в рамках задачи,
2. для чистых условий ожидания используйте подходящий планировщик или фоновую задачу,
3. при решениях пользователя или внешних зависимостях передайте управление с открытым гейтом и четким промежуточным статусом.

Не выводите дополнительную авторизацию из условия. Выполненный гейт меняет только последовательность; он не расширяет авторизованный объем работы.

## Примеры

### Цель с условием времени

```text
Ziel: Daten prüfen und Bericht veröffentlichen.
/condition time 16:00 Europe/Berlin -> Veröffentlichung starten
```

Проверка данных может быть проведена заранее. Публикация остается заблокированной до тех пор, пока запрос текущего времени не подтвердит как минимум 16:00.

### Промпт с несколькими условиями

```text
/condition 1 Tests erfolgreich
/condition 2 Review freigegeben
/if condition 1 /and condition 2 -> mergen
```

Подтвердите оба гейта отдельно. Слияние выполняйте только после этого.

### Запрет вместо задержки

```text
/if-only verifiziertes Backup vorhanden -> alte Dateien löschen
```

Без подтвержденного бэкапа ничего не удаляйте и укажите открытый запрет в итоговом отчете.

## Подводные камни

- Повторение условия только в сплошном тексте вместо сохранения его как состояния.
- Приостановка всей цели, хотя заблокирован только подшаг.
- Сохранение относительного времени без времени установки и часового пояса.
- Замена доказательства инструмента предположением или самооценкой.
- Отношение к `/if-only` как к простому ожиданию.
- Оставление открытыми ненужных альтернативных гейтов после `/or`.
- Жесткая кодировка имен провайдеров, моделей, пользователей или хостов в общей механике.
- Отношение к локальному пути среды выполнения как к требованию для самого языка.
