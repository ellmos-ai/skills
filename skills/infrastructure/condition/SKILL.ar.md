# condition — لغة الشروط للأهداف والمطالبات

## الفكرة الأساسية

يسهل أن تُغفَل الشروط المكتوبة ضمن النص الحر. لذلك يجب ترجمة كل شرط ذي صلة إلى بوابة مُسمّاة وقابلة للتحقق:

> كن متساهلًا عند القراءة، وصارمًا عند التوثيق.

قد يكون الإدخال بلغة طبيعية وغير مكتمل. أما الترجمة الداخلية فيجب أن تحدد بوضوح:

1. أي شرط يجب أن يتحقق،
2. أي جزء فرعي محظور،
3. أي استعلام أداة يُعدّ دليلًا،
4. هل يعني عدم التحقق تأجيلًا أم منعًا.

امنع الجزء المتأثر فقط، واستمر في العمل المستقل.

## عناصر اللغة

| التعبير | الدلالة | مثال |
| --- | --- | --- |
| `/condition <Bedingung> -> <Schritt>` | بوابة قياسية | `/condition Tests grün -> Release bauen` |
| `/if <Bedingung> -> <Schritt>` | مرادف لـ `/condition` | `/if Review abgeschlossen -> mergen` |
| `/when <Bedingung> -> <Schritt>` | التنفيذ بمجرد تحقق الشرط | `/when Export fertig -> Bericht prüfen` |
| `/if-only <Bedingung> -> <Schritt>` | التنفيذ عند التحقق فقط؛ وإلا فلا يُنفَّذ إطلاقًا | `/if-only Backup belegt -> Altbestand löschen` |
| `/after <Dauer> -> <Schritt>` | إزاحة زمنية ابتداءً من وقت الضبط | `/after 30 minutes -> Status prüfen` |
| `/and` | يجب أن تنطبق جميع الشروط المرتبطة | `/if Tests grün /and Review da -> mergen` |
| `/or` | يكفي شرط واحد على الأقل | `/if Freigabe da /or Notfallregel aktiv -> starten` |

استخدم شروطًا مرقّمة مثل `/condition 1 ...` و`/condition 2 ...` عندما يتضمن المطلب عدة بوابات. وعند الجمع بين `/and` و`/or`، لا تخترع ترتيبًا ضمنيًا للمعاملات، بل استخدم الأقواس أو الشروط الفرعية المرقمة. وإذا بقي المعنى ملتبسًا، فاسأل قبل الإذن بخطوة محفوفة بالمخاطر.

تعامل مع `/if-only` بوصفه منعًا. فإن تعذّر توثيق الشرط، فلا تنفذ الخطوة. وعند الصياغة غير الواضحة والعواقب التي لا يمكن التراجع عنها، اختر التفسير الأكثر صرامة.

## سير العمل

### 1. تطبيع الشرط

ترجم الإدخال إلى جملة قابلة للتحقق. وعند الضبط، حوّل الأوقات النسبية إلى وقت مطلق مع المنطقة الزمنية.

| الإدخال | الشرط المطبّع | فئة الدليل |
| --- | --- | --- |
| `time 06:00` | وقت النظام يساوي 06:00 على الأقل في المنطقة الزمنية المتفق عليها | أداة الساعة/الوقت |
| `after 2 hours` | وقت النظام يساوي وقت الضبط زائد ساعتين على الأقل | أداة الساعة/الوقت |
| `wenn Worker A fertig ist` | يُظهر عنصر الاستلام أو حالة المهمة A الإنجاز | أداة المهام/الملفات |
| `wenn Tests grün sind` | ينتهي تشغيل الاختبار المطلوب بنجاح | أداة العمليات/الاختبارات |
| `nach dem Push` | يحتوي المستودع البعيد المستهدف على الإيداع المقصود | أداة التحكم بالإصدارات |
| `wenn der User zustimmt` | توجد موافقة صريحة في المحادثة | إدخال المستخدم |

إذا لم يكن هناك مسار موضوعي واضح للتوثيق، فاذكر ذلك صراحةً. ولا تصِغ أي بوابة بحيث يمكن إغلاقها بالتخمين فقط.

### 2. تسجيل حالة البوابة

إذا كان متاحًا مخزن دائم للبوابات أو المهام أو الذاكرة، فاحفظ فيه على الأقل هذه الحقول:

```text
id
condition
blocks
mode = wait | only
proof_method
status = open | met | dropped
created_at
evidence
```

وإذا لم يوجد مخزن دائم، فاحتفظ بالحالة بصورة مرئية في الهدف الحالي أو خطة المهام أو وثيقة التسليم. ولا تدّعِ أن البوابة تبقى عبر الجلسات إلا إذا كان التخزين المستخدم دائمًا فعلًا.

يجوز لمحوّل التشغيل الموجود أن يستخدم أسماء أوامر مختلفة. لكنه يحتاج وظيفيًا إلى `open` و`list` و`meet` و`drop`، أو عمليات مكافئة.

### 3. إعادة ترتيب العمل

البوابة المفتوحة لا توقف المطلب كله. نفّذ جميع الخطوات المستقلة، وأعد فحص حالة البوابة قبل أي خطوة تابعة.

لا تستعلم بشكل نشط ومتكرر في حلقات قصيرة للوكيل. وللانتظار الطويل، استخدم مجدولًا أو مهمة خلفية أو حدثًا يُبلغ مرة واحدة عند التحقق. وبعد إشارة الإيقاظ، أعد التحقق من الشرط الفعلي بالأداة المخصصة له.

### 4. الفحص الصارم والإغلاق

نفّذ استعلام الأداة أولًا، ثم أغلق البوابة بدليل ملموس. من الأدلة المناسبة مثلًا:

- الوقت: طابع زمني مقيس مع المنطقة الزمنية،
- الملف: مسار أو بيانات وصفية أو تجزئة للعنصر المتوقع،
- الاختبارات: الأمر المنفَّذ ورمز الخروج وملخص ذو صلة،
- المستودع: الفرع ومعرّف الإيداع ومطابقة المستودع البعيد،
- العملية أو المهمة: معرّف ثابت وحالة نهائية مقيسة،
- الموافقة: رد واضح من المستخدم في السياق الحالي.

لا يكفي التقدير أو الحالة المتوقعة أو مجرد ادعاء عامل آخر، إذا كان ينبغي توفر دليل مستقل.

إذا أصبحت البوابة غير ذات جدوى بسبب تغيير المطلب، فعلّمها بالحالة `dropped` مع ذكر السبب. وعند `/or`، أغلق البدائل غير المطلوبة أو ألغِها أيضًا حتى لا تبقى بوابات معلّقة لا فائدة منها.

### 5. التصعيد

عندما تنتهي جميع الخطوات المستقلة:

1. تحقق مما إذا كان بالإمكان إنجاز العمل السابق المانع داخل نطاق المطلب،
2. إذا كان الشرط انتظارًا بحتًا، فاستخدم مجدولًا أو مهمة خلفية مناسبة،
3. إذا كان القرار للمستخدم أو التبعية خارجية، فسلّم العمل مع بوابة مفتوحة وحالة وسيطة واضحة.

لا تستنتج صلاحية إضافية من أي شرط. فالبوابة المحققة تغيّر ترتيب التنفيذ فقط، ولا توسّع النطاق المصرّح به للمطلب.

## أمثلة

### هدف مع شرط زمني

```text
Ziel: Daten prüfen und Bericht veröffentlichen.
/condition time 16:00 Europe/Berlin -> Veröffentlichung starten
```

يجوز إجراء فحص البيانات قبل ذلك. تبقى عملية النشر مقفلة حتى يُثبت استعلام وقت حالي أن الساعة 16:00 قد حانت على الأقل.

### مطالبة بعدة شروط

```text
/condition 1 Tests erfolgreich
/condition 2 Review freigegeben
/if condition 1 /and condition 2 -> mergen
```

وثّق البوابتين كلًّا على حدة. ولا تدمج الفروع إلا بعد ذلك.

### منع بدلًا من التأجيل

```text
/if-only verifiziertes Backup vorhanden -> alte Dateien löschen
```

لا تحذف أي شيء دون نسخة احتياطية موثّقة، واذكر المنع المفتوح في تقرير الإنجاز.

## المزالق

- تكرار الشرط في النص الحر بدلًا من تتبعه بوصفه حالة.
- إيقاف الهدف بأكمله رغم أن جزءًا فرعيًا واحدًا فقط مُعاق.
- تخزين الوقت النسبي دون وقت ضبط ومنطقة زمنية.
- استبدال دليل الأداة بالافتراض أو الإقرار الذاتي.
- معاملة `/if-only` كمجرد انتظار.
- ترك بوابات بديلة لم تعد مطلوبة بعد `/or`.
- إدراج أسماء المزودين أو النماذج أو المستخدمين أو المضيفين في الآلية العامة.
- معاملة مسار تشغيل محلي بوصفه شرطًا مسبقًا للغة نفسها.
