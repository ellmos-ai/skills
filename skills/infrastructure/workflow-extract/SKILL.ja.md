# Workflow-Extract — チャット履歴や外部自動化からの自動化構築 (日本語)

## 目的

一部のプロセスは、手動でロードするオンデマンドスキルではなく、**勝手に実行される無人自動化**（夜間チェック、ローテーションによるプロジェクト監査、定期的なメンテナンス実行）に属します。このスキルは、チャット履歴（対話的に開発され、将来無人で実行されるべきプロセス）と他のシステムの既存の自動化プロンプト（Codex 自動化、スケジュール済みタスク、n8n フローなど）の 2 つのソースタイプからそのようなワークフローを抽出し、ユーザーに依存しない堅牢な自動化プロンプトまたはスキルに変換します。

対話型プロセスとの違い: 自動化には **修正してくれるユーザーがいません**。ユーザーが対話セッションで拾い上げたものはすべて、自動化自身が捕捉する必要があります。まさにそのために `automation-bausteine.md` の構成要素が存在します。

## プロセス

### 1. ソースとターゲット形態の明確化

| ソース | 典型的なケース |
| --- | --- |
| 当前セッション / 文字起こし | 対話的に開発されたプロセスで、定期的に継続実行させたい |
| 外部自動化 (プロンプトファイル, Cron タスク, n8n フロー) | 別のシステムやライブラリへの移植/抽象化 |

ターゲット形態（1 つまたは複数）:

- **自動化プロンプト (Automation Prompt):** 独立したユーザーニュートラルなプロンプトテキスト。任意のスケジューラ（Codex 自動化、Claude `/schedule`/Cron、スケジュール済みタスク、n8n）で使用可能。
- **ワークフロースキル (Workflow Skill):** プロセスを記述するライブラリ内のスキル。自動化プロンプトはそれを呼び出し/パラメータ化するのみ（同じプロセスが複数のパイプライン/システムに適用される場合に推奨 — 単一の真実の情報源）。
- **コマンド:** 同一プロセスの手動トリガー用の薄いスラッシュコマンド。

### 2. ワークフローコアの抽出

ソースから抽出するもの:

- **コアタスク:** 何がチェック/メンテナンス/生成されているか？（1 文）
- **選択ロジック:** タスクが何に適用されるか — 固定ターゲットか、集合に対するローテーション（1 回の実行につき 1 プロジェクト）か？
- **前提条件:** 作業前に何を読み込み/チェックする必要があるか（ルートドキュメント、レジストリ、ロック）？
- **ドキュメント化義務:** 結果、ログ、後続タスクはどこに書き込まれるか？
- **終了パス:** 実行はいつリードオンリーで終了するか（「何もすることがない」は有効な結果です）？

チャット履歴の場合は、修正ループも評価します（`../skill-extractor/transcript-quellen.md` を参照）: ユーザーによるすべての修正は、自動化が将来自身で必要とするガードの候補です。

### 3. 抽象化 / 中立化 (Neutralize)

`../skill-extractor/neutralisierung.md` のルールに従います: メカニクスを設定から分離し、パス/ホスト/プロジェクト名を設定ブロックに引き出します。自動化プロンプトはスケジューラにそのままコピーされるため、この設定ブロックが緊急に必要です — 具体的な値はプロンプトヘッダーの 1 箇所に配置します。

### 4. 自動化構成要素の補完

抽出したコアを `automation-bausteine.md` のチェックリストと照らし合わせ、不足している構成要素を補完します — 特にチェックレジストリを伴うローテーション選択、べき等性、ログ衛生、ロック尊重、リードオンリー終了、および完了レポート。これらの構成要素がないワークフローはテスト時には機能しますが、継続的な運用で劣化します（重複チェック、ログの肥大化、並行エージェントとの衝突）。

### 5. ケイデンスと予算の設定

- **頻度を変更率にリンクさせる:** チェックは、その対象が変更される頻度よりも頻繁に実行する必要はありません。拡大した自動化アセットからの経験: 最初に毎時設定された多くのチェックが毎日/毎週に削減されました — ローテーション選択を使用すると、頻度が低くてもパイプライン全体をカバーできます。
- **重いタスクには夜間ウィンドウ**を割り当て、短いリードオンリーチェックはより頻繁に実行できます。
- **コスト意識:** すべての実行にトークン/計算コストがかかります。ほとんどがリードオンリーで終了する実行は、早期にそれを判断するべきです（高コストな分析の前にレジストリを読み込む）。

### 6. テストとデプロイ

1. **ドライラン:** 完成したプロンプトを一度対話的に実行し（スケジューラとして振る舞う）、検証します: クリーンに終了するか？レジストリ/ログを正しく書き込むか？スコープ内に留まっているか？
2. **境界ケーステスト:** 何もすることがない実行をシミュレートします — 「仕事を捏造する」ことなく、短いログエントリーとともにリードオンリーで終了する必要があります。
3. **デプロイ:** ターゲットスケジューラに登録します。スキル形態の場合は、ライブラリに保存してデプロイします。
4. **エラーパスの監視:** 最初の 2–3 回の実際の実行後にログ/レジストリを確認します — 自動化は、パスのドリフト（ターゲットが移動した）とログファイルの肥大化によって最も頻繁に失敗します。

## フリート監査モード (Fleet Audit Mode): 稼働中の自動化フリートを監査する

「私の自動化をチェックして」の場合: 抽出するのではなく、既存のフリートの運用を支援します。ターゲットシステムの自動化ソース（プロンプト/設定ファイル、スケジュール、実行ログ/メモリ）を通じて体系的にチェックします:

1. **サイレントエラー / 無効実行検出 (Silent Failure / No-Op):** 自動化は実行されているが何も達成していないか？（最近の実行のメモリ/ログを読み込む: 空振り、エラー、デッドパスばかりか？）
2. **冗長性 + リターン:** 自動化はスコープ内で重複しているか？リターン（出力、解決された問題）は消費（トークン、実行回数）に見合っているか？
3. **ドリフト:** プロンプトのパス、規則、スケジュールは依然として現実と一致しているか？（ターゲットの移動、ポリシーの変更、変更率に対して高すぎる頻度）
4. **カタログの照合:** 存在するべき自動化が不足しているか（パターングリッドのギャップ）？提案は承認ゲート（ブロック 12）を経由する必要があり、自ら有効化してはなりません。
5. **診断レポート:** 自動化ごとに 1 行（保持 | 調整 | 一時停止 | 統合 | 削除）+ 理由。変更は承認後にのみ実施します。

## バルクモード (Bulk Mode): 自動化資産や多数の文字起こしを審査する

「システム X のすべての自動化をチェックして抽象化可能なワークフローを探す」または「古いチャット履歴から自動化候補を抽出する」の場合:

1. **skill-extractor と同様のデータ削減**（サブエージェントによる Map-Reduce、`swarm-operations` パターン）: バンドルごとに 1 つのサブエージェントがソースごとに報告: コアタスク | パターン（例: ローテーションチェック、ヘルスチェック、アイデアマイニング） | 固有の要素 | ユーザーニュートラルに抽象化可能か？ | 既存のスキルでカバーされているか？
2. **単体よりもパターン:** 多くのソースが同じ骨組みを共有している場合（例: 40 個のローテーションチェック）、その骨組みがスキルになり、個々のケースはパラメータ化されます — 40 個の個別のスキルにはしません。
3. **既存のスキル/コマンド景観に対して重複排除**を行い、一括構築の前に番号付きの候補リストをユーザーに提示します。

## 例

```text
ユーザー: 「今日ペーパーの引用チェックをテストしました —
今後はこれをすべてのペーパーに対して毎週実行したいです。」

1. ターゲット形態: スケジューラ用の自動化プロンプト + rotation-check への参照。
2. コア: オリジナルのソース（Web/データベース）に対してペーパーの引用をチェックし、修正を適用し、変更された場合は TODO.md に後続タスク「再アップロード」を書き込む。
3. 抽象化: パイプラインルート、レジストリ/ログパス → 設定ブロック。
4. 構成要素の補完: ローテーション選択（1 回の実行につき 1 ペーパー）、選択前にレジストリを読み込む、リードオンリー終了（「すべてのソース OK」）、ログ衛生、完了レポート。
5. ケイデンス: 毎週で十分（ペーパーの変更は緩やか）; ドライラン + 空振りテスト、その後スケジューラへ。
```

## 危険信号 (Red Flags)

| 考え | 現実 |
| --- | --- |
| 「セッションで動いたのだから、自動化としても動く」 | ユーザーがいないとすべての是正ガードが欠落します — 構成要素のチェックリストは必須です。 |
| 「毎時実行しても害はない」 | 害があります: トークン消費、ログの肥大化、衝突リスク。頻度を変更率にリンクさせます。 |
| 「バリアントごとに個別の自動化を構築する」 | 共有の骨組みをスキルにし、バリアントはパラメータとします。 |
| 「何も見つからなかった — 別の仕事を探そう」 | ログエントリーを伴うリードオンリー終了が、空振り実行の正しい結果です。 |

## 関連スキル

- `skill-extractor` — 同じ抽出プロセス。ターゲットはオンデマンドで呼び出し可能なスキル。中立化と文字起こしソースを共有。
- `rotation-check` — ローテーションによるパイプラインチェックの標準的な骨組み（最も頻度の高い自動化タイプ）。再発明するのではなく構成要素として参照。
- `swarm-operations` — 一括審査のためのスウォームパターン。
