# ストレージ回収

## 目的と結果

このスキルは、Windows上で制御された形でストレージを取り戻し、同じ圧迫経路によってディスクがすぐに再び占有されることを防ぎます。作業は三つのフェーズで進みます：緊急解放、原因のフォレンジック、そして恒久的な制限です。

すべての変更は同じプロトコルに従います：

`Fund -> Entscheidung -> begrenzte Ausführung -> Readback -> Messung`

ユーザーがより高い目標を指定しない場合、最後の変更後にシステムボリュームが再び少なくとも50 GBの空き容量を報告するまで、タスクは完了とみなされません。追加10 GBという最初の緊急しきい値は、急性の状態を終わらせるだけであり、タスク全体を終わらせるものではありません。

## 有効化するタイミング

次の場合にこのスキルを使用してください：

- システムディスクの空きが少ない、または繰り返し容量が失われる場合；
- ログ、キャッシュ、ページングファイル、アーカイブ、ビルドが異常に大きい場合；
- 重複したクローン、バックアップ世代、またはローカルのクラウドコピーがある場合；
- リソース枯渇イベント、または急速にコミットが増加しているプロセスがある場合；
- スケジューラー、ウォッチャー、同期クライアントがデータを再生成している疑いがある場合。

## 安全規則

- 変更の前に、空き容量、ボリューム、プロセス状況、ロック、Reparse Point、解決済みの絶対ターゲットパスを確認してください。
- 再帰的な操作では、ターゲットが明示的に選択されたルート内にあることを確認してください。未検証の変数やグロブを削除対象として決して使用しないでください。
- ボリューム、ユーザー、リポジトリ、クラウド、プロジェクトのルートは削除しないでください。
- アクティブなソース、未コミットの作業、秘密情報、競合コピー、他者のロック、`.git`、および唯一の復元用コピーを保護してください。
- ごみ箱、隔離、圧縮、またはクラウドからのデハイドレーションを優先してください。取り消し不能な削除は、正確に特定され再生成可能な検出項目に限り許可され、パス、サイズ、復元方法を記録する必要があります。
- ページングファイル、休止状態、サービス、またはシステム全体の上限は、必要な権限、ロールバック、完全な読み戻しがある場合にのみ変更してください。`Zugriff
  verweigert`は成功した対策ではありません。
- ローカルの容量を解放するためにOneDriveのクラウドオブジェクトを削除しないでください。クラウド上の削除とローカルのデハイドレーションは別の操作です。

## フェーズ1：緊急解放

### 1. ベースライン

少なくとも次の項目を記録してください：

```powershell
Get-PSDrive -Name C | Select-Object Used, Free
Get-CimInstance Win32_LogicalDisk -Filter "DeviceID='C:'" |
  Select-Object DeviceID, Size, FreeSpace
Get-Process | Sort-Object PrivateMemorySize64 -Descending |
  Select-Object -First 15 Name, Id, PrivateMemorySize64, WorkingSet64
```

時刻、開始値、およびターゲットを記録します。`PrivateMemory`またはコミットと`WorkingSet`を区別してください：プロセスは作業セットではわずかなRAMしか示さなくても、ページングファイルを大量に占有していることがあります。

### 2. 範囲を限定した棚卸し

既知のローカルルートと最近の変更ウィンドウから始めてください。クラウドやユーザーディレクトリをすべて盲目的に再帰検索しないでください。適切な候補は次のとおりです：

- 明確に再生成可能なモデル、パッケージ、ビルドのキャッシュ；
- 古く完了したビルド出力；
- ローテーション可能なアプリケーションログ；
- 検証済みのアーカイブまたはバックアップ世代；
- 完全に同期済みのローカルクラウドコピー。

スパース、圧縮、およびクラウドのプレースホルダーファイルでは、ファイル長は物理的な占有量ではありません。NTFSの割り当て（`GetCompressedFileSizeW`）、`compact`、または同等のツールを使用し、前後の空き容量を比較してください。

### 3. 一つの検出項目を処理する

測定ステップごとに正確に一つの検出項目を処理してください。その後、次を確認します：

- 実際に得られたバイト数；
- エラー、開いているハンドル、残っているロック；
- 保護対象のソースが残っていること；
- 復元可能性または再生成可能性；
- あるプロセスがその項目を直ちに再生成していないか。

緊急モードは、追加10 GBが実証されて初めて終了します。その後、手順は直ちにフォレンジックへ移ります。

## フェーズ2：圧迫するプロセスと発生源のフォレンジック判定

### 1. リソース枯渇とページングファイル

現在の証拠と過去の証拠を合わせて読み取ってください：

```powershell
Get-CimInstance Win32_ComputerSystem |
  Select-Object AutomaticManagedPagefile
Get-CimInstance Win32_PageFileUsage |
  Select-Object Name, AllocatedBaseSize, CurrentUsage, PeakUsage
Get-WinEvent -FilterHashtable @{LogName='System'; Id=2004} -MaxEvents 20
```

Windows Resource Exhaustion Detectorのイベント2004には、イベント発生時点で最も高いコミットを持つプロセスが含まれます。PID、プロセス名、タイムスタンプ、バイト数を、現在のプロセスと照合してください。大きな`pagefile.sys`だけでは、そのファイル自体が原因であることは証明されません。探すべきは、コミットを引き起こしたプロセスです。

### 2. ファイルの増加

新規または変更されたファイルを次の単位でグループ化してください：

- 作成時刻および変更時刻の時間帯；
- 親パスと拡張子；
- 所有者または生成元のプロセス；
- ファイル数と物理的に占有されたバイトによる一日あたりの増加率。

特に、ログ、キャッシュ、同期、バックアップ、ビルド、ダウンロード、セッションのディレクトリを確認してください。クライアントが一日に数ギガバイトを書き込み、ボリュームが小さい場合、七日間の保持期間は不適切です。

### 3. 自動化

タスクスケジューラー、サービス、ウォッチャー、スタートアッププログラムについて、頻度、保持期間、成功状況を確認してください：

```powershell
Get-ScheduledTask | Where-Object State -ne 'Disabled'
Get-ScheduledTaskInfo -TaskName '<task-name>'
```

アクション、トリガー、繰り返し間隔、最後の戻りコード、次回実行時刻をそれぞれ個別に確認してください。タスクが存在することは、保持期間や頻度が実際の増加を抑えていることの証明にはなりません。

## フェーズ3：恒久的な制限

最も小さい、効果的で可逆的な対策を選んでください：

- ログのローテーションをより頻繁に実行し、さらにサイズ上限を設定する；
- 目立つクライアントを制御された形で再起動し、そのコミットを測定する；
- ターミナルのスクロールバックやデバッグログを適切な値に制限する；
- 古く再生成可能なキャッシュを削除し、自動的な再生成を観察する；
- 検証済みのクラウドコンテンツを「ストレージの空き領域を確保」でデハイドレーションする；
- スケジューラーの頻度と保持期間を、実測された一日あたりの増加率に合わせる；
- ページングファイルや休止状態の変更は、再起動とロールバック計画を伴う管理者操作としてのみ行う。

Windows Terminalの場合、制限されたデフォルトのスクロールバックは例えば次のようになります：

```json
{
  "profiles": {
    "defaults": {
      "historySize": 2000
    }
  }
}
```

既存の設定は保持し、変更後にJSONファイルを検証してください。

### OneDrive固有のゲート

デハイドレーションの前に、同期状態と保留中のアップロードを確認してください。クラウドフィルターに対応したファイルマネージャーか、エクスプローラーの「ストレージの空き領域を確保」コマンドを使用してください。デハイドレーションによってクラウド上のコンテンツが削除されてはなりません。

`$env:LOCALAPPDATA\Microsoft\OneDrive\logs` の下にあるローカルのOneDriveログ領域は個別に確認してください。サブ領域が一日あたりギガバイト単位のログを生成する場合は、時間ベースの保持期間と厳格なサイズ上限を組み合わせ、十分に高い頻度で定期実行してください。非常に新しいファイルや開いているファイルは保護し、実行後にタスクの状態と残りのサイズの両方を確認してください。

## 最終確認と報告

最後の変更の後：

1. 非同期のクラウド操作または削除操作が終わるまで待つ。
2. 空き容量とプロセスのコミットを再度読み取る。
3. 変更された設定、タスク、ログサイズを読み戻して確認する。
4. 短い再テストを実行する：観測期間中に再び過度なストレージが生成されないか？
5. 開始値、各検出項目とその判断、物理的に得られたバイト数、ストレージを圧迫したプロセス、恒久的な調整、ロールバック、残存リスク、終了値を報告する。

現在の適切な読み戻しなしに、クリーンアップ、プロセス制限、または50 GB目標の達成を主張しないでください。

## 既知の制限

- 管理者権限がない場合、ページングファイル、休止状態、またはサービスの変更はブロックされたままになることがあります。残っている正確な手順を文書化してください。
- 過去のプロセスイベントは以前の圧迫要因を示すだけであり、現在の状況にはプロセスとファイル増加のデータが追加で必要です。
- 計画されたバックアップ構想はバックアップではありません。転送や削除には、現在のターゲットの同一性、マニフェストまたはハッシュ、復元の証明、およびマウントが必要です。
- 所有関係が不明な場合、他者の作業が進行中の場合、またはターゲットが不明な場合は、`nichts`の判断が適用されます。
