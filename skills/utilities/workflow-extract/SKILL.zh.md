# Workflow-Extract — 从对话记录与外部自动化构建自动化流程 (中文)

## 目的

某些流程不属于手动加载的按需 Skill，而属于**自行运行的无人值守自动化**：每晚检查、轮换项目审计、定期维护运行。本技能从两种来源类型中提取此类工作流 — Chat 对话记录（交互式开发的流程，将来需要无人值守运行）以及其他系统的现有自动化 Prompt（例如 Codex 自动化、定时任务、n8n 流程）— 并将它们转化为用户中立、健壮的自动化 Prompt 或 Skill。

与交互式流程的区别：自动化**没有用户进行实时纠错**。用户在交互式 Session 中拦截的所有问题，自动化都必须自行拦截。这正是 `automation-bausteine.md` 中的构建块存在的原因。

## 流程

### 1. 明确来源与目标形式

| 来源 | 典型情况 |
| --- | --- |
| 当前 Session / 转录 | 交互式开发的流程，需要定期继续运行 |
| 外部自动化 (Prompt 文件, Cron 任务, n8n 流程) | 移植/抽象到另一个系统或技能库中 |

目标形式（一种或多种）：

- **自动化 Prompt (Automation Prompt)：** 独立、用户中立的 Prompt 文本，可用于任何调度器（Codex 自动化、Claude `/schedule`/Cron、定时任务、n8n）。
- **工作流 Skill (Workflow Skill)：** 技能库中描述该流程的 Skill，自动化 Prompt 仅对其进行调用或参数化（当相同的流程适用于多个 Pipeline/系统时优先选择 — 唯一事实来源）。
- **命令 (Command)：** 用于手动触发同一流程的精简 Slash 命令。

### 2. 提取工作流核心

从来源中提炼出：

- **核心任务：** 正在检查/维护/生成什么？（一句话）
- **选择逻辑：** 任务应用于什么 — 固定目标还是在一组目标上轮换（每次运行一个项目）？
- **前置条件：** 在工作之前必须读取/检查什么（根文档、注册表、锁）？
- **文档化义务：** 结果、日志、后续任务写到哪里？
- **退出路径：** 运行何时以只读方式结束（“无事可做”是一个有效的运行结果）？

对于对话记录，还需额外评估纠错循环（参见 `../skill-extractor/transcript-quellen.md`）：用户的每一次纠错，都是自动化将来自身需要的 Guard 候选者。

### 3. 中立化 (Neutralize)

遵循 `../skill-extractor/neutralisierung.md` 中的规则：将机制与配置分离，将路径/主机/项目名称提取到配置块中。自动化 Prompt 迫切需要这个配置块，因为它们会被逐字复制到调度器中 — 具体数值属于 Prompt 顶部的单一位置。

### 4. 补充自动化构建块

将提取的核心对照 `automation-bausteine.md` 中的检查清单，补全缺失的构建块 — 特别是带有检查注册表的轮换选择、幂等性、日志卫生、遵守锁机制、只读退出和完成报告。没有这些构建块的工作流在测试中可行，但在长期运行中会退化（重复检查、日志不断膨胀、与并行 Agent 发生碰撞）。

### 5. 设置节奏与预算

- **将频率与变更率挂钩：** 检查不需要比其检查对象的变更频率运行得更频繁。来自成熟自动化资产的经验：许多最初设为每小时运行的检查被缩减为每天/每周 — 通过轮换选择，即使较低的频率也能覆盖整个 Pipeline。
- **夜间窗口用于重型任务**，短小的只读检查可以更频繁。
- **成本意识：** 每次运行都会消耗 Token/计算资源；绝大多数情况下以只读结束的运行应该尽早确定这一点（在进行昂贵的分析之前读取注册表）。

### 6. 测试与部署

1. **试运行 (Dry Run)：** 将完成的 Prompt 交互式执行一次（扮演调度器的角色）并验证：它是否干净地结束？它是否正确写入注册表/日志？它是否保持在作用域内？
2. **边界情况测试：** 模拟一次无事可做的运行 — 它必须以带有简短日志条目的只读方式结束，而不是“虚构工作”。
3. **部署：** 在目标调度器中注册；对于 Skill 形式，另外保存在技能库中并部署。
4. **观察错误路径：** 在前 2–3 次真实运行后检查日志/注册表 — 自动化最常因路径漂移（目标被移动）和日志文件膨胀而失败。

## 舰队审计模式 (Fleet Audit Mode)：检查运行中的自动化舰队

针对“检查我的自动化”：不是提取，而是帮助运维现有的自动化舰队。通过目标系统的自动化来源（Prompt/配置文件、计划、运行日志/Memory）进行系统性检查：

1. **静默失败 / 无效运行检测 (Silent Failure / No-Op)：** 自动化是否在运行但不再产生任何效果？（读取最近运行的 Memory/Log：是否全为空转、错误、死路径？）
2. **冗余 + 收益：** 自动化在作用域上是否有重叠？收益（输出、解决的问题）是否仍与消耗（Token、运行次数）成比例？
3. **漂移 (Drift)：** Prompt 路径、约定和计划是否仍与现实相符？（目标已移动、策略已改变、频率相对于变更率过高。）
4. **目录对齐：** 是否缺失了本应存在的自动化（模式网格中的缺口）？建议必须经过审批关卡（构建块 12），绝不自动上线。
5. **诊断报告：** 每项自动化一行（保留 | 调整 | 暂停 | 合并 | 删除）+ 理由；仅在获得批准后才实施更改。

## 批量模式 (Bulk Mode)：审查自动化资产或大量对话转录

针对“检查系统 X 的所有自动化以寻找可抽象的工作流”或“从旧对话记录中提取自动化候选者”：

1. **类似于 skill-extractor 的数据归约**（通过 Subagent 进行 Map-Reduce，`swarm-operations` 模式）：每个包一个 Subagent，按来源汇报：核心任务 | 模式（例如轮换检查、健康检查、想法挖掘） | 独特元素 | 是否可用户中立抽象？ | 是否已由现有 Skill 覆盖？
2. **模式优于单件：** 当许多来源共享相同的骨架时（例如 40 个轮换检查），骨架将成为一个 Skill，而具体案例成为参数化 — 而不是 40 个单独的 Skill。
3. **对照现有 Skill/命令体系进行去重**，然后在批量构建前向用户呈报带编号的候选者列表。

## 示例

```text
用户：“我们今天完成了对一篇论文的引用检查 —
从现在开始，这应该每周对所有论文运行一次。”

1. 目标形式：调度器的自动化 Prompt + 对 rotation-check 的引用。
2. 核心：对照原始来源（Web/数据库）检查论文引用，应用修正，若有修改则在 TODO.md 中写入后续任务“重新上传”。
3. 中立化：Pipeline 根目录、注册表/日志路径 → 配置块。
4. 补充构建块：轮换选择（每次运行一篇论文），在选择前读取注册表，只读退出（“所有来源 OK”），日志卫生，完成报告。
5. 节奏：每周即可（论文变更缓慢）；试运行 + 空转测试，然后写入调度器。
```

## 危险信号 (Red Flags)

| 想法 | 现实 |
| --- | --- |
| “流程在 Session 中跑通了，所以作为自动化也能跑通” | 没有用户，所有纠错 Guard 都缺失了 — 构建块检查清单是强制性的。 |
| “每小时运行一次没坏处” | 有坏处：Token 消耗、日志膨胀、碰撞风险。将节奏与变更率挂钩。 |
| “我为每个变体构建一个单独的自动化” | 共享骨架作为 Skill，变体作为参数。 |
| “什么也没找到 — 那我就找点其他活干” | 带有日志条目的只读退出是空转运行的正确结果。 |

## 相关技能

- `skill-extractor` — 相同的提取过程，目标是按需调用的 Skill；共享中立化和转录来源。
- `rotation-check` — 轮换 Pipeline 检查的标准骨架（最常见的自动化类型）；作为构建块引用而不是重新捏造。
- `swarm-operations` — 用于批量审查的蜂群模式。
