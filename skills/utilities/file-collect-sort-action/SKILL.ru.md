# File Collect Sort Action

> Пользователь осознанно перевёл этот модуль в пассивный режим до появления конкретной задачи, которая в нём понадобится
> (Тикет T-20260818-916568570, слова пользователя дословно: *«ich werde irgendwann mal sagen hole aus dem
> ordner immer die und die dateien und sammle sie dort -> dann erkennst du den skill zu
> unserem modul und richtest das ein»*). Этот навык И ЕСТЬ то распознавание, которого он ждёт.

## Когда срабатывает этот навык

Триггерами являются пользовательские фразы, описывающие регулярный **сбор по правилу** — а не разовое «перемести этот один файл»:

- «Возьми из `<Ordner>` всегда `<Dateiart>` и собери их в `<Ziel>`»
- «Автоматически отсортируй папку `<X>` по `<Kriterium>`»
- «Собирай входящие файлы из `<Quelle>` в `<Ziel>`»
- «Наведи порядок в этой папке по правилам» / «автоматически перемещай все `<Dateiart>` из `<Ordner>`»
- Любой вариант, который называет **источник**, **признак распознавания** (тип файла/шаблон имени/содержимое) и **цель** и подразумевает, что это должно происходить **регулярно** (а не только сейчас один раз)

**Не** этот навык: перемещение одного разового файла (это агент делает напрямую, без конфигурационного слоя) — `dokument-ingest` (отвечает на вопрос «чем прочитать *содержимое*», а не «куда относится *файл*») — инкрементальная индексация текста без перемещения файлов (`gardener`).

## Что умеет модуль (кратко)

`file-collect-sort-action` (короткое имя **f-csa**, CLI **`fcsa`**) — это управляемый конфигурацией агент «сканировать→категоризировать→действовать» с тремя конфигурационными файлами и журналом обработки:

| Файл | Роль |
|---|---|
| `config.json` | `scan_paths` (белый список), включение/исключение форматов, правила выявления дубликатов, защитные шлюзы (`allow_hard_delete`) |
| `categories-definitions.json` | Шаблоны распознавания по категориям (имя файла/расширение/содержимое), проверки/шлюзы, `default_target`, `default_actions` + `default_stepping` |
| `action-rules.json` | Параметры действий по категориям (цели move/copy, режим дубликатов, режим удаления, OCR-бэкенд, порядок размещения) |
| `processing-csa.json` | записывается **в каждую просканированную папку** — известные файлы, их категория, применённые действия, действующий отпечаток настроек (fingerprint) |

Известные ID действий: `duplicate_check`, `move`, `copy`, `delete`, `ocr_extract`,
`place_information`. Семантика шагов: `default_stepping: true` = действия выполняются слева направо в перечисленном порядке, ID действия, указанный дважды, выполняется **дважды**; `false` = множество
(дубликаты схлопываются в одно выполнение).

## Модель безопасности — ВСЕГДА соблюдать при настройке

- **Пробный прогон обязателен перед каждым первым боевым запуском**, для каждого пути сканирования. `fcsa run` (без
  `--dry-run`) отказывает без зафиксированного пробного прогона именно для этого пути.
- **Изменение настроек снова обезвреживает подтверждение** (отпечаток по всем трём конфигурационным файлам) — после каждой правки конфигурации следующий боевой запуск снова требует свежего пробного прогона.
- **Удаление работает по принципу fail-closed.** `delete` всегда перемещает в `trash_dir`, если только *и* `action-rules.json` (`delete.hard_delete: true`), *и* `config.json`
  (`allow_hard_delete: true`) явно не дали согласие. **Для этого навыка дополнительно:**
  жёсткое удаление никогда не включается без отдельного явного разрешения пользователя — по умолчанию остаётся
  `_trash`.
- **`scan_paths` — это явный белый список**, любой другой путь выдаёт
  `PathNotAllowedError`; пути с сегментом `.PRIVAT` или `CREDENTIALS` отклоняются при загрузке.
- **Пробный прогон не оставляет следов в просканированной папке побайтово:** `processing-csa.json`
  записывается только при боевом запуске, никогда при пробном прогоне.

## Порядок: от фразы-триггера до настроенной автоматизации

1. **Структурировать задачу.** Из фразы пользователя выделить источник, признак(и) распознавания и цель(и).
   При неясности целенаправленно уточнить (тип файла? включать вложенные папки? что делать при совпадении имён в цели — skip/overwrite/rename/quarantine?).
2. **Найти модуль.** Сначала проверить с помощью `fcsa --help`, доступен ли CLI. Если его нет,
   определить разрешённый для текущей системы путь установки модуля или пакета; не придумывать локальный путь,
   имя пакета или параллельный checkout. После установки снова выполнить `fcsa --help`, прежде чем создавать конфигурации.
3. **Создать папку конфигурации.** `fcsa init <config-dir>` — сначала записывает `scan_paths` в новую папку `inbox/` **внутри** самой папки конфигурации, никогда автоматически
   в реальную пользовательскую папку. Примеры шаблонов для этого находятся в модуле: `fcsa/_examples/*.example.json`.
4. **Подогнать конфигурацию под реальную задачу.** В `scan_paths` задать названную исходную папку, в `categories-definitions.json` внести шаблон(ы) распознавания для названного
   типа файлов (`default_target` = названная цель), в `action-rules.json` настроить подходящие действия (обычно `move`, при необходимости `duplicate_check` перед ним).
   `state_dir`/`trash_dir` НЕ должны находиться внутри `scan_path` (модуль отклоняет это — иначе возникает петля самоподпитки).
5. **Всегда сначала показывать пробный прогон:** `fcsa run --config-dir <config-dir> --dry-run` — результат
   показать пользователю (что куда было бы перемещено, что распознано как дубликат).
6. **Боевой режим только после явного «Go» от пользователя.** Лишь тогда `fcsa run --config-dir
   <config-dir>` (без `--dry-run`). `fcsa status --config-dir <config-dir>` после этого показывает
   текущее состояние.
7. **Расширять постепенно** (пользователь: «и потом это со временем расширяется»): добавлять категории/папки,
   а не начинать новую настройку с нуля — три конфигурационных файла можно дополнять. Каждое расширение из-за отпечатка настроек снова требует пробного прогона перед следующим боевым запуском.

## Ограничения / известные открытые вопросы (состояние на тикет T-20260818-916568570)

- Модуль находится в первом проходе, статус «development» — основной конвейер, CLI и защитные шлюзы готовы и протестированы (63/63 тестов), но **ещё ни разу не запускались в боевом режиме на реальной пользовательской папке**. Первый боевой запуск намеренно является применением этого навыка. Видимость репозитория — «private»; публикация без отдельного `repo-publish-check` не производится.
- Задокументированы два варианта прочтения пробелов в спецификации (`CHANGELOG.md`/`TODO.md` в модуле): `default_stepping: false` схлопывает дважды указанное действие в **одно** выполнение; `duplicate_check` с результатом `skip` прерывает **всю** оставшуюся цепочку действий для файла (а не только move/copy). При необходимости уточнить у пользователя, прежде чем конфигурация будет на это полагаться.
- OCR является подключаемым бэкендом (`none`/`command`) — собственный OCR-движок не поставляется. Для реального извлечения текста через OCR подключить `ellmos-filecommander` `fc_ocr` через тип бэкенда `command`.
