# condition — 目標とプロンプトのための条件言語

## 基本コンセプト

文章中の条件は容易に見落とされがちです。そのため、すべての関連条件を名前付きの検証可能なゲートに変換します：

> 読み取りは寛容に、証拠付けは厳格に。

入力は自然言語で不完全な場合もあります。しかし、内部変換では以下を明確に記録しなければなりません：

1. どの条件が満たされる必要があるか、
2. どのサブステップがブロックされているか、
3. どのツール照会が証拠となるか、
4. 未達成が遅延を意味するか禁止を意味するか。

影響を受けるサブステップのみをロックします。独立した作業は継続します。

## 言語の構成要素

| 表現 | 意味論 | 例 |
| --- | --- | --- |
| `/condition <条件> -> <ステップ>` | 標準ゲート | `/condition テスト成功 -> リリースビルド` |
| `/if <条件> -> <ステップ>` | `/condition` の同義語 | `/if レビュー完了 -> マージ` |
| `/when <条件> -> <ステップ>` | 条件が発生し次第実行 | `/when エクスポート完了 -> レポート確認` |
| `/if-only <条件> -> <ステップ>` | 満たされた場合のみ実行；それ以外は実行しない | `/if-only バックアップ確認済み -> 旧データ削除` |
| `/after <期間> -> <ステップ>` | 設定時刻からのタイムオフセット | `/after 30 minutes -> ステータス確認` |
| `/and` | リンクされたすべての条件が成立する必要がある | `/if テスト成功 /and レビューあり -> マージ` |
| `/or` | 少なくとも1つの条件で十分 | `/if 承認あり /or 緊急ルールアクティブ -> 開始` |

プロンプトに複数のゲートが含まれる場合は、`/condition 1 ...` や `/condition 2 ...` のように番号付き条件を使用します。`/and` と `/or` が混在する場合は、暗黙の演算子優先順位を創作せず、括弧または番号付きサブ条件を使用してください。意味が曖昧なままの場合は、リスクのあるステップをリリースする前に確認を求めてください。

`/if-only` は「禁止」として扱います。条件が証明できない場合は、そのステップを実行しないでください。曖昧な表現で不可逆な影響がある場合は、より厳格な解釈を選択してください。

## ワークフロー

### 1. 条件の正規化

入力を検証可能な文章に変換します。相対時間を設定する場合は、タイムゾーン付きの絶対タイムスタンプに変換します。

| 入力 | 正規化された条件 | 証拠クラス |
| --- | --- | --- |
| `time 06:00` | システム時刻が合意されたタイムゾーンで06:00以上 | 時計/時間ツール |
| `after 2 hours` | システム時刻が設定時刻プラス2時間以上 | 時計/時間ツール |
| `wenn Worker A fertig ist` | Aの成果物またはタスクステータスが完了を示す | タスク/ファイルツール |
| `wenn Tests grün sind` | 指定されたテスト実行が正常終了 | プロセス/テストツール |
| `nach dem Push` | ターゲットリモートに対象コミットが含まれる | バージョン管理ツール |
| `wenn der User zustimmt` | 会話内に明確なユーザー同意が存在する | ユーザー入力 |

客観的な証拠方法が確認できない場合は、それを明示してください。推測によってのみクローズできるようなゲートを定式化してはなりません。

### 2. ゲート状態の記録

永続的なゲート、タスク、またはメモリストアが利用可能な場合は、少なくとも以下のフィールドを保存します：

```text
id
condition
blocks
mode = wait | only
proof_method
status = open | met | dropped
created_at
evidence
```

永続ストアが存在しない場合は、現在のGoal、タスク計画、または引き継ぎ文書内に状態を可視化して保持します。使用するストレージが実際に永続的である場合にのみ、ゲートがセッションを超えて生存すると主張してください。

既存のランタイムアダプターは異なるコマンド名を使用する場合があります。機能的には以下が必要です：`open`, `list`, `meet`, および `drop` または同等の操作。

### 3. 作業の並べ替え

オープン状態のゲートはタスク全体をブロックしません。すべての独立したステップを実行し、次の依存ステップの前にゲート状態を再確認します。

短いエージェントループ内で能動的にポーリングを行わないでください。長い待ち時間には、スケジューラー、バックグラウンドジョブ、または発生時に一回通知するイベントを使用します。ウェイクアップ信号の後、指定されたツールで実際の条件を再度検証してください。

### 4. 厳格な検証とクローズ

最初にツール照会を実行し、次に具体的な証拠をもってゲートをクローズします。適切な証拠には以下が含まれます：

- 時間：タイムゾーン付きの測定されたタイムスタンプ、
- ファイル：期待される成果物のパス、メタデータ、またはハッシュ、
- テスト：実行されたコマンド、終了コード、および関連サマリー、
- リポジトリ：ブランチ、コミットID、およびリモート照合、
- プロセスまたはタスク：安定したIDおよび測定された最終ステータス、
- 同意：現在のコンテキストにおける明確なユーザーの応答。

独立した証拠が取得可能であるべき場合、見積もり、予測された状態、または他のワーカーの単なる主張では不十分です。

タスクの変更によりゲートが不要になった場合は、理由を添えて `dropped` とマークします。`/or` の場合、ゾンビゲートが残らないよう、不要になった代替案もクローズまたは破棄します。

### 5. エスカレーション

すべての独立したステップが完了したとき：

1. ブロックしている前置作業がタスク内でアクティブに完了できるか確認する、
2. 単純な待機条件の場合は、適切なスケジューラーまたはバックグラウンドジョブを使用する、
3. ユーザーの決定や外部依存関係の場合は、オープンなゲートと明確な中間ステータスを添えて引き継ぐ。

条件から追加の権限を導き出さないでください。満たされたゲートは順序を変更するだけであり、承認されたスコープを拡張するものではありません。

## 例

### 時間条件付きの Goal

```text
Ziel: Daten prüfen und Bericht veröffentlichen.
/condition time 16:00 Europe/Berlin -> Veröffentlichung starten
```

データ検証は事前に実施可能です。公開は、現在の時刻照会で少なくとも16:00が証明されるまでロックされたままとなります。

### 複数の条件を持つプロンプト

```text
/condition 1 Tests erfolgreich
/condition 2 Review freigegeben
/if condition 1 /and condition 2 -> mergen
```

両方のゲートを個別に証明します。その後でのみマージします。

### 遅延ではなく禁止

```text
/if-only verifiziertes Backup vorhanden -> alte Dateien löschen
```

検証済みバックアップがない場合は何も削除せず、オープンな禁止事項を最終レポートに記載します。

## 落とし穴

- 条件を状態として維持せず、文章内で繰り返すだけにする。
- 一部のサブステップのみがブロックされているのにGoal全体を一時停止する。
- 設定時刻やタイムゾーンなしで相対時間を保存する。
- ツールの証明を推測や自己評価で置き換える。
- `/if-only` を単なる待機として扱う。
- `/or` の後に不要になった代替ゲートをオープンなままにする。
- プロバイダー名、モデル名、ユーザー名、ホスト名を一般的なメカニズムにハードコーディングする。
- ローカルランタイムのパスを言語自体の前提条件として扱う。
