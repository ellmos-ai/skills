# Bilingual-Doc-Sync — 保持并行语言版本同步

## 目的

双语维护的文档随着时间推移容易出现隐蔽偏离：积极编辑的版本不断扩展，
而另一个版本逐渐过时 — 直到“翻译”名存实亡。本 Skill
将同步检查转化为具有关键预先决定的标准流程：**哪种语言版本为主导？**
如果没有主导语言规则，每个差异点都会变成个案讨论，校验过程也无法复现。

## 流程

### 1. 确认现存版本

- 是否包含两种（或所有）语言版本？如果完全缺失某一版本 → **补齐**（对主导版本进行
  完整翻译，而非重新撰写）。
- 检查命名规范（例如 `DOCUMENT.md` + `DOCUMENT.en.md` 或 `_de`/`_en` 后缀）
  并统一异类命名 — 可发现性是同步的前提。

### 2. 明确主导语言（每次对齐前）

- 主导语言是进行主要内容创作的版本（论文通常为 EN，本地文档通常为母语）。存在冲突时以主导语言为准。
- **反向同步例外：** 如果副语言版本被证明做出了更好的修正（更清晰的表述、修正的错误），
  应将其**吸收**回主导版本 — 先进行反向同步，然后再进行正常同步。在采纳“更美观”的表述前需验证专业准确性。

### 3. 检查平行度

先结构，后内容：

1. **大纲对比：** 并排对比两个版本的章节/标题 —
   缺失、多余或重排的章节属于粗粒度的偏离。
2. **匹配大纲的逐章抽样检查：** 观点、数据、引用、示例是否一致？
   特别容易出现偏离的部位：变更日志（Changelog）、表格、数值、文献/链接列表、最近编辑的章节。
3. **检查不可翻译的不变量：** 代码块、标识符、公式、路径
   必须在两个版本中保持完全一致（代码绝不翻译）。

### 4. 修复差异

- 朝主导语言方向消解差异（或在反向同步之后）。
- 尊重目标语言的排版规范（例如标点符号与引号规范）。
- 同步元数据：版本号、日期字段、变更日志条目必须在**两个**版本中同时更新
  （Changelog 本身是最常见的偏离点）。

### 5. 记录文档

记录结果（哪些地方存在偏离、采纳了哪些内容、进行了哪些反向同步）。
作为针对文档库的定期运行任务：结合轮转框架（`rotation-check`）— 每次运行处理一个文档（对），利用注册表作为记忆。

## 扩展：扩展审计（是否需要支持更多语言？）

除了保持现有版本的同步外，语言维护还包括评估文档/项目是否值得扩展**更多语言**：

1. **评估适用性**而非盲目翻译：目标受众、国际通用性、应用商店/网站展示、内容的流动性。
   并非每个内部文档都需要英文；并非每个应用都需要五种语言。
2. **检查技术准备情况：** 目标项目是否已针对语言文件/并行版本做好准备
   （i18n 结构、命名规范）？如果否，**这**才是首要任务，而不是翻译。
3. **记录诊断结果，不立即进行批量翻译：** 将具体的翻译任务写入项目本地的 TODO 文件；
   “无需扩展其他语言”也是一个有效且应当记录的诊断结论。
4. **新增版本的质量检查（QA）：** 自动生成的翻译在认定为“已就绪”前，
   必须针对主导版本进行抽样检查（第 3 节）。

## 示例

```text
任务：“检查论文的 DE 和 EN 版本是否同步。”

1. 现有版本：包含 paper_en.tex（主导）+ paper_de.tex。
2. 大纲对比：DE 缺少新的 4.2 节（最新 EN 修订版）；DE 在 3.1 节中包含更好的证明段落。
3. 反向同步：3.1 节的表述经专业验证 → 吸收回 EN 版本。
4. 补齐：将 4.2 节翻译为 DE；核对表 2 中的数据（DE 包含旧数据）；统一文献列表。
5. 注册表条目：“paper-X | 2026-07-03 | de-en-sync | 修复 3 处差异，1 处反向同步 | 下次检查在下一次 EN 修订后”。
```

## 警示信号 (Red Flags)

| 想法 | 事实 |
| --- | --- |
| “我直接重新翻译有差异的部分” | 先明确主导语言 + 反向同步问题 — 否则更好的解决方案会被覆盖。 |
| “大纲一致，所以已经同步了” | 数据、变更日志和引用最早出现偏离 — 深入抽样检查是必须的。 |
| “我把代码注释也一起翻译了” | 代码块和标识符在两个版本中保持一致（英文）。 |
| “我一次性同步所有文档” | 每次运行处理一个文档对（轮转框架）才能保证校验质量。 |
