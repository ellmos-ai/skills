# Bilingual-Doc-Sync — 並行言語バージョンの同期維持

## 目的

二言語で運用されるドキュメントは時間の経過とともに徐々に乖離します。活発に編集されるバージョンが
拡張される一方で、もう一方が古くなり、「翻訳」が名ばかりのものになります。本Skillは、
同期検証を以下の決定的な事前定義を持つ標準化されたプロセスに変換します：**どの言語バージョンが主導するか？**
主言語ルールがなければ、すべての乖離が個別議論となり、突き合わせ作業の再現性が失われます。

## ワークフロー

### 0. 単一言語のみのコンテンツを検出する（毎回の照合の前に）

差異は常に「古くなった」わけではない — 時には**これまで一つのバージョンにしか存在しない、
新しい本物のコンテンツ**であることがある（非主要言語での外部貢献/PR、副次バージョンに先に
入った変更、履歴書き換えなどによるコンテンツ消失）。従来の手順は「EN か DE に記入して全体
へ配布する」しか知らず、一つのバージョンにしか存在しないケースを想定していなかった。実例：
`ellmos-ai/skills` の PR #1 は README.md にのみ中国語の発見用リンクを追加したが、後の履歴
書き換えでこれが失われた。どのステップも「他のどのバージョンにも対応物がないコンテンツが
存在するか」を確認していなかったため（T-20260926-967984806）。

- **確認する、思い込まない：** 実際の照合（ステップ3）の前に、最後に同期済みとわかっている
  状態との差分（または他のバージョンとの直接比較）を取り、主要言語のセクション欠落だけで
  なく、一つのバージョンでのみ新しく、他のどこにも対応物がないコンテンツを意図的に探す。
- **ツール：** `scripts/check_language_parity.py <ファイル1> <ファイル2> [...]` は渡された
  すべてのバージョンから Markdown と HTML の両方のリンク（`[テキスト](url)`、
  `<a href="url">`、`<img src="url">`）を抽出し（リンクは翻訳を経ても変わらないため、
  言語に依存しない頑健な指標となる）、すべてのバージョンに存在しないリンクを Exit 1 で
  報告する。Exit 0 はリンクの部分集合の不一致が見つからなかったことを意味する — 完全な
  パリティの証明ではないが、手動照合の前の的を絞ったステップ0のスモークテストである。
  `<!-- lang-only: <code> -->` ブロック内のリンクは、マーカーに記載された言語コードを持つ
  ファイル（ファイル名から判定、例：`README_zh.md` → `zh`、`README.md` → `en`）に対しての
  みチェックされ、他のバージョンで「欠落」とはみなされない。さらにこのスクリプトは既定で
  ラベルテキストがエンコードされた shields.io バッジ URL を除外する（翻訳されたラベルが
  URL に直接埋め込まれていることが多い — 実際のコンテンツ喪失ではなく想定内の翻訳差異、
  `--include-badges` でこのフィルタを無効化できる）。UTF-8 で読めないファイルや引数不足は
  トレースバックではなく終了コード2とエラーメッセージで終了する。
- **発見時の判断：** 単一言語のみのコンテンツは決して黙って捨てられない。三つの選択肢が
  あり、どれも黙った削除ではない：
  (a) **翻訳してすべてのバージョンに反映する** — 一般に関連性のあるコンテンツの通常ケース；
  (b) **意図的に一つ/複数の言語に限定する**（「lang-only」）— そのコンテンツが特定の対象
  読者にのみ当てはまる場合（実例 T-20260926-967984806：中国語の発見用リンクは DE/ES/JA/RU
  の読者には関連がなく、六つすべてのバージョンに翻訳したこと自体が誤りだった — この
  ステップの最初の版に対するユーザーからの訂正）。マーカー：
  **`<!-- lang-only: <code>[,<code>...] --> … <!-- /lang-only -->`**（HTML コメント、
  Markdown レンダラーでは不可視；複数の対象言語はカンマ区切り、例：`zh,ja`）。この限定的な
  ケースに対する確立された業界標準は見つかっていない（P-009 確認済み）— HTML コメントは
  Markdown において最も可搬性が高く不可視にレンダリングされる選択肢である。マークされた
  コンテンツは照合時に**翻訳もされず、欠落としても報告されない**；
  (c) **コンフリクトとしてエスカレーションする** — そのコンテンツがまだ望まれているか不明な
  場合（例：主要バージョンと矛盾しているように見える）— ユーザー/意思決定チェーンに確認する。
  いずれの場合も、他のバージョンに存在しないという理由だけで、コンテンツが存在するバー
  ジョンから無断で削除してはならない。

### 1. 資産の確認

- 両方（すべて）の言語バージョンが存在するか？片方が完全に欠落している場合 → **追いつかせる**（主導バージョンの
  完全な翻訳。再創作ではない）。
- 命名規則（例: `DOCUMENT.md` + `DOCUMENT.en.md` または `_de`/`_en` サフィックス）を確認し、
  表記揺れを統一する — 発見可能性は同期の半分を占めます。

### 2. 主言語の明確化（各突き合わせ作業の前）

- 主言語とは、内容の編集が主に行われるバージョンです（論文ではEN、ローカルドキュメントでは母国語が多い）。矛盾がある場合は主言語が優先されます。
- **逆転送の例外：** 副バージョンが明確に優れている解決策を提供している場合（より明確な表現、修正されたエラー）、
  それを主バージョンに**取り込み**ます — 先に逆転送を行ってから、通常の同期を行います。表現の「美しさ」を取り込む前に専門的な正確性を確認してください。

### 3. 並行性の検証

まず構造、次に内容：

1. **構成の比較：** 両バージョンのセクション/見出しを並べて比較 —
   欠落、追加、順序変更されたセクションが大まかな乖離点です。
2. **一致する構成のセクションごとのサンプリング：** 記述、数値、参照、例が一致しているか？
   特に乖離しやすい箇所：変更履歴（Changelog）、表、数値、文献/リンク一覧、最近編集されたセクション。
3. **翻訳不可の不変要素のチェック：** コードブロック、識別子、数式、パスは
   両バージョンで完全一致していなければなりません（コードは翻訳しません）。

### 4. 乖離の解消

- 主言語の方向へ乖離を解消する（または逆転送後）。
- ターゲット言語のタイポグラフィ規則を尊重する（引用符の規約など）。
- メタデータの同期：バージョン番号、日付フィールド、変更履歴の項目を**両方**のバージョンで更新する
  （Changelog自体が最も頻繁な乖離点です）。

### 5. 結果の記録

結果を記録する（何が乖離していたか、何を取り込んだか、何を逆転送したか）。
資産に対する定期実行として：ローテーションフレームワーク（`rotation-check`）と組み合わせる —
1回の実行につき1つのドキュメント（ペア）、レジストリを記憶として利用する。

## 拡張：拡張監査（さらに言語を増やすべきか？）

既存バージョンの同期維持に加え、言語管理にはドキュメント/プロジェクトが**追加の言語**に値するかどうかを問うことが含まれます：

1. **盲目的な翻訳ではなく適合性を評価：** ターゲット読者、国際的な有用性、
   ストア/Webでの露出、コンテンツのポータビリティ。すべての内部ドキュメントに英語が必要なわけではなく、
   すべてのアプリに5つの言語が必要なわけではありません。
2. **技術的準備の確認：** ターゲットが言語ファイル/並行バージョンに対して準備されているか
   （i18n構造、命名規則）？否である場合、翻訳ではなく**それ**が最初のタスクとなります。
3. **診断結果を記録し、直ちに大量翻訳しない：** 具体的な翻訳タスクをプロジェクトローカルのTODOファイルに記載する；
   「これ以上の言語は不要」という結論も記録に値する有効な結果です。
4. **追加バージョンのQA：** 自動生成された翻訳は、「存在」とみなす前に
   主バージョンに対してサンプリング検査（第3節）を行ってください。

## 例

```text
依頼：「論文のDEとENが同期しているか確認して。」

1. 資産：paper_en.tex（主導）+ paper_de.tex が存在。
2. 構成：DEに新しいセクション 4.2（最新ENリビジョン）が欠落。DEの3.1に優れた証明段落あり。
3. 逆転送：3.1の表現を専門的に検証 → ENに取り込み。
4. 補完：4.2をDEに翻訳。表2の数値を整合（DEに古い値が存在）。文献リストを統一。
5. レジストリエントリ：「paper-X | 2026-07-03 | de-en-sync | 3つの乖離を解消、1つの逆転送 | 次のENリビジョン後に次回チェック」。
```

## レッドフラグ (Red Flags)

| 考え方 | 現実 |
| --- | --- |
| 「差分を新しく翻訳し直せばいい」 | まず主言語 + 逆転送の検討を明確にする — そうしないと優位な解決策が上書きされます。 |
| 「構成が一致しているから同期されている」 | 数値、Changelog、参照が最初に乖離する — 深いサンプリングが必須です。 |
| 「コードのコメントも翻訳する」 | コードブロックと識別子は両バージョンで同一（英語）に保ちます。 |
| 「すべてのドキュメントを一度に同期する」 | 1回の実行につき1ペア（ローテーション枠組み）にすることで検証可能性を維持します。 |
