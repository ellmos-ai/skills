# Bilingual-Doc-Sync — 保持并行语言版本同步

## 概述与目的

双语文档往往会悄然产生分歧：积极编辑的版本不断丰富，而另一个版本则逐渐陈旧——直到“翻译”仅名存实亡。本 Skill 将同步检查转化为一套规范的流程，并包含一个关键的前置判定：**哪种语言版本为主导版本？** 如果没有主导语言规则，每一次差异都会变成临时决策，比对也将无法复现。

## 流程

### 1. 评估现有文档

- 两种（或所有）语言版本是否均已存在？若完全缺失某一版本 → **补齐**（主导版本的完整翻译，而非重新撰写）。
- 检查命名规范（例如 `DOCUMENT.md` + `DOCUMENT.en.md` 或 `_de`/`_en` 后缀），并统一不符合规范的文件名——易于检索是实现同步的一半。

### 2. 明确主导语言（每次同步前）

- 主导语言是指实质进行内容编辑与更新的版本（论文通常为英文 EN，本地文档通常为母语）。出现冲突时以主导语言为准。
- **反向吸收例外：** 如果辅语言版本在某些地方明显处理得更好（表述更清晰、修正了错误），应将其**吸收**到主导版本中——先进行反向吸收，再进行常规同步。在吸收更“优美”的表述前，务必验证其专业准确性。

### 3. 检查并行一致性

先结构，后内容：

1. **大纲对比：** 将两个版本的章节/标题并排对比——缺失、新增或排序变更的章节属于重大差异。
2. **匹配大纲的逐章抽查：** 论述、数据、引用、示例是否一致？极易产生分歧的项：变更日志 (Changelog)、表格、数值、文献/链接列表、最近编辑的章节。
3. **检查不可翻译的不可变要素：** 代码块、标识符、公式、路径在两个版本中必须保持**完全一致**（代码绝不翻译）。

### 4. 修复差异

- 朝着主导语言的方向消除差异（或在反向吸收后进行）。
- 遵循目标语言的版式与排版规范（例如德文中使用真正的变音字母 ä ö ü ß，而非 ae/oe/ue 替代写法；符合相应的引号规范）。
- 补充更新元数据：在**两个版本**中更新版本号、日期字段、变更日志条目（变更日志本身是最频繁的分歧点）。

### 5. 记录

记录比对结果（存在哪些分歧、吸收了什么内容、反向吸收了什么内容）。
作为对整个文档库的定期检查：与轮换框架 (`rotation-check`) 结合使用——每次运行处理一个文档（或一对文档），利用 Registry 保持记忆。

## 扩展：扩展性审计（是否需要支持更多语言？）

除了保持现有版本同步之外，语言维护还包括评估某个文档/项目是否值得支持**更多**语言：

1. **评估适用性**而非盲目翻译：目标受众、国际化可用性、应用商店/网站展示需求、内容的流动性。并非每个内部文档都需要英文；并非每个 App 都需要五种语言。
2. **检查技术准备情况：** 目标项目是否已为多语言文件/并行版本做好准备（i18n 结构、命名规范）？如果尚未准备好，**这**才是首要任务，而非直接翻译。
3. **记录审计结果，勿立即批量翻译：** 将具体的翻译任务写入项目本地的 TODO 文件；“无需增加其他语言”也是一个有效且需记录的结论。
4. **补齐版本的质量保证 (QA)：** 在将自动生成的翻译视为“就绪”之前，针对主导版本进行抽查（参阅第 3 节）。

## 示例与应用

```text
任务：“检查论文的 DE 和 EN 版本是否同步。”

1. 现有文档：paper_en.tex（主导）+ paper_de.tex 均存在。
2. 大纲对比：DE 缺少新增的 4.2 节（最新 EN 修订版）；DE 在 3.1 节中有更好的证明段落。
3. 反向吸收：3.1 节的表述经过专业验证 → 吸收至 EN 版本。
4. 补齐差异：将 4.2 节翻译至 DE；校对表 2 中的数据（DE 包含旧数值）；统一参考文献列表。
5. Registry 记录：“paper-X | 2026-07-03 | de-en-sync | 修复 3 处分歧，1 处反向吸收 | 下次 EN 修订后再次检查”。
```

## 避坑指南 (Red Flags)

| 误区 | 事实 |
| --- | --- |
| “我直接重新翻译差异部分” | 先明确主导语言与反向吸收问题——否则更优的解法会被覆盖。 |
| “大纲一致，所以已经同步了” | 数据、变更日志和引用最先产生分歧——必须进行深度抽查。 |
| “代码注释我也顺便翻译了” | 代码块和标识符在两个版本中均保持一致（英文）。 |
| “我一次性同步所有文档” | 每次运行处理一对文档（轮换框架）可确保同步过程可核查。 |
