# GitHub Repo Care — Repository সঠিকভাবে প্রকাশ ও রক্ষণাবেক্ষণ

## কখন এই Skill প্রযোজ্য

যখন কোনো GitHub-রিপোজিটরি নতুন তৈরি, প্রকাশ, রিলিজ, নিরীক্ষা বা পরবর্তীতে রক্ষণাবেক্ষণ করতে হবে, তখন এই Skill ব্যবহার করুন। প্রথম জনসমক্ষে push-এর আগে, রিলিজ ট্যাগের ক্ষেত্রে, রিপোজিটরি মেটাডেটার পরিবর্তনে, সংগঠনের প্রোফাইলে এবং গোপনীয়তা পরীক্ষার সময় এটি বিশেষভাবে গুরুত্বপূর্ণ।

GitHub-এ প্রকাশ ছাড়া শুধু কোড বাস্তবায়নের ক্ষেত্রে এই Skill প্রযোজ্য নয়। সেক্ষেত্রে আগে উপযুক্ত উন্নয়ন বা debugging Skill ব্যবহার করুন এবং প্রকাশের ধাপে এই Skill সক্রিয় করুন।

## মূল নিয়ম

প্রথম জনসমক্ষে push-এর আগে রিপোজিটরি প্রস্তুত করুন। সঠিক `.gitignore`, পরিষ্কার গোপনীয়তা-gate, লাইসেন্স, README, মেটাডেটা এবং রিলিজ-বর্ণনা — এগুলো জনসমক্ষে ইতিহাস তৈরি হওয়ার আগে ঠিক করা অনেক সহজ।

## ধাপসমূহ

1. **স্থানীয় নিয়ম পড়ুন।** `AGENTS.md`, `CLAUDE.md`, `START.md`, রিলিজ-নীতি, নামকরণ-নীতি ও লক-নীতি থাকলে পরীক্ষা করুন।
2. **লক পরীক্ষা করুন।** `LOCK.txt` বা উপযুক্ত `LOCK.*.txt` সক্রিয় থাকলে এই পরিধি পরিবর্তন করবেন না।
3. **রিপোজিটরির নাম ঠিক করুন।** নাম, সংগঠন, দৃশ্যমানতা, লাইসেন্স ও উদ্দেশ্য এক বাক্যে লিখে রাখুন।
4. **`git add`-এর আগে `.gitignore` তৈরি করুন।** Secret, স্থানীয় ডেটা, ডেটাবেস, build-আউটপুট, virtual environment, cache, IDE-ফাইল ও ব্যক্তিগত নোট বাদ দিন।
5. **Public-মৌলিক ফাইল যোগ করুন।** সাধারণত: `README.md`, `LICENSE`, `CHANGELOG.md`, `SECURITY.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `llms.txt` এবং CI।
6. **আবিষ্কারযোগ্যতার জন্য README লিখুন।** প্রথম পর্দার উচ্চতায়: উদ্দেশ্য, ইনস্টলেশন, ব্যবহার, গোপনীয়তা-মডেল, প্রকল্প-কাঠামো, লাইসেন্স ও ক্যানোনিকাল রিপোজিটরির নাম।
7. **দৃশ্য-সংকেত দিন।** ব্যানার, লোগো বা স্ক্রিনশট যোগ করুন, যদি তা উপযোগিতা স্পষ্ট করে। প্রকৃত পণ্যচিত্র বা স্পষ্ট ধারণাচিত্র সম্ভব হলে সাধারণ সাজসজ্জা দেবেন না।
8. **বহুভাষিকতা সচেতনভাবে পরিকল্পনা করুন।** ন্যূনতম: ইংরেজি ও প্রকল্পের ভাষা। ব্যবহারকারীমুখী মডিউলের জন্য অগ্রাধিকার: জার্মান, ইংরেজি, স্প্যানিশ, সরলীকৃত চীনা, জাপানি ও রুশ।
9. **পরীক্ষা ও smoke চালান।** সাফল্য দাবি বা রিলিজ তৈরির আগে স্থানীয়ভাবে যাচাই করুন।
10. **গোপনীয়তা-gate চালান।** Staged/tracked সেট পরীক্ষা করুন: Secret, স্থানীয় পথ, PII, `.env`, ডেটাবেস, ব্যক্তিগত নথি, তৈরি করা artefact এবং mojibake।
11. **Commit ও push করুন।** Gate পাস করার পরেই commit করুন। এরপর GitHub-রিপোজিটরি তৈরি বা সংযুক্ত করে push করুন এবং remote-অবস্থা পরীক্ষা করুন।
12. **মেটাডেটা সেট করুন।** বর্ণনা, topics, homepage, দৃশ্যমানতা ও branch-ডিফল্ট পরীক্ষা করুন।
13. **রিলিজ তৈরি করুন।** Tag ও GitHub-রিলিজ তৈরি করুন; branch ও tag-এর জন্য CI পরীক্ষা করুন।
14. **Discovery-পৃষ্ঠাগুলো হালনাগাদ করুন।** সংগঠনের প্রোফাইল, `llms.txt`, কেন্দ্রীয় রেজিস্ট্রি, স্থানীয় মডিউল-সূচি ও ইকোসিস্টেম README-তে লিংক দিন। **Publish ⇒ প্রোফাইল-পৃষ্ঠা (T-20260926-796851315):** রিপোজিটরির ব্যানার থাকলে যান্ত্রিকভাবে পরীক্ষা করুন, এটি সংগঠনের প্রোফাইল-পৃষ্ঠায় (`<org>/.github/profile/README.md`) ইতিমধ্যে আছে কি না — `python org_profile_gate.py --org <org>` (`.AI/.SKILLS/testing/`)। এন্ট্রি না থাকলে স্ক্রিপ্ট বসানোর জন্য প্রস্তুত Markdown-snippet দেবে।
    **নিজের স্টার দিন (T-20260926-299328659):** Aftercare প্রতিটি নিজস্ব public রিপোজিটরির জন্য পরীক্ষা করে অ্যাকাউন্ট নিজে ইতিমধ্যে স্টার দিয়েছে কি না, এবং না দিয়ে থাকলে নিজস্ব GitHub-রক্ষণাবেক্ষণ টুলের মাধ্যমে দেয় — যদি থাকে (পথ ও আহ্বান স্থানীয় config অনুযায়ী, যেমন একটি `--self-star`-flag: রিপোজিটরি উল্লেখ ছাড়া কনফিগার করা সব সংগঠনের জন্য বাকি থাকা স্টার নিশ্চিত করার (catch-up) চালনা, রিপোজিটরি উল্লেখসহ এই publish-এর পরে একক চালনা)। কখনো স্বয়ংক্রিয়ভাবে স্টার সরানো হবে না।
    **Stargazer-রক্ষণাবেক্ষণ:** নতুন stargazer-দের অনুসরণ করুন এবং প্রকৃত মানের ক্ষেত্রে তাদের সেরা প্রকল্পে পাল্টা স্টার দিন — নিজস্ব GitHub-রক্ষণাবেক্ষণ টুলে যদি আগে থেকেই পারস্পরিকতা-মডিউল থাকে, সেটি ব্যবহার করুন (এটি বিষয়গত প্রাসঙ্গিকতা মূল্যায়ন করে এবং পাল্টা স্টার/আমন্ত্রণ/পরীক্ষা/এড়িয়ে যাওয়ার প্রস্তাব দেয়; rate-cap, cooldown এবং Dry-run/Apply/Confirm নিরাপত্তা-জালসহ অনুসরণ চালায়)। যদি তা আগে থেকেই থাকে তবে নতুন করে বানাবেন না; সিদ্ধান্তগুলো মডিউল নিজেই লগ করে। কখনো স্বয়ংক্রিয়ভাবে আনফলো বা আনস্টার করা হবে না।
15. **সমাপ্তি পরীক্ষা করুন।** Remote README, রিলিজ-পৃষ্ঠা, topics, CI ও লিংকগুলো যাচাই করুন।

## গোপনীয়তা-Gate

শুধু দৃশ্যমান কর্মক্ষেত্র নয়, staged বা tracked সেটে খুঁজুন।

```bash
git diff --cached --check
git ls-files
rg -n "C:\\\\Us[e]rs\\\\|C:/Us[e]rs/|/c/Us[e]rs/|s[k]-[A-Za-z0-9]|gh[p]_|gh[o]_|API[_-]?KEY|TO[K]EN|PASS[W]ORD|SEC[R]ET|\\x{C3}|\\x{C2}|\\x{FFFD}" .
```

জনসমক্ষে মডিউলের ক্ষেত্রে অতিরিক্ত একটি `RELEASE_GATE.md` বা সমতুল্য gate নথিভুক্ত করুন: তারিখ, পরীক্ষিত কমান্ড, ফলাফল, অবশিষ্ট সতর্কতা এবং ইচ্ছাকৃত ব্যতিক্রম। কোনো secret একবার commit হয়ে গেলে `HEAD` থেকে মুছে ফেলা যথেষ্ট নয়; secret পরিবর্তন (rotate) করতে হবে।

**লিংক-করা রিপোজিটরির দৃশ্যমানতা পরীক্ষা করুন।** পথ/টোকেন স্ক্যান জনসমক্ষে README-তে থাকা ব্যক্তিগত GitHub-রিপোজিটরির লিংক ধরতে পারে না (শিক্ষণীয় ঘটনা T-20260926-820252321: ব্যক্তিগত রিপোজিটরি `ellmos-ai/ellmos-core` README-এর টেবিলে অলক্ষ্যে ছিল)। রিপোজিটরিতে থাকলে পুনঃব্যবহারযোগ্য পরীক্ষাটি চালান:

```bash
python testing/repo_link_visibility_gate.py --repo .
```

পরীক্ষাটি শুধু প্রকৃত অনিশ্চয়তায় fail-open (নেটওয়ার্ক ব্যর্থতা, rate-limit 403/429 — শুধু একটি সতর্কবার্তা, বাধা নয়); 404 নিশ্চিত `private: true`-এর মতোই বাধা দেয়, কারণ দুটোরই অর্থ বহিরাগতদের কাছে লিংকটি সমাধানযোগ্য নয় (ব্যক্তিগত বা অস্তিত্বহীন)। এই script না থাকলে (রিপোজিটরিতে পরীক্ষার নিজস্ব ক্লোন না থাকলে) `gh api repos/ORG/REPO --jq .private` দিয়ে README-তে লিংক-করা প্রতিটি বহিরাগত বা সহোদর রিপোজিটরির লিংক নমুনাভিত্তিকভাবে পরীক্ষা করুন।

## GitHub-মেটাডেটা

Push-এর পরে মেটাডেটা ও রিলিজ স্পষ্টভাবে সেট করুন।

```bash
gh repo edit ORG/REPO --description "Kurze konkrete Beschreibung" \
  --add-topic local-first --add-topic python --add-topic llm
git tag -a v1.0.0 -m "v1.0.0"
git push origin v1.0.0
gh release create v1.0.0 --repo ORG/REPO --title "v1.0.0" --notes "..."
```

এরপর যাচাই করুন:

```bash
gh repo view ORG/REPO --json nameWithOwner,visibility,description,repositoryTopics,url
gh release view v1.0.0 --repo ORG/REPO --json tagName,url,isDraft,isPrerelease
gh run list --repo ORG/REPO --limit 5
```

কোনো রিলিজের পরে CI লাল হলে রিপোজিটরিটি এখনো পরিষ্কারভাবে প্রকাশিত বলে গণ্য হবে না। সদ্য তৈরি প্রাথমিক রিলিজের ক্ষেত্রে সংশোধিত commit-এ নতুন ট্যাগটি সঙ্গে সঙ্গে ও ইচ্ছাকৃতভাবে সরানো গ্রহণযোগ্য।

## সাধারণ ভুল

| ভুল | সংশোধন |
|---|---|
| `.gitignore` তৈরি হয়েছে `git add`-এর পরে | আগে unstage করুন, ignore-নিয়ম ঠিক করুন, তারপর আবার add করুন |
| UI বা Skill বহুভাষিক, কিন্তু README একভাষিক | ভাষার লিংক বা স্থানীয়কৃত README যোগ করুন |
| ব্যানার, topics বা বর্ণনা নেই | ঘোষণার আগে discovery-উপাদান যোগ করুন |
| রিলিজ ট্যাগ আছে, কিন্তু CI লাল | CI ঠিক করুন ও নতুন run পরীক্ষা করুন |
