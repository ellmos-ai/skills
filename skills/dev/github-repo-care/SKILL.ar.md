# GitHub Repo Care — نشر مستودع GitHub وصيانته

## متى تُطبَّق هذه المهارة

استخدم هذه المهارة عندما يُراد إنشاء مستودع GitHub جديد أو نشره أو إصداره أو تدقيقه أو صيانته لاحقًا. وهي مهمة بشكل خاص قبل أول دفع عام، وعند وسوم الإصدار، وعند تغييرات البيانات الوصفية للمستودع، وعند ملفات تعريف المنظمات، وعند فحوصات الخصوصية.

لا تُطبَّق على تنفيذ الشيفرة البحتة دون نشر على GitHub. في هذه الحالة استخدم أولًا مهارة التطوير أو التصحيح المناسبة، ولا تُفعّل هذه المهارة إلا عند خطوة النشر.

## القاعدة الأساسية

جهّز المستودع قبل أول دفع عام. فإعداد `.gitignore` صحيح، وبوابة خصوصية نظيفة، والترخيص، وREADME، والبيانات الوصفية، وسرد الإصدار، كلها أيسر بكثير قبل إنشاء السجل العام منها بعده.

## سير العمل

1. **قراءة القواعد المحلية.** تحقّق من `AGENTS.md` و`CLAUDE.md` و`START.md` وسياسة الإصدار وسياسة التسمية وسياسة الأقفال، إن وُجدت.
2. **فحص الأقفال.** إذا كان `LOCK.txt` أو `LOCK.*.txt` مناسب نشطًا، فلا تُغيّر هذا النطاق.
3. **تحديد اسم المستودع.** دوّن الاسم والمنظمة وقابلية الرؤية والترخيص والغرض في جملة واحدة.
4. **إنشاء `.gitignore` قبل `git add`.** استبعد الأسرار والبيانات المحلية وقواعد البيانات ومخرجات البناء والبيئات الافتراضية وذاكرات التخزين المؤقت وملفات بيئة التطوير والملاحظات الخاصة.
5. **إضافة أساسيات النشر العام.** عادةً: `README.md` و`LICENSE` و`CHANGELOG.md` و`SECURITY.md` و`CONTRIBUTING.md` و`CODE_OF_CONDUCT.md` و`llms.txt` وCI.
6. **كتابة README للاكتشاف.** في الشاشة الأولى: الغرض، والتثبيت، والاستخدام، ونموذج الخصوصية، وبنية المشروع، والترخيص، واسم المستودع المعتمد.
7. **وضع الإشارات البصرية.** أضف بانرًا أو شعارًا أو لقطة شاشة إذا كانت تجعل الفائدة أوضح. لا تضف زخرفة عامة عندما تتوفر صورة حقيقية للمنتج أو صورة مفاهيمية واضحة.
8. **التخطيط متعدد اللغات بوعي.** الحد الأدنى: الإنجليزية إضافةً إلى لغة المشروع. وللوحدات الموجهة للمستخدمين يُفضَّل: الألمانية والإنجليزية والإسبانية والصينية المبسطة واليابانية والروسية.
9. **تشغيل الاختبارات وفحوص الدخان.** تحقّق محليًا قبل إعلان النجاح أو إنشاء إصدار.
10. **تشغيل بوابة الخصوصية.** افحص المجموعة المرحلية/المتتبَّعة: الأسرار، والمسارات المحلية، والمعلومات الشخصية، و`.env`، وقواعد البيانات، والوثائق الخاصة، والمخرجات المولَّدة، وخلل الترميز (Mojibake).
11. **الإيداع والدفع.** لا تُودِع إلا بعد اجتياز البوابة. بعد ذلك أنشئ مستودع GitHub أو اربطه وادفع، وتحقّق من حالة الطرف البعيد.
12. **ضبط البيانات الوصفية.** تحقّق من الوصف والوسوم والصفحة الرئيسية وقابلية الرؤية وفرع الافتراض.
13. **إنشاء الإصدار.** أنشئ الوسم وإصدار GitHub، وتحقّق من CI للفرع والوسم.
14. **تحديث أسطح الاكتشاف.** اربط ملف تعريف المنظمة و`llms.txt` والسجلات المركزية وفهارس الوحدات المحلية وREADMEs النظام البيئي. **النشر ⇐ صفحة الملف الشخصي (T-20260926-796851315):** إذا كان للمستودع بانر، تحقّق آليًا من ظهوره على صفحة ملف المنظمة الشخصي (`<org>/.github/profile/README.md`) — `python org_profile_gate.py --org <org>` (`.AI/.SKILLS/testing/`). إذا كان الإدخال مفقودًا، يوفّر السكربت مقتطف Markdown جاهزًا للإدراج.
    **وضع النجمة الخاصة بك (T-20260926-299328659):** تتحقّق عملية الرعاية اللاحقة، لكل مستودع عام خاص بك، مما إذا كان الحساب قد وضع نجمة بالفعل، وتضعها إن لم تكن موضوعة — عبر أداة صيانة GitHub الخاصة بك إن وُجدت (المسار والاستدعاء عبر إعدادات محلية، مثل علامة `--self-star`: دون تحديد مستودع تُنفَّذ عملية لحاق عبر جميع المنظمات المُعدّة، ومع تحديد مستودع تُنفَّذ عملية فردية مباشرة بعد هذا النشر). لا تُزيل النجمة تلقائيًا أبدًا.
    **صيانة المُعجبين بالنجوم (Stargazer):** تابع المستخدمين الجدد الذين وضعوا نجمة، وعند جودة حقيقية ضع نجمة لأفضل مشروع لديهم بالمقابل — إذا كانت أداة صيانة GitHub الخاصة بك تتضمن وحدة للمعاملة بالمثل فاستخدمها (تُقيّم الصلة الموضوعية وتقترح وضع النجمة بالمقابل أو الدعوة أو المراجعة أو التخطّي؛ وتنفّذ المتابعة بحدود معدل وفترة تهدئة وشبكة أمان تشغيل تجريبي/تطبيق/تأكيد). لا تُعِد بناءها إن كانت موجودة؛ إذ تسجّل الوحدة القرارات بنفسها. لا تُلغِ المتابعة أو النجمة تلقائيًا أبدًا.
15. **التحقق الختامي.** راجع README البعيد وصفحة الإصدار والوسوم وCI والروابط.

## بوابة الخصوصية

ابحث في المجموعة المرحلية أو المتتبَّعة، لا في شجرة العمل المرئية فقط.

```bash
git diff --cached --check
git ls-files
rg -n "C:\\\\Us[e]rs\\\\|C:/Us[e]rs/|/c/Us[e]rs/|s[k]-[A-Za-z0-9]|gh[p]_|gh[o]_|API[_-]?KEY|TO[K]EN|PASS[W]ORD|SEC[R]ET|\\x{C3}|\\x{C2}|\\x{FFFD}" .
```

بالنسبة للوحدات العامة، وثّق أيضًا `RELEASE_GATE.md` أو بوابة مكافئة: التاريخ، والأوامر التي شُغّلت، والنتيجة، والتحذيرات المتبقية، والاستثناءات المقصودة. إذا أُودع سرّ في أي وقت، فحذفه من `HEAD` لا يكفي؛ يجب تدويره.

**التحقق من قابلية رؤية المستودعات المرتبطة.** لا يكشف فحص المسارات/الرموز الروابط
إلى مستودعات GitHub الخاصة الواردة في READMEs العامة (حالة تعليمية
T-20260926-820252321: `ellmos-ai/ellmos-core` ورد دون ملاحظة في جدول README
رغم أن المستودع خاص). إذا كان متوفرًا في المستودع، شغّل فحص إعادة الاستخدام:

```bash
python testing/repo_link_visibility_gate.py --repo .
```

الفحص مفتوح الفشل (fail-open) فقط عند عدم اليقين الحقيقي (انقطاع الشبكة، وتجاوز حد المعدل 403/429 — مجرد تنبيه دون إيقاف)؛ أما 404 فيمنع كما يمنع `private: true` المؤكد، لأن كليهما يعني أن الرابط غير قابل للحل بالنسبة للغرباء (خاص أو غير موجود). دون هذا السكربت (إذا لم يكن للمستودع نسخة محلية من الفحص): تحقّق بالعينة باستخدام `gh api repos/ORG/REPO --jq .private` من كل رابط لمستودع خارجي أو شقيق مذكور في README.

## البيانات الوصفية لـ GitHub

بعد الدفع اضبط البيانات الوصفية والإصدار صراحةً.

```bash
gh repo edit ORG/REPO --description "Kurze konkrete Beschreibung" \
  --add-topic local-first --add-topic python --add-topic llm
git tag -a v1.0.0 -m "v1.0.0"
git push origin v1.0.0
gh release create v1.0.0 --repo ORG/REPO --title "v1.0.0" --notes "..."
```

ثم تحقّق:

```bash
gh repo view ORG/REPO --json nameWithOwner,visibility,description,repositoryTopics,url
gh release view v1.0.0 --repo ORG/REPO --json tagName,url,isDraft,isPrerelease
gh run list --repo ORG/REPO --limit 5
```

إذا فشل CI بعد إصدار، فلا يُعدّ المستودع منشورًا بشكل سليم بعد. وعند إصدار أولي حديث، من المقبول نقل الوسم الجديد فورًا وبشكل مقصود إلى الإيداع المُصحَّح.

## الأخطاء الشائعة

| الخطأ | التصحيح |
|---|---|
| يُنشأ `.gitignore` بعد `git add` | ألغِ التهيئة أولًا، وصحّح قواعد التجاهل، ثم أضف من جديد |
| README بلغة واحدة رغم أن الواجهة أو المهارة متعددة اللغات | أضف روابط اللغات أو READMEs مترجمة |
| لا بانر ولا وسوم ولا وصف | أضف أصول الاكتشاف قبل الإعلان |
| وسم الإصدار موجود لكن CI فاشل | أصلح CI وتحقّق من تشغيل جديد |
| حُدِّث README المنظمة لكن نُسي `llms.txt` | حدّث السطحين البشري والآلي القابل للقراءة |
| مسار محلي في وثائق عامة | استبدله بمسارات نسبية أو أمثلة عامة |
| يحتوي المستودع العام على قاعدة بيانات اختبار أو صندوق دفتر ملاحظات | أزل الملف من التتبع، وأضف قاعدة تجاهل، وأعد تشغيل البوابة |

## قائمة التحقق الختامية

- [ ] تم فحص القواعد المحلية والأقفال.
- [ ] كان `.gitignore` موجودًا قبل أول إضافة.
- [ ] الوثائق العامة والترخيص والأمان والمساهمة وسجل التغييرات و`llms.txt` موجودة.
- [ ] يتضمن README اسم المستودع والغرض والتثبيت والاستخدام والخصوصية والترخيص.
- [ ] تحقق توقع i18n.
- [ ] يوجد بانر أو شعار أو لقطة شاشة حيثما كان ذلك مناسبًا.
- [ ] نجحت الاختبارات وفحوص الدخان.
- [ ] فحوص الخصوصية والمسارات والأسرار وقواعد البيانات وخلل الترميز نظيفة.
- [ ] تم التحقق من وصف GitHub والوسوم والإصدار وCI.
- [ ] تم تحديث ملف تعريف المنظمة والسجل وروابط النظام البيئي.
- [ ] هل يوجد بانر؟ `org_profile_gate.py --org <org>` عمل دون ملاحظة لهذا المستودع.
