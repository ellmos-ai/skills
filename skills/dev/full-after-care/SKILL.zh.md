# Full After Care — 深度轮次 (同义词: Deep After Care)

## 何时使用此技能

当需要对已发布的仓库进行**彻底**检查时使用此技能：例如长期未检查、重大版本发布前、涉及法律相关主题，或者需要梳理与其他个人/组织项目的关联关系时。

与低成本轮次的区别在于工作量而非严谨度：第 2 阶段超越了单个仓库的边界。它查询外部资源（法律状况），清查**所有**组织，并深入修改应用本身（多语言支持）。因此它的执行频率较低 —— 通常每个仓库每年执行一次，或在特定事由触发时执行。

## 工作流程

### 首先完整执行第 1 阶段

**完整执行 `surface-after-care`** —— 包括步骤 0（分发平台）、隐私关卡、发布意图、Banner、实际与目标对比、README 多语言、可见性、组织注册、Issue 和 PR，以及 Commit、Push 和平台一致性。此处不重复也不缩减上述任何步骤。

接下来的三个步骤属于补充内容。它们会针对文档和代码产生修改 —— 请按照第 1 阶段中描述的节奏，以主题分离的 Commit 进行提交和推送。

---

### 5. 带年度复核机制的初步法律评估

#### 首先：是否确实需要评估？

请检查 `_after-care/RECHTSCHECK.md`（该文件夹已在 gitignore 中，见下文）。如果其中记录的审查日期**未满一年**，即使在深度轮次中也可以**跳过**此步骤。重新获取一份全新的评估报告既耗费时间又产生成本，且不会带来新信息。

如果日期**已超过一年**或文件不存在，则必须进行审查。设置年度复核的原因并非评估报告本身会变质，而是**法律状况**会发生改变：新出台的法规、调整后的阈值、新的司法判例、变更后的平台规则。一份两年前的法律评估可能在形式上正确，但实际中已过时。

在年度周期之外，当**项目本身**发生变更时也需重新评估：例如引入新的数据类别、新的分发渠道、新的商业模式、变更许可证、引入带 Copyleft 的新依赖、扩展到其他司法管辖区。

#### 仓库是否具有法律相关性？

并非所有项目都需要评估。触发条件包括但不限于：

- 处理个人数据，即使仅在本地处理
- 访问第三方服务、网站或 API（使用条款、数据爬取）
- 在受监管领域提供信息或建议（法律、医疗、税务、金融）
- 在名称、文档或 UI 中包含第三方商标、名称或 Logo
- 包含带有 Copyleft 或许可证不明确的依赖，或附带分发第三方内容
- 面向未成年人、处理支付或属于出口/密码学管制范围
- 针对人类做出自动化决策，或被划分为 AI 系统

如果以上均不适用，请在执行日志中**记录已检查且不适用** —— 否则下一轮维护又会重复提出相同的问题。

#### 获取法律评估

使用法律部门（技能 `law-checker`，模块 `law-checker`），提交具体的项目事实：应用的功能、涉及的数据、分发渠道、包含的许可证以及目标受众。事实越具体，引用的法律依据就越精准。评估结果是一份包含法律条文依据的初步评估 —— **并非法律咨询**；如果存在重大风险，结果将是建议寻求律师专业审查，而非最终判决本身。

#### 归档存放

```
_after-care/
├── LOG.md                    # 两个阶段的执行日志
└── RECHTSCHECK.md            # 日期、主题、结果、附加要求、复核日期
```

`_after-care/` 必须加入 `.gitignore`。这不是隐瞒，而是遵循第 1 阶段步骤 2b 中的规则：内部工作文档不属于仓库公开内容。对于法律评估而言，公开随附风险分析可能会被解读为自认过错，并为攻击者提供路线图。或者也可以将评估文件保存在仓库之外的专门文件夹中 —— 唯一重要的是在下次运行时**能够找到**，否则年度复核规则将无法生效。

文件头请保持机器可读的格式：

```markdown
# Legal check — <Project>
checked: 2026-07-24
subject: local file management, no cloud, no personal data of third parties
result: unproblematic
conditions: Note on MIT license of embedded library X in README
resubmission: 2027-07-24
```

评估报告中**公开**的仅仅是**执行结果**：许可证说明、免责声明、隐私提示或对应用功能的精确表述。这些修改属于仓库内容 —— 而背后的内部论证过程则不属于。

### 9. 跨所有组织的关联引用

第 1 阶段仅询问仓库是否列在组织页面上。第 2 阶段则深入一层：**所有自有组织中的哪些具体仓库与当前仓库存在关联 —— 且双方是否均已建立引用？**

```bash
gh api user/orgs --jq '.[].login'
for ORG in $(gh api user/orgs --jq '.[].login'); do
  gh repo list "$ORG" --limit 200 --json name,description,updatedAt,isArchived,primaryLanguage
done
```

建立价值的关键不在于罗列列表，而在于识别关联关系。相关类型包括：

- **使用 / 被使用** —— 双向的实际技术依赖关系
- **属于同一产品族** —— 共享产品线、共同前缀、通用架构
- **以不同方式解决相同问题** —— 访问其中一个仓库的用户往往也希望了解另一个
- **前代 / 后继** —— 被替代的项目需要指引标志，否则用户会长期停留在废弃版本上
- **组件 / 组合** —— 基础库与使用该库的应用

必须设置**双向**引用。仅建立单向链接是本步骤中最常见的错误：在维护的仓库中补充了相关项目列表，而相关项目中却没有任何说明。访问对方仓库的用户将永远无法找到回程路径。

反向引用需要在目标仓库中实际设置 —— 遵循第 1 阶段步骤 11 中的**脏树规则 (Dirty Tree Rule)**，简要概括为：干净的工作树 → 独立提交并推送；其他文件有未提交修改 → 按具体路径提交，但不推送；目标文件有未提交修改或存在活跃锁 → 切勿修改。如果未能设置引用，请将其记入目标仓库的任务列表（`AUFGABEN.txt`/`TODO.md`），若存在锁定则仅记录在自身的执行日志中。这样可以保证当前轮次的独立完整，既不影响他人的工作状态，也不会丢失引用信息。

撰写引用时应侧重实用价值，而非仅仅列出名称："**project-b** —— 读取此工具生成的导出文件并生成报告" 是有价值的表述，而 "参见: project-b" 则不是。

已归档或明显废弃的仓库不要进行链接 —— 除非作为指向新版本的明确后续提示。

清查工作是本轮维护中成本最高的环节。如果需要检查大量组织和仓库，建议将清查结果保存在执行日志中，以便其他仓库的下一次深度轮次可以直接参考。

### 在应用层补充所有语言支持

第 1 阶段负责 README 的多语言版本。这里关注的是**产品本身**：界面文本、提示信息、帮助文档、CLI 输出、错误信息、商店及注册表描述。

首先确认应用在技术上已支持哪些语言及其管理方式：

```bash
rg -l "gettext|i18n|locale|translations|LC_MESSAGES|\.po$|messages\.json" --hidden
fd -e po -e pot -e ftl . 2>/dev/null; ls locales/ i18n/ lang/ translations/ 2>/dev/null
```

然后围绕以下三个问题填补语言空白：

1. **是否缺少项目应当具备的语言？** 对于面向最终用户的应用，标准语言包括德语、英语、西班牙语、简体中文、日语、俄语。对于面向开发者的函数库，仅提供英语通常是正确的选择；增加不必要的语言是持续的维护负担，而非收益。
2. **现有的语言支持是否完整？** 每次功能迭代后，次要语言往往会滞后。缺少翻译的新键名在运行时通常会静默回退为主语言，从而难以察觉 —— 因此在此处应明确与主语言进行 diff 对比，而不是依赖表面观察。
3. **语言切换功能对用户是否易用？** 没人能够开启的完整翻译等同于不存在。切换开关是否存在、选择是否持久化保存、系统语言是否被识别为默认值？

请遵循项目现有的 i18n 机制，不要引入第二套机制。请在**实际界面**中验证结果，而非仅查看资源文件：过长的字符串会破坏页面布局，而缺少字符集支持只有在渲染时才会暴露（缺失的 CJK 字符会显示为空白方框）。

最后带上第 1 阶段步骤 0 中的分发平台：商店和注册表描述具有独立的语言字段，不会随应用翻译自动同步。

## 常见错误

| 错误 | 纠正措施 |
|---|---|
| 上次法律评估仅在 3 个月前，却再次获取评估 | 先阅读 `RECHTSCHECK.md` 中的日期 —— 未满一年直接跳过 |
| 以 "没有发生变化" 为由跳过法律评估 | 法律状况会独立于项目发生变化；满一年必须进行审查 |
| 将评估报告 Commit 到仓库中 | `_after-care/` 属于 `.gitignore`；仅将最终处理结果公开 |
| 未记录不具备法律相关性的结论 | 即使结论为 "不相关"，也是一项检查结果，必须记入日志 |
| 仅在维护的仓库中设置关联引用 | 必须双向设置，否则会形成单向死胡同 |
| 仅检查了自己的个人组织 | 第 2 阶段意味着清查所有组织 —— 这正是其与第 1 阶段的区别 |
| 将引用写成单纯的名称列表 | 用半句话说明实用价值，否则无人会点击 |
| 添加了新语言，但在 UI 中无法切换使用 | 检查切换器、持久化以及系统语言自动识别 |
| 仅在资源文件中验证翻译 | 必须在真实 UI 中检查 —— 布局错乱和字符缺失只有在 UI 中才会显现 |
| 遗漏了商店/注册表的语言字段 | 它们不会随应用内部翻译自动同步变更 |

## 最终检查清单

- [ ] `surface-after-care` 已完整执行（包含 Push 和平台一致性）。
- [ ] 法律相关性已审查；结果已记录 —— 即使结论为不适用。
- [ ] 法律审查是否到期？若到期：已获取评估、附加要求已落实、复核日期已设定。
- [ ] `_after-care/` 已加入 `.gitignore`，评估报告未加入 Git 追踪。
- [ ] 所有组织均已清查，关联关系已确认。
- [ ] 关联引用已双向设置，已在目标仓库中提交并推送。
- [ ] 因工作树脏或锁定而跳过目标仓库已记录为待办事项。
- [ ] 应用语言支持完整，切换开关正常，已在 UI 中验证。
