# Full After Care — 深度复查轮次（同义词：Deep After Care）(中文)

## 何时触发此 Skill

当已发布的仓库需要进行**根本性**全面检查时使用：长时间未检查、发布重大版本之前、涉及法律相关事项、或探讨与自己其他项目的关联交织时。

与轻量轮次（`surface-after-care`）的区别在于投入的工作量，而非严谨度：阶段 2 超出了单个仓库的边界。它会查询第三方资源（法律状况）、盘点**所有**组织，并深入到应用本身（语言）。因此它执行得不够频繁 — 通常每个仓库每年执行一次，或按需触发。

## 流程

### 阶段 1 必须首先完整执行

**完整执行 `surface-after-care`** — 包括步骤 0（分发平台）、隐私关口、发布意图、 Banner 标识、实况与目标对比、README 语言版本、可见性、组织条目、Issues 和 PRs 以及提交、推送和平台对等性。此处的任何内容都不重复或简略。

以下三个步骤在此基础上叠加。它们各自会对文档和代码产生更改 — 请按照阶段 1 中描述的相同节奏，在主题独立的分段提交中推送它们。

### 5. 带有年度追踪复核的初始法律评估

#### 首先：是否到了需要评估的时间？

请检查 `_after-care/RECHTSCHECK.md`（该文件夹已被 gitignore 忽略，见下文）。如果其中记录的检查日期距离现在**不足一年**，则即使在深度轮次中也会**跳过**此步骤。重新获取一份新鲜评估既耗费时间和资金，又不会带来新收益。

如果日期**超过一年**或者文件不存在，则必须进行检查。要求年度复核的原因并不是法律意见书会变质，而是**法律状况**会发生变化：新法规、阈值调整、新判例、变更的平台规则。两年前的意见书可能形式上正确，但实际中已过时。

在年度周期之外，如果**主体事项**发生变化，也必须重新评估：新的数据类别、新的分销渠道、新的商业模式、许可证变更、引入带 Copyleft 的新依赖项、扩展到其他司法管辖区。

#### 仓库是否具有法律相关性？

并非每个项目都需要这个。触发因素包括：

- 处理个人数据，即使仅在本地处理
- 访问第三方服务、网页或接口（使用条款、数据抓取）
- 在受监管领域提供咨询/信息（法律、医学、税务、金融）
- 在名称、文档或 UI 中带有第三方商标、名称或 Logo
- 包含带有 Copyleft 或许可证不明确的依赖项，或附带第三方内容
- 面向未成年人、处理支付或属于出口/密码学监管范畴
- 针对人类做出自动化决策，或被归类为 AI 系统

如果上述均不适用，请在运行日志中**明确记录已检查并确认不适用** — 否则下一轮又会从头询问相同的问题。

#### 获取评估

使用法律部门 Skill（Skill `law-checker`，模块 `law-checker`），向其提交具体事实：应用做什么、触及哪些数据、通过什么渠道分销、涉及哪些许可证、面向什么人群。事实越具体，引用的法律条文就越有参考价值。结论是一份带有法规依据的初始评估 — **并非法律咨询**；在遇到严重风险时，结论是建议寻求律师审查，而非最终判决本身。

#### 存储

```
_after-care/
├── LOG.md                    # 两个阶段的运行日志
└── RECHTSCHECK.md            # 日期、主体事项、结论、附加要求、复核时间
```

`_after-care/` 属于 `.gitignore` 目录。这不是玩隐蔽游戏，而是遵循与阶段 1 步骤 2b 相同的规则：内部工作文档不属于仓库公开内容。对于法律意见书，公开附带的风险分析可能会被解读为承认过失，并向攻击者提供路线图。或者，存储也可以在仓库外部的独立文件夹中进行 — 唯一重要的是在下一次运行中**能够找到**，否则年度规则无法生效。

保持文件头机器可读：

```markdown
# Rechtscheck — <Projekt> (中文)
geprüft: 2026-07-24
gegenstand: lokale Dateiverwaltung, keine Cloud, keine personenbezogenen Daten Dritter
ergebnis: unbedenklich
auflagen: Hinweis auf MIT-Lizenz der eingebetteten Bibliothek X im README
wiedervorlage: 2027-07-24
```

从评估中**公开**的仅仅是**执行后果**：许可证声明、免责声明、隐私政策提示、对应用功能的精细说明。这些更改属于仓库 — 背后的理由依据则不属于。

### 9. 跨所有组织的交叉引用

阶段 1 仅询问仓库是否列在组织页面上。阶段 2 深入一步：**来自所有内部组织的哪些单个仓库与此仓库存在关联 — 并且双方是否互知？**

```bash
gh api user/orgs --jq '.[].login'
for ORG in $(gh api user/orgs --jq '.[].login'); do
  gh repo list "$ORG" --limit 200 --json name,description,updatedAt,isArchived,primaryLanguage
done
```

其价值并非来自列出清单，而是来自识别关联关系。相关类型包括：

- **使用 / 被使用** — 两个方向上的真实技术依赖
- **属于同一家族** — 共同的产品线、共同的前缀、共同的架构
- **以不同方式解决相同问题** — 访问其中一个仓库的用户通常也想了解另一个
- **前身 / 后继** — 被替代的项目需要路标指引，否则用户会永久停留在死代码上
- **构件 / 组合** — 库以及使用该库的应用

设置**双向**引用。单向引用是此步骤最常见的错误：在维护的仓库中补充了相关项目列表，而在相关项目里什么都没写。到达那里的用户将永远找不到返回的路。

反向引用实际上应当在目标仓库中设置 —, 遵循阶段 1 步骤 11 中的**脏树规则**，简要总结为：干净的工作树 -> 独立提交并推送；其他文件有修改 -> 按路径精准提交，不推送；目标文件修改或存在活跃锁 -> 不触碰。如果无法设置引用，请将其放入目标仓库的任务列表（`AUFGABEN.txt`/`TODO.md`）中，若遇到锁则仅记录在自己的运行日志中。这样既保持了本轮工作的完整独立，又不会损害他人的工作状态，也不会丢失引用。

以实用导向的方式撰写引用，而非仅写名称列表："**project-b** — 读取此工具生成的导出文件并据此生成报告"是实用的；"参见：project-b"则毫无价值。

已归档和明显废弃的仓库不进行链接 — 除非是在相反方向上作为明确的后继者提示。

此盘点是本轮中最耗时耗力的部分。如果需要检查许多组织和仓库，非常值得将仓库盘点结果记录在运行日志中，以便另一个仓库的下一次深度复查轮次可以据此继续展开。

### 应用层面的所有语言同步

阶段 1 负责 README 语言版本。这里关注的是**产品本身**：界面文本、消息提示、帮助文档、CLI 输出、错误消息、应用商店和注册表描述。

首先确定应用在技术上已经支持哪些语言以及如何管理它们：

```bash
rg -l "gettext|i18n|locale|translations|LC_MESSAGES|\.po$|messages\.json" --hidden
fd -e po -e pot -e ftl . 2>/dev/null; ls locales/ i18n/ lang/ translations/ 2>/dev/null
```

然后围绕三个问题补全缺口：

1. **是否缺少**项目应该具备的语言？面向用户的应用的标准语言是德语、英语、西班牙语、简体中文、日语、俄语。对于面向开发者的库，仅英语往往就是正确答案；不必要的语言是长期的维护负担，而非收益。
2. **现有的语言是否完整？** 在每个功能周期之后，辅助语言都会滞后。没有翻译的新键在运行时通常会静默回退到主语言，因而根本不会被察觉 — 因此要显式地与主语言对比 diff，而不是依赖视觉检查。
3. **语言选择是否能被用户使用？** 没人能开启的完整翻译就等于没有翻译。切换开关是否存在、选择是否持久化保存、是否默认识别系统语言？

遵循项目中已建立的 i18n 机制，不要在其旁边引入第二个机制。请在**实际界面**中检查结果，而不仅仅在资源文件中检查：过长的字符串会破坏布局，而缺少字体支持只有在渲染时才会暴露（缺失的 CJK 字符会显示为空白方块）。

最后带上阶段 1 步骤 0 中的分发平台：商店和注册表描述有自己的语言字段，它们不会随应用翻译自动同步更新。

## 常见错误

| 错误 | 纠正方法 |
|---|---|
| 上次法律检查仅过去 3 个月却重新获取评估 | 先读取 `RECHTSCHECK.md` 中的日期 — 未满一年则跳过 |
| 因“没有任何变化”而跳过法律检查 | 法律状况的变化独立于项目本身；满一年即需检查 |
| 将法律意见书提交到仓库 | `_after-care/` 属于 `.gitignore`；仅执行后果对外公开 |
| 未记录否定的法律相关性 | 即使是“不相关”也是一项结论，必须记录在日志中 |
| 仅在维护的仓库中设置交叉引用 | 必须双向设置，否则就是单行道 |
| 仅检查了自己的组织 | 阶段 2 意味着所有组织 — 这正是它与阶段 1 的区别 |
| 引用仅作为纯名称列表 | 用半句话说明实用价值，否则没人会点击 |
| 创建了新语言但在 UI 中无法使用 | 同时测试切换器、持久化和系统语言识别 |
| 仅在资源文件中检查翻译 | 在实际界面中测试 — 布局破坏和字符缺失仅会在界面中显现 |
| 遗忘了商店/注册表语言字段 | 它们不会随应用翻译自动同步 |

- [ ] 法律检查是否到期？若到期：已获取评估、落实要求、设置复核时间。
- [ ] `_after-care/` 已在 `.gitignore` 中，未追踪意见书。
- [ ] 已盘点所有组织，确定了关联关系。
- [ ] 交叉引用已双向设置，已在目标仓库中提交并推送。
- [ ] 因脏树或锁定而跳过的目标仓库已记录为未决事项。
