# Full After Care — Глубокий раунд (Синоним: Deep After Care)

## Когда использовать этот навык

Используйте его, когда опубликованный репозиторий необходимо проверить **основательно**: если он давно не проверялся, перед крупным релизом, при наличии юридически значимых аспектов или когда требуется интеграция с остальными собственными проектами и организациями.

Отличие от недорогого раунда заключается в трудоемкости, а не в степени тщательности: Уровень 2 выходит за границы отдельного репозитория. Он запрашивает внешние источники (юридический статус), инвентаризирует **все** организации и вносит изменения в само приложение (языки). Поэтому он выполняется реже — обычно один раз на репозиторий в год или по особому поводу.

## Ход работы

### Сначала полностью Уровень 1

Выполните **`surface-after-care` в полном объеме** — включая Шаг 0 (площадки дистрибуции), шлюз приватности, намерение публикации, баннеры, сравнение план/факт, языки README, видимость, запись в организации, Issues и PR, а также коммит, пуш и паритет площадок. Ничто из этого здесь не повторяется и не сокращается.

Следующие три шага добавляются сверх того. Они создают изменения в документации и коде — пушьте их в том же ритме, что описан на Уровне 1, отдельными тематическими коммитами.

### 5. Предварительная юридическая оценка с ежегодной повторной проверкой

#### Сначала: Наступил ли срок проверки?

Загляните в `_after-care/RECHTSCHECK.md` (папка находится в gitignore, см. ниже). Если там указана дата проверки, с которой прошло **менее одного года**, этот шаг **пропускается** — даже в глубоком раунде. Запрос новой оценки раньше времени требует времени и денег и не дает новых результатов.

Если с момента проверки прошло **более года** или файл отсутствует, проводится проверка. Причина повторного контроля заключается не в том, что юридическое заключение портится, а в том, что меняется **правовая ситуация**: новые нормы, измененные пороговые значения, новая судебная практика, обновленные правила платформ. Заключение двухлетней давности может быть формально верным, но практически устаревшим.

Вне ежегодного ритма повторная оценка требуется, если изменился **предмет**: новые категории данных, новый канал дистрибуции, новая бизнес-модель, смена лицензии, новая зависимость с copyleft, расширение на другую юрисдикцию.

#### Имеет ли репозиторий юридическую значимость?

Не каждому проекту это требуется. Триггерами являются, помимо прочего:

- обработка персональных данных, даже если только локально
- доступ к сторонним сервисам, веб-сайтам или API (условия использования, парсинг)
- предоставление информации в регулируемых сферах (право, медицина, налоги, финансы)
- использование сторонних товарных знаков, наименований или логотипов в названии, документации или UI
- наличие зависимостей с copyleft или неясной лицензией, или поставка стороннего контента
- ориентация на несовершеннолетних, обработка платежей или подпадание под экспортный/криптографический контроль
- принятие автоматизированных решений в отношении людей или классификация как система ИИ

Если ничто из этого не применимо, зафиксируйте в журнале выполнения, **что проверка была проведена и результат отрицательный** — иначе в следующем раунде снова возникнет тот же вопрос.

#### Получение оценки

Воспользуйтесь юридическим отделом (навык `law-checker`, модуль `law-checker`) и предоставьте конкретные факты: что делает приложение, каких данных касается, через какие каналы распространяется, какие лицензии содержатся, на кого оно ориентировано. Чем конкретнее факты, тем полезнее ссылки на нормативные акты. Результатом является предварительная оценка со ссылками на статьи законов — **не юридическая консультация**; при серьезном риске результатом является рекомендация обратиться к адвокату, а не сам вердикт.

#### Хранение

```
_after-care/
├── LOG.md                    # Журнал выполнения обоих уровней
└── RECHTSCHECK.md            # Дата, предмет, результат, условия, повторный контроль
```

Папка `_after-care/` должна быть внесена в `.gitignore`. Это не сокрытие информации, а то же правило, что и в Шаге 2b Уровня 1: внутренние рабочие документы не являются содержимым репозитория. В случае с юридическим заключением публичный анализ рисков может восприниматься как признание вины и предоставлять злоумышленникам карту уязвимостей. Альтернативно хранение может осуществляться за пределами репозитория в отдельной папке — главное, чтобы файлы можно было **найти** при следующем запуске, иначе правило одного года не сработает.

Заголовок файла должен оставаться машиночитаемым:

```markdown
# Legal check — <Project>
checked: 2026-07-24
subject: local file management, no cloud, no personal data of third parties
result: unproblematic
conditions: Note on MIT license of embedded library X in README
resubmission: 2027-07-24
```

Публичными из оценки становятся только **последствия**: указание лицензии, отказ от ответственности, уведомление о конфиденциальности, уточненное описание того, что делает приложение. Эти изменения вносятся в репозиторий — внутреннее обоснование в него не входит.

### 9. Перекрестные ссылки по всем организациям

Уровень 1 проверяет только то, указан ли репозиторий на страницах организаций. Уровень 2 идет на шаг глубже: **Какие конкретные репозитории из всех собственных организаций связаны с этим — и знают ли обе стороны об этой связи?**

```bash
gh api user/orgs --jq '.[].login'
for ORG in $(gh api user/orgs --jq '.[].login'); do
  gh repo list "$ORG" --limit 200 --json name,description,updatedAt,isArchived,primaryLanguage
done
```

Ценность создает не сам список, а выявление связей. Релевантные типы:

- **использует / используется в** — реальная техническая зависимость в обоих направлениях
- **принадлежит к той же семье** — общая линейка продуктов, общий префикс, общая архитектура
- **решает ту же проблему иначе** — пользователь, попавший на один проект, часто хочет узнать о другом
- **предшественник / преемник** — устаревшим проектам нужен указатель, иначе пользователи навсегда останутся на заброшенном коде
- **компонент / составной проект** — библиотека и приложение, использующее её

Устанавливайте ссылки **двунаправленно**. Односторонняя ссылка — самая частая ошибка этого шага: в обслуживаемом репозитории добавляют список связанных проектов, а в связанных проектах ничего не указано. Пользователь, попавший туда, никогда не найдет дорогу обратно.

Обратная ссылка фактически устанавливается в целевом репозитории — по **правилу грязного дерева (Dirty Tree Rule)** из Шага 11 Уровня 1, кратко: чистое дерево → отдельный коммит и пуш; грязные изменения в других файлах → коммитить строго по путям, не пушить; грязные изменения в целевом файле или активная блокировка → не трогать. Если ссылка не была установлена, внесите её в список задач целевого репозитория (`AUFGABEN.txt`/`TODO.md`), при наличии блокировки — только в собственный журнал выполнения. Так раунд остается завершенным, не подвергая риску чужую работу и не теряя связь.

Формулируйте ссылки с ориентацией на пользу, а не простым списком имен: "**project-b** — читает экспорты, созданные этим инструментом, и формирует из них отчеты" — полезно, "см. также: project-b" — нет.

Архивированные и явно заброшенные репозитории не линкуются — за исключением явного указания на преемника в противоположном направлении.

Эта инвентаризация — самая затратная часть раунда. Если необходимо проверить много организаций и репозиториев, имеет смысл сохранить результаты инвентаризации в журнале выполнения, чтобы следующий глубокий раунд другого репозитория мог опереться на них.

### Актуализация всех языков на уровне приложения

Уровень 1 отвечает за языковые версии README. Здесь речь идет о **самом продукте**: текстах интерфейса, сообщениях, справке, выводе CLI, сообщениях об ошибках, описаниях в store и registry.

Сначала определите, какие языки приложение уже технически поддерживает и как ими управляет:

```bash
rg -l "gettext|i18n|locale|translations|LC_MESSAGES|\.po$|messages\.json" --hidden
fd -e po -e pot -e ftl . 2>/dev/null; ls locales/ i18n/ lang/ translations/ 2>/dev/null
```

Затем закройте пробелы, ответив на три вопроса:

1. **Не хватало ли языков**, которые должны быть у проекта? Стандартные языки: немецкий, английский, испанский, упрощенный китайский, японский, русский — для пользовательских приложений. Для библиотек разработчиков часто достаточно только английского; ненужный язык — это постоянная нагрузка на обслуживание, а не польза.
2. **Полностью ли переведены существующие языки?** После каждого цикла функций второстепенные языки отстают. Новые ключи без перевода в процессе работы часто незаметно возвращаются к основному языку и остаются незамеченными — поэтому здесь нужно явно сравнивать diff с основным языком, а не полагаться на внешний вид.
3. **Доступен ли выбор языка пользователям?** Полный перевод, который никто не может включить, равносилен его отсутствию. Переключатель присутствует, выбор сохраняется, системный язык определяется по умолчанию?

Придерживайтесь механизма i18n, принятого в проекте, и не внедряйте второй параллельно. Проверяйте результаты в **реальном интерфейсе**, а не только в файле ресурсов: слишком длинные строки ломают верстку, а отсутствие поддержки шрифтов проявляется только при рендеринге (отсутствующие CJK-глифы отображаются пустыми квадратами).

В завершение подтяните площадки из Шага 0 Уровня 1: описания в store и registry имеют собственные языковые поля, которые не обновляются автоматически вместе с переводом приложения.

## Частые ошибки

| Ошибка | Исправление |
|---|---|
| Повторный запрос юридической оценки, хотя последняя была 3 месяца назад | Сначала проверьте дату в `RECHTSCHECK.md` — менее года пропускается |
| Пропуск юридической оценки, так как "ничего не изменилось" | Правовая ситуация меняется независимо от проекта; через год требуется проверка |
| Коммит юридического заключения в репозиторий | `_after-care/` должен быть в `.gitignore`; публичными становятся только последствия |
| Отсутствие документации при отрицательной юридической значимости | Даже "не релевантно" является результатом и заносится в журнал |
| Перекрестные ссылки установлены только в обслуживаемом репозитории | Устанавливайте двунаправленно, иначе это тупик |
| Проверка только собственной организации | Уровень 2 означает все организации — именно это отличает его от Уровня 1 |
| Ссылки в виде простого списка имен | Объясните пользу в одном предложении, иначе никто не кликнет |
| Добавлен новый язык, но он недоступен в UI | Проверьте переключатель, сохранение и автоопределение системного языка |
| Перевод проверен только в файле ресурсов | Проверяйте в реальном UI — разрывы верстки и пропавшие глифы видны только там |
| Забыты языковые поля store/registry | Они не обновляются автоматически вместе с переводом приложения |

## Итоговый чек-лист

- [ ] `surface-after-care` полностью пройден (вкл. пуш и паритет площадок).
- [ ] Юридическая значимость проверена; результат задокументирован — даже если отрицательный.
- [ ] Наступил срок юридической проверки? Если да: получена, условия выполнены, повторный контроль установлен.
- [ ] `_after-care/` добавлен в `.gitignore`, заключение не отслеживается.
- [ ] Все организации проинвентаризированы, связи определены.
- [ ] Перекрестные ссылки установлены двунаправленно, скоммичены и запушены в целевых репозиториях.
- [ ] Пропущенные из-за грязного дерева или блокировок целевые репозитории записаны как открытые задачи.
- [ ] Языки приложения полные, переключатель доступен, проверено в интерфейсе.
- [ ] Языковые поля в store/registry обновлены.
- [ ] Запись в журнале выполнения с уровнем `full` создана.
