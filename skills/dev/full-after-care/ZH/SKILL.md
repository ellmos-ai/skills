# Full After Care — 深度维护轮次（同义词：Deep After Care）

## 何时使用此 Skill

当需要对已发布仓库进行**全面、彻底**的排查时使用此 Skill：长时间未检查、发布重大版本之前、涉及法律相关事项时，或需要梳理与自己其他项目之间的联动整合时。

深度轮次与轻量轮次（表面轮次）的区别在于工作量而非细致程度：阶段 2 超出了单个仓库的边界。它查询外部资源（法律状况）、盘点**所有**组织，并深入到应用本身（多语言支持）。因此它的执行频率较低 — 通常每个仓库每年执行一次，或视具体情况按需触发。

## 执行流程

### 首先完整执行第一阶段

**完整执行 `surface-after-care`** — 包括步骤 0（发布渠道/分发平台）、Privacy-Gate（隐私审查）、发布意图、Banner、现状与目标对齐、README 多语言、可见性设置、组织条目、Issues 和 PRs，以及 Commit、Push 和分发平台一致性。此处不会重复或简化其中任何内容。

以下三个步骤在此基础上叠加。它们本身会对文档和代码产生更改 — 请按照阶段 1 中描述的节奏，分主题提交 Commit 并 Push。

### 5. 带有年度复审的法律初步评估

#### 首先：是否需要进行评估？

查阅 `_after-care/RECHTSCHECK.md`（该文件夹已被 gitignore 忽略，见下文）。如果其中记录的检查日期距离现在**不足一年**，则**跳过**此步骤 — 即使在深度轮次中也是如此。重新获取一份全新的评估既耗费时间与成本，又不会带来新的价值。

如果日期**超过一年**或者该文件不存在，则需要进行评估。要求重新复审的原因并非评估报告本身变质，而是**法律环境**发生了变化：颁布了新法规、调整了阈值、出现了新的司法判例或平台规则变更。一份两年前的法律评估在形式上可能正确，但在实际应用中可能已经过时。

在年度周期之外，如果**评估对象**发生了变化，也必须重新评估：新增数据类别、新分发渠道、新商业模式、许可证变更、引入带 Copyleft 的新依赖项，或扩展至其他司法管辖区。

#### 仓库具有法律相关性吗？

并非所有项目都需要评估。触发因素包括但不限于：

- 处理个人数据，即使仅在本地
- 访问第三方服务、网站或 API（服务条款、网络爬取）
- 在受监管领域提供信息（法律、医疗、税务、金融）
- 在名称、文档或 UI 中包含第三方商标、名称或 Logo
- 包含带 Copyleft 许可或许可证不明确的依赖项，或附带第三方内容
- 面向未成年人、处理支付或受出口/密码学法规管辖
- 对人做出自动化决策或被归类为 AI 系统

如果以上都不适用，请在执行日志中**记录已评估并确认不适用** — 否则下一轮又会从头问同样的问题。

#### 获取评估

使用法律部门 Skill（`law-checker`，模块 `law-checker`），并向其提交具体的项目事实：应用做什么、触及哪些数据、通过哪些渠道分发、随附哪些许可证、面向什么受众。事实越具体，得出的依据越有参考价值。评估结果是带有法律条款依据的初步判断 — **非正式法律咨询**；在存在严重风险的情况下，结果是建议寻求律师审核，而非最终裁决本身。

#### 存放路径

```
_after-care/
├── LOG.md                    # Laufprotokoll beider Stufen
└── RECHTSCHECK.md            # Datum, Gegenstand, Ergebnis, Auflagen, Wiedervorlage
```

`_after-care/` 属于 `.gitignore`。这不是玩捉迷藏，而是遵循与阶段 1 步骤 2b 相同的规则：内部工作文档不属于仓库内容。对于法律意见书，还因为公开发布的风险分析可能会被解读为某种供认，并为攻击者提供指南。或者，也可以将存放文件放在仓库之外的独立文件夹中 — 唯一重要的是在下次运行中**能够找到**它，否则一年复审规则将无法生效。

保持文件文件头可被开箱即用的机器读取：

```markdown
# Rechtscheck — <Projekt> (Deutsch)
geprüft: 2026-07-24
gegenstand: lokale Dateiverwaltung, keine Cloud, keine personenbezogenen Daten Dritter
ergebnis: unbedenklich
auflagen: Hinweis auf MIT-Lizenz der eingebetteten Bibliothek X im README
wiedervorlage: 2027-07-24
```

从评估结果中向**公众公开**的仅是**具体改进措施/后果**：许可证声明、免责声明、隐私说明，或对应用功能的具体描述。这些更改属于仓库内容 — 而背后的论证过程则不属于。

### 9. 跨所有组织的交叉引用

阶段 1 仅询问仓库是否列在组织页面上。阶段 2 则更深一步：**所有自建组织中的哪些具体仓库与当前仓库相关 — 并且双方是否都互相知情？**

```bash
gh api user/orgs --jq '.[].login'
for ORG in $(gh api user/orgs --jq '.[].login'); do
  gh repo list "$ORG" --limit 200 --json name,description,updatedAt,isArchived,primaryLanguage
done
```

价值并非来自简单列表，而是来自识别关系。相关类型：

- **使用 / 被使用于** — 两个方向上的真实技术依赖关系
- **属于同一个系列** — 共同的产品线、共同的前缀、共同的架构
- **以不同方式解决相同问题** — 访问其中一个项目的用户通常想了解另一个项目
- **前身 / 后续项目** — 被替代的项目需要指引，否则用户会永久停留在停更的版本上
- **组件 / 组合** — 库及其调用的应用程序

请**双向设置**引用。单行道是此步骤中最常见的错误：在维护的仓库中添加了相关项目列表，而相关项目中却没有写任何内容。访问那里的用户永远找不到返回的路径。

因此，必须在目标仓库中实际设置反向链接 — 遵循阶段 1 步骤 11 中的 **Dirty-Tree 规则**，简要总结：干净的 Working Tree → 独立 Commit 并 Push；其他文件存在修改（dirty） → 精确路径 Commit，不 Push；目标文件存在修改或已被锁锁定 → 切勿动它。如果未设置反向链接，应将其记录在目标仓库的任务列表中（`AUFGABEN.txt`/`TODO.md`），若存在锁则仅记录在自己的执行日志中。这样既保持了本轮工作的完整独立，又不会破坏他人的工作状态，同时避免引用丢失。

撰写引用时应以用户实用价值为导向，而非纯名称列表：“**project-b** — 读取此工具生成的导出数据并生成报告”是很有用的说明，而“另请参阅：project-b”则毫无价值。

已归档和明显停更的仓库不进行链接 — 除非作为反方向的明确后续项目提示。

这种盘点是本轮成本最高的环节。如果要排查的组织和仓库很多，将仓库盘点结果记录在执行日志中是值得的，这样其他仓库的下一次深度轮次就可以在此基础上开展。

### 在应用层面补齐所有语言

阶段 1 负责 README 的多语言版本。这里讨论的是**产品本身**：界面文本、提示消息、帮助文档、CLI 输出、错误信息、商店和注册局描述。

首先确定应用在技术上已经支持哪些语言以及如何管理它们：

```bash
rg -l "gettext|i18n|locale|translations|LC_MESSAGES|\.po$|messages\.json" --hidden
fd -e po -e pot -e ftl . 2>/dev/null; ls locales/ i18n/ lang/ translations/ 2>/dev/null
```

然后围绕三个问题补齐缺口：

1. **是否缺少项目应该具备的语言？** 对于面向用户的应用，标准语言为德语、英语、西班牙语、简体中文、日语、俄语。对于面向开发者的库，仅提供英语通常就是正确的选择；不必要的语言是持续的维护负担，而非好处。
2. **现有语言是否完整？** 在每个功能周期之后，次要语言往往会滞后。没有翻译的新键在运行时通常会退回到主语言，从而根本不会引起注意 — 因此这里要专门针对主语言做 diff，而不是凭表面印象判断。
3. **用户能否选择并切换语言？** 一份没人能够启用的完整翻译与没有翻译无异。是否有切换开关？选择是否持久化？是否默认识别了系统语言？

请遵循项目中建立的 i18n 机制，不要在旁边引入第二套机制。要在**真实的界面中**验证结果，而不仅仅在资源文件中检查：过长的字符串会破坏布局，而字体支持的缺失只有在渲染时才会展示出来（缺失的 CJK 字符会显示为空白方块）。

最后，带上阶段 1 步骤 0 中的发布渠道：商店和注册局描述有自己的语言字段，不会随着应用翻译自动同步。

## 常见错误

| 错误 | 纠正措施 |
|---|---|
| 上次法律检查仅过去 3 个月却再次重新评估 | 首先查阅 `_after-care/RECHTSCHECK.md` 中的日期 — 未满一年直接跳过 |
| 以“没有任何改变”为由跳过法律检查 | 法律环境的变化独立于项目本身；满一年必须检查 |
| 将法律意见书提交到仓库 | `_after-care/` 属于 `.gitignore`；公开的仅应是处理结果 |
| 未记录判定为无法律相关性的结论 | 即使是“无关/不适用”也是一项结论，必须写入日志 |
| 仅在当前维护的仓库中设置交叉引用 | 必须双向设置，否则就是单行道 |
| 仅检查了自己的组织 | 阶段 2 意味着检查所有组织 — 这正是它与阶段 1 的区别所在 |
| 引用仅表现为纯名称列表 | 用半句话说明用途/价值，否则没人会点击 |
| 添加了新语言，但在 UI 中无法切换 | 一并检查切换器、持久化以及系统语言识别 |
| 仅在资源文件中检查翻译 | 在真实的界面中检查 — 布局错乱和缺字（Glyph）只有在渲染时才会展示出来 |
| 遗漏了应用商店/注册局的语言字段 | 它们不会随着应用翻译自动同步 |

## 最终检查清单

- [ ] 完整运行 `surface-after-care`（包括 Push 和分布页面一致性）。
- [ ] 法律相关性已评估；结论已记录 — 即使为否。
- [ ] 是否需要法律检查？如果是：已获取检查意见、已履行具体要求、已设置复审日期。
- [ ] `_after-care/` 已加入 `.gitignore`，且未追踪法律意见书。
- [ ] 已对所有组织进行盘点，并确定相关关系。
- [ ] 交叉引用已双向设置，并在目标仓库中完成 Commit 和 Push。
- [ ] 因 Dirty Tree 或锁限制而跳过对端仓库，已列为待办事项。
- [ ] 应用语言已补齐，切换开关可用，且已在 UI 中验证。
- [ ] 应用商店/注册局的语言字段已完成更新。
- [ ] 已撰写标记为 `full` 阶段的执行日志条目。
