# Full After Care — 深層ラウンド（同義語: Deep After Care）

## この Skill の適用条件

公開済みリポジトリを**抜本的**に点検する必要がある場合に使用します: 長期間チェックされていない、大規模リリース前、法的に関連する問題がある場合、または自社の他のプロジェクトとの連携・統合がテーマとなっている場合などです。

簡易ラウンドとの違いは注意深さではなく労力です: ステージ 2 は単一リポジトリの境界を超えます。外部ソース（法的状況）への照会、**すべて**の組織の棚卸し、 possessed アプリケーション自体への介入（言語対応）を行います。そのため実行頻度は低く、通常はリポジトリごとに年 1 回、または必要に応じて実施されます。

## 手順

### まずステージ 1 を完全に実行

**`surface-after-care` を完全に実行してください** — ステップ 0（配信プラットフォーム）、Privacy-Gate、公開の意図、バナー、現状と目標の擦り合わせ、README の言語対応、公開設定、組織への登録、Issue や PR の対応、ならびにコミット、プッシュ、各面の同期を含みます。ここでの重複や省略はありません。

以下の 3 つのステップはそれに上乗せして実施されます。これら自体がドキュメントやコードの変更を生成します — ステージ 1 で説明したのと同じリズムで、テーマごとに分割したコミットでプッシュしてください。

### 5. 年次再提出を伴う法的初期評価

#### 最初に: そもそも評価が必要か？

`_after-care/RECHTSCHECK.md` を確認してください（このフォルダは gitignore されています。下記参照）。そこに記録された確認日付が**1 年未満**の場合、このステップは深層ラウンドであっても**スキップ**されます。改めて新しい評価を取得することは時間とコストがかかり、新しい知見も得られません。

日付が **1 年以上経過している**場合、またはファイルが存在しない場合は確認を行います。再提出を行う理由は見解の質が低下するためではなく、**法的状況**が変化するためです: 新しい規制、閾値の変更、判例の更新、プラットフォーム規約の変更などです。2 年前の法的見解は、形式的には正しくても実務的には陳腐化している可能性があります。

年次周期以外 shared であっても、**対象**が変更された場合は再評価が必要です: 新しいデータカテゴリ、新しい販売チャネル、新しいビジネスモデル、ライセンスの変更、コピーレフトを伴う新しい依存関係、別の管轄区域への拡大など。

#### リポジトリに法的な関連性があるか？

すべてのプロジェクトでこれが必要なわけではありません。トリガーとなるのは以下のような場合です:

- 個人データを処理している（ローカルのみの場合も含む）
- 外部サービス、ウェブサイト、APIにアクセスしている（利用規約、スクレイピング）
- 規制分野（法律、医療、税務、金融）に関する情報を提供している
- 名称、ドキュメント、UIに第三者の商標、名前、ロゴが含まれている
- コピーレフトや不明なライセンスの依存関係が含まれている、または第三者のコンテンツを同梱している
- 未成年者を対象としている、決済を処理する、または輸出/暗号規制の対象となる
- 人に関する自動意思決定を行う、またはAIシステムとして分類される

いずれも当てはまらない場合は、ログに**確認の上、該当なしと判定した旨を記録**してください。そうしないと、次のラウンドで同じ質問が繰り返されます。

#### 評価の取得

法務部門（Skill `law-checker`、モジュール `law-checker`）を利用し、具体的な事実関係を提示してください: アプリケーションの機能、扱うデータ、配信チャネル、同梱ライセンス、対象ユーザーなど。事実関係が具体的なほど、役立つ典拠が得られます。結果は条文の根拠を伴う初期評価であり、**法的助言ではありません**。重大なリスクがある場合の結果は、判決そのものではなく弁護士への相談の推奨となります。

#### 格納場所

```
_after-care/
├── LOG.md                    # Laufprotokoll beider Stufen
└── RECHTSCHECK.md            # Datum, Gegenstand, Ergebnis, Auflagen, Wiedervorlage
```

`_after-care/` は `.gitignore` に含めます。これは隠し事ではなく、ステージ 1 のステップ 2b と同じルールです: 内部作業ドキュメントはリポジトリのコンテンツではありません。法的見解の場合、公に同梱されたリスク分析が自白とみなされ、攻撃者にマップを提供してしまうリスクもあります。あるいは、リポジトリ外の独自のフォルダに保管することも可能です — 重要なのは次の実行時に**発見可能**であることであり、そうでなければ 1 年ルールが機能しません。

ファイルのヘッダーは機械判判読可能に保ってください:

```markdown
# Rechtscheck — <Projekt> (Deutsch)
geprüft: 2026-07-24
gegenstand: lokale Dateiverwaltung, keine Cloud, keine personenbezogenen Daten Dritter
ergebnis: unbedenklich
auflagen: Hinweis auf MIT-Lizenz der eingebetteten Bibliothek X im README
wiedervorlage: 2027-07-24
```

評価から**公開**されるのは**結果・対応策**のみです: ライセンス表記、免責事項、プライバシーに関する注意事項、アプリの動作に関する明確化された説明など。これらの変更はリポジトリに含まれますが、その背後にある理由付けは含まれません。

### 9. 全組織にわたる相互参照

ステージ 1 ではリポジトリが組織ページに記載されているかのみを確認します。ステージ 2 では一歩踏み込みます: **すべての所有組織のうち、どの個別のリポジトリがこのリポジトリと関連しているか — そして双方でそれを認識しているか？**

```bash
gh api user/orgs --jq '.[].login'
for ORG in $(gh api user/orgs --jq '.[].login'); do
  gh repo list "$ORG" --limit 200 --json name,description,updatedAt,isArchived,primaryLanguage
done
```

価値は単にリストアップすることではなく、関係性を認識することから生まれます。関連するタイプ:

- **使用している / 使用されている** — 両方向の実際の技術的依存関係
- **同じファミリーに属する** — 共通のプロダクトライン、共通の接頭辞、共通のアーキテクチャ
- **同じ問題を別の方法で解決する** — 一方にたどり着いたユーザーは、もう一方も知りたいことが多い
- **前身 / 後継** — 置き換えられたプロジェクトには案内が必要です。そうしないとユーザーが永久に古い状態に留まります
- **構成要素 / 結合** — ライブラリとそれを使用するアプリケーション

参照は**双方向に設定**してください。一方通行はこのステップで最もよくある間違いです: メンテナンス対象のリポジトリに関連プロジェクトのリストを追加しても、関連プロジェクト側には何も書かれていないという状況です。そこに辿り着いた人は二度と戻る道を見つけられません。

したがって、逆方向のリンクは相手側のリポジトリで実際に設定されます — ステージ 1 のステップ 11 にある **Dirty-Tree ルール** に従って要約すると: クリーンなツリー → 独自のコミットとプッシュ; 他のファイルが dirty → パスを正確に指定してコミット、プッシュはしない; ターゲットファイルが dirty またはアクティブなロックあり → 触らない。参照が設定されない場合は、相手側リポジトリのタスクリスト（`AUFGABEN.txt`/`TODO.md`）に含め、ロックされている場合は自身の実行ログのみに記録します。これにより、外部の作業状態を危険に晒すことなく、参照を失わずにラウンドを自己完結させることができます。

参照文は単なる名前のリストではなく、ユーザーの利便性を考慮して記述してください: 「**project-b** — このツールが生成したエクスポートを読み込み、そこからレポートを作成します」は有用ですが、「参照: project-b」は役に立ちません。

アーカイブ済みや明らかに更新が止まっているリポジトリはリンクしません — ただし、逆方向への明示的な後継案内としての場合を除きます。

この棚卸しはラウンドの中で最もコストがかかる部分です。確認すべき組織やリポジトリが多い場合は、リポジトリ棚卸しの結果を実行ログに保存しておくと、別のリポジトリの次の深層ラウンドで活用できます。

### アプリケーションレベルでの全言語の追従

ステージ 1 は README の言語バージョンをケアします。ここでは**プロダクト自体**を扱います: UI テキスト、メッセージ、ヘルプ、CLI 出力、エラーメッセージ、ストアおよびレジストリの説明。

まず、アプリケーションが技術的にどの言語を認識しており、どのように管理しているかを特定します:

```bash
rg -l "gettext|i18n|locale|translations|LC_MESSAGES|\.po$|messages\.json" --hidden
fd -e po -e pot -e ftl . 2>/dev/null; ls locales/ i18n/ lang/ translations/ 2>/dev/null
```

次に、3 つの質問に沿って不足を埋めます:

1. **プロジェクトが備えるべき言語が不足していませんか？** ユーザー向けアプリケーションの場合、標準言語はドイツ語、英語、スペイン語、簡体字中国語、日本語、ロシア語です。開発者向けのライブラリでは英語のみで十分な場合が多く、不要な言語はメリットではなく永久的な保守の負担となります。
2. **既存の言語は完全ですか？** 機能追加のサイクルごとに、サブ言語は取り残されがちです。翻訳のない新しいキーは運用時に主要言語にフォールバックされるため見落とされがちです。目視に頼るのではなく、主要言語との差分（diff）を意図的に確認してください。
3. **言語選択はユーザーにとって利用可能ですか？** 誰も切り替えられない完全な翻訳は、存在しないのも同然です。切替スイッチはあるか、選択は保持されるか、システム言語がデフォルトとして検出されるか？

プロジェクトで確立されている i18n メカニズムに従い、並行して 2 つ目のメカニズムを導入しないでください。リソースファイルだけでなく、**実際のインターフェース**で結果を確認してください: 文字列が長すぎるとレイアウトが崩れ、フォントサポートの欠落はレンダリング時（表示できない CJK 文字が空の四角「豆腐」として表示される）に初めて判明します。

最後に、ステージ 1 のステップ 0 から各面を含めます: ストアやレジストリの説明には独自の言語フィールドがあり、アプリの翻訳と自動的に連動するわけではありません。

## よくあるエラー

| エラー | 修正方法 |
|---|---|
| 直近の法的事前チェックから3ヶ月しか経っていないのに再取得した | まず `_after-care/RECHTSCHECK.md` の日付を確認する — 1年未満ならスキップ |
| 「何も変わっていない」という理由で法的事前チェックをスキップした | 法的状況はプロジェクトとは無関係に変化するため、1年経過後は確認が必要 |
| 意見書をリポジトリにコミットした | `_after-care/` は `.gitignore` に含めるべき。公開するのは対応策のみ |
| 法的関連性の否定が記録されていない | 「関連なし」という結果も所見であり、ログに記録すべき |
| 相互参照がメンテナンス対象のリポジトリにしか設定されていない | 双方向に設定すること。さもないと一方通行になります |
| 自組織のみを確認した | ステージ 2 は「すべての組織」を意味します。それこそがステージ 1 との違いです |
| 参照が単なる名前のリストになっている | ひとこと利点を説明しないと、誰もクリックしません |
| 新しい言語を追加したがUIからアクセスできない | 切替スイッチ、保持性、システム言語の検出も併せて確認する |
| 翻訳をリソースファイル内だけで確認した | 実際のUIで確認すること。レイアウトの崩れや豆腐（グリフ欠落）はそこでしか見えません |
| ストア/レジストリの言語フィールドを忘れた | アプリの翻訳と自動的に連動するわけではありません |
