# piggyback-hosting

**一种从一开始就从不接收外部数据的应用托管模式。**

> 该蓝图创建于 2026-08-02，在构建三个通话代理时形成。
> 可复用于任何为单一本地用户设计、但也希望能够被托管给其他人的应用。

## 关于名称

在英文中，这一模式称为 **piggyback**——“搭乘他人的基础设施”在那里已经是它的专业术语。因此，本 Skill 中的英文正文使用 *piggyback*；**“huckepack”是德语工作标题**，即构建该模式时所用的名称，同时也是本 Skill 迁移自的代码仓库名称。**字面的模式值仍为 `huckepack-gift` 和 `huckepack-only-host`**——它们是随代码和配置一同发布的内容，无论周围正文使用何种语言，都保持这样书写。

## 问题

应用在本地构建：一个数据库、一个 API 密钥、存在于进程中的状态。在自己的机器上，这完全正确。一旦有人把它托管给其他人，这三个假设中的每一个都会变成缺陷——每位访问者共享同一份状态、同一个数据库、同一个密钥。打开页面的人会看到所有其他人的数据。

常见的解决方案是用户管理：账户、登录、访问权限检查、删除期限、隐私声明、数据处理协议。这往往比应用本身更庞大。

## 思路

**访问者把一切保留在自己的设备上。主机什么都不保留。**

这并没有解决用户管理问题——而是让它**失去了必要性**。当服务器上不存在他人数据时，就无需在访问者之间做隔离，无需按计划删除，隐私声明也会缩减为服务实际所做的事情。

## 三种模式

| 模式 | API 密钥 | 数据 | 用户管理 |
|---|---|---|---|
| **`huckepack-gift`** | 由主机提供 | 在访问者的设备上 | 无 |
| **`huckepack-only-host`** | 由访问者提供 | 在访问者的设备上 | 无 |
| **`pay-membership`** | 主机的，计费 | 服务器 | 需要 |

- **`huckepack-gift`**——主机提供自己的密钥并免费提供运行。一种让人轻松试用该工具的邀请方式。
- **`huckepack-only-host`**——访问者自带密钥。主机不付费，也不存储任何内容。
- **`pay-membership`**——有意保留为占位实现。此处又需要前两者所要避免的一切——账户、计费、服务器端存储。这是一项独立的工作，而不是可以切换的开关。

始终存在一个 **`local`** 默认值：不做任何配置的人，获得的应用与之前在自己机器上运行时完全一致。

## 构建模块

| 模块 | 用途 |
|---|---|
| 安装时设置的模式 | 部署的属性，而非会话的属性 |
| 可替换的存储层 | 同一数据库，不同的存放位置 |
| 浏览器中的 SQLite（WASM + OPFS） | 相同的架构、相同的查询，不同的执行位置 |
| 掩码的密钥字段 | 仅在 `only-host` 模式下出现，从不记录日志 |
| 导出与导入 | **并非可选**——浏览器数据是易失的 |
| 以可下载文件形式提供的凭证，可选目标文件夹 | 交付过程中不涉及服务器 |

真正的工程工作在于让存储层可替换：应用无论如何都写入 SQLite，但中间层决定这些写入是落在服务器上，还是访问者的浏览器中（`sql.js` / 官方 SQLite-WASM 构建，通过 Origin Private File System 持久化）。如果 WASM 太重，则按重量对浏览器存储选项排序：SQLite-WASM + OPFS（真正的数据库，容量最大）> IndexedDB（结构化，有自己的查询模型）> `localStorage`（仅适合语言和主题等小数据）。

## 本模式不解决的问题——坦率说明

- **浏览器数据一旦被删除，一切就都没了。** 服务器端没有副本。因此导出是必需条件，而不是锦上添花。
- **更换设备时**，若不先导出再导入，数据无法迁移。
- **存在于浏览器中的密钥**（`only-host`）比服务器上的密钥受保护程度低。但它属于访问者，而替代方案是把它交给主机——这显然不是更安全的选择。
- **执行仍然经由主机进行。** 对于需要联系第三方的服务（例如打电话），无论访问者自己的记录存放在哪里，主机都会处理该第三方的数据。这并不会使隐私声明变得多余，只是使其变得简短。

## 法律审查结果

一份法律初步评估（`references/RECHT.md`，德语——它检查的是德国和欧盟法规，因此翻译后的引用会更不精确，而不会更易于理解）将该模式与 DSGVO、TDDDG 和 UWG 进行了核对。**这是附出处的初步评估，不构成法律建议。** 三项发现，每项一行：

- **即使主机不存储任何内容，它仍是控制者（Verantwortlicher）。** 《通用数据保护条例》第 4(7) 条将责任与决定目的和手段挂钩，而非与存储挂钩；欧盟法院已明确这样表述（C-683/21）。变得多余的是**用户管理**，而不是责任。
- **对于被联系的人，负担并未减轻。** 第 14 条下的告知义务、有文件记录的法律依据权衡、与执行联系操作的服务之间的数据处理协议——这些通常是隐私声明中最长的部分，而该模式并未触及它们。
- **家庭例外对访问者有利，对主机无益。** 它涵盖自然人的纯个人使用；提供给他人的服务并非纯个人活动。恰恰在这里，piggyback 托管开始了。

其收益在于**义务的范围和攻击面的大小**，而非其性质——这也是对该模式更为诚实的表述。

## 如何应用该模式

1. 阅读 `references/DATA-FLOW-TEMPLATE.md`，并针对实际应用、基于证据填写（每一行都需要一个 `file:line` 或“未找到”）。这能准确揭示，在多访问者托管下，哪些本地假设会失效，且是在修改代码之前。
2. 决定应用真正需要哪些模式——`local` 始终是默认值；`huckepack-gift` 和 `huckepack-only-host` 是两种避免用户管理的模式；在没有真正需要账户的具体理由之前，`pay-membership` 保持为占位实现。
3. 使存储层可替换（上文所述的核心步骤），为 `only-host` 添加掩码的密钥字段，并在发布任何内容之前接通导出/导入——这是易失浏览器存储的安全网。
4. 为具体部署填写 `references/PRIVACY-TEMPLATE.md`；删除不适用的部分，将每个提供商声明与当前合同核对，并在处理真实数据之前征求针对具体案情的法律审查。该模板是起点，而非成品声明。
5. 对于任何涉及真实第三方的安装（电话呼叫、发送给未自行注册之人的消息），或涉及研究参与者的安装，应将 `references/RECHT.md` 中的建议视为检查清单而非许可——在首次公开运行之前，请咨询律师。

## 参考资料

- `references/DATA-FLOW-TEMPLATE.md`——数据流计划的模板与流程：每一行都需要 file:line，否则只是猜测，而非发现。
- `references/PRIVACY-TEMPLATE.md`——针对 piggyback 安装、带有标记占位符的示范隐私声明。
- `references/RECHT.md`——德语法律初步评估，附 DSGVO、TDDDG 和 UWG 出处。

两份模板都是**范例，不构成法律建议**。托管应用的人需对其进行调整，并对结果负责。
