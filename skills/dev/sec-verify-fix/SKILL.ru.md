# sec-verify-fix - закрывает ли патч брешь?

Фаза «verify-fix». Контракт: `sec-scan/references/contract.md` (жизненный цикл §2, правило 7 в §6). Требуется находка со статусом `fixed` и `fix.patchFile`.

## Сначала независимость

Ревьюер - **не** автор патча (правило 7): предпочтительно другой провайдер (Claude <-> Codex), иначе независимый субагент высшего уровня со свежим контекстом, получающий только находку, патч и код - но не рассуждения автора. Если всё же приходится проверять самому, указать это в результате; тогда `verifiedBy` остаётся пустым, а статус остаётся `fixed`.

## Процедура

1. **Применить патч во временной копии** (никогда в оригинале); проверить блокировку, как в `sec-fix` (правило 2). Если патч не применяется чисто, это уже и есть результат.
2. **Заново проследить путь:** построчно пройти исходный путь source-to-sink из `evidence` на исправленном состоянии. Достижим ли sink по-прежнему? Есть ли параллельные пути (другие вызывающие, варианты входа, другие кодировки), которых патч не покрывает?
3. **Негативный тест:** минимальный, не превращённый в оружие вход, который раньше вызвал бы находку, теперь должен отклоняться или нейтрализоваться. Только во временной копии, только собственный код (правило 1). Если тест нельзя осмысленно выполнить, сообщить как «not tested».
4. **Регрессионный тест:** тесты проекта до/после; легитимные входы по-прежнему работают. Назвать красные или не запущенные тесты.
5. **Оценить риск регрессии:** затронутые пути выполнения и вызывающий код, изменённые контракты (сигнатуры, форматы, поведение при ошибках), тестовое покрытие места, обратимость (чисто кодовый патч против миграции данных/конфигурации). Уровень low/medium/high с обоснованием.
6. **Автоматическое слияние?** да/нет с обоснованием. **По умолчанию нет для critical/high**; да - только если путь закрыт, негативный и регрессионный тесты зелёные, риск низкий, а откат прост. Ревьюер никогда не решает в одиночку; правила слияния репозитория имеют приоритет.

## Результат

- **Закрывает:** да / частично / нет, с указанием конкретного места, остающегося открытым. При «нет»/«частично» статус остаётся `fixed`, и работа возвращается в `sec-fix`; находка не снимается.
- **При «да»:** `status: verified`, `fix.verifiedBy: "<provider>/<model>"` и `python scripts/secfind.py validate findings.json coverage.json` (скрипт в `sec-scan`). Обоснование, уровень риска и рекомендация по слиянию идут в отчёт для пользователя; в контракте для них нет поля, поэтому не выдумывать его.
- Ничего не применяет, не коммитит и не отправляет push (правило 3).
