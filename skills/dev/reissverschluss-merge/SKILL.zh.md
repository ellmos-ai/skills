# 拉链式合并(zipper merge)

## 何时使用此方法

同一仓库的两个分支**严重分歧**,且**双方都有价值**——
典型情况:`main` 与 `master` 经过并行维护后产生差异,一个旧 PR 对比已经向前推进的目标分支,或两个各自带有修复的智能体/团队版本。
普通合并要么会覆盖某一方("ours"/"theirs"),要么产生一团无法理清的冲突。拉链式方法通过让两侧的"齿"**逐节交错咬合**来解决这一问题:每节由经证明更好的版本胜出——或采用有理由的混合方案。

在琐碎的冲突中**不需要**此方法(一方明显过时、冲突块很少):此时直接正常合并即可。当需要针对多个文件/章节认真权衡时,该方法才值得使用。

## 阶段 0 — 全局概览与基准选择

1. **完整查看双方内容**(不仅仅是冲突标记):
   `git log --oneline A..B` 与 `B..A`、`git diff A...B --stat`,然后阅读双方版本中存在差异的文件。
2. **依据现实而非日期选择基准。** 基准应是与**已发布现实**相符的分支:注册表状态(npm/PyPI/…)、已部署版本、通过的 CI、发布标签。日期较新但与外部世界不符的分支只是素材,而不是基准。
3. **检查双方的一致性**——常见情况是双方内部都不一致(例如基准有版本 X 却没有对应的变更日志,另一方维护了变更日志却在版本号上落后)。这类发现应列入表格,而不是被忽略。

## 阶段 1 — 决策表(核心)

对每个存在分歧的章节(文件、块、字段——粒度足够细即可),写一行:

| 章节 | 取用 | 理由 |
|---|---|---|
| `package.json` → version | 基准 | 与注册表一致 |
| `overrides` 块 | 另一方 | 包含基准缺少的安全升级 |
| ↳ 其中的条目 `X` | **混合** | 采用另一方的条目,但将其提升到基准的较新版本 |
| 变更日志 `[Unreleased]` | **混合** | 合并两个块,去除重复项 |

规则:

- **依据事实,而非猜测。** 每个"理由"单元格都应基于可验证的内容:注册表查询、测试运行、安全公告数据库、对有争议文件的隔离试装。凭猜测合并,就是把猜测合并进去。
- **"混合"是合法的结论**——拉链允许在同一章节内让两侧的齿都咬合。
- **舍弃也是合法的结论**——两侧都站不住脚的内容(失效的徽章、只完成一半的功能)应当删除。中间状态("功能只引入了一半")是最糟糕的选择:要么完整保留,要么完整移除。
- 完成的表格是实施的**契约文档**——会话切换或交接时,凭它就能机械地继续工作。

## 阶段 2 — 实施:分节提交,最后推送

1. 在基准上开始一次真正的合并:`git merge <gegenseite>`(刻意**不**使用 `-X ours/theirs`——冲突需要保持可见)。
2. 严格依照表格**逐节**解决冲突。
3. **每个逻辑章节一个提交**(或者如果只有一个合并提交,则在提交信息中为每个章节记录一个已文档化的解决步骤)。每条提交信息都应写明表格中的结论(例如"overrides: 采用另一方 + 将 vitest 提升到基准状态")。这样每一个拉链"齿"都可以被单独追溯和回滚。
4. **实施后进行测试**(测试套件、构建、可安装性)——全部通过后再继续。
5. **最后才推送**——在此过程中本地历史可以重写,远程只看到最终结果。
6. **在不删除的前提下关闭分歧**:将落败的分支通过快进(fast-forward)指向结果(`git checkout <gegenseite> &&
   git merge --ff-only <basis>`)。此后两个名称指向同一状态,历史不会丢失。

## 升级路径——重建而非合并(最后手段)

当拉链式方法不再奏效时,**不合并,而是重建**:提炼分支/PR 的**意图/功能**(它想达成什么——而非如何实现),并在当前状态上重新实现。旧分支/PR 随后附上指向重建版本的说明后关闭。

升级的触发条件(满足其一即可):

- 另一方**已证实有缺陷**(例如从未能安装、构建始终失败)——那么原本就没有可以合并的可用状态。
- 冲突量远大于实质内容:改动很小,却被夹杂的重命名/格式化波动撕裂到数百行。
- 历史已被污染(例如双方对**不同**内容使用了相同的版本号)——合并会把这种错误一并继承。
- PR 太旧,其上下文(API、结构)已经不复存在。

操作步骤:用 2–5 句话记录意图(来自 PR 描述、提交记录、差异实质)→ 在当前状态上重新实现 → 测试 → 在旧 PR/分支中记录**哪些内容被采纳、哪些被有意放弃**,然后关闭。在提交或 PR 文本中注明这一想法的来源。

## 常见陷阱(来自最初的会话,代价不小)

- **重复的 `[Unreleased]` 变更日志块**是并行维护分支时最常见的热点——应始终合并,绝不要悄悄丢弃其中一个。
- **双方对不同内容分配了相同的版本号:**合并前先确定注册表认可哪个编号;另一方在合并后的变更日志中应获得一条更正说明。
- **合并是一次审计机会:**逐节阅读时,会发现两个分支都没注意到的问题(未关闭的安全公告、失效链接、不一致的版本锁定)。这些发现应带入,但作为独立提交处理——不要与拉链式决策混在一起。
- **"因为更新而采用":**日期不是理由。每一次采用都需要可验证的依据。
- **强制推送的本能反应:**此方法无需强制推送(合并 + 快进)。如果感觉必须强制推送,通常说明基准选择有误。

## 危险信号

| 想法 | 事实 |
|---|---|
| "我直接取较新的那一方" | 日期不等于质量。先建立表格。 |
| "冲突我一次性全部解决" | 一个汇总提交会让每个单独决策都无法再修订。 |
| "先推送一下没关系" | 远程上的半成品拉链会让每个读者都感到困惑。只在最后推送。 |
| "合并总能想办法完成" | 当另一方有缺陷或历史已被污染时,重建更诚实也更快。 |
| "表格太繁琐了" | 没有表格,处理到第三个文件时就会忘记第一节为何那样决定。 |
