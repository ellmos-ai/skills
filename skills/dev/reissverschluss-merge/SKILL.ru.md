# Merge по принципу застёжки-молнии (zipper merge)

## Когда применять этот метод

Две ветки одного репозитория **сильно разошлись** и **обе содержат ценность** —
типично: `main` против `master` после параллельной поддержки, старый PR против
ушедшей вперёд целевой ветки, два состояния агентов/команд с собственными исправлениями.
Обычный merge либо затрёт одну сторону («ours»/«theirs»), либо создаст неразбираемую
кашу конфликтов. Метод «застёжки-молнии» решает это, позволяя зубцам обеих сторон
**входить друг в друга поразделно**: в каждом разделе побеждает доказуемо лучшая
версия — или обоснованное смешение.

**Не нужен** при тривиальных конфликтах (одна сторона очевидно устарела,
мало hunks): тогда обычный merge. Метод окупается, когда для нескольких файлов/разделов
нужно всерьёз взвешивать варианты.

## Фаза 0 — Обзор ситуации и выбор основы

1. **Полностью просмотреть обе стороны** (не только маркеры конфликтов):
   `git log --oneline A..B` и `B..A`, `git diff A...B --stat`, затем прочитать расходящиеся файлы
   обеих версий.
2. **Выбрать основу — по реальности, а не по дате.** Основой становится ветка,
   которая совпадает с **опубликованным состоянием**: состояние реестра (npm/PyPI/…),
   развёрнутая версия, зелёный CI, теги релизов. Ветка с более новой датой,
   но без соответствия внешнему миру, — это материал, а не основа.
3. **Проверить согласованность обеих сторон** — часто ОБЕ внутренне несогласованны
   (например, у основы версия X без подходящего changelog, у другой стороны
   changelog ведётся, но версия отстаёт). Такие находки относятся в таблицу,
   а не замалчиваются.

## Фаза 1 — Таблица решений (ядро метода)

Для каждого расходящегося раздела (файл, блок, поле — настолько мелко, насколько нужно)
одна строка:

| Раздел | Беру | Почему |
|---|---|---|
| `package.json` → version | Основа | совпадает с реестром |
| Блок `overrides` | Другая сторона | содержит обновления безопасности, которых нет в основе |
| ↳ в нём запись `X` | **смешать** | взять запись другой стороны, но поднять до более новой версии основы |
| Changelog `[Unreleased]` | **смешать** | объединить оба блока, убрать дубликаты |

Правила:

- **Факты, а не предположения.** Каждая ячейка «Почему» опирается на что-то
  проверяемое: запрос к реестру, прогон тестов, база уязвимостей, изолированная
  пробная установка спорного файла. Кто гадает, тот сливает предположения.
- **«Смешать» — законное решение**: застёжка может сцепить оба зубца внутри одного раздела.
- **Отбросить — тоже законное решение**: то, что не держится ни на одной стороне
  (мёртвый бейдж, наполовину внедрённая функция), удаляется. Промежуточное состояние
  («функция наполовину внутри») — худший вариант: либо полностью внутри, либо полностью снаружи.
- Готовая таблица — это **договорный документ** реализации: при смене сессии или
  передаче достаточно её, чтобы продолжить механически.

## Фаза 2 — Реализация: фиксация по разделам, отправка в конце

1. На основе начать настоящий merge: `git merge <gegenseite>`
   (намеренно НЕ `-X ours/theirs` — конфликты должны быть видимы).
2. Разрешать конфликты **поразделно** строго по таблице.
3. **Один commit на логический раздел** (либо при одном merge-commit: один
   задокументированный шаг решения на раздел в сообщении commit). В каждом сообщении
   commit указывается вердикт таблицы («overrides: другая сторона + vitest на
   уровень основы»). Так каждый зубец застёжки остаётся отдельно прослеживаемым
   и откатываемым.
4. **Тесты после реализации** (набор тестов, сборка, устанавливаемость) — сначала
   зелёные, потом дальше.
5. **Отправлять только в конце** — локальная история может перестраиваться во время
   метода, удалённый репозиторий видит только готовый результат.
6. **Закрыть расхождение без удаления:** уступившую ветку перевести fast-forward
   на результат (`git checkout <gegenseite> &&
   git merge --ff-only <basis>`). После этого оба имени указывают на одно состояние;
   история не теряется.

## Путь эскалации — пересборка вместо merge (последний уровень)

Если застёжка больше не срабатывает, **не выполняется merge, а происходит пересборка**:
выделяется **намерение/функциональность** ветки/PR
(ЧТО он должен был достичь — а не КАК) и реализуется заново на текущем состоянии.
Старый branch/PR закрывается со ссылкой на пересборку.

Триггеры эскалации (достаточно одного):

- Другая сторона **доказуемо неисправна** (например, никогда не устанавливалась,
  сборка падает) — тогда рабочего состояния для merge никогда не было.
- Объём конфликтов ≫ содержания: изменение небольшое, но размазано по сотням
  сдвинутых строк (волны переименований/форматирования между ними).
- История отравлена (например, один и тот же номер версии на обеих сторонах для
  **разного** содержимого — merge унаследовал бы ложь).
- PR настолько стар, что его контекст (API, структура) больше не существует.

Порядок действий: зафиксировать намерение в 2–5 предложениях (из описания PR, commits,
сути diff) → заново реализовать на текущем состоянии → тесты → в старом
PR/branch задокументировать, ЧТО перенесено и ЧТО намеренно нет, затем закрыть.
Указать авторство идеи в тексте commit/PR.

## Подводные камни (из исходной сессии, усвоенные дорогой ценой)

- **Дублированный блок changelog `[Unreleased]`** — самая частая проблемная точка (хотспот)
  при параллельно ведущихся ветках: всегда объединять, никогда молча не отбрасывать ни один.
- **Обе стороны присваивают один номер версии разному содержимому:** до merge выяснить,
  какой номер знает реестр; другая сторона в объединённом changelog получает исправление.
- **Merge — повод для аудита:** при поразделном чтении замечаются вещи, которых не видела
  ни одна из веток (открытые advisories, мёртвые ссылки, несогласованные pins).
  Находки зафиксировать, но отдельными commits — не смешивать с решениями застёжки.
- **Перенос «потому что новее»:** дата — не аргумент. Каждый перенос требует
  проверяемого основания.
- **Рефлекс force-push:** метод обходится без force-push (merge + fast-forward).
  Если force кажется необходимым, обычно неверно выбрана основа.

## Красные флаги

| Мысль | Реальность |
|---|---|
| «Просто возьму более новую сторону» | Дата ≠ качество. Построить таблицу. |
| «Конфликты решу разом» | Один общий commit делает каждое отдельное решение невозможным пересмотреть или откатить по отдельности. |
| «Пушну пока промежуточно» | Полуготовые застёжки на удалённом репозитории сбивают с толку каждого читателя. Push — только в конце. |
| «Merge всегда как-нибудь выходит» | При неисправной другой стороне или отравленной истории пересборка честнее и быстрее. |
| «Таблица — перебор» | Без таблицы после третьего файла забывается, почему раздел 1 решён именно так. |
