# ジッパー式マージ（zipper merge）

## この手法を使う場面

同じリポジトリの二つのブランチが**大きく分岐**しており、**どちらにも価値がある**場合です。
典型例は、並行して保守された後の `main` と `master`、先へ進んだ対象ブランチに対して残っている古いPR、それぞれ独自の修正を持つ二つのエージェント／チームの状態です。
通常のマージでは、一方を丸ごと潰す（「ours」／「theirs」）か、解きほぐせないコンフリクトの山になります。ジッパー方式は、両側の歯を**セクションごとにかみ合わせる**ことでこれを解決します。
各セクションでは、確実に良いと示せるバージョンが採用されるか、理由のある組み合わせが採られます。

**トリビアルなコンフリクトでは不要です**（一方が明らかに古い、ハンクが少ない場合）。その場合は通常どおりマージします。この手法が役立つのは、複数のファイルやセクションについて本気で比較検討する必要が出てきたときです。

## フェーズ0: 全体把握と基準の選択

1. **両側を完全に確認する**（コンフリクトマーカーだけでなく）。
   `git log --oneline A..B` と `B..A`、`git diff A...B --stat` を確認し、その後で両バージョンの分岐したファイルを読みます。
2. **基準は日付ではなく実態で選ぶ。** 基準となるのは、**公開されている実態**と一致するブランチです。具体的には、レジストリの状態（npm/PyPI/…）、デプロイされたバージョン、緑のCI、リリースタグです。日付が新しくても外部と一致しないブランチは、基準ではなく材料として扱います。
3. **両側の整合性を確認する。** 両方が自己矛盾していることがよくあります（例: 基準側はバージョン X を持つのに対応する変更履歴がない、相手側は変更履歴を保守しているがバージョンが遅れている）。このような発見は表に載せるべきで、見過ごしてはいけません。

## フェーズ1: 判断表（中核）

分岐した各セクション（ファイル、ブロック、フィールド。必要な細かさで）について、1行を書きます。

| セクション | 採用 | 理由 |
|---|---|---|
| `package.json` → version | 基準 | レジストリと一致する |
| `overrides`-ブロック | 相手側 | 基準にないセキュリティ更新を含む |
| ↳ その中の項目 `X` | **混合** | 相手側の項目を取り込むが、基準の新しいバージョンに合わせて引き上げる |
| 変更履歴 `[Unreleased]` | **混合** | 両方のブロックを統合し、重複を削除する |

ルール:

- **推測ではなく事実に基づく。** 「理由」の各セルは、レジストリの照会、テスト実行、アドバイザリデータベース、問題のファイルを隔離した試験インストールなど、検証可能なものに基づく必要があります。推測でマージしてはいけません。
- **「混合」は正当な判定です。** ジッパーは、一つのセクションの中で両方の歯をかみ合わせてよいのです。
- **「破棄」も正当な判定です。** どちらの側でも支えられないもの（機能しないバッジ、中途半端に導入された機能）は取り除きます。中間状態（「機能は半分だけ入っている」）が最悪の選択肢です。完全に取り込むか、完全に取り除くかのどちらかにしてください。
- 完成した表が実装の**契約文書**になります。セッションを切り替えたり引き継いだりするときも、この表があれば機械的に作業を続けられます。

## フェーズ2: 実装 — セクションごとにコミットし、最後にプッシュする

1. 基準上で本物のマージを開始します: `git merge <gegenseite>`（あえて `-X ours/theirs` は使わない。コンフリクトは意図的に見えるようにしておく）。
2. コンフリクトを**セクションごとに**、表どおりに正確に解決します。
3. **論理セクションごとに一つのコミット**を作ります（単一のマージコミットにまとめる場合は、コミットメッセージの中でセクションごとに解決手順を記録します）。
   各コミットメッセージには表の判定を書きます（「overrides: 相手側 + vitest を基準の状態に引き上げ」など）。こうすることで、ジッパーの一つ一つの歯を個別に追跡でき、個別に元に戻せます。
4. **実装後にテストを実行します**（テストスイート、ビルド、インストール可能性）。緑になってから先へ進みます。
5. **プッシュは最後だけ。** 手順の途中ではローカルの履歴を作り直してもかまいませんが、リモートに見えるのは完成した結果だけにします。
6. **削除せずに分岐を解消する。** 劣る側のブランチを、ファストフォワードで結果に合わせます（`git checkout <gegenseite> &&
   git merge --ff-only <basis>`）。その後は両方の名前が同じ状態を指し、履歴は失われません。

## エスカレーション経路 — マージではなく再構築（最終段階）

ジッパーがもはや機能しない場合は、**マージせず、作り直します**。ブランチやPRの**意図や機能**（何を達成しようとしていたか。どのように実装したかではない）を抽出し、現在の状態の上で新たに実装し直します。古いブランチやPRは、再構築への参照を付けてクローズします。

エスカレーションの引き金（一つで十分）:

- 相手側が**確実に壊れている**（例: 一度もインストールできなかった、ビルドが失敗する）。その場合、マージすべき動作する状態は一度も存在していません。
- コンフリクトの量が内容に比べて過大である。変更は小さいのに、移動された数百行に広がっている（間にリネームやフォーマットの波がある）。
- 履歴が汚染されている（例: 同じバージョン番号を、**異なる**内容に両側で割り当てている）。マージすると、その偽りを引き継いでしまいます。
- PRが古すぎて、その文脈（API、構造）がもう存在しない。

手順: 意図を2〜5文で書き留める（PRの説明、コミット、差分の実質から）→ 現在の状態の上で新たに実装する → テスト → 古いPR／ブランチに、何を取り込み、何を意図的に取り込まなかったかを記録する → クローズする。アイデアの作成者は、コミットやPRの文面で明記します。

## 落とし穴（元のセッションから得た、高くついた教訓）

- **重複した `[Unreleased]` の変更履歴ブロック**は、並行して保守されたブランチで最もよく起きるホットスポットです。必ず統合し、どれか一つを黙って捨てないでください。
- **両側が異なる内容に同じバージョン番号を割り当てている**場合: マージ前に、どちらの番号をレジストリが把握しているかを確認します。もう一方の側には、統合された変更履歴の中で修正を入れてもらいます。
- **マージは監査の機会でもあります。** セクションごとに読んでいると、どちらのブランチも気づいていなかった問題（未解決のアドバイザリ、壊れたリンク、整合しないピン留め）が見つかります。見つかったものは持ち帰りますが、独立したコミットにしてください。ジッパーの判断とは混ぜないでください。
- **「新しいから」という取り込み:** 日付は理由になりません。どの取り込みにも、検証可能な根拠が必要です。
- **フォースプッシュの反射:** この手法はフォースプッシュなしで進みます（マージ + ファストフォワード）。フォースが必要に思えるなら、たいてい基準の選択が誤っています。

## レッドフラグ

| 考え | 現実 |
|---|---|
| 「新しい方をそのまま採用すればいい」 | 日付は品質ではない。表を作る。 |
| 「コンフリクトは一気に解決する」 | まとめて一つのコミットにすると、個々の判断を後から見直せなくなる。 |
| 「途中で一度プッシュしておこう」 | 途中のジッパーがリモートにあると、読む人全員が混乱する。プッシュは最後だけ。 |
| 「マージはなんとかなるものだ」 | 相手側が壊れている、または履歴が汚染されている場合は、再構築の方が正直で速い。 |
| 「表は大げさだ」 | 表がなければ、三つ目のファイルのころには、なぜセクション1をそう判断したか忘れてしまう。 |
