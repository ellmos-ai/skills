# Surface After Care — جولة الصيانة الدورية لمستودع منشور

## متى تنطبق هذه المهارة

استخدمها لمستودع **عام بالفعل** ويجب مراجعته بشكل دوري. وهي المرحلة الاقتصادية: كل ما يمكن البت فيه على مستوى المستودع نفسه دون جرد مستودعات أخرى أو طلب رأي قانوني.

الفرق عن المهارات المجاورة:

| الوضع | المهارة |
|---|---|
| يُنشر المستودع للمرة الأولى | `github-repo-care` |
| المستودع عام، وجولة صيانة دورية | **هذه المهارة** |
| إضافة إلى فحص قانوني + مراجع متقاطعة عبر كل المنظمات + توطين التطبيق | `full-after-care` (الاسم البديل `deep-after-care`) |
| فحص قانوني/خصوصية/ترخيص بحت قبل جعل المستودع عامًا | `repo-publish-check` |
| إبقاء النسخ اللغوية متزامنة في المحتوى | `bilingual-doc-sync` |
| توزيع هذه الجولة على مستودعات كثيرة بالتناوب العادل | `rotation-check` |

## الفكرة الأساسية

يتباعد المستودع المنشور في اتجاهين: **تصف الوثائق برمجية أقدم من تلك الموجودة في المستودع**، و**تتراكم ملفات لم تُعدّ أبدًا للعين الخارجية**. كلاهما نادرًا ما يكون درامياً، لكنهما يكلفان بالضبط المستخدمين الذين تريد كسبهم — أحدهم يغادر لأن دليل التثبيت لم يعد مطابقًا، والآخر لأنه يصادف في الجذر `AUFGABEN.txt` و`Plan.txt` فيظن أن أحدًا يعمل هنا لنفسه فقط.

تعالج هذه الجولة الأمرين. وهي مصممة عمدًا لتكون قابلة للتكرار: نصف ساعة أربع مرات في السنة أفضل من تنظيف شامل مرة واحدة.

## التسلسل

الترتيب ليس اعتباطيًا. الخطوة 0 في البداية لأنها تحدد نطاق كل ما يليها. الخطوة 2 تسبق كل ما يدفع تغييرات — وإلا فستؤجل التحسينات خلف حالة ما تزال تحتاج إلى تنظيف. والخطوة 1 تعمل من جهة الخادم فقط ولا تعيق شيئًا.

### 0. حصر أسطح التوزيع

**قبل تغيير أي شيء: حدد أين يوجد هذا المشروع.** مستودع GitHub نادرًا ما يكون السطح الوحيد. لا يفيد تصحيح README إذا ظلت صفحة حزمة npm تعرض النسخة القديمة بتعليمات التثبيت الخاطئة — وهناك تحديدًا يصل معظم المستخدمين، لأن سجلات الحزم كثيرًا ما تحتل مرتبة أعلى في محركات البحث من المستودع.

```bash
# Manifeste verraten die Kanäle
cat package.json pyproject.toml setup.py Cargo.toml 2>/dev/null | rg -n "name|version|keywords|repository|homepage"
rg -n "npmjs.com|pypi.org|marketplace|registry|crates.io|hub.docker|zenodo|doi" README* docs/ .github/ 2>/dev/null

# Veröffentlichten Stand der Kanäle abfragen (nur was zutrifft)
npm view <paket> version description keywords 2>/dev/null
pip index versions <paket> 2>/dev/null
gh release list --repo ORG/REPO --limit 5
```

الأسطح المعتادة: npm وPyPI وCrates وDocker Hub وسجل MCP ودلائل الإضافات/المهارات وأسواق VS Code أو المتصفح ومتاجر التطبيقات وZenodo/DOI والموقع الخاص بالمشروع وصفحة المنظمة و`llms.txt` والمستودعات المرآة على مضيفين آخرين.

دوّن القائمة التي وجدتها في سجل التشغيل. ستصبح من الآن **المجموعة المستهدفة**: كل تغيير في الخطوات التالية يُعكس في النهاية على هذه القائمة (انظر "التكافؤ عبر كل الأسطح"). وإذا وجدت سطحًا لا يعتني به أحد ويشير إلى حالة ميتة، فهذا نتيجة مستقلة — إما تحديثه أو سحبه عن قصد، لكن لا تتركه كما هو.

### 1. تعيين الوسوم

الوسوم هي أهم سطح بحث داخل GitHub وتكلف تقريبًا لا شيء.

```bash
gh repo view ORG/REPO --json nameWithOwner,description,repositoryTopics,homepageUrl,visibility
gh repo edit ORG/REPO --add-topic <topic> --add-topic <topic>
```

الهدف نحو 5 إلى 12 وسمًا من ثلاثة اتجاهات: **ما هو** (`cli` و`mcp-server` و`python-library`)، و**موضوعه** (`file-management` و`tax` و`note-taking`)، و**كيف يعمل** (`local-first` و`offline` و`privacy`). اعتمد على الوسوم المستخدمة فعلًا في مشاريع مشابهة — الوسوم المختلقة لا تجذب مستخدمين. راجع الوصف والصفحة الرئيسية في الوقت نفسه، فهما في المنظور ذاته.

للوسوم نظير على الأسطح الأخرى في الخطوة 0: `keywords` في `package.json`، و`keywords`/`classifiers` في `pyproject.toml`، والفئات والوسوم في الأسواق والمتاجر. حافظ على اتساقها في المحتوى — فهي القرار نفسه في أماكن متعددة.

### 2أ. بوابة الخصوصية — تعمل دائمًا

لا تُحذف هذه الخطوة أبدًا، حتى في جولة تبدو بريئة. البحث يكون في المجموعة **المتتبَّعة** لا في شجرة العمل المرئية، فهذا هو الفرق بين "يبدو نظيفًا" و"نظيف فعلًا".

```bash
git ls-files
rg -n "C:\\\\Us[e]rs\\\\|/home/[a-z]|s[k]-[A-Za-z0-9]{16}|gh[p]_|gh[o]_|AKIA[0-9A-Z]{16}|API[_-]?KEY|TO[K]EN|PASS[W]ORD|SEC[R]ET|BEGIN [A-Z ]*PRIVATE KEY" $(git ls-files)
rg -n "\x{C3}\x{83}|\x{C2}\x{A0}|\x{FFFD}" $(git ls-files -- '*.md' '*.txt' '*.json')
```

أضف إلى النمط أسماء **مجلداتك الداخلية** — مجلدات خطوط الإنتاج والمواضيع ومساحات العمل الخاصة:

```bash
rg -n "\.SOFTWARE|\.RESEARCH|_control-center|<weitere eigene Ordnernamen>" $(git ls-files)
```

هذه الإشارات ليست أسرارًا ولا تطلق إنذارًا، ولهذا تمر — لكنها بالنسبة للقراء **غير قابلة للحل** ("أُعيد نقلها من خط أنابيب .SOFTWARE" لا تعني شيئًا للغرباء) وتكشف بنية الجهة. يجب استبدالها أو إزالتها، لا التسامح معها. وبحث يقتصر على `C:\Users\…` وأنماط الرموز لن يجدها أبدًا.

وجدتَ شيئًا؟ عندها يحدد **نوع** الاكتشاف الإجراء — انظر قسم "قاعدة الدفع القسري". السر الذي دخل يومًا إلى المستودع أصبح محروقًا: إزالته من `HEAD` لا تكفي، بل يجب تدويره.

### 2ب. التحقق من نية نشر المستندات

جوهر هذه الجولة. راجع `.md` و`.txt` و`.json` المتتبَّعة، واسأل عن كل ملف: **هل كان موجّهًا يومًا للغرباء؟**

```bash
git ls-files -- '*.md' '*.txt' '*.json' | sort
```

لا تخمّن من اسم الملف — ألقِ نظرة سريعة على محتواه. قد يكون `PLAN.md` خارطة طريق عامة، وقد يكون `notes.md` الذي يبدو بريئًا استراتيجية تسعير داخلية. ثلاث فئات:

**ينتمي إلى المستودع** — README وLICENSE وCHANGELOG وSECURITY وCONTRIBUTING و`docs/` ومراجع API وأمثلة الإعدادات وخرائط الطريق الحقيقية والبيانات الوصفية للحزم (`package.json` و`pyproject.toml`) وملفات القفل وإعدادات CI.

**لا ينتمي إلى المستودع لكنه غير خطير** — الحالة المعتادة في هذه الجولة. ملفات المهام والتخطيط (`AUFGABEN.txt` و`Plan.txt` و`TODO-intern.md`)، وملاحظات الجلسات والتسليمات (`HANDOFF` و`BRIEFING` و`_handoff/`)، وملفات الحالة لخط الإنتاج الخاص، ويوميات التطوير، و`_archive/`، وملفات JSON للسجل والفهرسة التي تحمل مسارات محلية، والمسودات والنواتج المولّدة، وملفات عمل الوكلاء. هذه الملفات ليست خطيرة، لكنها تُحدث فوضى وانطباعًا بأن الموقع ورشة عمل غريبة. التعامل معها: أضف `.gitignore` و`git rm --cached <datei>` و**ادفع بشكل عادي تمامًا**.

**لا ينتمي إلى المستودع وهو حساس** — بيانات اعتماد، وبيانات شخصية، وبيانات عملاء، وحسابات داخلية، واستراتيجيات تسعير وتفاوض، وخطط عمل غير منشورة، ومسودات عقود، وكل ما له قيمة تنافسية. هنا لا يكفي الإيداع العادي، انظر قاعدة الدفع القسري.

عند `.json` يستحق الأمر نظرة ثانية: تبقى ملفات البيان وملفات القفل، لكن الإعدادات المحلية وملفات المهام والسجل وملفات التصدير وكل ما يحمل مسارات مطلقة أو أسماء مضيفين هي الركاب المختبئون المعتادون.

إذا أزلت ملفًا قد يبحث عنه أحد (كخارطة طريق مثلًا)، فاذكر في رسالة الإيداع أو في README أين أصبحت المعلومة — وإلا بدا الأمر تراجعًا.

### 3. اللافتات

اللافتة تحدد جزئيًا ما إذا كان أحد سيبدأ القراءة أصلًا. تحقق من وجودها ومن إدراجها في README كأول عنصر.

إذا لم تكن موجودة فهناك ثلاثة طرق — وهذا الترتيب مناسب:

1. **مولّد صور لدى أحد الوكلاء** (مثل agy؛ كلمة "generiere" (أو "ولّد" بالعربية) هناك هي المحفز لتوليد PNG فعلي)، عندما يكون الموضوع البصري أنسب من الطباعة.
2. **Codex**، عندما يجب أن تنشأ اللافتة من الشيفرة ويوجد نموذج أسلوب تستند إليه.
3. **بنفسك كـ SVG**، عندما تتكون اللافتة أساسًا من علامة كلمية وصياغة شكلية — وغالبًا هذا هو الخيار الأسرع والأسهل في التحكم، وSVG قابل للتعديل لاحقًا.

حافظ على عائلة التصميم إذا كان المشروع ينتمي إلى مجموعة: اللون الأساسي نفسه والجماليات نفسها ومعالجة العلامة الكلمية نفسها. اللافتة التي تخرج عن السرب تبدو أسوأ من عدم وجود لافتة. الحجم المعتاد 1200x300؛ كـ PNG داخل المستودع، وSVG كمصدر بجانبه.

### 4. مطابقة العبارات مع الحالة الفعلية

هنا تتولد أكبر قيمة. يقدم README ادعاءات — تحقق منها بدل تصديقها:

- **الإصدار** في README/الشارة مقابل `pyproject.toml`/`package.json`/`__version__` ومقابل آخر وسم إصدار. عند وجود عدة حاملات للإصدار تحقق من كلها، لا من واحدة فقط.
- **مسار التثبيت**: مرّره فعليًا ولو بالقراءة فقط — هل الحزمة موجودة تحت الاسم المذكور؟ هل الأوامر والخيارات صحيحة؟
- **قائمة الميزات** مقابل الشيفرة: هل كل ما هو مذكور موجود، وهل ينقص شيء جديد من القائمة؟
- **الأرقام** (عدد الأدوات، الصيغ المدعومة، تغطية الاختبارات) تُعاد عدّها من المصدر لا تُنسخ كما هي. الأرقام في README تتقادم بصمت.
- **لقطات الشاشة** مقابل الواجهة الحالية.
- **المتطلبات** (إصدار Python/Node، والاعتماديات) مقابل ملفات البيان.
- **الروابط** إلى المشاريع المجاورة والوثائق والسجلات: هل ما تزال تعمل؟

**التصحيح يسري على كل الأسطح، لا على السطح الذي لوحظ فيه فقط.** إذا ثبت خطأ عبارة جوهرية — خاصة إذا صححها صاحب الطلب — فالأرجح أن العبارة نفسها موجودة في مكان آخر: في صفحة المنظمة، وفي `llms.txt`، وفي النسخة اللغوية الثانية، وفي README لمشروع مجاور. ابحث عنها بقصد قبل أن تشطب النقطة:

```bash
gh search code "<prägnante Formulierung>" --owner ORG
```

وإلا فستصحح موضعًا وتترك ثلاثة، ولن يظهر التناقض إلا عند المستودع التالي. هذا لا يكلف وقتًا فحسب، بل يضر بالثقة في الوثائق: من يجد وصفين لأمر واحد لا يصدق أيًّا منهما.

بعد ذلك حسّن **العرض** حيث يكون ضعيفًا: القوائم الطويلة من الخيارات تصبح أسهل قراءة كجدول؛ وكتل الشيفرة تحتاج إلى وسوم اللغة؛ ونظرة على البنية أو التدفق أسرع كمخطط Mermaid أو شجرة ASCII منها في النثر؛ ويجب أن يُظهر الارتفاع الأول للشاشة الغرض والتثبيت ومثال استخدام، لا الشارات والتاريخ. إذا تجاوز README نحو 400 سطر فانقل التفاصيل إلى `docs/` واربط إليها.

**قاعدة اللغة لملفات README:** الافتراض هو **README إنجليزي** `README.md` مع **نسخة ألمانية ثانية**. الاستثناء: إذا كان مجال التطبيق نفسه ألمانيًا (القانون الألماني، أو الضرائب أو التمويل الألماني، أو جمهور ناطق بالألمانية) أو لم تكن هناك حتى الآن إلا نسخة ألمانية — عندها تبقى الألمانية اللغة الأساسية. ولكل لغة إضافية يتحدث بها المشروع بالفعل، يلزم ملف README خاص بها. التزم بالاتفاقية المستخدمة في المستودع فعلًا (`README_de.md` و`README.de.md` و`docs/README.de.md`) ولا تخترع اتفاقية ثانية بجانبها. اربط النسخ ببعضها في رأس الملف.

### 6. إنشاء اللغات القياسية الناقصة

أكمل ملفات README التي تفتقر إلى **اللغات القياسية**: الألمانية والإنجليزية والإسبانية والصينية المبسطة واليابانية والروسية. الغرض هو الوصول إلى أكبر عدد من الناس، لذلك ينطبق هذا خاصة على المشاريع الموجهة للمستخدمين النهائيين — فلمكتبة موجهة للمطورين بجمهور إنجليزي فقط لا تعود نسخة روسية بمكسب، بل مجرد عبء صيانة إضافي. قرّر عن وعي، ودوّن القرار في سجل التشغيل كي لا تعيد الجولة التالية النقاش فيه.

النسخ الجديدة تُملأ **ولا تُنشأ فارغة** — الهيكل الفارغ مع "TODO: translate" أسوأ من عدم وجود ملف، لأنه يوحي بالاكتمال. التوازي في المحتوى والمزامنة الرجعية تنظمها `bilingual-doc-sync`؛ وإذا كانت هناك أكثر من نسختين فيستحق الأمر الاستعانة بهذه المهارة للمزامنة.

### 7. الرؤية والترويج

فكّر في الإجراءات التي تجلب مستخدمين **لهذا** المشروع تحديدًا، ونفّذها:

- **السجلات** التي ينتمي إليها المشروع تقنيًا: سجلات الحزم (npm وPyPI)، وسجل MCP، ودلائل الإضافات/المهارات، والأسواق.
- **القوائم المنتقاة** (`awesome-*` والمجموعات الموضوعية) بشرط أن تتحقق معايير القبول فعلًا. طلب إدراج في قائمة لا يستوفي المشروع معاييرها يكلف السمعة.
- **أسطح خاصة بك**: صفحة المنظمة، و`llms.txt`، والموقع الخاص بالمشروع، وREADME الخاص بالنظام البيئي، وروابط من مستودعات ذات صلة.
- **ملاحظات الإصدار** كمناسبة: إصدار دون ذكر ما هو جديد لا يُلاحَظ.

**بوابة الموافقة:** كل ما يخرج إلى الخارج — طلبات السحب إلى مستودعات الآخرين، والإدراج في قوائم الغير، والمنشورات، والتقديمات — يُقترح و**لا يُنفَّذ إلا بعد موافقة صريحة**، ما لم تكن هناك موافقة دائمة لهذه القناة. التغييرات على أسطحك الخاصة لا تحتاج هذه البوابة. السبب بسيط: طلب سحب تم التراجع عنه إلى مستودع غريب يبقى مرئيًا علنًا ويرتد على المشروع.

### 11. الإيداع والدفع والتحقق

لا تنتهي الجولة بالتغييرات، بل بأن تصبح **منشورة فعلًا**. شجرة العمل المليئة بتحسينات غير مدفوعة هي أسوأ نتيجة: الجلسة التالية — ربما وكيل آخر أو جهاز آخر — يجب أن تتعلم حالة غريبة نصف منجزة، والأسطح العامة لم تتحسن شيئًا.

قبل الدفع تأكد مما يمكن التحقق منه: شغّل الاختبارات والفحوص الدخانية، وعند تغييرات الوثائق تحقق من الروابط ومن العرض المُصيَّر. ثم اجمع التغييرات في **إيداعات منفصلة موضوعيًا** بدلًا من إلقاء كل شيء في إيداع واحد — التنظيف وتحديث الوثائق والإصلاحات ثلاثة أشياء مختلفة، ومن يريد لاحقًا التراجع عن واحد منها سيشكرك:

```bash
git add .gitignore && git rm --cached <interne dateien>
git commit -m "chore: interne Arbeitsdateien aus dem Repo nehmen"
git commit -am "docs: README auf aktuellen Stand (Version, Toolzahl, Screenshots)"
git commit -am "fix: <Issue-Nummer> ..."

git pull --rebase        # bei divergiertem Branch, vor dem Push
git push
```

بعد ذلك تحقق بدلًا من الافتراض: README البعيد في العرض المُصيَّر، وتشغيل CI، وحالة الإصدار والوسم.

```bash
gh run list --repo ORG/REPO --limit 3
gh repo view ORG/REPO --json description,repositoryTopics,url
```

**إذا كان CI أحمر رغم أن إيداعك لم يمس إلا الوثائق**، فالسبب نادرًا ما يكون فيك. الحالة الأكثر شيوعًا بفارق كبير — وقد حدثت لدى هذه العائلة من المستودعات **ثلاث مرات** في يوم واحد — هي **أداة فحص (Linter) غير مثبتة الإصدار بلا مجموعة قواعد محددة**. تحقق من ذلك **أولًا**، قبل أن تشك في إيداعك بأي شكل.

الآلية: إذا شغّل سير العمل `ruff check` (أو flake8 أو eslint …) ضد اعتمادية غير مثبتة (`ruff>=0.12`، أو بلا إصدار إطلاقًا)، ولم يحدد اختيارًا صريحًا للقواعد (`[tool.ruff.lint] select = [...]`، أو في `ruff.toml` مستقل عند غياب `pyproject.toml`)، فإن الفحص يتبع الافتراضي لـ**النسخة المثبتة حديثًا**. إصدار جديد من الأداة يغيّر هذا الافتراضي، فتصبح شيفرة لم تتغير حمراء. المؤشرات الدالة:

- رموز قواعد لم يعرفها المشروع من قبل (`UP045` و`UP006` و`BLE001` و`RUF100` و`DTZ005` و`N999` …)، وقد تبلغ عدد المخالفات المئات.
- الكسر غالبًا **منقسم حسب المنصة**: المشغّلات ذات النسخة القديمة المخزّنة تبقى خضراء، والجديدة تحمر.
- أحيانًا تعترض قاعدة على شيء لا يمكن إصلاحه (`N999` اسم الحزمة نفسه) — علامة مؤكدة على أن القاعدة لم تكن أبدًا افتراضية.

الإصلاح: ثبّت مجموعة القواعد التي كانت خضراء سابقًا — `select = ["E4","E7","E9","F"]` هي القواعد الافتراضية الكلاسيكية لـ ruff. إذا لم يوجد `pyproject.toml` فأنشئ `ruff.toml`. تحقق مقابل **النسخة الجديدة** من الأداة نفسها (ثبّتها، وأعد إنتاج الملاحظات بلا إعداد، ثم تأكد من أن الإعداد يجعلها "ناجحة"). القواعد الجديدة تصبح **مهمة** في المشروع — تبنيها عن قصد قرار لا أثر جانبي لتحديث الأداة. وهذا نتيجة حقيقية متكررة: بدون التثبيت ينكسر CI مع الإصدار التالي للأداة، وفي **كل** مستودع مُعدّ بهذا الشكل.

حالتان لا يُدفع فيهما: عندما يطبق على المشروع حظر للنشر أو للتقديم، أو عندما يكون الوضع غير مكتمل صراحة. كلتاهما استثناءان يجب تعليلهما — والحالة المعتادة: إيداع ودفع.

عند حظر النشر لا تُلغى الجولة، بل **تُحوَّل**: أودِع محليًا على فرع خاص (`judging-hold/…`، `freeze/…`)، واترك الفرع الرئيسي دون مساس على الحالة المقدَّمة، وسجّل سبب الحظر في سجل التشغيل، وانقل التغييرات بعد رفعه. والمهم هنا الاتساق: المحظور ليس فقط `git push`، بل **كل تغيير مرئي عن بُعد** — الوسوم والوصف والصفحة الرئيسية والإصدارات وإجراءات المسائل وطلبات السحب تغيّر المشروع المنشور تمامًا كالدفع.

إذا كانت هناك نسخ أخرى من المستودع نفسه (جهاز ثانٍ، أو نسخة نشر، أو مرآة)، فحدّثها فور الدفع. نسخة متأخرة بعشرة إيداعات تُنتج تشخيصًا لحالة لم تعد موجودة عند البحث عن العطل التالي.

#### التغييرات في مستودعات أخرى — استثناء شجرة العمل المتسخة

تنتج هذه الجولة بانتظام تغييرات **خارج** المستودع المصون: سطر في الملف الشخصي للمنظمة (الخطوة 8)، ولاحقًا في الجولة العميقة إشارة عكسية في مستودع ذي صلة. تُودَع هذه التغييرات أيضًا وتُدفع — الإشارة العكسية غير المنشورة ليست إشارة عكسية.

قبل المس بمستودع غريب تحقق من حالته:

```bash
git -C <pfad> status --porcelain
```

**شجرة عمل نظيفة** ← نفّذ التغيير، وأودِعه في **إيداع خاص ومتماسك موضوعيًا** (`docs: link <projekt>`) وادفعه. لا تخلطه مع إيداعات المستودع المصون: إنه مستودع آخر بتاريخ آخر وقرّاء آخرين.

**متسخة، لكن التغييرات الغريبة في ملفات أخرى** ← يمكن تنفيذ تغييرك بنظافة. أضف للتحضير وأودِع **بمسار دقيق لملفك وحده**، حتى لا ينتقل عمل غريب غير مُراجَع معه:

```bash
git -C <pfad> add README.md
git -C <pfad> commit -m "docs: link <projekt>"     # nur der gestagte Pfad
```

لكن **لا تدفعه**. الإيداع محليًا غير ضار؛ أما الدفع فليس كذلك بالضرورة: لا تعرف إلى أين يتجه العمل الآخر المعلَّق — ربما يُعدَّل أو يُعاد تأسيسه (rebase) أو يُقطَّع بطريقة أخرى، وإيداعك يجبره على التعامل معه. الإيداع المحلي يحفظ عملك دون أن يفرض شيئًا على أحد؛ والجولة التي تعود لاحقًا إلى ذلك المستودع ستجده وتأخذه معها.

**متسخة في الملف نفسه الذي يجب تغييره** ← لا تلمسه. ستحتاج إلى البناء على حالة غريبة وسطية وتضمينها في إيداعك؛ وفهمها يكلف أكثر من قيمة هذه الإشارة الواحدة.

**قفل نشط (`LOCK*.txt`) في المستودع الهدف** ← **اقرأ القفل أولًا، لا تعامله كمنع شامل.** القفل يصف نطاقه، وهذا النطاق غالبًا أضيق من "كل شيء". حالات معتادة:

- **قفل تحرير** ("يعمل شخص ما هنا الآن") ← لا تلمس شيئًا، ولا حتى ملفًا جانبيًا.
- **قفل نشر/دفع فقط** (تقديم، أو تحكيم، أو تجميد) ← العمل المحلي يبقى مسموحًا، والاتصال البعيد فقط محظور. اعمل عندها على فرع خاص وأودِع محليًا؛ **الخطوات المؤثرة عن بُعد تسقط** — ليس الدفع وحده، بل الوسوم والوصف والصفحة الرئيسية والإصدارات وإجراءات المسائل وطلبات السحب، لأنها كلها تغيّر المشروع المنشور.

قراءة قفل يمنع الدفع فقط كمنع كامل تُضيّع الجزء المحلي كله من الجولة دون مكسب أمني. والعكس صحيح: لا يكفي الامتناع عن الدفع مع الاستمرار في تغيير البيانات الوصفية. عند الشك اقتبس القفل واسأل.

#### الرغبة لا يجب أن تضيع

إذا لم تُنفَّذ التغييرات لأحد هذه الأسباب، تنتقل إلى قائمة المهام في المستودع الهدف — `AUFGABEN.txt` أو `TODO.md` أو `TODO.txt`، حسب ما يوجد هناك. بند مع التاريخ والتغيير المطلوب والسبب:

```markdown
- [ ] [2026-07-24, after-care] Rückverweis auf <projekt> im README ergänzen
      (übersprungen: README hatte uncommittete Fremdänderungen)
```

هذا هو الفرق بين "مؤجَّل" و"منسيّ": قائمة المهام موجودة حيث ينظر المحرر التالي لهذا المستودع أصلًا — وهي أوثق من ملاحظة في سجل تشغيل شخص آخر. إذا لم توجد قائمة مهام فلا تنشئ واحدة؛ يكفي البند المفتوح في سجل تشغيلك.

عند **قفل نشط لا يُعفى حتى هذا** — فلا يُمس الملف، وتبقى الملاحظة في سجل تشغيلك. دوّن الملاحظة في الحالتين هناك أيضًا، كي تعرف الجولة التالية البند المفتوح.

أخيرًا، عالج الأسطح الواردة في الخطوة 0 — انظر القسم التالي.

## التكافؤ عبر كل أسطح التوزيع

في نهاية الجولة تحقق مقابل القائمة من الخطوة 0: **كل تغيير يلاحظه المستخدم يجب أن يصل إلى كل سطح يبحث فيه عنه.** المستودع الذي تروي صفحة npm الخاصة به قصة مختلفة يكون أسوأ حالًا من مستودع بسطح واحد.

الآلية الحاسمة: **سجلات الحزم تعرض README لآخر نشر، لا حالة المستودع الحالية.** تصحيح README لا يظهر على npm أو PyPI إلا مع إصدار جديد. إذا كان التصحيح مهمًا (تثبيت خاطئ، أو إصدار خاطئ، أو قائمة ميزات قديمة)، فلا بد من إصدار تصحيحي — وإلا يبقى الإصلاح بلا أثر.

| السطح | ما يُصان فيه | كيف يصل إليه |
|---|---|---|
| npm | README و`description` و`keywords` ورابط المستودع | فقط عبر `npm publish` (إصدار تصحيحي)؛ والبيانات الوصفية من `package.json` |
| PyPI | README (`long_description`) والتصنيفات وروابط المشروع | فقط عبر رفع جديد؛ والبيانات الوصفية من `pyproject.toml` |
| سجل MCP / دلائل الإضافات | الوصف والإصدار وقائمة الأدوات ووثائق البداية | حسب السجل: تحديث البيان أو إعادة التقديم |
| السوق / المتجر | الوصف ولقطات الشاشة والفئات والنسخ اللغوية | عبر واجهة الإدارة الخاصة به؛ لقطات الشاشة تتقادم هناك بسرعة خاصة |
| Docker Hub / سجل الحاويات | الوصف والوسوم ومثال الاستخدام | وصف المستودع مع وسم جديد |
| Zenodo / DOI | البيانات الوصفية والمؤلفون والإصدار | تعديل في المكان للبيانات، وإصدار جديد للمحتوى |
| الموقع / ملف المنظمة / `llms.txt` | الوصف المختصر والرابط والتموضع | قابل للتحرير مباشرة — أرخص الأسطح، لذا لا تنسها أبدًا |

عند رفع رقم الإصدار يجب أن **تنتقل كل حاملات الإصدار** في الوقت نفسه: البيان، وثابت الشيفرة، وشارة README، وCHANGELOG، ووسم الإصدار، و`llms.txt`. الإصدار المرفوع نصفيًا أصعب في التشخيص من إصدار قديم بالكامل.

إذا تعذّر تحديث سطح ما أو لم يكن مناسبًا في الوقت الحالي (مثل إصدار بسبب خطأ مطبعي فقط)، فدوّن ذلك في سجل التشغيل، كي لا تعتبر الجولة التالية الفرق خطأ غير مقصود.

## قاعدة الدفع القسري

الافتراض هو **عدم الدفع القسري**. إضافة ملفات التخطيط الداخلية إلى التجاهل لاحقًا لا يبرر إعادة كتابة التاريخ: الجهد كبير، وكل نسخة محلية وكل فورك (fork) ينكسر، وطلبات السحب المفتوحة تصبح غير صالحة — والمكسب ضئيل لأن المحتوى غير خطير. الطريق المعتاد:

```bash
git rm --cached <datei>            # aus dem Tracking, bleibt lokal erhalten
# .gitignore ergänzen
git commit -m "chore: interne Arbeitsdateien aus dem Repo nehmen"
git push
```

إعادة كتابة التاريخ (وبالتالي دفع `--force-with-lease`) لا تُبرَّر إلا في حالة **التسريبات الحقيقية**: بيانات الاعتماد والمفاتيح، والبيانات الشخصية أو بيانات العملاء، والمستندات ذات القيمة التنافسية الحقيقية — حسابات داخلية، واستراتيجيات تسعير، وخطط غير منشورة، وتفاصيل تعاقدية داخلية. في هذه الحالة:

1. **دوّر الأسرار المتأثرة أولًا** — التاريخ منسوخ حينها بالفعل ومعمول بنسخه المتفرعة وذاكرات التخزين المؤقت. التدوير يُحدث أثرًا، والحذف تجميلي فقط.
2. نظّف التاريخ (`git filter-repo` أو BFG)، ثم ادفع `--force-with-lease`.
3. افحص النسخ المتفرعة وذاكرات التخزين المؤقت؛ وعند الحاجة تواصل مع دعم GitHub بشأن الكائنات اليتيمة.
4. وثّق العملية في سجل التشغيل: ما الذي حدث، ومتى، وأي تدوير أُجري.

عند الشك بين "غير حرج" و"حساس" عامل الأمر كحساس واعرضه. التكلفة غير متماثلة.

## النتائج تصبح مهامًا، لا مجرد أسطر في السجل

تجد جولة الصيانة عادةً أكثر مما تستطيع معالجته في الجولة نفسها أو يُفترض بها أن تعالجه: لغة ناقصة، أو تأخر في التحديث، أو إصدار لم يحدث قط. **هذه النتائج تتحول إلى مهام لحظة اكتشافها** — وإلا تبقى معلقة في سجل جولة منتهية لا ينظر فيه المحرر التالي للمشروع.

المهمة تنتمي إلى **نظام المهام المحلي للمجلد** الخاص بالمشروع — حيث يبحث عنها من يعمل على المشروع لاحقًا. عادةً هو `AUFGABEN.txt` أو `TODO.md` في مجلد المشروع، وغالبًا لا يكون في **مستودع Git**، بل في المكان الذي يعيش فيه التخطيط. المستودع يحتوي الشيفرة، ومجلد المشروع يحتوي التوجيه؛ والبند داخل المستودع الذي يختفي عند `git clean` ليس مهمة.

ثلاثة أمور:

1. **افصل قائمة المهام الداخلية عن خارطة الطريق العامة.** `TODO.md` قد يكون خارطة طريق عامة مُدارة — عندها ليس مكانًا للعمل الداخلي المتأخر. انظر فيه قبل الإلحاق: إذا وجدت عنوانًا مثل "Public roadmap" فاكتب في الملف الداخلي بجانبه (`AUFGABEN.txt`) وعلّمه بأنه داخلي.
2. **تحقق من البنود الموجودة قبل التكرار.** غالبًا النتيجة موجودة بالفعل. عندها لا تنشئها من جديد، بل **تُثريها** — بالدليل التجريبي من هذه الجولة ("مؤكّد: `--help` يُخرج نصوصًا ألمانية كاملة"). بند معروف مع دليل جديد أثمن من بند ثانٍ بجانبه.
3. **دوّن المنجز أيضًا.** ما أصلحته الجولة يُضاف كبند مُعلَّم بالإنجاز مع تجزئة الإيداع. هذا يفسر للجولة التالية لماذا اختفت نتيجة، ويمنعها من "اكتشافها" مرة أخرى.

صِغ المهمة بحيث تُفهم دون سياق هذه الجولة: ما الذي وُجد، ولماذا يهم، وما الخطوة التالية. "i18n غير مكتمل" ليست مهمة؛ "الكتالوج يحتوي `status.title` فقط، والباقي فارغ في es/zh/ja/ru — حوّل أولًا نصوص CLI إلى الكتالوج، ثم املأ اللغات الست كلها" هي المهمة.

## الأخطاء الشائعة

| الخطأ | التصحيح |
|---|---|
| النظر إلى شجرة العمل فقط دون `git ls-files` | افحص دائمًا المجموعة المتتبَّعة — المشكلة هناك |
| بوابة الخصوصية موجهة للمسارات والرموز فقط | ابحث أيضًا عن أسماء خطوط الإنتاج والمجلدات الداخلية — لا تطلق إنذارًا وتمر |
| حذف ملف داخلي وإعادة كتابة التاريخ معه | للملفات غير الحرجة يكفي `git rm --cached` + دفع عادي |
| إزالة سر من `HEAD` واعتبار العملية منتهية | دوّر السر؛ البقية تجميل |
| تصنيف الملفات بحسب الاسم | ألقِ نظرة سريعة — الأسماء لا تحمل النية بموثوقية |
| تحديث أرقام README بالنسخ بدل إعادة العدّ | عدّ من المصدر (قائمة الأدوات، تشغيل الاختبارات، البيان) |
| إنشاء نسخة لغوية فارغة كهيكل | املأها أو احذفها — الهيكل يوحي بالاكتمال |
| إدخال اتفاقية ثانية لأسماء README بجانب الموجودة | التزم بالاتفاقية القائمة |
| تقديم طلب سحب إلى قائمة غريبة دون موافقة | اعرض التواصل مع الخارج للموافقة؛ الأسطح الخاصة فقط حرة |
| عدّ المسائل بدل معالجتها | أصلحها أو أغلقها أو اسأل بقصد — كل حالة لها حالة نهائية |
| إنشاء لافتة منفردة بأسلوب غريب عن النظام البيئي | التزم بعائلة التصميم المعتمدة في النظام البيئي |
| تصحيح README في المستودع بينما تبقى صفحة npm/PyPI على القديم | صفحات السجلات من آخر نشر — أتبع بإصدار تصحيحي |
| رفع الإصدار في البيان فقط | حاملات الإصدار كلها في الوقت نفسه: البيان والشيفرة والشارة وCHANGELOG والوسم و`llms.txt` |
| تغييرات منتهية لكن تُركت دون دفع | الإيداع والدفع جزء من الجولة؛ فقط الحظر يبرر الاستثناء |
| كل شيء في إيداع تجميعي واحد | افصل التنظيف والوثائق والإصلاحات — وإلا لا شيء قابل للتراجع منفردًا |
| CI أحمر بعد إيداع وثائقي والاشتباه في الذات | أداة فحص غير مثبتة بلا `select` تتبع افتراضي النسخة الجديدة — ثبّت مجموعة القواعد |
| تصحيح عبارة خاطئة في الموضع الذي لوحظت فيه فقط | ابحث على مستوى المنظمة بالصياغة نفسها — غالبًا موجودة في الملف الشخصي و`llms.txt` والنسخة اللغوية الثانية |
| العمل داخل مستودع غريب متسخ بـ `commit -a` | أضف وأودِع بمسار دقيق، لا تدفع — عمل الغير يبقى كما هو |
| تغيير في مستودع الملف الشخصي النظيف دون دفع | المستودعات الغريبة النظيفة تحصل على إيداع خاص **ودفع** خاص |
| تغيير مؤجَّل مُدوَّن في السجل الخاص فقط | أضفه أيضًا إلى قائمة مهام المستودع الهدف إن وُجدت |
| النتيجة كُتبت في سجل التشغيل فقط | تتحول إلى مهمة في نظام المهام المحلي للمجلد — لن ينظر أحد في السجل لاحقًا |
| إلحاق عمل داخلي متأخر بخارطة طريق عامة | انظر أولًا؛ "Public roadmap" تعني استخدام الملف الداخلي بجانبه |
| تكرار نتيجة معروفة كبند جديد | أثرِ البند الموجود بالدليل التجريبي من هذه الجولة |
| كتابة سطر TODO في مستودع مُقفَل بقفل تحرير | قفل التحرير يشمل المشروع كله — لا تلمس شيئًا هناك |
| قراءة قفل الدفع كمنع شامل وتخطي المستودع كله | اقرأ القفل: إن كان يمنع النشر فقط، تستمر الجولة المحلية على فرع خاص |
| عدم الدفع تحت القفل، لكن تغيير الوسوم أو الوصف | البيانات الوصفية مرئية عن بُعد أيضًا — تحت حظر النشر تسقط معه |
