# Surface After Care — 公開済みリポジトリの定期メンテナンスルーティン

## この Skill が適用されるタイミング

**すでに公開されている**リポジトリで、定期的に見直しを行う場合に使用します。軽量なステップです：外部リポジトリのインベントリ作成や法的レビューの開始を伴わず、リポジトリ自体で判断できるすべての事項を対象とします。

関連 Skill との比較：

| 状況 | Skill |
|---|---|
| リポジトリを初めて公開する | `github-repo-care` |
| リポジトリが公開済み、定期メンテナンス | **本 Skill** |
| 追加の法的チェック + 全 Org にわたる相互参照 + アプリ i18n | `full-after-care`（エイリアス `deep-after-care`） |
| 公開前の純粋な法的/プライバシー/ライセンスチェック | `repo-publish-check` |
| 言語バージョンの内容を同期状態に維持する | `bilingual-doc-sync` |
| 多数のリポジトリにこのメンテナンスを公平に回転分配する | `rotation-check` |

## コアコンセプト

公開されたリポジトリは 2 つの方向に乖離していきます：**ドキュメントがリポジトリ内のコードより古いソフトウェアを説明している**、そして**部外者に見せる意図のなかったファイルが蓄積している**。どちらも致命的になることは稀ですが、どちらも獲得したいユーザーを失う原因になります。一方はインストールガイドが合わなくなったために離脱し、もう一方はルートディレクトリで `AUFGABEN.txt` や `Plan.txt` に遭遇し、「ここでは自分のためだけに作業している」という印象を受けるためです。

このルーティンは両方を解消します。意識的に反復可能に設計されています：年に一度の大掃除よりも、年 4 回の 30 分の整備が勝ります。

## 実行手順

順番は任意ではありません。ステップ 0 が最初に来るのは、後続の全ステップの範囲を決定するためです。ステップ 2 は変更を Push するすべての操作より前に実行します。そうしないと、まだクリーンアップが必要な状態の上に改善を押し重ねることになります。ステップ 1 は純粋にサーバー側であり、干渉しません。

### 0. 配信チャネルのインベントリ作成

**何かを変更する前に：このプロジェクトがどこに存在するかを明確にします。** GitHub リポジトリが唯一の露出面であることは稀です。修正された README も、npm パッケージページに誤ったインストール指示を含む古いバージョンが表示され続けていては意味がありません。パッケージレジストリは検索エンジンでリポジトリより上位にランクされることが多いため、まさにそこに大半のユーザーが到達します。

```bash
# Manifeste verraten die Kanäle (Deutsch)
cat package.json pyproject.toml setup.py Cargo.toml 2>/dev/null | rg -n "name|version|keywords|repository|homepage"
rg -n "npmjs.com|pypi.org|marketplace|registry|crates.io|hub.docker|zenodo|doi" README* docs/ .github/ 2>/dev/null

# Veröffentlichten Stand der Kanäle abfragen (nur was zutrifft) (Deutsch)
npm view <paket> version description keywords 2>/dev/null
pip index versions <paket> 2>/dev/null
gh release list --repo ORG/REPO --limit 5
```

代表的なチャネル：npm, PyPI, Crates, Docker Hub, MCP レジストリ, プラグイン/Skill ディレクトリ, VS Code やブラウザのマーケットプレイス, アプリストア, Zenodo/DOI, プロジェクト Web サイト, 組織 Profile, `llms.txt`, 他ホスト上のミラーリポジトリ。

見つかったリストを実行ログに記録します。ここから先、これが**ターゲットセット**となります：以降のステップでのあらゆる変更は、最終的にこのリストと照合されます（「全チャネルにわたる同等性」を参照）。誰もメンテナンスしておらず古い状態を指しているチャネルを見つけた場合、それは独自の検出事項です。更新するか明示的に取り下げるかのいずれかを行い、放置しないでください。

### 1. Topic の設定

Topic は GitHub 内部で最も重要な検索面であり、コストはほとんどかかりません。

```bash
gh repo view ORG/REPO --json nameWithOwner,description,repositoryTopics,homepageUrl,visibility
gh repo edit ORG/REPO --add-topic <topic> --add-topic <topic>
```

3 つの観点から約 5〜12 個の Topic を設定することを目指します：**それが何であるか** (`cli`, `mcp-server`, `python-library`)、**何に関するものか** (`file-management`, `tax`, `note-taking`)、アンド**どのように動作するか** (`local-first`, `offline`, `privacy`)。同種のプロジェクトで実際に使用されている Topic を参考にしてください。造語の Topic ではユーザーが見つかりません。Description と Homepage も同じビューに表示されるため、同時に確認してください。

Topic はステップ 0 の他のチャネルにも対応するものがあります：`package.json` の `keywords`、`pyproject.toml` の `keywords`/`classifiers`、マーケットプレイスやストアのカテゴリとタグ。これらは複数の場所にある同じ決定であるため、内容を同一に保ちます。

### 2a. プライバシーゲート (Privacy Gate) — 常に実行

一見害のないラウンドであっても、このステップをスキップすることは絶対にありません。表示されている作業ツリーではなく、**追跡されている (tracked)** セット内で検索します。これこそが「綺麗に見える」と「実際に綺麗である」の違いだからです。

```bash
git ls-files
rg -n "C:\\\\Us[e]rs\\\\|/home/[a-z]|s[k]-[A-Za-z0-9]{16}|gh[p]_|gh[o]_|AKIA[0-9A-Z]{16}|API[_-]?KEY|TO[K]EN|PASS[W]ORD|SEC[R]ET|BEGIN [A-Z ]*PRIVATE KEY" $(git ls-files)
rg -n "\x{C3}\x{83}|\x{C2}\x{A0}|\x{FFFD}" $(git ls-files -- '*.md' '*.txt' '*.json')
```

パターンに**自身内部の保管場所の名前**（パイプラインフォルダ、トピックディレクトリ、プライベート作業領域）を追加します：

```bash
rg -n "\.SOFTWARE|\.RESEARCH|_control-center|<weitere eigene Ordnernamen>" $(git ls-files)
```

このような参照は Secret ではないためアラームを発生させず、すり抜けてしまいます。しかし、読者にとっては**解決不能**であり（「.SOFTWARE パイプラインから再転送」は部外者には何も伝わりません）、内部構造を暴露することになります。単に許容するのではなく、置換または削除します。`C:\Users\...` や Token パターンのみを検索するチェックでは、これらを確実に発見できません。

該当するものが見つかりましたか？その場合、検出事項の**種類**によって手順が決まります（「Force-Push ルール」のセクションを参照）。一度でも Commit された Secret は無効化（焼き払われた）とみなされます：`HEAD` から削除するだけでは不十分であり、ローテーションする必要があります。

### 2b. ドキュメントの公開意図の確認

このルーティンの真の核心です。追跡されている `.md`, `.txt`, `.json` ファイルを巡回し、各ファイルについて確認します：**これは部外者に見せる意図が一度でもあったか？**

```bash
git ls-files -- '*.md' '*.txt' '*.json' | sort
```

ファイル名で推測せず、内部を短く確認します。`PLAN.md` が公開ロードマップであることもあれば、一見害のなさそうな `notes.md` が内部の価格戦略を含んでいることもあります。3 つのカテゴリ：

**リポジトリに属するもの** — README, LICENSE, CHANGELOG, SECURITY, CONTRIBUTING, `docs/`, API リファレンス, サンプル設定, 実際のロードマップ, マニフェスト (`package.json`, `pyproject.toml`), Lockfile, CI 設定。

**リポジトリに属さないが非機密** — このルーティンの標準的なケース。タスクおよび計画ファイル (`AUFGABEN.txt`, `Plan.txt`, `TODO-intern.md`)、セッションメモや引き継ぎ (`HANDOFF`, `BRIEFING`, `_handoff/`)、自身パイプラインのステータスファイル、開発日記、`_archive/`、ローカルパスを含むレジストリおよびインデックス JSON、中間状態および生成されたアーティファクト、Agent 作業ファイル。このようなファイルは危険ではありませんが、雑然とした印象を与え、放置された現場のような印象を与えます。対処法：`.gitignore` に追加し、`git rm --cached <file>` を実行して**通常通り Push** します。

**リポジトリに属さず機密性が高い** — 資格情報 (Credentials)、個人データ、顧客データ、内部試算、価格・交渉戦略、未公開の事業計画、契約案、競争上の価値を持つすべてのもの。ここでは通常の Commit では不十分です。Force-Push ルールを参照してください。

`.json` ファイルについては再確認の価値があります：マニフェストや Lockfile は残しますが、ローカル設定、タスク/レジストリファイル、エクスポートダンプ、および絶対パスやホスト名を含むものは典型的な密航者です。

誰かが探す可能性のあるファイル（ロードマップなど）を削除する場合は、Commit メッセージや README で情報が現在どこにあるかを簡単に言及してください。さもなければ後退（退化）のように見えてしまいます。

### 3. バナー

バナーは、誰かが読み始めるかどうかを決定づける要素の 1 つです。バナーが存在し、README の最初の要素として埋め込まれているか確認します。

欠落している場合、3 つの選択肢があります（この順序での検討が合理的です）：

1. **Agent の画像ジェネレーター**（例: agy。そこでは「generate」という単語が実際の PNG 生成のトリガーとなります）、タイポグラフィよりも視覚的モチーフが適している場合。
2. **Codex**、コードからバナーを生成し、参考にできるスタイルモデルが存在する場合。
3. **SVG として自作**、バナーが主にワードマーク＋デザイン言語である場合。これは多くの場合、最も迅速で制御可能なバリエーションであり、SVG は後から変更可能です。

プロジェクトがグループに属している場合は、ファミリーの統一性を維持します：同じベースカラー、同じ美学、同じワードマークの扱い。スタイルから外れたバナーは、無い方がマシに見えます。通常のサイズは 1200x300。PNG としてリポジトリに保存し、SVG ソースをその隣に配置します。

### 4. 記述内容と実際の状態との照合

ここで最大の価値が生まれます。README は様々な主張をしています — 鵜呑みにせず検証してください：

- README/Badge 内の**バージョン** vs. `pyproject.toml`/`package.json`/`__version__` および最新の Release Tag。複数のバージョン保持場所がある場合、1 つだけでなくすべて確認します。
- **インストール手順**を実際に（少なくとも頭の中で）通して実行します：指定された名前でパッケージが存在するか？コマンドと Flag は正しいか？
- **Feature リスト** vs. コード：記載されているすべてのものが存在し、新しい機能がリストから漏れていないか？
- **数値**（Tool 数、サポートフォーマット数、テストカバー率）をそのまま引き継ぐのではなく、ソースでカウントし直します。README 内の数値は静かに古くなります。
- **スクリーンショット** vs. 現在の UI。
- **Requirements**（Python/Node バージョン、依存関係）vs. マニフェスト。
- 関連プロジェクト、ドキュメント、レジストリへの**リンク**：まだ機能しているか？

**修正は、問題が発覚した箇所だけでなく、すべてのチャネルに適用されます。** 事実の記述が誤っていると判明した場合 — 特にクライアントがそれを正した場合 —、同じ記述が他の場所にも存在する可能性が非常に高いです：組織 Profile 内、`llms.txt` 内、第 2 言語バージョン内、関連プロジェクトの README 内。項目にチェックを入れる前に、特定して検索してください：

```bash
gh search code "<prägnante Formulierung>" --owner ORG
```

さもなければ、1 箇所を修正して 3 箇所を放置することになり、次のリポジトリの番が来たときに初めて矛盾に気づくことになります。これは時間を浪費するだけでなく、ドキュメントへの信頼を損ないます：同じことについて 2 つの矛盾する説明を見つけた人は、どちらも信じなくなります。

続いて、表現が弱い部分の**レイアウト・プレゼンテーション**を改善します：オプションの長い列挙はテーブル形式にすると読みやすくなります。コードブロックには言語 Tag が必要です。構造やプロセスの概要は散文よりも Mermaid ダイアグラムや ASCII ツリーの方が迅速に把握できます。最初の画面領域には Badge や前史ではなく、目的、インストール、使用例を表示すべきです。README が約 400 行を超える場合は、詳細を `docs/` に移行してリンクします。

**README の言語ルール：** 標準は**英語の `README.md`** に加えて**ドイツ語の第 2 バージョン**です。例外：アプリケーションのドメイン領域自体が本質的にドイツ語である場合（ドイツの法律、ドイツの税制・助成金制度、ドイツ語圏のターゲット層）、または現在ドイツ語版のみが存在する場合 — その場合はドイツ語がプライマリ言語のままとなります。プロジェクトがすでにサポートしているその他の各言語について、それぞれの README バージョンが対応します。リポジトリで既に使用されている命名規則（`README_de.md`, `README.de.md`, `docs/README.de.md`）に従い、その隣に別の規則を作り出さないでください。ヘッダーでお互いのバージョンを相互リンクします。

### 6. 不足している標準言語の作成

**標準言語**の中で不足している README を追加します：ドイツ語、英語、スペイン語、簡体字中国語、日本語、ロシア語。目的はリーチの拡大であるため、これは主にユーザー向けのプロジェクトに適用されます — 純粋に英語圏のユーザーを対象とする開発者向けライブラリの場合、ロシア語の README は利益をもたらさず、維持管理の負担が増えるだけです。意識的に決定し、次のラウンドで再議論しないよう実行ログに決定を記録してください。

新しいバージョンは**内容を補填して作成し、空のまま放置しないでください** — 「TODO: translate」とだけ書かれた Stub は、完全性を偽るためファイルが全くないより悪質です。内容の同期と逆同期は `bilingual-doc-sync` が処理します。3 つ以上のバージョンがある場合は、この Skill を導入して照合を行う価値があります。

### 7. 可視性とプロモーション

**この**プロジェクトにとって実際にユーザーをもたらす施策を検討し、実行します：

- プロジェクトが技術的に属する **レジストリ**：パッケージレジストリ (npm, PyPI)、MCP レジストリ、プラグイン/Skill ディレクトリ、マーケットプレイス。
- **キュレーションリスト**（`awesome-*` やテーマ別コレクション）、受入基準が実際に満たされている場合に限ります。基準を満たさないリストへの PR は評判を落とします。
- **自社・自組織の露出面**：組織 Profile、`llms.txt`、プロジェクト Web サイト、エコシステムの README、関連する自社リポジトリからの参照。
- 機会としての **Release Notes**：新機能のアピールがないリリースは認知されません。

**承認ゲート (Approval Gate)：** 外部に向かうすべての操作 — 外部リポジトリへの PR、外部リストへの登録、投稿、申請 — は、そのチャネルに対する恒久的な許可が存在しない限り、**提案し、明確な承認を得た後にのみ実行**されます。自組織の露出面の変更にはこのゲートは不要です。理由は単純です：外部リポジトリに提出した後に取り下げられた PR は公に可視化され、プロジェクト自体の評判に影響するためです。

### 8. 組織ページへの掲載

まず自身の組織：リポジトリが Profile README (`ORG/.github` → `profile/README.md`) に掲載されているか、正しいカテゴリにあるか、最新の Description がついているか確認します。

```bash
gh api user/orgs --jq '.[].login'
```

次に**すべて**の組織を回り、組織ごとに 1 つの質問に答えます：この組織ページの訪問者はこのリポジトリから利益を得られるか？通常、答えは「いいえ」です — その場合、「リンクしない」のが正しい結果であり、欠落ではありません。答えが「はい」の場合（テーマの親和性、共通のユーザー層、そこのプロジェクトを補完するツール）、名前だけでなく有用性を説明する 1 行を添えて参照を設定します。

Profile は独立したリポジトリ (`ORG/.github`) に存在します。そこでの変更もあわせて維持・Push します — ステップ 11 の Dirty-Tree ルールに従います。

### 10. Issue と Pull Request

```bash
gh issue list --repo ORG/REPO --state open --limit 50
gh pr list --repo ORG/REPO --state open --limit 30
```

単に数を数えるのではなく、処理を進めます：

- **修正可能な Bug**：直接修正します — このラウンドでは文脈がすでにロードされています。テストと Issue 番号への参照を伴う、小さく明確に定義された修正。
- **解決済みの Issue**：解決した内容を 1 文添えて Close します。
- **不鮮明な報告**：具体的な確認質問（バージョン、OS、再現手順）が必要です。
- **PR**：Diff を実際に読み、テストを実行し、Merge するか理由を添えて返答します。何ヶ月も未回答のまま放置された PR は、礼儀正しい拒否よりも多くの好意を失います。
- **Stale なケース**：引きずらずに解決します。

**承認ゲート：** 公開のコメント、理由付きの Close、外部の寄稿の Merge は外部コミュニケーションです — 恒久的な許可がない限り、実行前に提示してください。自身のリポジトリでの純粋なコード修正は影響を受けません。

### 11. Commit, Push, 検証

このラウンドは変更を加えることで終わるのではなく、それが**外部に押し出された (Pushed out)** ときに終了します。Push されていない改善でいっぱいの作業ツリーは最悪の結果です：次のセッション — おそらく別の Agent や別のマシン — は、まず見慣れない半完成の状態を把握しなければならず、公開面では何も改善されていないためです。

Push の前に、検証可能な内容を簡単に確認します：テストと Smoke Check を実行し、ドキュメントの変更ではリンクとレンダリング表示を確認します。その後、すべてを 1 つの巨大な Commit にまとめるのではなく、**テーマごとに分離された Commit** にバンドルします — クリーンアップ、ドキュメント更新、バグ修正は 3 つの異なる事象であり、後でそのうち 1 つを取り消したいと思う人は感謝するはずです：

```bash
git add .gitignore && git rm --cached <interne dateien>
git commit -m "chore: interne Arbeitsdateien aus dem Repo nehmen"
git commit -am "docs: README auf aktuellen Stand (Version, Toolzahl, Screenshots)"
git commit -am "fix: <Issue-Nummer> ..."

git pull --rebase        # bei divergiertem Branch, vor dem Push
git push
```

その後、想定するのではなく検証します：レンダリング表示でのリモート README、CI 実行、リリースおよび Tag の状態。

```bash
gh run list --repo ORG/REPO --limit 3
gh repo view ORG/REPO --json description,repositoryTopics,url
```

**Commit がドキュメントのみを触ったにもかかわらず CI が赤くなった場合**、原因があなたの変更にあることはほぼありません。最も頻繁に発生するケース — このリポジトリファミリーで 1 日に**3 回**遭遇しました — は、**明示的なルールセットを持たない未ピン留めの Linter** です。自分の Commit を疑う前に、**まずこれを確認**してください。

そのメカニズム：Workflow が未ピン留めの依存関係 (`ruff>=0.12` またはバージョン指定なし) に対して `ruff check` (または flake8, eslint...) を実行しており、明示的なルール選択 (`[tool.ruff.lint] select = [...]`、`pyproject.toml` がない場合は独自の `ruff.toml`) が欠落している場合、Linter は**新しくインストールされた**バージョンのデフォルトに従います。新しい Linter リリースはこのデフォルトを変更するため、変更されていないコードベースが赤くなります。敗北のサイン：

- プロジェクトに以前存在しなかったルールコード (`UP045`, `UP006`, `BLE001`, `RUF100`, `DTZ005`, `N999`...) が、時には 3 桁の数で発生する。
- 失敗が**プラットフォーム間で分裂**することが多い：キャッシュされた古いバージョンを持つ Runner は緑のまま、新しい Runner は赤になる。
- ルールが修正不可能なもの（`N999` がパッケージ名自体を指摘するなど）を指摘することがある — それが標準でなかったことの確実な証拠。

修正方法：以前緑だったルールセットを固定します — `select = ["E4","E7","E9","F"]` は ruff の古典的なデフォルトです。`pyproject.toml` が存在しない場合は `ruff.toml` を作成します。**新しい** Linter バージョン自体に対して検証します（インストールし、設定なしで検出事項を再現し、設定ありで "passed" になることを確認）。新しいルールは**Task**としてプロジェクトに入ります — 意識的な採用は決定であり、ツール更新の副作用ではありません。これは実際に繰り返し発生する検出事項です：ピン留めしない限り、次の Linter リリース時に、このように設定された**すべての**リポジトリで CI が再び破損します。

**Push しない** 2 つのケース：プロジェクトに公開または提出の凍結 (Hold) が適用されている場合、または状態が明示的に未完成である場合。どちらも理由を要する例外です — 通常のケースは：Commit して Push です。

公開凍結期間中、ラウンドは中止されるのではなく**重定向 (Reroute)** されます：独立したブランチ (`judging-hold/...`, `freeze/...`) でローカルに Commit し、Main ブランチを提出された状態のまま手つかずに保ち、凍結理由を実行ログに記録し、解除後に追平します。一貫性を保つことが重要です：ブロックされるのは `git push` だけでなく、**リモートで視認可能なすべての変更**です — Topic、Description、Homepage、Release、Issue/PR 操作も公開プロジェクトを同様に変更します。

同じリポジトリの他の Clone（第 2 のマシン、デプロイコピー、ミラー）が存在する場合、Push 直後にそれらを追平します。10 コミット遅れている Clone は、次のトラブルシューティング時にすでに存在しない状態に基づいて診断を出してしまいます。

#### 他のリポジトリへの変更 — Dirty-Tree の例外

このラウンドでは、メンテナンス対象リポジトリの**外部**で変更が定期的に発生します：組織 Profile 内の 1 行（ステップ 8）、あるいは後のディープラウンドでの関連リポジトリ内のバック参照。このような変更も同様に Commit して Push されます — 未公開のバック参照は存在しないのも同然です。

外部リポジトリに手を加える前に、その状態を簡単に確認します：

```bash
git -C <pfad> status --porcelain
```

**クリーンな作業ツリー (Clean)** → 変更を行い、**独立したテーマの明確な Commit** (`docs: link <projekt>`) で Commit して Push します。メンテナンス対象リポジトリの Commit と混ざないでください：それは独自の履歴と読者を持つ別のリポジトリです。

**Dirty だが、外部の変更が他のファイルにある** → 自身の変更はクリーンに実行可能です。未検証の外部作業が含まれないよう、**パスを指定して自身のファイルのみを Stage して Commit** します：

```bash
git -C <pfad> add README.md
git -C <pfad> commit -m "docs: link <projekt>"     # nur der gestagte Pfad
```

ただし **Push はしないでください**。Commit はローカルでは無害です。Push は必ずしも無害とは限りません：相手の作業状態がどこに向かっているか分からないためです — 修正、Rebase、あるいは別の切り分けが行われている最中かもしれず、あなたの Push は相手に対処を強制することになります。ローカル Commit は誰にも何かを強制することなくあなたの作業を保護します。後でそのリポジトリに向かう実行プロセスがそれを見つけて持ち連れて行きます。

**変更する必要があるまさにそのファイルで Dirty** → 触らないでください。ここでは外部の中間状態の上に構築して共同 Commit する必要があり、まずそれを理解するコストはこの 1 つの参照の価値を上回ります。

**ターゲットリポジトリにアクティブな Lock (`LOCK*.txt`) が存在** → **一律の禁止として扱うのではなく、まず Lock を読みます。** Lock は自身の適用範囲を記述しており、それは「一切禁止」よりも狭いことがよくあります。典型的なケース：

- **編集 Lock**（「現在誰かがここで作業中」）→ 補助ファイルを含め、何も触らない。
- **純粋な公開/Push Lock**（提出、審査、凍結）→ ローカル作業は許可されたままであり、リモートの接触のみがブロックされます。独立したブランチで作業し、ローカルで Commit します。**リモートで効力を持つステップは省略されます** — Push だけでなく、Topic、Description、Homepage、Release、Issue/PR 操作も公開プロジェクトを変更するため省略されます。

Push のみをブロックする Lock を完全な禁止として誤読すると、安全上の利益なしにラウンドのローカルパート全体を失うことになります。逆に、Push のみを控えて Metadata を変更するのも不十分です。疑問がある場合は Lock を引用して質問してください。

#### 要求を失ってはならない

these 理由のいずれかによって変更が実行**されない**場合、それはターゲットリポジトリのタスクリスト（そこに存在するファイルに応じて `AUFGABEN.txt`, `TODO.md`, `TODO.txt`）に移動します。日付、希望する変更、理由を含むエントリー：

```markdown
- [ ] [2026-07-24, after-care] Rückverweis auf <projekt> im README ergänzen
      (übersprungen: README hatte uncommittete Fremdänderungen)
```

これが「延期」と「失念」の違いです：タスクリストは、このリポジトリの次の担当者がいずれにせよ目を通す場所に位置しています — 外部実行ログのメモよりもはるかに信頼性があります。タスクリストが存在しない場合は作成しないでください。自身実行ログの未解決項目で十分です。

**アクティブな Lock の下ではこれすら適用されません** — ファイルは触られず、メモは自身実行ログにとどまります。ローテーションが未解決項目を把握できるよう、どちらの場合もそこに記録してください。

最後に、ステップ 0 の露出面を対応します — 次のセクションを参照。

## すべての配信チャネルにわたる同等性

ラウンドの最後に、ステップ 0 のリストと照合します：**ユーザーの目に入るすべての変更は、ユーザーがそれを探すすべてのチャネルに到達しなければなりません。** npm ページが異なるストーリーを語っているリポジトリは、チャネルが 1 つしかないリポジトリよりも悪い状態にあります。

決定的なメカニズム：**パッケージレジストリは現在のリポジトリ状態ではなく、最後の Publish 時の README を表示します。** npm や PyPI 上の README の修正は、新しいバージョンによって初めて視認可能になります。修正が内容的に関連している場合（誤ったインストール、誤ったバージョン、古い Feature リスト）、パッチリリースが伴う必要があります — さもなければ Fix は無効なままとなります。

| 露出面/チャネル | そこで維持管理されるもの | どのように到達するか |
|---|---|---|
| npm | README, `description`, `keywords`, リポジトリリンク | `npm publish`（パッチバージョン）経由のみ。Metadata は `package.json` から |
| PyPI | README (`long_description`), Classifiers, プロジェクト URL | 新しいアップロード経由のみ。Metadata は `pyproject.toml` から |
| MCP レジストリ / プラグインディレクトリ | Description, バージョン, Tool リスト, 入門ドキュメント | レジストリに応じて Manifest 更新または再提出 |
| マーケットプレイス / ストア | Description, スクリーンショット, カテゴリ, 言語バージョン | それぞれの管理インターフェース経由。スクリーンショットはそこで特に早く老化する |
| Docker Hub / コンテナレジストリ | Description, Tag, 使用例 | リポジトリ Description プラス新しい Tag |
| Zenodo / DOI | Metadata, 著者, バージョン | Metadata はインプレース編集、コンテンツ更新は新バージョン |
| Web サイト / Org Profile / `llms.txt` | 簡潔な Description, リンク, ポジショニング | 直接編集可能 — 最も低コストな露出面であるため、絶対に忘れないこと |

バージョンを上げる際、**すべてのバージョン保持場所**が同時に移行する必要があります：マニフェスト、コード定数、README Badge、Changelog、Release Tag、`llms.txt`。半分だけ上がったバージョン状態は、全体的に古い状態よりも診断が困難です。

チャネルでの更新が現在不可能または合理的でない場合（例: タイポ修正のためだけのリリース）、次のラウンドが差異を過失と勘違いしないよう、実行ログに記録してください。

## Force-Push ルール

標準は **Force-Push なし** です。内部の計画ファイルを後から Ignore することは、履歴の書き換えを正当化しません：コストが高く、すべての Clone や Fork が破損し、オープンな PR が使用不能になります — そして内容は無害であるため利得は低いです。標準手順：

```bash
git rm --cached <datei>            # aus dem Tracking, bleibt lokal erhalten
# .gitignore ergänzen (Deutsch)
git commit -m "chore: interne Arbeitsdateien aus dem Repo nehmen"
git push
```

履歴の書き換え（したがって `--force-with-lease` での Push）が正当化されるのは、**真のリーク (Leak)** の場合に限られます：資格情報やキー、個人データや顧客データ、および真の競争価値を持つドキュメント — 内部試算、価格戦略、未公開の計画、契約の詳細。この場合：

1. 影響を受ける Secret を**まずローテーション**します — 履歴はその時点で送信・コピー・Fork・キャッシュされています。ローテーションが有効であり、削除は単なる表面的な処置です。
2. 履歴をクリーンアップし（`git filter-repo` または BFG）、`--force-with-lease` で Push します。
3. Fork とキャッシュを確認し、必要に応じて孤立したオブジェクトについて GitHub Support に連絡します。
4. プロセスを実行ログに記録します：何を、いつ、どのようなローテーションを行ったか。

「非機密」と「機密」の間で疑わしい場合：機密として扱い、レビューに提示します。コストは非対称です。

## 検出事項は単なるログ行ではなく Task となる

メンテナンスラウンドでは、同じラウンドで修正できる/すべき以上のものが定期的に見つかります：欠落している言語バージョン、近代化の遅れ、行われなかったリリース。**このような検出事項は発見された瞬間に Task となります** — さもなければ終了した実行のログに留まり、プロジェクトの次の担当者はそこを見ません。

Task は**プロジェクトのフォルダローカルなタスクシステム**に属します — 次にこのプロジェクトで作業する人が確認する場所です。通常、それはプロジェクトフォルダ内の `AUFGABEN.txt` または `TODO.md` であり、そのフォルダは**Git Clone 内には存在せず**、計画が存続するディレクトリにあることが多いです。Clone にはコードが含まれ、プロジェクトフォルダには管理が含まれます。次の `git clean` で消える Clone 内のエントリーは Task ではありません。

3 つの点に注意してください：

1. **内部タスクリストと公開ロードマップを分離する。** `TODO.md` が整備された公開ロードマップである場合があります — その場合、内部の追及作業を置く場所ではありません。追記する前に内部を確認してください：「Public roadmap」のような見出しがある場合は、隣の内部ファイル (`AUFGABEN.txt`) に書き込み、内部としてマークします。
2. **重複させるのではなく既存のエントリーを確認する。** 検出事項がすでにそこに記載されていることがよくあります。その場合、新しく作成するのではなく、今回の実行からの実証的証拠で**エンリッチ（補強）**します（「確認済み: `--help` は完全にドイツ語の出力を与える」）。新鮮な証拠を伴う既知の項目は、隣にある 2 つ目のエントリーよりも価値があります。
3. **完了した内容を書き添える。** ラウンドが解決した内容は、Commit Hash を伴うチェック済み項目として含めます。これは次のラウンドに対して検出事項が消えた理由を説明し、再び「発見」されるのを防ぎます。

今回の実行の文脈なしでも理解できるように Task を公式化します：何が見つかったか、なぜ重要か、次のステップは何か。「i18n 不完全」は Task ではありません。「カタログには `status.title` のみが含まれ、es/zh/ja/ru は空である — まず CLI 文字列をカタログに移行し、その後 6 言語すべてを補填する」が Task です。

## 実行ログ

結果を `_after-care/LOG.md` に記録します（このフォルダは `.gitignore` に属します — ステップ 2b のルールに従い、パイプライン資材であってリポジトリコンテンツではありません）。実行ごとに 1 行、日付、段階、意識的な決定を記述します：

```markdown
## 2026-07-24 — surface
- Flächen: GitHub, npm (<paket>), MCP-Registry, Org-Profil, llms.txt
- Topics: +local-first, +mcp-server; keywords in package.json angeglichen
- Entfernt: AUFGABEN.txt, _handoff/ (gitignored, kein Force-Push nötig)
- README: Version 0.9 -> 1.2 korrigiert, Toolzahl 23 -> 26 nachgezählt
- Sprachen: EN + DE gepflegt; ES/ZH/JA/RU bewusst nicht (entwicklernahes Publikum)
- Issues: #12 gefixt, #7 geschlossen (erledigt), #15 Rückfrage gestellt
- Push: 3 Commits, CI grün; npm-Republish 1.2.1 wegen README-Korrektur
- Offen: Store-Screenshots veraltet, brauchen neuen Build
```

ログは次のラウンドが同じ決定を再試行する手間を省き、多数のリポジトリにわたる回転メンテナンス（`rotation-check`）の基盤となります。

## よくある間違い

| 間違い | 修正 |
|---|---|
| 作業ツリーのみを観察し、`git ls-files` を見なかった | 常に追跡対象セットを確認する — そこに問題がある |
| プライバシーゲートがパスと Token のみに向けられていた | 自社のパイプライン/フォルダ名も検索する — アラームを発生させずすり抜けるため |
| 履歴を書き換えて内部ファイルを削除した | 非機密ファイルの場合、`git rm --cached` + 通常の Push で十分 |
| `HEAD` から Secret を削除して完了とみなした | Secret をローテーションする。それ以外は表面上の処置に過ぎない |
| ファイル名のみでファイルを分類した | 内部を短く確認する — ファイル名は意図を確実には伝えない |
| README 内の数値を再カウントせず引き継いだ | ソースでカウントする（Tool リスト、テスト実行、マニフェスト） |
| 新しい言語バージョンを空の Stub として作成した | 補填するか省略する — Stub は完全性を偽る |
| 既存のものの隣に第 2 の README 命名規則を導入した | 既存の命名規則を採用する |
| 承認なしで外部リストに PR を提出した | 外部コミュニケーションはレビューに提示する。自組織の露出面のみが自由 |
| Issue を処理せずにカウントのみした | 修正、Close、または具体的に確認質問をする — すべてのケースに状態を与える |
| 独断で異様スタイルのバナーを生成した | エコシステムのデザインファミリーを遵守する |
| リポジトリ内の README を修正したが、npm/PyPI ページは古いまま | レジストリページは最後の Publish に由来する — パッチリリースを追随させる |
| マニフェスト内でのみバージョンを上げた | すべてのバージョン保持場所を同時に上げる：マニフェスト、コード、Badge、Changelog、Tag、`llms.txt` |
| 変更が完了したが Push せずに放置した | Commit と Push はラウンドの一部である。凍結のみが例外を正当化する |
| すべてを 1 つの集約 Commit にまとめた | クリーンアップ、ドキュメント、Fix を分離する — さもなければ個別に取り消し不可能 |
| ドキュメント Commit 後に CI が赤くなり、自身を疑った | `select` のない未ピン留め Linter は新バージョンのデフォルトに従う — ルールセットを固定する |
| 誤った記述を発見した場所でのみ修正した | Org 全体で表現を検索する — Org Profile、`llms.txt`、第 2 言語にも存在することが多い |
| Dirty な他者リポジトリで `commit -a` で作業した | パスを指定して Stage・Commit し、Push しない — 他者の作業には手を触れない |
| Clean な Org Profile リポジトリで変更を行ったが Push しなかった | Clean な他者リポジトリは独自の Commit **および** 独自の Push を受け取る |
| スキップした変更を自身のログにのみ記録した | ターゲットリポジトリのタスクリスト（存在する場合）にも追加で記入する |
| 検出事項を実行ログにのみ記述した | フォルダローカルなタスクシステムの Task となる — 後から古いログを見る人はいない |
| 内部の追及作業を公開ロードマップに吊るした | まず内部を確認する。「Public roadmap」は隣の内部ファイルを使用することを意味する |
| 既知の検出事項を新しいエントリーとして重複させた | 今回の実行からの実証的証拠で既存の項目を補強する |
| 編集 Lock 中に Lock されたリポジトリに TODO 行を書き込んだ | 編集 Lock はプロジェクト全体に適用される — そこでは何も触らない |
| Push Lock を完全な禁止として誤読し、リポジトリ全体をスキップした | Lock を読む：公開のみをブロックする場合、ローカルラウンドは独立ブランチで継続する |
| Push Lock 下で Push しなかったが Topic や Description を変更した | Metadata もリモートで可視化される — 公開凍結下では同様に省略される |

## 変更履歴

### 1.6.0 (2026-07-24)
- ルール追加: 内容の修正はすべての露出面に適用される。経験的に学習 —
  ユーザーによる説明がパス 1 で Hub 内で修正されたが、気づかないうちに組織 Profile
  (EN, DE, `llms.txt`) にさらに 5 箇所残っており、9 パス後に初めて気づかれた。

### 1.5.0 (2026-07-24)
- パターンが 1 日に 3 回発生した後、Linter 診断を厳格化
  (n8n-workflow-manager ruff 0.15, clirec + swarm-ai ruff 0.16)：「まず確認」、具体的な
  敗北ルールコード、プラットフォームの分裂、`pyproject.toml` が欠落している場合の Fix としての `ruff.toml`、
  新しい Linter バージョン自体に対する検証。

### 1.4.0 (2026-07-24)
- 診断の追加: 純粋なドキュメント Commit 後に CI が赤くなった場合、最も頻繁な原因は
  固定ルールセットのない未ピン留め Linter である — 新しいツールリリースがデフォルトをずらし、
  変更されていないコードを赤くする。Fix: ルールセットを固定し、新しいルールを Task とする。
  2 回連続で発生（n8n-workflow-manager で ruff 0.15、clirec で 0.16）。

### 1.3.0 (2026-07-24)
- 新セクション「検出事項は Task となる」: ラウンドで自ら修正しない内容は、発見された瞬間に
  プロジェクトのフォルダローカルなタスクシステムのエントリーとなる — 次の担当者が目にする場所であり、
  終了した実行のログではない。内部リストと公開ロードマップの分離、重複ではなく補強、Commit を伴う完了項目を含む。

### 1.2.0 (2026-07-24)
- プライバシーゲートが自身内部保管場所の名前も追加で検索する。これらは Secret ではないため
  アラームを発生させず、パスと Token のみを対象とするゲートを通過する — しかし読者にとっては解決不能であり、
  自身の構造を暴露する。

### 1.1.0 (2026-07-24)
- Lock を一律の禁止として扱うのではなく解釈する: 純粋な公開/Push Lock は、ラウンドを中止するのではなく
  ローカルブランチに重定向する。同時に、そのような Lock の下では Metadata、Release、
  Issue/PR 操作も省略されることを明確化した — これらは Push と同様にリモートで可視化されるためである。

### 1.0.0 (2026-07-24)
- 初版。`github-repo-care` から派生したリポジトリ事後メンテナンスのステージ 1。
