# Surface After Care — Регулярный раунд обслуживания опубликованного репозитория

## Когда применяется этот skill

Используйте его для репозитория, который **уже публичен** и требует регулярной проверки. Это облегчённый этап: всё, что можно решить внутри самого репозитория, без проведения инвентаризации сторонних репозиториев или инициирования юридической экспертизы.

Отличие от смежных skill'ов:

| Ситуация | Skill |
|---|---|
| Репозиторий публикуется впервые | `github-repo-care` |
| Репозиторий публичный, регулярный раунд обслуживания | **этот skill** |
| Дополнительная юридическая проверка + перекрёстные ссылки по всем организациям + i18n приложения | `full-after-care` (псевдоним `deep-after-care`) |
| Чисто юридическая проверка / приватность / лицензии перед публикацией | `repo-publish-check` |
| Синхронизация содержания языковых версий | `bilingual-doc-sync` |
| Распределение этого раунда по множеству репозиториев с честной ротацией | `rotation-check` |

## Основная идея

Опубликованный репозиторий расходится в двух направлениях: **документация описывает более старое программное обеспечение, чем то, что лежит в репозитории**, и **накапливаются файлы, которые никогда не предназначались для посторонних глаз**. Ни то, ни другое обычно не катастрофично, но и то, и другое стоит именно тех пользователей, которых вы хотите привлечь: один уходит, потому что инструкция по установке больше не подходит, а другой — потому что спотыкается в корневом каталоге о `AUFGABEN.txt` и `Plan.txt` и получает впечатление, что здесь кто-то работает только для себя.

Этот раунд наводит порядок в обоих направлениях. Он намеренно сделан повторяемым: лучше четыре раза в год по полчаса, чем один раз генеральная уборка.

## Порядок выполнения

Последовательность не случайна. Шаг 0 стоит в самом начале, так как он определяет объем всех последующих шагов. Шаг 2 выполняется перед любым push'ем изменений — иначе вы отправите улучшения поверх состояния, которое ещё только предстоит очистить. Шаг 1 выполняется исключительно на стороне сервера и ничему не мешает.

### 0. Инвентаризация площадок дистрибуции

**Перед тем как что-либо менять: выясните, где именно находится этот проект.** Репозиторий GitHub редко бывает единственной площадкой. Исправленный README малополезен, если страница пакета npm продолжает показывать старую версию с неверными инструкциями по установке — а именно туда попадает большинство пользователей, так как реестры пакетов часто ранжируются в поисковых системах выше, чем сам репозиторий.

```bash
# Manifeste verraten die Kanäle (Deutsch)
cat package.json pyproject.toml setup.py Cargo.toml 2>/dev/null | rg -n "name|version|keywords|repository|homepage"
rg -n "npmjs.com|pypi.org|marketplace|registry|crates.io|hub.docker|zenodo|doi" README* docs/ .github/ 2>/dev/null

# Veröffentlichten Stand der Kanäle abfragen (nur was zutrifft) (Deutsch)
npm view <paket> version description keywords 2>/dev/null
pip index versions <paket> 2>/dev/null
gh release list --repo ORG/REPO --limit 5
```

Типичные площадки: npm, PyPI, Crates, Docker Hub, реестр MCP, каталоги плагинов/skill'ов, маркетплейсы VS Code или браузеров, магазины приложений, Zenodo/DOI, веб-сайт проекта, профиль организации, `llms.txt`, зеркальные репозитории на других хостах.

Запишите найденный список в журнал выполнения. Отныне он является **целевым множеством**: каждое изменение из последующих шагов в конце сверяется с этим списком (см. «Паритет по всем площадкам»). Если вы обнаружите площадку, которую больше никто не поддерживает и которая указывает на устаревшее состояние, это отдельная находка — либо обновите её, либо сознательно отозовите, но не оставляйте как есть.

### 1. Установка Topics (тем)

Topics — важнейшая поисковая площадка внутри GitHub, и они почти ничего не стоят.

```bash
gh repo view ORG/REPO --json nameWithOwner,description,repositoryTopics,homepageUrl,visibility
gh repo edit ORG/REPO --add-topic <topic> --add-topic <topic>
```

Цель — примерно 5–12 Topics с трёх точек зрения: **чем это является** (`cli`, `mcp-server`, `python-library`), **о чём это** (`file-management`, `tax`, `note-taking`) и **как это работает** (`local-first`, `offline`, `privacy`). Ориентируйтесь на Topics, реально используемые в аналогичных проектах — выдуманные Topics не приведут пользователей. Заодно проверьте Description и Homepage, они находятся в том же представлении.

У Topics есть аналоги на других площадках из Шага 0: `keywords` в `package.json`, `keywords`/`classifiers` в `pyproject.toml`, категории и теги в маркетплейсах и магазинах. Держите их идентичными по содержанию — это одно и то же решение, просто в нескольких местах.

### 2a. Фильтр приватности (Privacy Gate) — выполняется всегда

Этот шаг никогда не пропускается, даже при внешне безобидном раунде. Поиск ведётся в **отслеживаемом (tracked)** множестве, а не в видимом рабочем дереве, потому что в этом и заключается разница между «выглядит чистым» и «является чистым».

```bash
git ls-files
rg -n "C:\\\\Us[e]rs\\\\|/home/[a-z]|s[k]-[A-Za-z0-9]{16}|gh[p]_|gh[o]_|AKIA[0-9A-Z]{16}|API[_-]?KEY|TO[K]EN|PASS[W]ORD|SEC[R]ET|BEGIN [A-Z ]*PRIVATE KEY" $(git ls-files)
rg -n "\x{C3}\x{83}|\x{C2}\x{A0}|\x{FFFD}" $(git ls-files -- '*.md' '*.txt' '*.json')
```

Дополните шаблон **именами ваших собственных внутренних хранилищ** — папки пайплайнов, тематические каталоги, приватные рабочей области:

```bash
rg -n "\.SOFTWARE|\.RESEARCH|_control-center|<weitere eigene Ordnernamen>" $(git ls-files)
```

Такие ссылки не являются секретами и не вызывают тревогу, поэтому они проскакивают — но для читателей они **неразрешимы** («перенесено из пайплайна .SOFTWARE» ничего не говорит посторонним) и раскрывают вашу внутреннюю структуру. Их следует заменить или удалить, а не просто терпимо к ним относиться. Поиск, проверяющий только `C:\Users\...` и шаблоны токенов, гарантированно их не найдёт.

Нашли что-то? Тогда **тип** находки определяет дальнейшие действия — см. раздел «Правило Force-Push». Секрет, который хоть раз был закоммичен, скомпрометирован: удаления из `HEAD` недостаточно, его необходимо ротировать.

### 2b. Проверка намерения публикации документов

Самая суть этого раунда. Пройдитесь по отслеживаемым файлам `.md`, `.txt` и `.json` и спросите себя по поводу каждого файла: **Предназначался ли он хоть когда-либо для посторонних?**

```bash
git ls-files -- '*.md' '*.txt' '*.json' | sort
```

Не угадывайте по имени файла — бегло загляните внутрь. `PLAN.md` может быть публичной дорожной картой, а безобидно звучащий `notes.md` — содержать внутреннюю стратегию ценообразования. Три категории:

**Относится к репозиторию** — README, LICENSE, CHANGELOG, SECURITY, CONTRIBUTING, `docs/`, справочники API, примеры конфигураций, реальные дорожные карты, манифесты (`package.json`, `pyproject.toml`), lock-файлы, конфигурация CI.

**Не относится к репозиторию, но не критично** — обычный случай этого раунда. Файлы задач и планирования (`AUFGABEN.txt`, `Plan.txt`, `TODO-intern.md`), заметки сессий и передачи дел (`HANDOFF`, `BRIEFING`, `_handoff/`), файлы статуса собственного пайплайна, дневники разработки, `_archive/`, JSON-файлы реестров и индексов с локальными путями, промежуточные состояния и сгенерированные артефакты, рабочие файлы агентов. Такие файлы не опасны, но создают беспорядок и впечатление чужой недостроенной площадки. Обработка: добавить в `.gitignore`, выполнить `git rm --cached <файл>` и **сделать обычный push**.

**Не относится к репозиторию и является конфиденциальным** — учётные данные (Credentials), персональные данные, данные клиентов, внутренние расчёты, стратегии цен и переговоров, неопубликованные бизнес-планы, проекты договоров, всё, что имеет коммерческую ценность. Здесь обычного коммита недостаточно — см. Правило Force-Push.

В случае с `.json` стоит присмотреться внимательнее: манифесты и lock-файлы остаются, но локальные конфиги, файлы задач/реестров, дампы экспорта и всё с абсолютными путями или именами хостов — типичные «безбилетники».

Если вы удаляете файл, который кто-то мог бы искать (например, дорожную карту), кратко упомяните в коммите или в README, где теперь находится эта информация — иначе это выглядит как шаг назад.

### 3. Баннер

Баннер влияет на то, начнёт ли кто-то вообще читать. Проверьте, существует ли он и включен ли в README первым элементом.

Если он отсутствует, есть три пути — в следующем логическом порядке:

1. **Генератор изображений агента** (например, agy; слово «generate» там является триггером для создания настоящего PNG), если визуальный мотив подходит лучше, чем типографика.
2. **Codex**, если баннер должен быть создан из кода и существует образец стиля, на который можно ориентироваться.
3. **Самостоятельно в формате SVG**, если баннер представляет собой в первую очередь текстовый логотип плюс язык дизайна — это часто самый быстрый и наиболее контролируемый вариант, и SVG можно будет изменить позже.

Соблюдайте стилевое единство, если проект входит в группу: тот же базовый цвет, та же эстетика, то же оформление текстового логотипа. Баннер, выбивающийся из общей концепции, выглядит хуже, чем его отсутствие. Обычный размер 1200x300; сохраняйте как PNG в репозиторий, а исходник SVG — рядом.

### 4. Сверка утверждений с реальным состоянием

Здесь создаётся наибольшая ценность. README утверждает вещи — проверьте их, вместо того чтобы верить на слово:

- **Версия** в README/Badge против `pyproject.toml`/`package.json`/`__version__` и против последнего тега релиза. При наличии нескольких носителей версии проверьте все, а не только один.
- **Путь установки** действительно промоделируйте (хотя бы мысленно): существует ли пакет под указанным именем? Верны ли команды и флаги?
- **Список возможностей (Features)** против кода: всё ли указанное присутствует, и не отсутствуют ли новые функции в списке?
- **Цифры** (количество инструментов, поддерживаемые форматы, покрытие тестами) пересчитайте в источнике, а не просто копируйте дальше. Цифры в README тихо устаревают.
- **Скриншоты** против текущего интерфейса.
- **Требования (Requirements)** (версия Python/Node, зависимости) против манифестов.
- **Ссылки** на соседние проекты, документацию и реестры: работают ли они всё ещё?

**Исправление применяется ко всем площадкам, а не только к той, где оно бросилось в глаза.** Если содержательное утверждение оказалось неверным — особенно если заказчик его поправил —, то то же самое утверждение с высокой вероятностью есть и в других местах: в профиле организации, в `llms.txt`, во второй языковой версии, в README соседнего проекта. Специально поищите его перед тем, как закрыть пункт:

```bash
gh search code "<prägnante Formulierung>" --owner ORG
```

Иначе вы исправите одно место и оставите три — и противоречие всплывёт только тогда, когдадойдёт очередь до следующего репозитория. Это не только отнимает время, но и подрывает доверие к документации: тот, кто находит два противоречивых описания одного и того же, не верит ни одному.

Затем улучшите **представление**, где оно слабое: длинные перечисления опций становятся более читаемыми в виде таблицы; блокам кода нужны языковые теги; обзор структуры или процесса в виде диаграммы Mermaid или дерева ASCII воспринимается быстрее, чем проза; первый экран должен показывать назначение, установку и пример использования, а не значки и предысторию. Если README превышает ~400 строк, вынесите подробности в `docs/` и поставьте ссылки.

**Языковое правило для README:** Стандартом является **английский `README.md`** плюс **немецкая вторая версия**. Исключение: Предметная область приложения сама по себе является немецкоязычной (немецкое право, немецкая налоговая или субсидиарная система, немецкоязычная целевая аудитория) или до сих пор существует исключительно немецкая версия — тогда немецкий остаётся основным языком. Для каждого дополнительного языка, который проект уже поддерживает, полагается отдельная версия README. Придерживайтесь соглашения об именовании, уже используемого в репозитории (`README_de.md`, `README.de.md`, `docs/README.de.md`), и не изобретайте второе рядом. Связывайте версии ссылками в заголовке.

### 6. Создание отсутствующих стандартных языков

Добавьте README на тех **стандартных языках**, которые отсутствуют: немецкий, английский, испанский, упрощенный китайский, японский, русский. Цель — охват, поэтому это относится прежде всего к пользовательским проектам; для ориентированной на разработчиков библиотеки с чисто англоязычной аудиторией русский README не даст никакой пользы, а станет лишь дополнительной обузой по обслуживанию. Принимайте решение осознанно и фиксируйте его в журнале выполнения, чтобы в следующий раз не обсуждать его снова.

Новые версии **заполняются, а не создаются пустыми** — заглушка с «TODO: translate» хуже, чем отсутствие файла вообще, так как она создает ложную полноту. Параллелизм содержания и обратную синхронизацию регулирует `bilingual-doc-sync`; при наличии более двух версий имеет смысл привлечь этот skill для сверки.

### 7. Видимость и продвижение

Подумайте, какие меры действительно приведут пользователей для **этого** проекта, и реализуйте их:

- **Реестры**, к которым проект технически относится: реестры пакетов (npm, PyPI), реестр MCP, каталоги плагинов/skill'ов, маркетплейсы.
- **Курируемые списки** (`awesome-*` и тематические подборки), если критерии приёма действительно выполнены. PR в список, критериям которого проект не соответствует, стоит репутации.
- **Собственные площадки**: профиль организации, `llms.txt`, веб-сайт проекта, README экосистемы, ссылки из связанных собственных репозиториев.
- **Заметки о релизе (Release Notes)** как повод: релиз без рассказанных новшеств остаётся незамеченным.

**Шлюз одобрения (Approval Gate):** Всё, что выходит наружу — PR в чужие репозитории, записи в чужие списки, посты, заявки —, **предлагается и выполняется только после явного одобрения**, если для этого канала нет постоянного разрешения. Изменения на собственных площадках не требуют этого шлюза. Причина проста: отозванный PR в чужой репозиторий виден публично и бросает тень на проект.

### 8. Запись на страницах организаций

Сначала собственная организация: указан ли репозиторий в README профиля (`ORG/.github` → `profile/README.md`) вообще, в правильном ли разделе, с актуальным ли описанием?

```bash
gh api user/orgs --jq '.[].login'
```

Затем пройдите по **всем** организациям и ответьте на один вопрос по каждой организации: выиграет ли посетитель этой страницы организации от данного репозитория? Обычно ответ «нет» — тогда «не ссылаться» является правильным результатом, а не пробелом. Где ответ «да» (тематическая близость, общие пользователи, инструмент, дополняющий тамошние проекты), поставьте ссылку с одной строкой, объясняющей пользу, а не просто называющей имя.

Профиль находится в отдельном репозитории (`ORG/.github`). Изменения там поддерживаются и отправляются (push) наряду с остальными — по правилу грязного дерева (Dirty Tree) из Шага 11.

### 10. Issues и Pull Requests

```bash
gh issue list --repo ORG/REPO --state open --limit 50
gh pr list --repo ORG/REPO --state open --limit 30
```

Проработайте их вместо того, чтобы просто посчитать:

- **Исправимые баги** исправляйте сразу — в этом раунде контекст и так загружен. Небольшие, чётко очерченные фиксы с тестом и ссылкой на номер Issue.
- **Уже решённые Issues** закрывайте с предложением, объясняющим, что их решило.
- **Неясные сообщения** требуют точного уточняющего вопроса (версия, ОС, шаги воспроизведения).
- **PR**: действительно прочитайте Diff, запустите тесты, затем слейте (merge) или аргументированно ответьте. PR, месяцами лежащий без ответа, стоит больше доброжелательности, чем вежливый отказ.
- **Устаревшие случаи (Stale)** разрешайте, а не тащите дальше.

**Шлюз одобрения:** Публичные комментарии, закрытия с обоснованием и слияния чужих вкладов являются внешней коммуникацией — предоставляйте их перед выполнением, если нет постоянного разрешения. Чистые фиксы кода в собственном репозитории этим не затрагиваются.

### 11. Коммит, push, верификация

Раунд заканчивается не изменениями, а тем, что они **оказались снаружи**. Рабочее дерево, полное неотправленных улучшений — худший результат: следующая сессия — возможно, другой агент или другое устройство — должна сначала вникать в чужое полуготовое состояние, а на публичных площадках ничего не улучшилось.

Перед push'ем кратко проверьте то, что поддаётся проверке: запустите тесты и smoke-проверки, при изменениях документации проверьте ссылки и отрендеренный вид. Затем объедините в **тематически разделённые коммиты**, вместо того чтобы сваливать всё в один сборный коммит — уборка, обновление документации и исправление багов являются тремя разными вещами, и тот, кто позже захочет откатить одну из них, будет благодарен:

```bash
git add .gitignore && git rm --cached <interne dateien>
git commit -m "chore: interne Arbeitsdateien aus dem Repo nehmen"
git commit -am "docs: README auf aktuellen Stand (Version, Toolzahl, Screenshots)"
git commit -am "fix: <Issue-Nummer> ..."

git pull --rebase        # bei divergiertem Branch, vor dem Push
git push
```

После этого верифицируйте вместо того, чтобы предполагать: удалённый README в отрендеренном виде, прогон CI, состояние релизов и тегов.

```bash
gh run list --repo ORG/REPO --limit 3
gh repo view ORG/REPO --json description,repositoryTopics,url
```

**Если CI «красный», хотя ваш коммит затронул только документацию**, причина почти никогда не в вас. Самый частый случай — встретившийся за один день **трижды** в этом семействе репозиториев — это **незакреплённый линтер без зафиксированного набора правил**. Проверьте это **в первую очередь**, прежде чем подозревать что-либо в своём коммите.

Механизм: Если в workflow запускается `ruff check` (или flake8, eslint...) с незакреплённой зависимостью (`ruff>=0.12` или вообще без версии) и отсутствует явный выбор правил (`[tool.ruff.lint] select = [...]`, при отсутствии `pyproject.toml` — собственный `ruff.toml`), то линтер следует дефолту **свежеустановленной** версии. Новый релиз линтера смещает этот дефолт, и неизменённая кодовая база становится «красной». Признаки:

- Коды правил, которых у проекта никогда не было (`UP045`, `UP006`, `BLE001`, `RUF100`, `DTZ005`, `N999`...), иногда в трехзначном количестве.
- Сбой часто оказывается **расколот по платформам**: раннеры с кэшированной старой версией остаются «зелеными», свежие становятся «красными».
- Иногда правило делает замечание неисправимому элементу (`N999` самому имени пакета) — верный признак того, что оно никогда не было стандартом.

Исправление: зафиксировать набор правил, который раньше был «зеленым» — `select = ["E4","E7","E9","F"]` являются классическими дефолтами ruff. Если `pyproject.toml` отсутствует, создайте `ruff.toml`. Проверьте относительно **новой** версии самого линтера (установить, без конфига воспроизвести находки, с конфигом убедиться в "passed"). Новые правила входят в проект как **задача** — осознанное принятие является рішенням, а не побочным эффектом обновления инструмента. Это реальная, повторяющаяся проблема: без пина CI снова сломается при следующем релизе линтера в **каждом** так настроенном репозитории.

Два случая, когда push **не** выполняется: когда для проекта действует мораторий на публикацию или сдачу, или когда состояние заведомо незавершённое. И то, и другое — исключения, требующие обоснования; нормальный случай — закоммитить и отправить (push).

При моратории на публикацию раунд не прерывается, а **перенаправляется**: закоммитить локально в отдельной ветке (`judging-hold/...`, `freeze/...`), оставить основную ветку нетронутой в сданном состоянии, отметить причину блокировки в журнале выполнения и догнать после снятия. При этом важно соблюдать последовательность: заблокирован не только `git push`, но и **любое внешне видимое изменение** — Topics, Description, Homepage, релизы, действия с Issues и PR изменяют опубликованный проект точно так же.

Если существуют другие клоны того же репозитория (второе устройство, копия для деплоя, зеркало), подтяните их сразу после push'а. Клон, отстающий на десять коммитов, при следующем поиске ошибок выдаст диагностику на состоянии, которого больше нет.

#### Изменения в других репозиториях — Исключение грязного дерева (Dirty Tree)

Этот раунд регулярно вызывает изменения **за пределами** обслуживаемого репозитория: строка в профиле организации (Шаг 8), позже в глубоком раунде — обратная ссылка в связанном репозитории. Такие изменения также коммитятся и отправляются — неопубликованная обратная ссылка не существует.

Перед тем как трогать чужой репозиторий, кратко проверьте его состояние:

```bash
git -C <pfad> status --porcelain
```

**Чистое рабочее дерево (Clean)** → внести изменение, закоммитить в **отдельном, тематически чистом коммите** (`docs: link <projekt>`) и отправить. Не смешивать с коммитами обслуживаемого репозитория: это другой репозиторий со своей историей и читателями.

**Грязное (Dirty), но чужие изменения лежат в других файлах** → собственное изменение всё равно можно сделать чисто. Застейджите и закоммитьте **точно по пути только свой файл**, чтобы чужая непроверенная работа не ушла вместе с вашим коммитом:

```bash
git -C <pfad> add README.md
git -C <pfad> commit -m "docs: link <projekt>"     # nur der gestagte Pfad
```

Но **не отправляйте (don't push)**. Коммит локально бесвреден; push не обязательно будет таковым: вы не знаете, к чему ведёт чужое рабочее состояние — возможно, его сейчас правят, делают rebase или иначе режут, и ваш push заставит других разбираться с этим. Локальный коммит сохраняет работу, никому ничего не навязывая; прогон, который позже обратится к тому репозиторию, найдет его и заберёт с собой.

**Грязное в том самом файле, который вам нужно изменить** → не трогать. Здесь вам пришлось бы строить поверх чужого промежуточного состояния и коммитить его вместе; понимание его сперва стоит дороже, чем эта одна ссылка.

**Активный Lock (`LOCK*.txt`) в целевом репозитории** → **сначала прочитайте Lock, вместо того чтобы относиться к нему как к категорическому запрету.** Блокировка описывает свой собственный объем, и он часто узкий, а не «вообще ничего». Типичные случаи:

- **Блокировка редактирования** («здесь прямо сейчас кто-то работает») → ничего не трогать, даже побочные файлы.
- **Чистая блокировка публикации/push'а** (сдача, жюри, заморозка) → локальная работа остаётся разрешённой, заблокирован только удалённый контакт. Работать в отдельной ветке и коммитить локально; **шаги с удалённым эффектом опускаются** — не только push, но и Topics, Description, Homepage, релизы и действия с Issues/PR, так как они тоже меняют опубликованный проект.

Чтение блокировки, запрещающей только push, как полного запрета, теряет всю локальную часть раунда без выигрыша в безопасности. И наоборот, просто отказаться от push'а, но изменить метаданные — недостаточно. В случае сомнений процитируйте Lock и спросите.

#### Пожелание не должно быть потеряно

Если изменение **не** выполнено по любой из этих причин, оно переходит в список задач целевого репозитория — `AUFGABEN.txt`, `TODO.md` или `TODO.txt`, в зависимости от того, что там существует. Запись с датой, желаемым изменением и причиной:

```markdown
- [ ] [2026-07-24, after-care] Rückverweis auf <projekt> im README ergänzen
      (übersprungen: README hatte uncommittete Fremdänderungen)
```

В этом разница между «отложено» и «забыто»: список задач находится там, куда в любом случае заглянет следующий исполнитель этого репозитория — гораздо надежнее, чем запись в журнале чужого прогона. Если списка задач не существует, не создавайте его; незакрытого пункта в собственном журнале выполнения достаточно.

При **активном Lock это тоже не применяется** — файл не трогается, а запись остаётся в собственном журнале выполнения. Отметьте его в обоих случаях и там, чтобы ротация знала об открытом пункте.

В завершение обслужить площадки из Шага 0 — см. следующий раздел.

## Паритет по всем площадкам дистрибуции

В завершение раунда сверьтесь со списком из Шага 0: **Каждое изменение, которое увидел бы пользователь, должно дойти до каждой площадки, где он его ищет.** Репозиторий, страница npm которого рассказывает другую историю, находится в худшем положении, чем репозиторий с единственной площадкой.

Решающий механизм: **Реестры пакетов показывают README последнего publish'а, а не текущее состояние репозитория.** Исправление README на npm или PyPI становится видимым только с новой версией. Если исправление существенно по содержанию (неверная установка, неверная версия, устаревший список возможностей), к нему полагается патч-релиз — иначе фикс останется безрезультатным.

| Площадка | Что там поддерживается | Как поступает |
|---|---|---|
| npm | README, `description`, `keywords`, ссылка на репозиторий | Только через `npm publish` (патч-версия); метаданные берутся из `package.json` |
| PyPI | README (`long_description`), классификаторы, URL проекта | Только через новую загрузку; метаданные из `pyproject.toml` |
| Реестр MCP / Каталоги плагинов | Описание, версия, список инструментов, вводная документация | В зависимости от реестра — обновление манифеста или повторная сдача |
| Маркетплейс / Магазин | Описание, скриншоты, категории, языковые версии | Через соответствующий интерфейс управления; скриншоты там стареют особенно быстро |
| Docker Hub / Реестр контейнеров | Описание, теги, пример использования | Описание репозитория плюс новый тег |
| Zenodo / DOI | Метаданные, авторы, версия | In-place редактирование для метаданных, новая версия для содержимого |
| Веб-сайт / Профиль организации / `llms.txt` | Краткое описание, ссылка, позиционирование | Прямо редактируемые — самые дешёвые площадки, поэтому никогда не забывать |

При поднятии версии **все носители версии** должны подтягиваться одновременно: манифест, константа в коде, значок README, чейнджлог, тег релиза, `llms.txt`. Наполовину поднятое состояние версии диагностировать сложнее, чем сквозное старое.

Если обновление на какой-то площадке сейчас невозможно или нецелесообразно (например, релиз только из-за опечатки), зафиксируйте это в журнале выполнения, чтобы следующий раунд не принял расхождение за оплошность.

## Правило Force-Push

Стандарт — **никакого Force-Push**. Задним числом проигнорировать внутренние файлы планирования не оправдывает переписывание истории: затраты высоки, каждый клон и форк ломается, открытые PR становятся непригодными — а выигрыш мал, так как содержимое безвредно. Обычный путь:

```bash
git rm --cached <datei>            # aus dem Tracking, bleibt локально сохранённым
# .gitignore ergänzen (Deutsch)
git commit -m "chore: interne Arbeitsdateien aus dem Repo nehmen"
git push
```

Переписывание истории (и тем самым push с `--force-with-lease`) оправдано только при **реальных утечках (Leaks)**: учётные данные и ключи, персональные данные или данные клиентов, а также документы с реальной коммерческой ценностью — внутренние расчёты, стратегии цен, неопубликованные планы, детали договоров. В этом случае:

1. Сначала **ротировать** затронутые секреты — история к этому моменту уже скопирована, сфоркана и находится в кэшах. Ротация работает, удаление — лишь косметика.
2. Очистить историю (`git filter-repo` или BFG), сделать push с `--force-with-lease`.
3. Проверить форки и кэши; при необходимости обратиться в поддержку GitHub по поводу осиротевших объектов.
4. Зафиксировать процесс в журнале выполнения: что, когда, какая ротация.

При сомнениях между «некритично» и «чувствительно»: относиться как к чувствительному и предоставить на рассмотрение. Затраты асимметричны.

## Находки становятся задачами, а не просто строками журнала

Раунд обслуживания регулярно находит больше, чем может или должен исправить в том же раунде: отсутствующая языковая версия, отставание по модернизации, публикация, которая так и не состоялась. **Такие находки в момент обнаружения становятся задачами** — иначе они повиснут в журнале завершённого прогона, куда следующий исполнитель проекта не заглянет.

Задача относится к **локальной системе задач папки проекта** — туда, куда заглянет тот, кто следующим будет работать над этим проектом. Обычно это `AUFGABEN.txt` или `TODO.md` в папке проекта, и она часто **лежит не в Git-клоне**, а в каталоге, где живёт планирование. Клон содержит код, папка проекта — управление; запись в клоне, которая исчезнет при следующем `git clean`, не является задачей.

Учитывайте три вещи:

1. **Отделяйте внутренний список задач от публичной дорожной карты.** `TODO.md` может быть ухоженной публичной дорожной картой — тогда это не место для внутренней доработки. Загляните внутрь перед добавлением: если там есть заголовок вроде «Public roadmap», пишите во внутренний файл рядом (`AUFGABEN.txt`) и отмечайте как внутреннее.
2. **Проверяйте существующие записи вместо дублирования.** Часто находка уже там записана. Тогда она не создаётся заново, а **обогащается** эмпирическим доказательством из этого прогона («подтверждено: `--help` выдаёт полностью немецкий вывод»). Известный пункт со свежим доказательством ценнее, чем вторая запись рядом.
3. **Записывайте выполненное.** То, что раунд исправил, добавляется как отмеченный пункт с хэшем коммита. Это объясняет следующему раунду, почему находка исчезла, и предотвращает её повторное «открытие».

Сформулируйте задачу так, чтобы она была понятна без контекста этого прогона: что найдено, почему это важно, каков следующий шаг. «i18n неполный» — не задача; «Каталог содержит только `status.title`, es/zh/ja/ru пустые — сначала перенести строки CLI в каталог, затем заполнить все шесть языков» — задача.

## Журнал выполнения

Зафиксируйте результат в `_after-care/LOG.md` (папка относится к `.gitignore` — это материал пайплайна, а не содержимое репозитория, строго по правилу из Шага 2b). На один прогон — одна строка с датой, уровнем и осознанными решениями:

```markdown
## 2026-07-24 — surface
- Flächen: GitHub, npm (<paket>), MCP-Registry, Org-Profil, llms.txt
- Topics: +local-first, +mcp-server; keywords in package.json angeglichen
- Entfernt: AUFGABEN.txt, _handoff/ (gitignored, kein Force-Push nötig)
- README: Version 0.9 -> 1.2 korrigiert, Toolzahl 23 -> 26 nachgezählt
- Sprachen: EN + DE gepflegt; ES/ZH/JA/RU bewusst nicht (entwicklernahes Publikum)
- Issues: #12 gefixt, #7 geschlossen (erledigt), #15 Rückfrage gestellt
- Push: 3 Commits, CI grün; npm-Republish 1.2.1 wegen README-Korrektur
- Offen: Store-Screenshots veraltet, brauchen neuen Build
```

Журнал избавляет следующий раунд от повторного принятия тех же решений и является основой для ротационных прогонов обслуживания по множеству репозиториев (`rotation-check`).

## Частые ошибки

| Ошибка | Исправление |
|---|---|
| Рассматривали только рабочее дерево, а не `git ls-files` | Всегда проверять отслеживаемый сет — проблема кроется там |
| Фильтр приватности направлен только на пути и токены | Искать также имена собственных пайплайнов/папок — они не вызывают тревогу и проскакивают |
| Удален внутренний файл с переписыванием истории | Для некритичных файлов достаточно `git rm --cached` + обычный push |
| Секрет удален из `HEAD` и задача считается решенной | Ротировать секрет; всё остальное — косметика |
| Файлы классифицированы по имени | Бегло заглянуть внутрь — имена не гарантируют намерение |
| Цифры в README скопированы, а не пересчитаны | Считать в источнике (список инструментов, прогон тестов, манифест) |
| Новая языковая версия создана как пустая заглушка | Заполнить или опустить — заглушка имитирует полноту |
| Введена вторая конвенция именования README рядом с существующей | Перенять существующую конвенцию |
| PR в чужой список отправлен без одобрения | Предоставлять внешнюю коммуникацию; свободны только собственные площадки |
| Issues посчитаны вместо обработки | Исправить, закрыть или задать уточняющий вопрос — каждый случай получает статус |
| Баннер создан единолично в чужом стиле | Соблюдать дизайн-код экосистемы |
| README в репозитории исправлен, страница npm/PyPI показывает старый | Страницы реестров берутся из последнего publish — сделать патч-релиз |
| Версия поднята только в манифесте | Все носители версии одновременно: манифест, код, значок, чейнджлог, тег, `llms.txt` |
| Изменения готовы, но оставлены неотправленными | Коммит и push входят в раунд; только блокировки оправдывают исключение |
| Всё сгружено в один общий коммит | Разделять уборку, документацию и фиксы — иначе ничто нельзя откатить по отдельности |
| CI «красный» после коммита документации, подозревают себя | Незакрепленный линтер без `select` следует дефолту новой версии — зафиксировать набор правил |
| Неверное утверждение исправлено только там, где замечено | Искать формулировку по всей организации — она часто есть в профиле организации, в `llms.txt` и во второй версии |
| Работали в грязном чужом репозитории с `commit -a` | Стейджить и коммитить точно по пути, не делать push — чужая работа остаётся нетронутой |
| Изменение сделано в чистом репозитории профиля организации, но не отправлено | Чистые чужие репозитории получают собственный коммит **и** собственный push |
| Пропущенное изменение отмечено только в своем журнале | Дополнительно внести в список задач целевого репозитория (если есть) |
| Находка записана только в журнал выполнения | Становится задачей в локальной системе задач папки — в старые журналы позже никто не смотрит |
| Внутренняя доработка привязана к публичной дорожной карте | Сначала заглянуть внутрь; «Public roadmap» означает: использовать внутренний файл рядом |
| Известная находка продублирована как новая запись | Обогатить существующий пункт эмпирическим доказательством из этого прогона |
| Строка TODO записана в заблокированный репозиторий при блокировке редактирования | Блокировка редактирования действует на весь проект — ничего там не трогать |
| Блокировка push прочитана как полный запрет и репозиторий пропущен целиком | Прочитать Lock: если он блокирует только публикацию, локальный раунд продолжается в отдельной ветке |
| При блокировке push не делался push, но изменены Topics или Description | Метаданные также видны удаленно — при моратории на публикацию они опускаются |

## История изменений

### 1.6.0 (2026-07-24)
- Добавлено правило: Содержательное исправление применяется ко всем площадкам. Усвоено эмпирически —
  уточнение пользователя в прогоне 1 было исправлено в Hub, но незаметно оставалось ещё в пяти местах
  в профиле организации (EN, DE, `llms.txt`) и бросилось в глаза только через девять прогонов.

### 1.5.0 (2026-07-24)
- Ужесточена диагностика линтера после того, как паттерн встретился трижды за день
  (n8n-workflow-manager ruff 0.15, clirec + swarm-ai ruff 0.16): «сначала проверить», конкретные
  выдающие коды правил, раскол по платформам, `ruff.toml` как фикс при отсутствии `pyproject.toml`,
  проверка относительно новой версии самого линтера.

### 1.4.0 (2026-07-24)
- Добавлена диагностика: Если CI становится «красным» после коммита только документации, наиболее
  частая причина — незакреплённый линтер без зафиксированного набора правил: новый релиз инструмента
  смещает дефолт и делает неизменённый код «красным». Фикс: зафиксировать набор правил, новые правила — как задача.
  Встретилось дважды подряд (n8n-workflow-manager с ruff 0.15, clirec с 0.16).

### 1.3.0 (2026-07-24)
- Новый раздел «Находки становятся задачами»: То, что раунд не исправляет сам, в момент обнаружения
  становится записью в локальной системе задач папки проекта — там, куда заглянет следующий исполнитель,
  а не в журнале завершённого прогона. Включая разделение внутреннего списка и публичной дорожной карты,
  обогащение вместо дублирования, выполненное с коммитом.

### 1.2.0 (2026-07-24)
- Фильтр приватности дополнительно ищет имена собственных внутренних хранилищ. Они не являются
  секретами, поэтому не вызывают тревогу и проходят фильтр, нацеленный только на пути и токены, —
  но остаются неразрешимыми для читателей и раскрывают собственную структуру.

### 1.1.0 (2026-07-24)
- Блокировки читаются, а не трактуются как категорический запрет: чистая блокировка публикации/push'а
  перенаправляет раунд на локальную ветку вместо его отмены. Заодно уточнено, что при такой блокировке
  метаданные, релизы и действия с Issues/PR также опускаются — они так же видны удалённо, как и push.

### 1.0.0 (2026-07-24)
- Начальная версия. Этап 1 постобслуживания репозитория, производный от `github-repo-care`.
