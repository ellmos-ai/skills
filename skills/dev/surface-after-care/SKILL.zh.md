# Surface After Care — 已发布仓库的定期维护轮次

## 何时使用此技能

当某个仓库**已经公开**且需要进行定期例行检查时使用此技能。它是低成本阶段：包含所有可在仓库自身内部决定的事项，无需清查第三方仓库或发起法律鉴定。

与相关技能的区别：

| 场景 | 技能 |
|---|---|
| 仓库首次公开发布 | `github-repo-care` |
| 仓库已公开，定期维护轮次 | **本技能** |
| 额外包含法律审查 + 跨所有组织的关联引用 + 应用 i18n | `full-after-care` (同义词 `deep-after-care`) |
| 公开前的纯法律/隐私/许可证审查 | `repo-publish-check` |
| 保持文档多语言版本的内容同步 | `bilingual-doc-sync` |
| 在多个仓库间公平轮换分配本轮检查 | `rotation-check` |

## 核心理念

一个已发布的仓库通常会在两个方向上产生偏离：**文档描述的是比仓库内实际代码更旧的软件版本**，以及**积累了大量从未打算给外部人员查看的文件**。这两者通常都不是致命的，但都会精准流失你想吸引的目标用户 —— 有人因为安装指南失效而放弃使用，有人因为在根目录看到 `AUFGABEN.txt` 和 `Plan.txt` 而产生“作者只是在为自己随便写代码”的印象。

本轮维护旨在同时清理这两类问题。它的设计倡导高频重复：与其每年搞一次大扫除，不如每季度花半小时维护。

## 工作流程

步骤顺序经过精心设计。步骤 0 放在最前面，因为它决定了后续所有步骤的作用范围。步骤 2 在任何 Commit/Push 之前运行 —— 否则你会在尚未清理的陈旧代码上叠加提交改进。步骤 1 纯属服务端配置，不会产生干涉。

### 0. 清查分发平台

**在修改任何内容之前：首先明确该项目分布在哪些地方。** GitHub 仓库很少是唯一的展示平台。如果 npm 包页面依然展示着包含错误安装命令的旧版 README，那么仅修改 GitHub 上的 README 毫无意义 —— 事实上大多数用户正是从包注册表进入的，因为包注册表在搜索引擎中的排名往往高于仓库本身。

```bash
# 从清单文件中查找分发渠道
cat package.json pyproject.toml setup.py Cargo.toml 2>/dev/null | rg -n "name|version|keywords|repository|homepage"
rg -n "npmjs.com|pypi.org|marketplace|registry|crates.io|hub.docker|zenodo|doi" README* docs/ .github/ 2>/dev/null

# 查询各渠道已发布的状态（仅查询适用的渠道）
npm view <paket> version description keywords 2>/dev/null
pip index versions <paket> 2>/dev/null
gh release list --repo ORG/REPO --limit 5
```

常见平台包括：npm、PyPI、Crates、Docker Hub、MCP 注册表、Plugin/Skill 目录、VS Code 或浏览器 Marketplace、App Store、Zenodo/DOI、项目官方网站、组织 Profile 页面、`llms.txt`、其他托管平台上的镜像仓库。

在执行日志中记录查明的文件列表。从现在起它就是你的**目标集合**：后续步骤中的各项修改，最终都要镜像同步至该列表中的所有平台（参见"所有分发平台的一致性"）。如果发现某个无人维护且指向废弃版本的平台，这本身就是一项检查发现 —— 要么更新它，要么明确撤销，绝不能任其悬空。

### 1. 设置主题标签 (Topics)

Topics 是 GitHub 内部最重要的检索入口，且几乎没有任何成本。

```bash
gh repo view ORG/REPO --json nameWithOwner,description,repositoryTopics,homepageUrl,visibility
gh repo edit ORG/REPO --add-topic <topic> --add-topic <topic>
```

目标是从三个维度设置约 5–12 个 Topics：**它是什么**（`cli`、`mcp-server`、`python-library`）、**它的领域**（`file-management`、`tax`、`note-taking`）以及**它的工作方式**（`local-first`、`offline`、`privacy`）。参考同类热门项目实际使用的标签 —— 自创的标签无法吸引流量。同时检查 Description 和 Homepage，它们处于同一视图中。

Topics 在步骤 0 的其他平台上也有对应项：`package.json` 中的 `keywords`，`pyproject.toml` 中的 `keywords`/`classifiers`， Marketplace 和 Store 中的分类与标签。保持它们在内容上的一致 —— 它们是同一决策的不同呈现。

### 2a. 隐私关卡 (Privacy-Gate) — 始终运行

无论本轮维护看起来多么简单，此步骤绝不能省略。必须在**已追踪 (tracked)** 的文件集合中进行检索，而非仅看当前的工作树，因为这正是"看起来干净"与"真正干净"的区别所在。

```bash
git ls-files
rg -n "C:\\\\Us[e]rs\\\\|/home/[a-z]|s[k]-[A-Za-z0-9]{16}|gh[p]_|gh[o]_|AKIA[0-9A-Z]{16}|API[_-]?KEY|TO[K]EN|PASS[W]ORD|SEC[R]ET|BEGIN [A-Z ]*PRIVATE KEY" $(git ls-files)
rg -n "\x{C3}\x{83}|\x{C2}\x{A0}|\x{FFFD}" $(git ls-files -- '*.md' '*.txt' '*.json')
```

在检索模式中补充**你自己的内部存放路径名称** —— 流水线文件夹、主题目录、个人私有工作区：

```bash
rg -n "\.SOFTWARE|\.RESEARCH|_control-center|<weitere eigene Ordnernamen>" $(git ls-files)
```

此类引用并非 Secret，不会触发安全报警，因此极易漏网 —— 但它们对外部读者来说是**无法解析**的（例如"从 .SOFTWARE 流水线迁移"对陌生人毫无意义），并且泄露了内部目录结构。应当替换或删除它们，而不是听之任之。仅针对 `C:\Users\…` 和 Token 模式的检索保证查不出此类问题。

如果发现了隐患，由问题的**性质**决定后续处理方式 —— 参见"Force-Push 规则"一节。一旦密钥被 Commit 提交过，就已彻底失效：仅在 `HEAD` 中删除是不够的，必须进行轮换。

### 2b. 审查文档的发布意图

本轮维护的核心所在。逐一查看已追踪的 `.md`、`.txt` 和 `.json` 文件，并询问：**这个文件当初是打算给外部人员看的吗？**

```bash
git ls-files -- '*.md' '*.txt' '*.json' | sort
```

不要仅凭文件名猜测 —— 务必打开快速浏览。一个 `PLAN.md` 可能是公开的路线图，也可能是内部的定价策略；一个听起来无害的 `notes.md` 可能是私密笔记。分为三类：

**应当保留在仓库中** — README、LICENSE、CHANGELOG、SECURITY、CONTRIBUTING、`docs/`、API 引用、示例配置、真实的 Roadmap、清单文件（`package.json`、`pyproject.toml`）、Lockfile、CI 配置。

**不应存在于仓库中，但无敏感信息** — 本轮维护的最常见情况。任务与规划文件（`AUFGABEN.txt`、`Plan.txt`、`TODO-intern.md`）、Session 笔记与交接文件（`HANDOFF`、`BRIEFING`、`_handoff/`）、自有流水线的状态文件、开发日记、`_archive/`、包含本地路径的注册表/索引 JSON、中间生成物、Agent 临时工作文件。此类文件没有危险，但会造成杂乱并让人产生未整理工地的印象。处理方法：补充到 `.gitignore`，执行 `git rm --cached <file>` 并**正常 Push**。

**不应存在于仓库中且属于敏感信息** — Credentials、个人数据、客户数据、内部财务核算、价格与谈判策略、未公开的商业计划、合同草案、任何具备商业竞争价值的内容。此时仅做普通 Commit 是不够的，参见 Force-Push 规则。

对于 `.json` 文件需要额外注意：Manifest 和 Lockfile 应当保留，但本地配置、Task/Registry 文件、导出 Dump 以及任何包含绝对路径或主机名件都是典型的偷渡者。

如果删除了某个可能会有人寻找的文件（比如路线图），请在 Commit 或 README 中简要说明该信息现在存放在何处 —— 否则看起来会像是功能退化。

### 3. Banner 横幅

Banner 很大程度上决定了访客是否会继续阅读。检查 README 中是否存在 Banner 且作为第一元素引入。

如果缺少 Banner，有三种创建途径 —— 推荐按以下顺序考虑：

1. **智能体图像生成器**（例如 agy；在其中输入"生成"单词是触发真实 PNG 图像生成的指令），当视觉图形比单纯的文字排版更合适时使用。
2. **Codex**，当 Banner 应当由代码生成且存在可参考的视觉风格规范时。
3. **手动构建 SVG**，当 Banner 主要是文字标志（Wordmark）加上形式语言时 —— 这通常是最快且最可控的方式，且 SVG 在后续易于修改。

如果项目属于某个产品族，请保持设计语言的一致：相同的基调颜色、相同的审美风格、相同的文字标志处理。一个脱离家族风格的 Banner 比没有 Banner 效果更差。推荐尺寸为 1200x300；PNG 放入仓库，SVG 源文件保存在旁边。

### 4. 对照真实代码校对描述

这是产生最大价值的环节。README 中做出了各种声明 —— 请去代码中验证它们，而不是盲目相信：

- README/Badge 中的**版本号**与 `pyproject.toml`/`package.json`/`__version__` 以及最新的 Release Tag 进行对比。如果存在多个版本记录位置，需全部核对。
- **安装路径**实际运行一遍（至少在逻辑上推演）：该名称的包是否存在？命令和 Flag 是否匹配？
- **功能列表**对比代码：提及的功能是否全部存在？新增加的功能是否在列表中遗漏？
- **数据统计**（Tool 数量、支持的格式、测试覆盖率）在源头重新计数，而不是直接递增。README 中的数字往往在不经意间陈旧。
- **截图**对比最新的实际界面。
- **依赖要求**（Python/Node 版本、依赖包）对比 Manifest。
- 指向关联项目、文档和注册表的**链接**：是否依然有效？

**一处更正适用于所有平台，而非仅在发现问题的那个平台上修改。** 如果发现某项内容表述有误 —— 尤其是项目负责人亲自更正的情况 —— 那么相同的表述极有可能也存在于其他地方：组织 Profile、`llms.txt`、第二语言版本、关联项目的 README 中。在标记完成前进行针对性搜索：

```bash
gh search code "<特征表述>" --owner ORG
```

否则你只修正了一处，却留下了三处 —— 当下一个仓库轮到维护时，这种矛盾才会再次暴露。这不仅浪费时间，更会损害对文档的信任：当读者发现对同一件事有两种矛盾的描述时，将不再相信任何一份文档。

接着改善排版较弱的**展示效果**：选项的长列表改为表格更易读；代码块需要添加语言 Tag；结构或流程概览用 Mermaid 图表或 ASCII 树表示比长篇大论更直观；首屏高度应当展示项目目的、安装方式和使用示例，而非一堆 Badge 和背景故事。如果 README 超过 ~400 行，将细节拆分迁移至 `docs/` 并附上链接。

**README 语言规则：** 标准配置是**英文 `README.md`** 加上**德文第二版本**。例外情况：应用本身的主题领域就是德语区（德国法律、税务、资助体系、德语目标受众），或者目前仅存在德文版本 —— 此时德文保持为主语言。对于项目代码本身已支持的其他语言，均应配备对应的 README 版本。遵循仓库中已有的命名规范（`README_de.md`、`README.de.md`、`docs/README.de.md`），不要另创第二套规范。在页眉中设置互相对照的链接。

### 6. 补全缺失的标准语言版本

补全缺失的**标准语言** README 版本：德语、英语、西班牙语、简体中文、日语、俄语。其目的是扩大覆盖范围，因此这主要适用于面向最终用户的项目 —— 对于纯英文受众的开发者函数库，俄语 README 并非收益，而是额外的维护负担。请做出明确决策并将决策记录在执行日志中，以免下一轮重复讨论。

新创建的版本必须**填入实际内容，而非仅创建一个空壳** —— 带有 "TODO: translate" 的文件比没有文件更糟，因为它伪造了完整性。内容平行性与同步调整由 `bilingual-doc-sync` 处理；当超过两个语言版本时，建议调用该技能协助比对。

### 7. 可见性与推广

思考哪些措施能为**当前**项目真正带来用户，并予以实施：

- 技术上项目应当入驻的**注册表**：包注册中心（npm、PyPI）、MCP 注册表、Plugin/Skill 目录、Marketplace。
- **精选列表**（`awesome-*` 及主题收录集），前提是确实符合收录标准。向不符合标准的目标仓库提交 PR 会损害项目声誉。
- **自有平台**：组织 Profile、`llms.txt`、项目官网、生态系统 README、关联自有仓库中的引用。
- **Release Notes 发布日志**作为契机：没有讲述新特性故事的 Release 是无法引起关注的。

**审批关卡 (Approval Gate)：** 所有对外发出的动作 —— 向第三方仓库提交 PR、在第三方列表中登记、发帖、提交申请 —— 必须**先提出方案，经明确批准后方可执行**（除非对该渠道拥有长期授权）。对自有平台的修改不需要此关卡。原因很简单：向外提交后又撤回的 PR 是公开可见的，会对项目造成不良影响。

### 8. 组织页面上的条目

首先检查自己的组织：该仓库是否已在 Profile README（`ORG/.github` → `profile/README.md`）中列出？分类是否正确？描述是否最新？

```bash
gh api user/orgs --jq '.[].login'
```

然后遍历**所有**组织，对每个组织回答一个问题：访问该组织页面的访客能否从当前仓库中获益？大多数情况下答案是否定的 —— 此时"不建立链接"是正确的结论，而非遗漏。如果答案是肯定的（主题相近、目标用户重叠、补充了该组织项目的工具），请添加一行说明其具体价值的引用，而非仅罗列名称。

Profile 位于独立的仓库中（`ORG/.github`）。其中的修改将同步维护并推送 —— 遵循步骤 11 中的脏树规则。

### 10. 处理 Issue 和 Pull Request

```bash
gh issue list --repo ORG/REPO --state open --limit 50
gh pr list --repo ORG/REPO --state open --limit 30
```

深入处理它们，而非仅仅统计数量：

- **可修复的 Bug** 直接修复 —— 本轮维护中上下文本来就已经加载。提交包含测试和 Issue 编号引用的精简 Fix。
- **已解决的 Issue** 予以关闭，并附带一句话说明解决方案。
- **描述不清的报告** 进行针对性追问（版本号、操作系统、复现步骤）。
- **PR**：仔细阅读 Diff，运行测试，然后 Merge 或附带合理理由予以拒绝。一个搁置数月不处理的 PR 比礼貌拒绝更伤人心。
- **无进展的 Stale 事项** 及时清理，不要长期拖延。

**审批关卡 (Approval Gate)：** 公开评论、附带理由关闭以及 Merge 外部贡献属于对外沟通 —— 执行前需提交方案（除非有长期授权）。仓库内部纯代码修复不受此限。

### 11. 提交、推送与验证

本轮维护并非终止于本地修改，而是终止于修改**已成功发布到远端**。工作树中留下一堆未推送的改进是最糟糕的结果：下一阶段（可能是另一个 Agent 或另一台设备）必须先花时间熟悉一份陌生且半成品的状态，而公共平台上却没有得到任何改善。

在 Push 之前简要验证可测试项：运行 Test 和 Smoke 检查，对于文档修改检查链接和渲染效果。然后按**主题拆分为独立的 Commit**，而不是混在一个大包 Commit 中 —— 清理文件、更新文档和 Bug 修复是三件不同的事，后续如果有人想单独 Care/Revert 其中一项会非常感激：

```bash
git add .gitignore && git rm --cached <interne dateien>
git commit -m "chore: 将内部工作文件移出 Git 追踪"
git commit -am "docs: 更新 README 至最新状态 (版本号、Tool 数量、截图)"
git commit -am "fix: <Issue 编号> ..."

git pull --rebase        # 如果分支发生分叉，在 Push 前执行
git push
```

推送后去验证而非盲目假设：查看远端 README 的渲染效果、CI 运行状态、Release 和 Tag 状态。

```bash
gh run list --repo ORG/REPO --limit 3
gh repo view ORG/REPO --json description,repositoryTopics,url
```

**如果仅仅修改了文档 CI 却变红了**，原因几乎从来不在你身上。到目前为止最常见的情况 —— 在本仓库族群中一天内**遇到过三次** —— 是**使用了未锁定版本的 Linter 且缺乏固定的规则集**。在怀疑自己的 Commit 之前，请**首先**检查这一点。

发生机制：如果 Workflow 中针对未锁定版本的依赖（如 `ruff>=0.12` 或根本未指定版本）运行 `ruff check`（或 flake8, eslint …），且缺乏显式的规则选择（`[tool.ruff.lint] select = [...]`，若无 `pyproject.toml` 则缺少独立的 `ruff.toml`），Linter 将会直接使用**最新安装版本**的默认规则。Linter 的新版本更新了默认规则，导致未经修改的代码变红。典型特征：

- 出现项目从未配置过的规则代码（`UP045`、`UP006`、`BLE001`、`RUF100`、`DTZ005`、`N999` …），数量有时达数百个。
- 失败往往呈现**跨平台分裂**：带有旧版本缓存的 Runner 依然是绿色，而全新的 Runner 变红。
- 有时规则会报错一些无法修复的内容（如 `N999` 报错包名本身） —— 这是它从未被列为标准规则的铁证。

修复方法：锁定此前为绿色的规则集 —— `select = ["E4","E7","E9","F"]` 是经典的 ruff 默认配置。如果不存在 `pyproject.toml`，请新建 `ruff.toml`。针对**新版** Linter 本身进行验证（安装新版，无配置时复现报错，有配置时显示 "passed"）。新规则作为一项**新任务**加入项目 —— 明确采用是一项决策，而不是工具更新带来的副作用。这是一个真实的、重复发生的发现：如果不进行锁定，下次 Linter 发布新版时，**每个**类似配置的仓库 CI 都会再次崩溃。

存在两种**不进行 Push** 的情况：项目正处于发布/提交冻结期，或者当前状态明确属于未完成状态。两者都是需要说明理由的特例 —— 标准操作是：Commit 并 Push。

在发布冻结期下，本轮维护不会终止，而是**改变路由**：在独立分支（`judging-hold/…`、`freeze/…`）上进行本地提交，主分支保持在已提交的冻结状态，在执行日志中记录冻结原因，待解冻后补充同步。关键在于保持一致性：冻结的不仅是 `git push`，还包括**任何远端可见的修改** —— Topics、描述、主页、Release、Issue 和 PR 操作都会同样改变已发布的项目。

如果存在该仓库的其他克隆（第二台设备、部署副本、镜像），请在 Push 后立即同步拉取。落后十个 Commit 的克隆会在下一次排错时基于已不存在的状态给出错误诊断。

#### 修改其他仓库 — 脏树特例 (Dirty-Tree-Ausnahme)

本轮维护经常会在维护仓库**之外**产生修改：在组织 Profile 中添加一行（步骤 8），或在后续深度轮次中在关联仓库添加反向链接。此类修改同样需要 Commit 和 Push —— 未推送的反向链接等于不存在。

在修改第三方仓库前简要检查其状态：

```bash
git -C <path> status --porcelain
```

**工作树干净** → 进行修改，在**独立且主题明确的 Commit** 中提交（`docs: link <projekt>`）并 Push。切勿与当前维护仓库的 Commit 混在一起：那是另一个具有独立历史和读者的仓库。

**Dirty 但第三方修改位于其他文件中** → 你的修改依然可以干净地完成。**按具体路径仅 Stage 并 Commit 你修改的文件**，确保他人未验证的工作不会被混入：

```bash
git -C <path> add README.md
git -C <path> commit -m "docs: link <projekt>"     # 仅提交暂存的路径
```

但是**不要 Push**。该 Commit 在本地是无害的；但 Push 则未必：你不知道他人的工作状态最终目标是什么 —— 也许正在进行 Amend、Rebase 或拆分，你的 Push 会迫使他们去处理冲突。本地 Commit 保护了你的工作成果而不会强加于人；后续处理该仓库的轮次会发现并带走它。

**在你需要修改的具体文件中存在 Dirty 修改** → 切勿修改。此时你必须基于他人的中间状态进行提交；先去理解他人的修改所付出的成本远超这一条链接的价值。

**目标仓库存在活跃锁 (`LOCK*.txt`)** → **首先阅读锁文件的内容，而不是将其一律视为绝对禁令。** 锁文件会描述其具体作用范围，通常比"绝对禁止任何操作"要窄。典型情况：

- **编辑锁**（"有人正在此工作"） → 切勿触碰任何内容，包括旁边的文件。
- **纯发布/Push 锁**（提交中、评审中、冻结期） → 本地工作依然允许，仅禁止远端交互。在独立分支上工作并在本地 Commit；**远端可见的步骤予以省略** —— 不仅是 Push，还包括 Topics、描述、主页、Release 以及 Issue/PR 操作。

将仅限制 Push 的锁解读为完全禁止操作，会白白浪费本轮维护的整个本地部分而没有任何安全收益。反过来，仅不执行 Push 却依然修改元数据也是不对的。如有疑问，引用锁文件内容并提出询问。

#### 需求不能遗失

如果由于上述原因导致修改**未能**执行，请将其写入目标仓库的任务列表中 —— 根据实际存在的文件选择 `AUFGABEN.txt`、`TODO.md` 或 `TODO.txt`。添加包含日期、预期修改和原因的条目：

```markdown
- [ ] [2026-07-24, after-care] 在 README 中补充指向 <projekt> 的反向链接
      (已跳过: README 存在未提交的第三方修改)
```

这就是"延后"与"遗忘"的区别：任务列表存在于该仓库下一位维护者必然会查看的地方 —— 比记录在其他仓库维护日志中的未决事项更加可靠。如果不存在任务列表，无需专门新建；在自己的执行日志中记录未决事项即可。

在**活跃锁限制下，连上述写入操作也不适用** —— 此时保持文件完全不动，记录仅留存在自己的执行日志中。在这两种情况下都要在自己的日志中做好记录，以便轮换检查能够掌握未决事项。

最后处理步骤 0 中的分发平台 —— 参见下一节。

## 所有分发平台的一致性

在本轮维护结束时，对照步骤 0 的列表进行核对：**用户能够看到的每一项修改，必须同步更新到用户可能搜索到的每一个平台上。** 一个在 npm 上展示着不同故事的仓库，比只有一个平台的仓库状况更糟糕。

核心机制：**包注册中心展示的是上次 Publish 时的 README，而非仓库当前的真实状态。** README 在 npm 或 PyPI 上的修正只有在发布新版本时才会生效。如果修正涉及重要内容（错误的安装命令、错误的版本号、陈旧的功能列表），必须随之发布一个 Patch 版本 —— 否则修复将毫无效果。

| 平台 | 维护内容 | 如何生效 |
|---|---|---|
| npm | README、`description`、`keywords`、仓库链接 | 仅通过 `npm publish`（Patch 版本）；元数据取自 `package.json` |
| PyPI | README (`long_description`)、Classifiers、项目 URLs | 仅通过重新上传生效；元数据取自 `pyproject.toml` |
| MCP 注册表 / Plugin 目录 | 描述、版本、Tool 列表、入门文档 | 取决于注册表：更新 Manifest 或重新提交 |
| Marketplace / Store | 描述、截图、分类、语言版本 | 通过各自的管理后台；截图在这些平台上老化得特别快 |
| Docker Hub / 容器注册表 | 描述、Tag、使用示例 | 仓库描述加新 Tag |
| Zenodo / DOI | 元数据、作者、版本号 | 元数据可原地编辑，内容更新需发布新版本 |
| 官网 / 组织 Profile / `llms.txt` | 简短描述、链接、定位 | 可直接编辑 —— 成本最低的平台，切勿遗忘 |

当版本号提升时，**所有版本记录位置**必须同时同步更新：Manifest、代码常量、README Badge、Changelog、Release Tag、`llms.txt`。版本号不一致的状态比整体陈旧的状态更难诊断。

如果当前在某个平台上无法或不宜进行更新（例如仅为了修复一个错别字而不值得发布 Release），请在执行日志中记录说明，以免下一轮维护将其误认为是疏忽遗漏。

## Force-Push 规则

标准原则是**绝不 Force-Push**。事后忽略内部规划文件不足以构成重写历史的理由：付出的成本极高，每个 Clone 和 Fork 都会损坏，未决的 PR 会失效 —— 且收益微乎其微，因为内容并无危险。标准做法：

```bash
git rm --cached <file>            # 从 Git 追踪中移除，本地予以保留
# 更新 .gitignore
git commit -m "chore: 将内部工作文件移出 Git 追踪"
git push
```

只有在发生**真正的泄漏 (Leak)** 时，重写历史（并使用 `--force-with-lease` 推送）才是合理的：Credentials 和 Key、个人或客户数据、以及具有真正商业竞争价值的文件（内部财务核算、价格策略、未公开计划、合同内部细节）。在此情况下：

1. **首先轮换受影响的 Secret** —— 此时历史记录可能已被复制、Fork 和缓存。轮换才是有效的防护，删除仅仅是形式上的。
2. 清理历史（使用 `git filter-repo` 或 BFG），使用 `--force-with-lease` 推送。
3. 检查 Fork 和缓存；必要时联系 GitHub 支持团队清理孤立对象。
4. 在执行日志中记录整个过程：泄漏内容、时间、轮换措施。

当在"无危险"与"敏感"之间存疑时：按敏感处理并上报。两者的风险成本是不对称的。

## 发现问题转化为任务，而非仅作日志记录

一次维护轮次定期发现的内容，往往超出其在同一轮次中能够或应当修复的范围：缺失的语言版本、现代化滞后、从未执行过的发布。**此类发现必须在发现的当下转化为任务** —— 否则它们会沉淀在已完成轮次的技术日志中，而项目的下一位维护者根本不会去翻阅日志。

任务属于**项目本地文件夹的任务系统** —— 即下一位在该项目上工作的人会去查看的地方。通常是项目文件夹中的 `AUFGABEN.txt` 或 `TODO.md`，而该文件夹往往**不在 Git 克隆库内部**，而是在存放项目规划的目录中。克隆库包含代码，项目文件夹包含管理；在克隆库中添加一条在下次 `git clean` 时就会消失的记录不能算作任务。

请注意以下三点：

1. **将内部任务列表与公开路线图区分开。** 一个 `TODO.md` 可能是精心维护的公开路线图 —— 此时它不是堆放内部补救工作的地方。在追加内容前先打开查看：如果包含 "Public roadmap" 等标题，请写在旁边的内部文件中（`AUFGABEN.txt`）并标记为内部任务。
2. **在重复创建前先检查现有条目。** 很多时候发现的问题已经列在上面了。此时不要新建条目，而是**补充丰富它** —— 附加上本轮维护的实证（"已确认：`--help` 完全输出中文内容"）。一个带有最新实证的已知问题比旁边新建的重复条目更有价值。
3. **记录已完成事项。** 本轮维护解决的问题，应当作为带有 Commit Hash 的已完成事项列出。这向下一轮维护解释了为何某个问题消失了，防止其被再次"重新发现"。

表述任务时，应使其在脱离本轮维护上下文时依然易于理解：发现了什么、为什么重要、下一步应当做什么。"i18n 不完整" 不是合格的任务；"目录中仅包含 `status.title`，其中 es/zh/ja/ru 为空 —— 先将 CLI 字符串提取至目录，再补全所有六种语言" 才是合格的任务。

## 常见错误

| 错误 | 纠正措施 |
|---|---|
| 仅查看工作树，未检查 `git ls-files` | 务必检查已追踪的文件集合 —— 问题往往隐藏在其中 |
| 隐私关卡仅检索路径和 Token | 还要检索自有的流水线/文件夹名称 —— 它们不会触发报警且容易漏网 |
| 删除内部文件时重写了 Git 历史 | 对于非敏感文件，`git rm --cached` + 正常 Push 即可 |
| 在 `HEAD` 中删除了 Secret 就认为处理完毕 | 必须轮换 Secret；其他做法纯属表面文章 |
| 仅凭文件名对文件进行归类 | 务必打开快速查看 —— 文件名无法可靠反映真实意图 |
| README 中的数字直接递增而非重新计数 | 在源头重新计数（Tool 列表、测试运行、Manifest） |
| 将新语言版本创建为空白骨架 | 填入实际内容或直接不创建 —— 空白骨架伪造了完整性 |
| 在已有规范旁引入了第二套 README 命名规范 | 沿用仓库中已有的命名规范 |
| 未经批准向第三方列表提交 PR | 对外沟通必须先提交方案；仅自有平台可以自由修改 |
| 仅统计 Issue 数量而不进行处理 | 修复、关闭或针对性追问 —— 给每个 Issue 一个明确的状态 |
| 擅自以脱离家族风格的设计创建 Banner | 遵循生态系统既有的设计语言 |
| 修正了仓库中的 README，npm/PyPI 页面依然展示旧版 | 注册中心页面来自上次 Publish —— 需随之发布 Patch 版本 |
| 仅在 Manifest 中提升了版本号 | 所有版本记录位置同步更新：Manifest、代码、Badge、Changelog、Tag、`llms.txt` |
| 修改已完成，但留在本地未 Push | Commit 并 Push 属于本轮维护的一部分；仅冻结限制可以例外 |
| 将所有修改混在一个大包 Commit 中 | 拆分清理、文档和修复 —— 否则后续无法单独 Revert |
| 文档提交后 CI 变红，怀疑是自己的修改所致 | 未锁定的 Linter 在无 `select` 时采用了新版默认规则 —— 锁定规则集 |
| 仅在发现报错的地方修正了错误表述 | 在组织范围内搜索该表述 —— 它通常也存在于 Profile、`llms.txt` 和第二语言版本中 |
| 在 Dirty 的第三方仓库中使用 `commit -a` | 按路径精准 Stage 并 Commit，不要 Push —— 保持他人工作不受影响 |
| 在干净的组织 Profile 仓库中做了修改但未 Push | 干净的第三方仓库获得独立的 Commit **以及** 独立的 Push |
| 跳过的修改仅记录在自己的日志中 | 额外记录在目标仓库的任务列表中（如果存在） |
| 发现的问题仅写入执行日志 | 在项目本地文件夹系统中转化为任务 —— 日后没人会翻看日志 |
| 内部补救工作挂在了公开路线图上 | 先查看内部；"Public roadmap" 意味着应当使用旁边的内部文件 |
| 将已知问题作为新条目重复创建 | 使用本轮维护的最新实证丰富现有条目 |
| 在编辑锁限制下向被锁仓库写入 TODO 行 | 该锁适用于整个项目 —— 切勿触碰其中的任何内容 |
| 将 Push 锁解读为完全禁止操作并直接跳过仓库 | 阅读锁文件：如果仅限制发布，在独立分支上继续进行本地轮次 |
| 在 Push 锁限制下虽未 Push，但修改了 Topics 或描述 | 元数据同样在远端可见 —— 在发布冻结期下同样需要省略 |

- 补充诊断说明：如果纯文档提交后 CI 变红，最常见的原因是使用了未锁定版本的 Linter 且缺乏固定规则集 —— 工具的新版本发布改变了默认规则，使未经修改的代码变红。修复方法：锁定规则集，新规则作为任务处理。连续发生两次（n8n-workflow-manager 使用 ruff 0.15，clirec 使用 0.16）。

### 1.3.0 (2026-07-24)
- 新增章节 "发现问题转化为任务"：本轮维护无法自行解决的问题，在发现的当下即转化为项目本地文件夹任务系统中的条目 —— 即下一位维护者会去查看的地方，而非沉淀在已完成轮次的日志中。包含内部列表与公开路线图的区分、丰富现有条目而非重复创建、带有 Commit 的已完成事项。
