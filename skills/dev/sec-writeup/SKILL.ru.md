# sec-writeup - отчёт об уязвимости для раскрытия

Отчёт, понятный без предварительных знаний и воспроизводимый тем, кто не знает об ошибке. Контракт: `sec-scan/references/contract.md` (правило 1 собственный код, правило 4 секреты, правило 6 egress, правило 9 сообщать достоверно).

## Процедура

1. **Собрать исходный материал:** находка (`findings.json`), заметки, PoC, патч. Только уязвимости в собственном или явно разрешённом коде (правило 1).
2. **Скептически проверить перед написанием:** самому попытаться опровергнуть каждое ключевое утверждение («достижимо без аутентификации», «удалённое выполнение кода», «затрагивает все версии»). Затем пометить каждое утверждение как **evidenced** (с доказательством: расположение в коде, вывод теста, коммит) или **unverified** (так и помечено в тексте). Серьёзность - только по шкале контракта (§3); число CVSS или идентификатор CVE - только если их предоставляет пользователь - никогда не выдумывать.
3. **Определить затронутые версии по истории** (появление через `git log -S`/`git blame`, исправление через коммит/тег), а не оценивать на глаз; неопределённую границу указать как открытую.
4. **Структура отчёта:** краткое содержание (2-3 предложения) · затронутый компонент и версии · предпосылки для атакующего · шаги воспроизведения · воздействие (конкретное, без преувеличений) · исправление/обходное решение · хронология · благодарности/контакт.
5. **Минимальный PoC:** только то, что нужно сопровождающему для воспроизведения (вход + ожидаемое неверное поведение). Без превращённого в оружие эксплойта, без целевых систем, без закрепления. В сомнительных случаях описывать, а не прикладывать код.
6. **Вычистить:** удалить секреты, имена хостов, внутренние пути и персональные данные; в находках показывается только расположение, никогда значение (правило 4). Раскрытый секрет заменяется у провайдера.
7. **Хронология только с реальными датами** (обнаружение, сообщение, подтверждение получения, исправление). Срок раскрытия задаёт пользователь или `SECURITY.md` (`sec-policy`), а не навык.
8. **Передача:** черновик остаётся у пользователя. Отправка (почта, advisory, платформа) имеет эффект вовне и требует его явного одобрения (правило 6); для публичных репозиториев предпочтительны черновик advisory или приватный канал сообщений.
