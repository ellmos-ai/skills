# sec-fix - минимальный патч безопасности

Фаза «fix» семейства навыков безопасности ellmos. Контракт: `sec-scan/references/contract.md` (каталог §1, жизненный цикл §2, правила §6). Здесь описано только применение.

## Когда (и когда нет)

- **Только по явному запросу.** Сканирование или валидация никогда сами не запускают исправление.
- **Только находки со статусом `validated` или `triaged`.** `candidate` сначала проходит через `sec-validate`; `rejected` остаётся как есть.
- Обычная ошибка, не связанная с безопасностью: `bugfix-protocol`. Хорош ли существующий патч: `sec-verify-fix`. Структурная причина за несколькими находками: `sec-hardening`.

## Процедура

1. **Прочитать находку и её окружение:** `findings.json` (находка, `evidence`, `recommendation`), затронутый файл и вызывающий код этого места. Устранять причину, а не симптом в одном месте вызова; если несколько вызывающих используют одну и ту же небезопасную функцию, патчить общее место.
2. **Проверить блокировку (контракт §6 правило 2):** `lock_scan.py --check-dir <repo> --json`; exit 0 = свободно, 1 = заблокировано, всё остальное = неизвестно = остановиться; на хосте без `lock_scan.py` вместо этого искать `LOCK*.txt` в репозитории и его родительских папках (нет = свободно, иначе остановиться). Никогда не трогать `LOCK.user.*`.
3. **Рабочая копия:** временная копия или `git worktree` в папке вне оригинала. В оригинал ничего не записывается.
4. **Измерить исходное состояние:** один раз запустить тесты проекта до патча и зафиксировать результат (зелёные/красные, количество). Если тестов нет, так и сказать - не выдумывать их.
5. **Патчить минимально:** самое малое изменение, закрывающее путь source-to-sink (валидация, параметризация, allowlist, экранирование в нужном месте). Без рефакторинга, без правок стиля, без новых зависимостей без необходимости. Регрессионный тест для находки входит в патч, если в проекте есть тесты.
6. **Измерить снова:** повторить тесты; честно сообщить до/после, включая красные тесты и тесты, которые не запускались.
7. **Сохранить патч:** `git diff` рабочей копии в `patches/<id>.diff` в каталоге сканирования; проверить `git apply --check` относительно целевого состояния (ничего не меняет).
8. **Обновить находку:** `status: fixed`, `fix.patchFile: patches/<id>.diff`; затем `python scripts/secfind.py validate findings.json coverage.json` (скрипт находится в `sec-scan`).

## Ограничения

- **Без применения, без коммита, без push (правило 3).** Для этого нужно прямое распоряжение пользователя.
- **Находки с секретами:** старое значение неизбежно оказывается в строках `-` diff. Хранить патч локально в каталоге сканирования, никогда в тикете, чате или отчёте; сначала сменить секрет у провайдера (правило 4). Открыто: был бы ли замаскированный diff пригоден для применения - не выдумывать.
- Автор патча его не проверяет: `sec-verify-fix` с другим ревьюером (правило 7).
- Предупреждение о стоимости при исправлении многих находок сразу (правило 5); обрабатывать их последовательно.
