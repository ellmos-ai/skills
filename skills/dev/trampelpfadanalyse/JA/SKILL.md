# 欲望の道分析 (Desire-Path Analysis) — 規約をLLMに対して実証的に可視化する

コードのバグではなく、**規約がLLMにとって不可視であること**に起因するパイプラインおよびコントロールファイル・ワークフローのエラーを解明するための手法です。READMEやルールが「十分に明確か」を推測する代わりに、実証的に測定します。事前知識のない朴拙（ナイーブ）なサブエージェントをワークフローに放ち、その行動を**ベースライン (Baseline)**とし、ターゲットを絞ったドキュメント変更（「道標」 / signpost）を**介入 (Intervention)**として適用し、新しいナイーブサブエージェントで**再テスト (Retest)**を行います。ベースラインとの差分 (Diff) が成功の測定値となります。

この名称は*ケモノ道*（欲望の道 / 英語: *desire path* / ドイツ語: *Trampelpfad*）に由来します。舗装された道路ではなく、人々が実際に歩く場所こそが道のあるべき場所です。同様に、ナイーブなLLMの歩む経路は、私たちが仮定した場所ではなく、実際にドキュメントやガードレールが必要とされる場所を示しています。

## このSkillを使用するタイミング

- エージェントがドキュメント化されているにもかかわらず、ルール/規約を繰り返し無視する場合。
- さらにドキュメントを書く前に、手順がLLMにとって**可視/発見可能**であるかを知りたい場合（「ここで壁に向かって話している人はいないか？」）。
- 再構築（新しいディレクトリ、名前変更）の後：エージェントは依然としてエントリーポイントを見つけられるか？
- ドキュメント変更を行い、それが機能することを単なる期待ではなく**証明**したい場合。
- 新しいLLMパートナーをパイプラインに統合する前のオンボーディングテスト。

対象外：純粋なコードのバグ（→ 体系的デバッグ）、本番タスクのためのスウォーム協調パターンの選択（→ `swarm-operations` を参照）。本Skillは、ナイーブエージェントのスウォームを純粋に**測定器具**として使用します。

## 一言で表すコア概念

ドキュメントをUXのように扱う：重要なのは何を書いたかではなく、偏見のないユーザー（ここではナイーブエージェント）が実際にそれで何をするかであり、それを測定し、変更し、再び測定する。

## プロセス：5つのステップ

```
1. BASELINE       naive subagents → measure current behavior (quantitative)
2. PATH ANALYSIS  where exactly does it fail? which doc location misleads?
3. INTERVENTION   put up a "signpost" (README/convention made more prominent)
4. RETEST         FRESH naive subagents, identical test case
5. DIFF           retest vs. baseline → success measurement + honest assessment
```

### ステップ 1 — ベースライン (Baseline)：現在の行動をナイーブに測定する

まず、問題を「エージェントは規約で指定された場所にログを作成するか？」や「エージェントはパイプラインのエントリーポイントを見つけるか？」といった**検証可能な質問**として定義します。

次に、ナイーブなサブエージェントを放ちます：

- **ナイーブとは：** プロジェクトの記憶なし、Skillなし、事前のヒントなし — エージェントは上記のエントリーパスとタスクのみを知っています。これにより、エージェントの事前知識ではなく、**既存のドキュメントを通じた純粋な発見可能性**を測定します。
- **孤立したサンドボックスコピー：** 各プローブエージェントは影響を受けるフォルダ/ワークフローの独自コピーで作業するため、プローブ同士が影響し合うことはなく、実際の状態は変更されません。
- **同一のテストケース、複数回の繰り返し：** ばらつきは実在します。1回のプローブはエピソードに過ぎません。n回の繰り返し（例：3回、必要に応じてそれ以上）によって割合が得られます。
- **安価で「ナイーブ」なモデル**で十分かつ現実的です — 賢く推測するのではなく、ドキュメントが平均的なエージェントをどこへ導くかを示すべきです。

最小プローブプロンプト（プレースホルダーを調整）：

```
You are exploring <SYSTEM>. It is located at: <PATH>.
TASK: <specific task>.
RULES:
1. You only know the path above, nothing else.
2. Explore to complete the task. Max. <N> steps.
3. Report at the end: VISITED_DIRECTORIES, READ_FILES,
   TASK_COMPLETED (yes/no), MOST_HELPFUL_FILE.
```

**ベースラインメトリクスとして記録**（常に定量的に、「良くなった気がする」は不可）：

| メトリクス | 意味 |
|---|---|
| 成功率 | 規約通りにタスクが完了した頻度（例：0/3） |
| 誤った行動 | 誤った場所/方法が使用された頻度（例：エントリごとではなく一括ログが3/3） |
| ゴールへの経路 | ゴールに到達するまでのステップ数/遠回り |
| ブラインドスポット | 誰にも開かれない関連ファイル/場所 |

### ステップ 2 — 経路分析 (Path analysis)：どこで実際に失敗しているか？

プローブレポートをまとめて評価します（訪問した場所の「ヒートマップ」で十分です）：

- どのファイルが**頻繁に**読まれているか (HOT)？ そこでガイダンスが不足している場合、そこが道標を設置するのに最も効果的な場所です。
- どの関連場所が**一度も**開かれていないか (COLD / ブラインドスポット)？ 内容がどれほど優れていても、実質的に不可視です。
- エージェントがどこでループしたり規約を回避しているか (行き止まり、回避行為)？ それが具体的なドキュメントの欠落を示しています。

発見事項テーブル：

| 発見事項 | 意味 | アクション (→ ステップ 3) |
|---|---|---|
| HOT + ガイダンスなし | 高トラフィック、道標なし | まさにその場所に道標を設置する |
| WARM + エラー | エージェントは到達するがつまずく | 例/説明を追加する |
| COLD | 場所が絶対に見つからない | HOTファイルからリンクを貼る |
| 回避行為 | 規約が回避されている | 回避が発生しているポイントにヒントを配置 |

ステップ 2 の成果：**1つの具体的かつ局所化された仮説** — 「エージェントはXを読むが、Xには規約が記載されていないため、結果としてYに到達する。」

### ステップ 3 — 介入 (Intervention)：道標 (Signpost) を設置する

**正確に1つ**の道標を設置します（1回のパスにつき1つの変数のみ。そうでないとDiffの解釈が不可能になります）。典型的な道標：

- HOTパスがすでに通過する場所に**規約を目立つように配置する**（例：最も読まれているREADME/コントロールファイルの最上部に短い明示的なヒントを配置）。
- 中央のアーキテクチャ/概要ファイルの冒頭に、以前のブラインドスポットを指し示す**クイックナビゲーションテーブル**を配置する。
- HOTファイルからCOLDな場所への**道標/相互参照 (Cross-reference)**。
- 危険または規約違反の行動に対するオプションの**ガードレール (Guardrail)**（例：PreToolUseのヒント）。

道標は短く見落とせないものにしてください — エージェントはスキム読みに終始し、長文を読むことは滅多にありません。

### ステップ 4 — 新しいナイーブサブエージェントによる再テスト (Retest)

ステップ 1 を**同一条件で**繰り返します — 同一タスク、同一繰り返し回数、同一モデル、同一ナイーブ条件 — ただし、新しい道標が含まれたサンドボックスコピー**上**で実施します。重要：

- ベースライン実行の記憶を持たない**新しい**エージェント（そうでないと可視性ではなく学習を測定することになります）。
- ベースライン設定との違いは**道標のみ**であること。

### ステップ 5 — ベースラインとのDiff + 誠実な成功測定

再テストとベースラインを直接並べて比較します：

| メトリクス | ベースライン | 道標設置後 | Δ |
|---|---|---|---|
| 成功率 | 例: 0/3 | 例: 3/3 | +3 |
| 誤った行動 | 例: 3/3 | 例: 0/3 | −3 |
| ブラインドスポット | 例: 1 | 例: 0 | −1 |

評価 — ここで結果を美化してはいけません：

- **効果あり**（誤った行動が測定可能に減少）：道標を維持し、ドキュメント化する。
- **効果なし**（Δ がわずか）：道標の位置が間違っているか、あまりにも控えめすぎた → ステップ 2/3に戻り、別の道標を試して再測定する。
- **限界を率直に述べる：** 小さな n は指標であって証明ではありません。ナイーブエージェントはすべてのリアルユーザーではなく「平均的な情報不足状態」をモデル化しています。成功スコアリングにおける偽陽性/偽陰性を明示的にチェックします（何が正確に「完了」とカウントされたか？）。

## ミニケーススタディ（実際の数値による実例）

問題：チケットパイプラインでは、軽微な完了ごとに**1つ**の専用チケットログを作成することが定められていましたが、エージェントはすべてを**1つの集合ログ**に書き込んでいました。

- **ステップ 1 (ベースライン)：** 3つのナイーブサブエージェント、同一タスク → **3/3 が集合ログを使用**（規約が遵守されない）。
- **ステップ 2 (経路分析)：** 最も読まれているREADMEの目立つ場所にチケットごとのルールが記載されていなかった → ナイーブな経路が集合ログへと導いていた。
- **ステップ 3 (介入)：** ログ規約に関する短く明示的な「道標」をREADMEの目立つ場所に配置。
- **ステップ 4 (再テスト)：** 3つの新しいナイーブサブエージェント、同一タスク。
- **ステップ 5 (Diff)：** **3/3 誤り → 0/3 誤り**、3つすべてが正しいチケットごとのログを作成した。（チケット T-20260621-44 に記録。）

教訓：規約の「表現が弱すぎた」のではなく、実際に読まれていた経路上で**不可視**だったのです。適切な場所に配置され、実証的に検証された道標が問題を解決しました。

## 出典と関連手法

本手法は Desire-Path Analysis v2.0（LLM行動の実証的測定器具としてのスウォーム）に由来します。大規模実行（100回のナイーブプローブ）の元の参照結果がソースからのエビデンスとして記録されています。最大のブラインドスポットはヘルプディレクトリであり、**0/100** のエージェントしか訪問しませんでした（多数のヘルプファイルが存在したにもかかわらず）。また、「新しいSkillを作成する」タスクの成功率は **0%** でした。テンプレートディレクトリを誰も見つけられなかったためです — これらは両方ともコンテンツの問題ではなく、典型的な可視性の問題です。
