# Анализ троп желания (Desire-Path Analysis) — Делаем соглашения эмпирически видимыми для LLM

Метод выявления ошибок в воркфлоу пайплайнов и управляющих файлов, причиной которых является не сломанный
код, а то, что **соглашение невидимо для LLM**. Вместо того чтобы гадать, является ли README или правило
"достаточно понятным", вы измеряете это эмпирически: наивные субагенты без предварительных знаний запускаются
в воркфлоу, их поведение становится **базовой линией (baseline)**, точечное изменение документации
("указатель" / signpost) служит **вмешательством (intervention)**, а новые наивные субагенты обеспечивают
**ретест (retest)**. Diff по сравнению с базовой линией является измерением успеха.

Название происходит от понятия *народная тропа* / *тропа желания* (англ. *desire path*, нем. *Trampelpfad*):
тропа должна проходить там, где люди действительно ходят, а не там, где проложен асфальт. По аналогии, пути
наивных LLM показывают, где действительно необходима документация и ограждения (guardrails), а не там, где
мы предполагаем их наличие.

## Когда использовать этот skill

- Агенты неоднократно игнорируют правило/соглашение, хотя оно задокументировано.
- Вы хотите узнать, является ли процедура **видимой/обнаруживаемой** для LLM перед написанием дополнительной
  документации ("говорит ли кто-нибудь здесь со стеной?").
- После реструктуризации (новые директории, переименования): могут ли агенты по-прежнему находить точки входа?
- Вы внесли изменение в документацию и хотите **доказать**, что оно работает, а не просто надеяться на это.
- Онбординг-тест перед интеграцией новых LLM-партнеров в пайплайн.

Не подходит для: чистых багов кода (→ систематический багфиксинг), или выбора паттернов координации роя для
продакшен-задач (→ см. `swarm-operations`). Этот skill использует рой наивных агентов исключительно в качестве
**измерительного инструмента**.

## Главная идея в одном предложении

Относитесь к документации как к UX: важно не то, что вы написали, а то, что беспристрастный пользователь
(здесь: наивный агент) реально с этим делает — и вы измеряете это, меняете и измеряете снова.

## Процесс: 5 шагов

```
1. BASELINE       naive subagents → measure current behavior (quantitative)
2. PATH ANALYSIS  where exactly does it fail? which doc location misleads?
3. INTERVENTION   put up a "signpost" (README/convention made more prominent)
4. RETEST         FRESH naive subagents, identical test case
5. DIFF           retest vs. baseline → success measurement + honest assessment
```

### Шаг 1 — Базовая линия (Baseline): наивное измерение текущего поведения

Сначала сформулируйте проблему как **тестируемый вопрос**, например: "Создает ли агент лог в месте,
предусмотренном соглашением?" или "Находит ли агент точку входа в пайплайн?".

Затем запустите наивных субагентов:

- **Наивный означает:** отсутствие памяти проекта, отсутствие скиллов, отсутствие предварительных подсказок —
  агент знает только путь входа и задачу. Это измеряет **чистую обнаруживаемость через существующую
  документацию**, а не предварительные знания агента.
- **Изолированные копии в песочнице:** каждый зондирующий агент работает в собственной копии затронутой
  папки/воркфлоу, поэтому зонды не влияют друг на друга, а реальное состояние остается нетронутым.
- **Один и тот же тест-кейс, несколько повторений:** вариативность реальна. Один зонд — это анекдот;
  n повторений (например, 3 или больше при необходимости) дают статистическую долю.
- **Дешевая, "наивная" модель** достаточна и реалистична — она не должна догадываться, а должна показать,
  куда документация ведет среднего агента.

Минимальный промпт для зонда (настройте плейсхолдеры):

```
You are exploring <SYSTEM>. It is located at: <PATH>.
TASK: <specific task>.
RULES:
1. You only know the path above, nothing else.
2. Explore to complete the task. Max. <N> steps.
3. Report at the end: VISITED_DIRECTORIES, READ_FILES,
   TASK_COMPLETED (yes/no), MOST_HELPFUL_FILE.
```

**Фиксируйте как метрики базовой линии** (всегда количественные, никогда "кажется лучше"):

| Метрика | Значение |
|---|---|
| Доля успеха | как часто задача выполнялась по соглашению (напр. 0/3) |
| Неверное поведение | как часто использовались неверное место/метод (напр. 3/3 общий лог вместо лога на запись) |
| Путь к цели | сколько шагов/обходов потребовалось для достижения цели |
| Слепые зоны | какой релевантный файл/локацию никто не открывает |

### Шаг 2 — Анализ путей (Path analysis): где именно происходит сбой?

Оцените отчеты зондов вместе (достаточно "тепловой карты" посещенных локаций):

- Какой файл читается **часто** (ГОРЯЧИЙ / HOT)? Если там не хватает ориентации, это самое эффективное место для указателя.
- Какая релевантная локация **никогда** не открывается (ХОЛОДНАЯ / COLD / слепая зона)? Она фактически невидима — независимо от качества ее содержимого.
- Где агент зацикливается или обходит соглашение (тупик, обходной путь)? Это обозначает конкретную брешь в документации.

Таблица находок:

| Находка | Значение | Действие (→ Шаг 3) |
|---|---|---|
| HOT + нет ориентации | высокий трафик, нет указателя | разместить указатель прямо там |
| WARM + ошибки | агенты доходят, но спотыкаются | добавить пример/разъяснение |
| COLD | локация никогда не находится | дать ссылку на нее из HOT-файла |
| Обход соглашения | соглашение обходится | добавить подсказку в точке обхода |

Результат Шага 2: **одна конкретная локализованная гипотеза** — "Агенты читают X, но в X не упоминается соглашение; поэтому они оказываются в Y."

### Шаг 3 — Вмешательство (Intervention): установка указателя (signpost)

Установите **ровно один** указатель (одна переменная за проход, иначе diff невозможно интерпретировать). Типичные указатели:

- Разместить соглашение **на видном месте там, где ГОРЯЧИЙ путь уже проходит** (например, короткая явная подсказка в самом верху наиболее часто читаемого README/управляющего файла).
- **Таблица быстрой навигации** в начале центрального файла архитектуры/обзора, указывающая на бывшие слепые зоны.
- **Указатель/перекрестная ссылка** из ГОРЯЧЕГО файла в ХОЛОДНУЮ локацию.
- Опционально **ограждение (guardrail)** (например, подсказка PreToolUse) для опасных или нарушающих соглашение действий.

Делайте указатель коротким и броским — агенты читают по диагонали и редко вникают в длинные тексты.

### Шаг 4 — Ретест с СВЕЖИМИ наивными субагентами

Повторите Шаг 1 **идентично** — та же задача, то же количество повторений, та же модель, те же наивные условия — но на копиях в песочнице **с** новым указателем. Важно:

- **Свежие** агенты без памяти о прогоне базовой линии (иначе вы измеряете обучение, а не обнаруживаемость).
- **Только указатель** отличается от конфигурации базовой линии.

### Шаг 5 — Diff с базовой линией + честное измерение успеха

Поставьте ретест и базовую линию непосредственно бок о бок:

| Метрика | Базовая линия | После указателя | Δ |
|---|---|---|---|
| Доля успеха | напр. 0/3 | напр. 3/3 | +3 |
| Неверное поведение | напр. 3/3 | напр. 0/3 | −3 |
| Слепые зоны | напр. 1 | напр. 0 | −1 |

Оценка — и не приукрашивайте результаты:

- **Работает** (неверное поведение измеримо снижается): сохранить указатель, задокументировать его.
- **Не работает** (небольшая Δ): указатель был не в том месте или слишком незаметен → возврат к Шагу 2/3, другой указатель, измерить снова.
- **Честно заявлять об ограничениях:** небольшие n являются индикаторами, а не доказательствами; наивный агент моделирует "среднего неосведомленного", а не каждого реального пользователя; явно проверяйте ложноположительные/ложноотрицательные результаты при подсчете успеха (что именно считалось "выполненным"?).

## Мини-кейс (реальный, с фактическими цифрами)

Проблема: Пайплайн тикетов требовал, чтобы тривиальные завершения получали **по одному** выделенному логу на тикет — но агенты вместо этого помещали всё в **один общий лог**.

- **Шаг 1 (baseline):** 3 наивных субагента, та же задача → **3/3 использовали общий лог** (соглашение не соблюдено).
- **Шаг 2 (анализ путей):** в наиболее часто читаемом README правило для отдельных тикетов не упоминалось на видном месте → наивный путь вел к общему логу.
- **Шаг 3 (вмешательство):** короткий, явный "указатель" о соглашении по логированию размещен на видном месте в README.
- **Шаг 4 (ретест):** 3 свежих наивных субагента, идентичная задача.
- **Шаг 5 (diff):** **3/3 неверно → 0/3 неверно**, все три создали правильный лог для каждого тикета. (Задокументировано в тикете T-20260621-44.)

Урок: Соглашение не было "сформулировано слишком слабо" — оно было **невидимым** на реально читаемом пути. Указатель в нужном месте, эмпирически проверенный, решил проблему.

## Источник и сопутствующие методы

Этот метод извлечен из Desire-Path Analysis v2.0 (рой как эмпирический измерительный инструмент для поведения LLM). Оригинальные эталонные результаты крупного прогона (100 наивных зондов) задокументированы как доказательства из источника: крупнейшей слепой зоной была директория справки, которую посетили **0/100** агентов (несмотря на множество файлов справки), а задача "создать новый skill" завершилась с успехом **0%**, потому что никто не нашел директорию шаблонов — и то, и другое являются классическими проблемами видимости, а не содержимого.

## См. также

- `swarm-operations` (dev) — каталог **паттернов координации** роя для продакшен-задач; содержит анализ троп желания только в виде концептуального раздела. Этот skill представляет собой применимый вариант **процесса** с циклом baseline → ретест.
- `pipeline-optimizer` (dev) — 6-шаговая реновация пайплайна; его ретест со свежими субагентами соответствует Шагам 4–5 здесь.
- `bugfix-protocol` / систематический багфиксинг — для реальных багов кода, а не проблем видимости.
