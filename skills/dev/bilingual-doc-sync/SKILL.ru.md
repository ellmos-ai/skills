# Bilingual-Doc-Sync — Поддержание синхронизации параллельных языковых версий

## Цель

Двуязычные документы со временем незаметно расходятся: активно редактируемая версия
растет, а другая устаревает — пока «перевод» не становится таковым лишь по названию. Этот
навык превращает проверку синхронизации в четко определенный процесс с ключевым
предварительным решением: **Какая версия является ведущей?** Без правила ведущего языка каждое
расхождение превращается в индивидуальный спор, а процесс сверки становится невоспроизводимым.

## Рабочий процесс

### 1. Проверка наличия

- Присутствуют ли обе (все) языковые версии? Если одна полностью отсутствует → **подтянуть** (полный
  перевод ведущей версии, а не создание заново).
- Проверить соглашения об именовании (например, `DOCUMENT.md` + `DOCUMENT.en.md` или суффиксы `_de`/`_en`)
  и привести отклонения к единому стандарту — находимость составляет половину синхронности.

### 2. Определение ведущего языка (перед каждой сверкой)

- Ведущий язык — это версия, в которой ведутся основные работы по содержанию (часто EN для научных статей,
  родной язык для локальной документации). Она имеет приоритет при противоречиях.
- **Исключение обратного переноса:** Если вторичная версия доказуемо решает что-то лучше (более четкая
  формулировка, исправленная ошибка), это ПРИНИМАЕТСЯ в ведущую версию — сначала обратный перенос,
  затем обычная синхронизация. Проверьте техническую корректность перед принятием «более красивой» формулировки.

### 3. Проверка параллелизма

Сначала структура, затем содержание:

1. **Сравнение структуры:** Разделы/заголовки обеих версий бок о бок —
   отсутствующие, дополнительные или переставленные разделы представляют собой грубые расхождения.
2. **Пораздельная выборочная проверка** совпадающей структуры: совпадают ли утверждения, цифры,
   перекрестные ссылки, примеры? Особенно подвержены расхождениям: журналы изменений (Changelog), таблицы,
   числовые значения, списки литературы/ссылок, недавно отредактированные разделы.
3. **Проверка непереводимых инвариантов:** Блоки кода, идентификаторы, формулы, пути
   должны быть ИДЕНТИЧНЫМИ в обеих версиях (код никогда не переводится).

### 4. Устранение расхождений

- Устранить расхождения в направлении ведущего языка (или после обратного переноса).
- Соблюдать типографику целевого языка (например, правила оформления кавычек).
- Обновить метаданные: номера версий, поля дат, записи журнала изменений в ОБЕИХ
  версиях (сам Changelog является наиболее частой точкой расхождения).

### 5. Документирование результатов

Зафиксировать результаты (что расходилось, что было принято, что перенесено обратно).
Для периодического запуска по реестру документов: объединить с каркасом ротации
(`rotation-check`) — одна пара документов за запуск, с использованием реестра в качестве памяти.

## Расширение: Аудит расширения (Нужно ли БОЛЬШЕ языков?)

Помимо поддержания синхронизации существующих версий, языковое обслуживание включает вопрос о том,
заслуживает ли документ/проект ДОПОЛНИТЕЛЬНЫХ языков:

1. **Оценка пригодности** вместо слепого перевода: целевая аудитория, международная полезность,
   присутствие в магазинах/вебе, портативность контента. Не каждый внутренний документ требует английского языка;
   не каждому приложению требуется пять языков.
2. **Проверка технической подготовки:** Подготовлена ли целевая система к языковым файлам / параллельным
   версиям (структура i18n, соглашение об именовании)? Если нет, ЭТО первая
   задача, а не перевод.
3. **Документирование результатов, отказ от немедленного массового перевода:** Внести конкретные задачи по переводу
   в локальный файл TODO проекта; вывод «никакой другой язык не имеет смысла» является валидным,
   заслуживающим фиксации результатом.
4. **Контроль качества добавленных версий:** Выборочно проверять автоматически сгенерированные переводы
   относительно ведущей версии (раздел 3), прежде чем считать их «присутствующими».

## Пример

```text
Задача: «Проверь, синхронизирована ли статья на DE и EN».

1. Наличие: paper_en.tex (ведущий) + paper_de.tex присутствуют.
2. Структура: в DE отсутствует новый раздел 4.2 (последняя редакция EN); в DE более
   удачный абзац с доказательством в 3.1.
3. Обратный перенос: формулировка 3.1 технически проверена → принята в EN.
4. Подтягивание: 4.2 переведен на DE; цифры в Таблице 2 сверены (в DE были
   устаревшие значения); список литературы сделан идентичным.
5. Запись в реестре: «paper-X | 2026-07-03 | de-en-sync | устранены 3 расхождения,
   1 обратный перенос | следующая проверка после следующей редакции EN».
```

## Тревожные флаги (Red Flags)

| Мысль | Реальность |
| --- | --- |
| «Я просто переведу различия заново» | Сначала определите ведущий язык + вопрос обратного переноса — иначе лучшее решение будет перезаписано. |
| «Структура совпадает, значит все синхронизировано» | Цифры, чейнджлоги и ссылки расходятся первыми — глубокая выборочная проверка обязательна. |
| «Я также переведу комментарии в коде» | Блоки кода и идентификаторы остаются идентичными в обеих версиях (на английском). |
| «Я синхронизирую все документы за один раз» | Одна пара за запуск (каркас ротации) позволяет сохранять проверяемость. |
