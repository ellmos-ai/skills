# sec-policy - определить и проверить SECURITY.md

Политика говорит, что считается уязвимостью в этом репозитории. `sec-triage` оценивает находки по ней (контракт `sec-scan/references/contract.md` §2: `triaged` = серьёзность и приоритет определены по политике). Без политики триаж гадает.

## Содержание SECURITY.md

| Раздел | На какой вопрос отвечает |
|---|---|
| Поддерживаемые версии | какие версии получают исправления безопасности? |
| Область применения | какие компоненты, интерфейсы, развёртывания имеются в виду? |
| Исключено | что явно не считается (тестовый код, примеры, известные ограничения, атаки, требующие доступа к хост-системе)? |
| Требуемые свойства безопасности | что должен гарантировать проект (например, «нет секретов в репозитории», «сетевой ввод валидируется», «плагины работают без доступа к файлам вне X»)? Триаж измеряет по этому. |
| Канал сообщений | куда сообщать: заполнитель `<security-contact>`; или приватный приём сообщений об уязвимостях GitHub, если он включён в репозитории. **Не выдумывать адрес.** |
| Сроки реакции | подтверждение получения, оценка, цель по исправлению - значения даёт сопровождающий, а не навык; предложения помечать как таковые. |
| Раскрытие | координированное, сроки задаёт сопровождающий; сослаться на `sec-writeup`. |

## Процедура

1. **Прочитать существующее:** текущий `SECURITY.md`, README, файлы зависимостей и сборки, структуру кода (точки входа, auth, доступ к файлам, сеть, механизмы плагинов).
2. **Утверждение против доказательства:** сверить каждое обещание политики («весь ввод валидируется», «нет телеметрии», «версии X.y поддерживаются») с кодом или релизами. Противоречие - это находка (`sec-scan`) или поправка к политике, но не молчаливое игнорирование. То, что нельзя проверить, пометить как непроверенное.
3. **Черновик или diff:** новый SECURITY.md или предложение изменений с открытыми пунктами (заполнители `<...>`) для решений сопровождающего. Если ответа нет, спросить, а не гадать.
4. **Размещение:** черновик в чате или в каталоге сканирования. В репозиторий пишется только по прямому распоряжению пользователя (проверить блокировку, правило 2; без commit/push, правило 3). Файл никогда не содержит секретов, путей хоста или приватных контактов (правило 4).
