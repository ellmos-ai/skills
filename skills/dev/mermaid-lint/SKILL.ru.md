# mermaid-lint

Диаграмма Mermaid с синтаксической ошибкой на GitHub вместо изображения показывает
блок **"Unable to render rich display"**. Локально это незаметно, потому что ни один
инструмент не проверяет блок. Этот навык закрывает данный пробел.

## Когда применять

- README или документ на GitHub показывает ошибку рендеринга вместо диаграммы.
- Перед публикацией или релизом документации с диаграммами.
- После каждой переработки Markdown, которая затрагивает блоки Mermaid.
- Массово по нескольким репозиториям, если неизвестно, где именно что-то сломано.

## Два инструмента

### 1. `mermaid_lint.mjs` — проверка синтаксиса без браузера

```
node mermaid_lint.mjs <repo-pfad> [...] [--json]
node mermaid_lint.mjs --from <liste.txt> [--json]
```

Рекурсивно ищет все `.md`-файлы, извлекает каждый блок ```mermaid и пропускает его
через `mermaid.parse()` — **тот же парсер, который GitHub использует в браузере**.
Выход 0 = все блоки разбираются, выход 1 = есть хотя бы один неисправный блок. Вывод
указывает файл, номер блока, строку и дословное сообщение парсера.

`--from <datei>` читает список путей, по одному на строку. Используй его вместо множества аргументов:
пути Windows с обратными слешами в оболочке Bash молча искажаются
(из `D:\code\my-repo` получается `D:codemy-repo`). Пиши пути с прямыми слешами.

Один процесс обрабатывает сотни репозиториев, потому что Mermaid загружается только один раз.
Без Puppeteer и без загрузки Chromium.

### 2. `readback.mjs` — подтверждение на живой странице

```
node readback.mjs <github-url> [...]
```

Открывает страницы в уже установленном Edge (без загрузки браузера) и подсчитывает реальные
ошибки рендеринга. Вердикт для каждой страницы: `OK`, `DEFEKT`, `UNKLAR` или `KEIN-MERMAID`.

## Три ловушки, из-за которых нужен этот навык

**GitHub отображает Mermaid во вложенных sandboxed iframe** с `viewscreen.githubusercontent.com`.
Основная страница не видит их содержимое. Кто анализирует только `document.body.innerText` или
`msedge --dump-dom`, получает отсутствие ошибок на **каждой** странице — даже на заведомо сломанной.
Поэтому `readback.mjs` анализирует все фреймы.

**Одиночный вывод DEFEKT не является надёжным.** Во время загрузки GitHub на короткое время
показывает заглушку, похожую на ошибку рендеринга. По измерениям от 2026-09-20: для одной и той же
страницы сначала было получено `ERR=1`, затем дважды `ERR=0`. `readback.mjs` поэтому
автоматически повторяет отрицательные результаты; `OK` никогда не повторяется.

**`mermaid.parse()` требует DOM**, иначе он падает на `DOMPurify.addHook` и ошибочно
помечает корректные блок-схемы как сломанные. `mermaid_lint.mjs` заранее предоставляет
окно jsdom. Если всё же остаётся ошибка окружения, она выводится отдельно под
`envIssues` и **не** засчитывается как синтаксическая ошибка.

## Всегда проверяй на отрицательном контроле

Прежде чем доверять зелёному результату, запусти инструмент на состоянии, которое заведомо сломано,
например на коммите до твоего исправления:

```
node readback.mjs "https://github.com/<org>/<repo>/blob/<alter-sha>/README.md"
```

Если он тоже сообщает `OK`, твоя проверка ничего не измеряет. Именно так была
обнаружена описанная выше ловушка с iframe.

## Частые причины ошибок и минимально инвазивное исправление

| Симптом в сообщении парсера | Причина | Исправление |
|---|---|---|
| `Expecting '+', '-', '()', 'ACTOR', got 'loop'` | Участник назван как зарезервированное слово: `loop`, `alt`, `opt`, `par`, `end`, `critical`, `break`, `rect`, `note` | Объявить псевдоним: `participant L as Loop`, сообщения используют `L`. **Отображаемое имя сохраняется** — не переименовывать. |
| `got 'PS'` в блок-схеме | Круглые скобки в подписи узла | Заключить подпись в кавычки: `A["Start (hier)"]` |
| `Lexical error ... Unrecognized text` | Обратные кавычки или двоеточие в подписи | Заключить подпись в кавычки, убрать обратные кавычки |
| `Expecting 'SEMI', 'NEWLINE', 'EOF'` в `graph`/`flowchart` | `Note:` поддерживается только в диаграммах последовательности и классов | Вынести пояснительный текст из блока и поставить его отдельной строкой Markdown под блоком, чтобы информация оставалась видимой |
| `Expecting 'SOLID_OPEN_ARROW' ... got 'NEWLINE'` в диаграмме последовательности | **HTML-сущность** в тексте сообщения (`&lambda;`, `&Delta;`, `&ge;`). Скобки и `=` здесь не ломают разбор — завершающий `;` сущности лексер воспринимает как конец оператора, и всё после него становится новым оператором. | Заменить сущность на буквальный символ (λ, Δ, ≥), остальной текст не менять. Скобки можно оставить. Числовые значения и их написание никогда не менять. |
| Точка с запятой в сообщении последовательности | Воспринимается как конец оператора | Заменить на ` - ` |

В **заключённых в кавычки подписях блок-схем** сущности не создают проблем — правило относится
только к сообщениям последовательностей. `mermaid_lint.mjs` сообщает такие сущности отдельной строкой
`[WARN]` (поле `warnings` в JSON), в дополнение к ошибке парсера: парсер сообщает только
`got 'NEWLINE'` и не называет причину.

**Принцип:** минимальное вмешательство. Компоновка, идентификаторы узлов, порядок и видимый текст
по возможности остаются неизменными. В научных репозиториях это особенно касается числовых значений и их
написания. При паритете EN/DE обе версии должны сохранять одинаковую структуру.

## Работа с несколькими репозиториями

1. Инвентаризация через `gh repo list <org> --limit 200 --json name,isArchived,isPrivate,defaultBranchRef`.
2. Клоны **подтягивать до состояния удалённого репозитория** и серьёзно относиться к расхождениям. Проверка
   на устаревшем клоне измеряет неверное состояние. Если `git pull --ff-only` падает, проверяй по
   `origin`, а не по рабочей копии:
   `git archive origin/<branch> | tar -x -C <tempdir>` и проверь временную папку.
3. **Репозитории с одинаковыми именами из разных организаций** (типично `.github`) нельзя сопоставлять с
   одним и тем же клоном — иначе девять раз проверяется один и тот же репозиторий. При совпадении имён
   клонировать плоско в `<org>__<repo>` и проверять свежее состояние.
4. Перед каждым изменением проверять блокировки (`lock_scan.py`, `LOCK*.txt` в клоне **и** в
   пути проекта OneDrive), ставить собственную блокировку и снимать её после push.
   **Читать область действия, а не только факт наличия:** `LOCK.team.*` с истёкшим
   `expires_after` можно игнорировать; `LOCK.user.zenodo-upload.txt` блокирует исключительно внешнюю операцию записи в Zenodo и
   явно разрешает изменения документации.
   Напротив, `LOCK.user.until-winners-announcement.txt` (Judging) блокирует любой push —
   там проверять только на чтение и оформлять результат как тикет.
5. Исправить, проверять до зелёного результата, сделать commit, `git pull --rebase`, push.
6. Подтверждение на живой странице с отрицательным контролем. Только после этого задача считается выполненной.

## Установка

```
npm install mermaid jsdom playwright-core
```

В папке со скриптами или глобально; `playwright-core` использует установленный Edge
(`channel: 'msedge'`) и не загружает собственный браузер. Нужен только для подтверждения на живой странице —
проверка синтаксиса работает без него.

## Связанное

- `_tools/lint_mermaid.py` в GithubBot: более старый линтер на основе регулярных выражений с `--fix`.
  Он автоматически исправляет известные шаблоны, но **не знает зарезервированных слов** и
  не заменяет этот навык. Разумный порядок: сначала `mermaid_lint.mjs` для диагностики, затем при необходимости `lint_mermaid.py --fix`
  для массовых шаблонов, затем повторная проверка.
- `github-repo-care`: общий протокол для ведения репозиториев и публикации.
