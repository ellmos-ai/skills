# 软件测试：测试策略与测试选择

本技能回答的问题是**"这里需要哪些测试、现在做、为了什么目的？"**——以系统化方式作答，而非凭直觉。它提供决策逻辑；完整的测试类型、方法与定义目录位于同一文件夹中的 `testarten-katalog.md`（如需细节请在该处查阅）。

---

## 1. 框架：从三个维度思考

在规划或编写测试之前，先将任务定位到三个维度上（ISTQB）。若只维护"一份测试清单"，就会混淆这些维度，导致规划存在缺口：

| 维度 | 问题 | 取值 |
|---|---|---|
| **测试级别** | 处于哪个层面？ | 单元 → 集成 → 系统 → 验收 |
| **测试类型** | 验证哪种属性？ | 功能性 / 非功能性 / 结构性 / 变更相关 |
| **测试方法** | 测试用例如何产生？ | 黑盒 / 白盒 / 基于经验 |

横向还有：**静态**（评审、静态分析——不执行代码，最早、成本最低的缺陷发现方式）与**动态**（执行代码）。

## 2. 情境路由：当前是什么情况？

根据具体情境选择切入点：

| 情境 | 做法 |
|---|---|
| **开发新功能** | 在编写代码之前明确验收标准（ATDD/BDD 思路）。与实现并行编写单元测试（等价类 + 边界值）。为新接口编写集成测试。只做一条端到端的 Happy Path，不要更多。 |
| **修复缺陷** | 先写复现缺陷的测试（红），再修复（绿）= **重测**。之后对环境做**回归**。诊断本身 → `bugfix-protocol`。 |
| **重构** | 不新增功能测试——现有测试套件就是安全网。先检查套件是否真正覆盖了既有行为（必要时补充特征化测试）。以覆盖率/变异测试作为缺口指标。 |
| **无测试的遗留代码** | 不要从为每个函数编写单元测试开始。先在系统/API 层面编写特征化测试锁定现有行为，之后在修改各个部分时再补充单元测试。 |
| **API / 微服务** | 以服务层的 API 测试为重点（金字塔中层）。若团队与部署相互独立：采用**契约测试**（如 Pact），而非共享的预发布集成测试。 |
| **准备发布** | 顺序：冒烟（构建是否稳定？）→ 完整回归 → 非功能性测试（负载、安全）→ UAT/验收 → 对发布候选版本再做冒烟。 |
| **性能隐患** | 先定义可度量的目标（例如"1,000 名用户下 P95 < 300 ms"），否则任何测试都无法评估结果。负载测试 = 常规负载，压力测试 = 崩溃点及恢复能力。必须使用接近生产的环境。 |
| **搭建测试流水线** | 实施第 4 节中的 CI/CD 门禁；从每次提交时的单元测试 + 代码检查开始，然后逐步扩展。 |
| **编写测试策略/测试方案** | 按三个维度 + 阶段映射（第 4 节）+ 基于风险的优先级排序（第 6 节，第 10 点）组织结构。 |

## 3. 测试级别：测试对象、目标、时机

| 级别 | 检验内容 | 时机 | 经验法则 |
|---|---|---|---|
| **单元/组件** | 孤立的单个函数/类（使用 Mock/Stub） | 实现过程中，每次提交 | 金字塔的宽广基座；快速（秒级以内）、确定性强 |
| **集成** | 协作、接口、数据库连接 | 单元测试之后，每次合并时 | 增量式集成（自顶向下/自底向上），大型系统切勿一次性集成（Big Bang） |
| **系统** | 对照技术需求检验整个系统 | 集成版本可用后 | 功能性与非功能性兼顾；独立测试人员很有价值 |
| **验收** | 业务期望、真实使用场景 | 上线前的最后一级 | 由业务部门执行 UAT；别忘了运维层面（备份/部署/监控）；必要时进行 Alpha/Beta 测试 |

**测试金字塔**描述的是数量比例：大量单元测试、有针对性的集成/API 测试、少量端到端测试（约 70/20/10 作为起点的经验值——应根据实际缺陷来源调整）。倒置的金字塔（大量 UI 测试）速度慢且不稳定——应避免。

## 4. 阶段映射：何时检验什么？

### CI/CD 门禁（现代标准映射）

| 流水线阶段 | 门禁 |
|---|---|
| 每次提交 | 单元测试、代码检查、静态分析（秒至分钟级） |
| 拉取请求 | 代码评审、SAST/SCA、有针对性的组件测试 |
| 合并 | 集成/API/契约测试，测试环境冒烟 |
| 夜间构建 / 发布前 | 完整回归、端到端、性能/负载测试、DAST |
| 发布候选版本 | 预发布环境冒烟、UAT、验收 |
| 生产环境（Shift-Right） | 监控/可观测性、金丝雀/蓝绿部署、功能开关，视情况进行混沌实验 |

**时间预算与阻断规则（实践中的经验值）：**

- 对快速路径（代码检查 + 单元测试 + 关键集成测试），**提交到反馈 < 10 分钟**；到预发布的完整流水线 **< 30–45 分钟**；完整回归放在夜间或发布前。反馈回路节奏过慢，就会被绕过。
- **阻断与仅报告：** 单元、集成与冒烟门禁**始终阻断**（失败即不允许合并/部署）。夜间阶段（回归、负载、DAST）通过工单/修复进行报告，但不阻断每次提交。生产部署后：冒烟 + 监控——失败则回滚并启动事件处理。
- **交接点：** 提交（git push）将内循环（本地：TDD、单元测试、快速迭代）与外循环（带门禁的共享流水线）分隔开。能够前移到内循环的检查，在那里发现成本最低（左移）。

### 经典（V 模型）：在编写规格时设计测试

需求↔验收测试 · 系统设计↔系统测试 · 架构↔集成测试 · 代码↔单元测试。核心思想：每一级的测试应**在编写对应规格时**就设计好，而不是等到最后。对需求/设计的评审（静态测试）是最早的缺陷发现手段。

### 敏捷测试象限（冲刺规划框架）

Q1 单元/TDD 与 Q2 故事测试/BDD 持续运行并**预防**缺陷；当产品达到一定规模后，Q3 探索式/可用性/UAT 与 Q4 性能/安全用于**评估**产品。详情见目录。

## 5. 选择测试设计方法

| 若测试基础…… | ……则采用 |
|---|---|
| 具有输入范围/取值集合 | **等价类**（每类取一个代表值）+ **边界值分析**（恰好位于每个边界上及其紧邻之外：对于 5–50，测试 4、5、50、51）——几乎所有单元测试的基本配置 |
| 包含复杂业务规则/条件组合 | **决策表测试** |
| 包含状态与转换（工作流、会话、设备） | **状态转换测试**（同时测试被禁止的转换） |
| 描述用户操作流程 | **用例/场景测试**，包括错误与异常路径 |
| 是代码，且需要度量覆盖率 | **语句/分支覆盖** —— 作为缺口指标，而非目标（100% 覆盖率 ≠ 正确） |
| 不清晰、有缺口或时间紧迫 | **探索式测试**（带测试章程的定时会话）+ **错误推测**（空值、空字符串、特殊字符、时区、竞态条件） |

先使用系统化方法，有意识地**辅以**基于经验的方法——后者能发现脚本遗漏的问题。

## 6. 最佳实践（规划/评审测试时的检查清单）

1. **左移（Shift-Left）：** 从需求阶段开始进行评审与静态分析——缺陷发现得越晚，成本越高（广为流传的 Boehm 经验法则；方向上无争议，具体倍数存在争议）。
2. **尊重测试金字塔**——端到端测试从严控制，单元测试基座要宽。
3. **将重复性工作自动化**（冒烟、回归、API、单元）并纳入 CI/CD 门禁；为探索式与可用性测试保留人工精力。
4. **系统化地设计测试用例**（第 5 节），而非随意为之。
5. **让非功能性需求可度量**——没有数值目标，就无法评估性能/负载测试结果。
6. **重测 ≠ 回归：** 先确认修复有效，再检查副作用。顺序：冒烟 → 健全性/重测 → 回归。
7. **立即处理不稳定（Flaky）测试**——隔离、修复根因或删除；不稳定的套件会摧毁对流水线的信任。
8. **管理测试数据与环境：** 可复现（容器/IaC）、接近生产、使用脱敏或合成数据。
9. **度量测试本身的质量：** 以覆盖率作为缺口指标；在覆盖率数字可能产生误导之处使用**变异测试**。
10. **基于风险排序优先级：** 测试深度取决于失效影响 × 缺陷概率——而非平均分配。
11. **质量是团队的职责**（全团队方法）：尽早让测试人员参与需求；以 BDD/ATDD 作为与业务部门的共同载体。
12. **别忘了 Shift-Right：** 监控、金丝雀、功能开关；只有在可观测性成熟后才引入混沌工程。

## 7. 现代方法——何时额外采用

| 方法 | 适用场景 |
|---|---|
| **契约测试**（Pact） | 微服务，部署与团队相互独立 |
| **变异测试**（Stryker、PIT、mutmut） | 需要评估现有测试套件的质量 |
| **基于属性的测试**（Hypothesis、fast-check） | 存在不变式（"排序是幂等的"）且担心边界情况 |
| **模糊测试（Fuzzing）** | 解析器、反序列化、安全敏感的输入 |
| **混沌工程** | 分布式系统 + 成熟的可观测性 + 可靠的回滚机制 |
