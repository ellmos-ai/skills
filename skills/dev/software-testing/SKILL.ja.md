# ソフトウェアテスト：テスト戦略とテスト選択

このスキルは「ここで、今、何のために、どのテストが必要か」という問いに、勘ではなく体系的に答えるものです。判断ロジックを提供します。すべてのテスト種類、手法、定義の完全なカタログは同じフォルダ内の `testarten-katalog.md` にあります（詳細はそちらを参照してください）。

---

## 1. 枠組み：3つの次元で考える

テストを計画または作成する前に、タスクを3つの軸（ISTQB）上に位置づけてください。「テストの一覧」だけを管理すると軸が混ざり、計画に抜けが生じます。

| 軸 | 問い | 種類 |
|---|---|---|
| **テスト段階** | どのレベルか？ | 単体 → 統合 → システム → 受入 |
| **テストの種類** | どの特性か？ | 機能的 / 非機能的 / 構造ベース / 変更関連 |
| **テスト技法** | テストケースはどう導出されるか？ | ブラックボックス / ホワイトボックス / 経験ベース |

これと直交して、**静的**（レビュー、静的解析：実行なし、最も早く最も安価な欠陥発見）と**動的**（コードを実行する）があります。

## 2. 状況ルーター：何が起きているか？

具体的な状況に応じて入り口を選んでください。

| 状況 | 進め方 |
|---|---|
| **新機能の構築** | コードの前に受入基準を明確にする（ATDD/BDDの考え方）。実装と並行して単体テストを書く（同値クラス＋境界値）。新しいインターフェースには統合テストを用意する。E2Eはハッピーパスのみ、それ以上は不要。 |
| **バグ修正** | まずバグを再現するテスト（赤）を書き、次に修正（緑）＝ **再テスト**。その後、環境の **回帰テスト**。診断そのものは → `bugfix-protocol`。 |
| **リファクタリング** | 新しい機能テストは書かない。既存のテストスイートが安全網である。事前に、スイートが実際に振る舞いをカバーしているか確認する（必要に応じて特性テストを追加）。カバレッジ／ミューテーションを不足の指標として使う。 |
| **テストのないレガシーコード** | すべての関数に単体テストを書くところから始めない。まず、現在の振る舞いを固定する特性テストをシステム／API レベルで置き、個々の部分に手を入れるときに単体テストを追加していく。 |
| **API／マイクロサービス** | サービスレベルのAPIテストを重点に置く（ピラミッドの中間層）。チームやデプロイが分かれている場合は、共有のステージング統合テストではなく **コントラクトテスト**（例：Pact）を使う。 |
| **リリース準備** | 順序：スモーク（ビルドは安定しているか）→ 完全な回帰 → 非機能テスト（負荷、セキュリティ）→ UAT／受入 → リリース候補でのスモーク。 |
| **性能への懸念** | まず測定可能な目標を定義する（例：「1,000ユーザーでP95 < 300 ms」）。さもないと、どのテストも評価できない。負荷テスト＝通常負荷、ストレステスト＝限界点と回復。本番に近い環境が必須。 |
| **テストパイプラインの構築** | セクション4のCI/CDゲートを実装する。まずコミットごとに単体テストとリントから始め、段階的に拡張する。 |
| **テスト戦略／テストコンセプトの作成** | 3つの次元＋フェーズ対応（セクション4）＋リスクベースの優先順位付け（セクション6、項目10）に沿って構成する。 |

## 3. テスト段階：対象、目的、タイミング

| 段階 | 検査対象 | いつ | 目安 |
|---|---|---|---|
| **単体／コンポーネント** | 個々の関数／クラスを分離して（モック／スタブ） | 実装中、すべてのコミット | ピラミッドの広い基盤。高速（秒未満）、決定論的 |
| **統合** | 連携、インターフェース、DB接続 | 単体テストの後、すべてのマージ時 | 段階的に統合する（トップダウン／ボトムアップ）。大規模システムでビッグバンは避ける |
| **システム** | 技術要件に対する全体システム | 統合されたビルドが存在したら直ちに | 機能的かつ非機能的；独立したテスターが有効 |
| **受入** | 事業上の期待、実運用での利用 | 本番稼働前の最終段階 | 業務部門によるUAT；運用面（バックアップ／デプロイ／監視）も忘れない；必要に応じてアルファ／ベータ |

**テストピラミッド**は量の比率を示します：単体テストが多く、統合／API テストは的を絞り、E2E テストは少なく（出発点として約70/20/10の経験則。実際の欠陥の発生源に応じて調整）。逆転したピラミッド（UIテストが多い）は遅くて不安定になるため避ける。

## 4. フェーズ対応：いつ何を検査するか？

### CI/CDゲート（現代の標準的な対応）

| パイプライン段階 | ゲート |
|---|---|
| 全コミット | 単体テスト、リンター、静的解析（秒〜分） |
| プルリクエスト | コードレビュー、SAST/SCA、対象を絞ったコンポーネントテスト |
| マージ | 統合／API／コントラクトテスト、テスト環境でのスモーク |
| 夜間／リリース前 | 完全な回帰、E2E、性能／負荷テスト、DAST |
| リリース候補 | ステージングでのスモーク、UAT、受入 |
| 本番（Shift-Right） | 監視／オブザーバビリティ、カナリア／ブルーグリーン、フィーチャーフラグ、必要に応じてカオス実験 |

**時間予算とブロック規則（実務からの目安値）：**

- 高速パスは **コミットからフィードバックまで10分未満**（リント＋単体＋重要な統合テスト）；ステージングまでのパイプライン全体は **30〜45分未満**；完全な回帰は夜間またはリリース前。より遅く回るフィードバックループは回避されてしまう。
- **ブロックする vs. 報告のみ：** 単体、統合、スモークのゲートは **常にブロックする**（赤なら、マージ／デプロイ不可）。夜間段階（回帰、負荷、DAST）はチケット／修正として報告するが、すべてのコミットをブロックはしない。本番デプロイ後は、スモーク＋監視；赤ならロールバック＋インシデント。
- **引き渡しポイント：** コミット（git push）が、インナーループ（ローカル：TDD、単体、高速な反復）とアウターループ（ゲートを持つ共有パイプライン）を分ける。インナーループに移せるものは、そこで最も安価に捕捉される（Shift-Left）。

### 古典的（Vモデル）：仕様作成と同時にテストを設計する

要件↔受入テスト · システム設計↔システムテスト · アーキテクチャ↔統合テスト · コード↔単体テスト。中心となる考え方：ある段階のテストは、対応する仕様を **作成する時点で** 設計される — 最後に初めて考えるのではない。要件／設計のレビュー（静的テスト）は、そもそも最も早い欠陥発見である。

### アジャイルテストの象限（スプリント計画のための枠組み）

Q1 単体／TDD と Q2 ストーリーテスト／BDD は継続的に実行され、欠陥を **防ぐ**；Q3 探索的／ユーザビリティ／UAT と Q4 性能／セキュリティは、十分なプロダクトが存在したら製品を **評価する**。詳細はカタログを参照。

## 5. テスト設計手法の選択

| テストの根拠が… | …なら手法 |
|---|---|
| 入力範囲／値の集合を持つ | **同値クラス**（クラスごとに代表1つ）＋ **境界値分析**（各境界の上と直後：5〜50 なら 4, 5, 50, 51 をテスト）— ほぼすべての単体テストの基本装備 |
| 複雑な業務ルール／条件の組み合わせを持つ | **決定表テスト** |
| 状態と遷移を持つ（ワークフロー、セッション、デバイス） | **状態遷移テスト**（禁止された遷移もテストする） |
| ユーザーの操作手順を記述している | **ユースケース／シナリオテスト**（エラーパスと例外パスを含む） |
| コードがあり、カバレッジを測定したい | **命令／分岐カバレッジ** — 目標ではなく不足の指標として（100％カバレッジ ≠ 正しさ） |
| 不明確で不完全、または時間が少ない | **探索的テスト**（チャーター付きの時間区切りセッション）＋ **エラー推測**（null、空文字列、特殊文字、タイムゾーン、競合状態） |

体系的な技法を先に、経験ベースは意図的に **補完として** 用いる — 経験ベースは、スクリプトが見落とすものを見つける。

## 6. ベストプラクティス（テストの計画／レビュー時のチェックリスト）

1. **Shift-Left：** 要件段階からレビューと静的解析を行う — 欠陥が発見されるのが遅いほど高くつく（Boehm に由来する広く知られた経験則；方向性は確かだが、正確な係数は議論がある）。
2. **テストピラミッドを尊重する** — E2E テストは控えめに、単体の基盤は広く。
3. **繰り返すものを自動化する**（スモーク、回帰、API、単体）し、CI/CD ゲートに組み込む；手動の能力は探索的テストとユーザビリティ用に確保する。
4. **テストケースは体系的に設計する**（セクション5）、場当たり的にしない。
5. **非機能要件を測定可能にする** — 数値目標がなければ、性能／負荷テストは評価できない。
6. **再テスト ≠ 回帰：** まず修正を確認し、その後に副作用を確認する。順序は スモーク → サニティ／再テスト → 回帰。
7. **不安定なテストはすぐに対処する** — 隔離し、原因を修正するか削除する；不安定なスイートはパイプラインへの信頼を損なう。
8. **テストデータと環境を管理する：** 再現可能（コンテナ／IaC）、本番に近い、匿名化または合成されたデータ。
9. **テストの品質そのものを測定する：** カバレッジは不足の指標として；カバレッジの数値が誤解を招きうる箇所では **ミューテーションテスト**。
10. **リスクに基づいて優先順位を付ける：** テストの深さは、障害の影響 × 欠陥の発生確率に応じて — 均等に割り振らない。
11. **品質はチーム全体の仕事**（Whole-Team アプローチ）：テスターは要件の早い段階から関わる；業務部門との共通の手段として BDD／ATDD を使う。
12. **Shift-Right も忘れない：** 監視、カナリア、フィーチャーフラグ；カオスエンジニアリングは、オブザーバビリティが成熟してから。

## 7. 現代的な手法 — いつ追加で使うか

| 手法 | 使う場面 |
|---|---|
| **コントラクトテスト**（Pact） | デプロイとチームが分かれたマイクロサービス |
| **ミューテーションテスト**（Stryker、PIT、mutmut） | 既存のテストスイートの品質を評価したいとき |
| **プロパティベーステスト**（Hypothesis、fast-check） | 不変条件が存在し（「ソートは冪等」）、エッジケースが懸念されるとき |
| **ファジング** | パーサー、デシリアライズ、セキュリティ上重要な入力 |
| **カオスエンジニアリング** | 分散システム＋成熟したオブザーバビリティ＋確実なロールバック |
