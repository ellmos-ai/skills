# Тестирование программного обеспечения: стратегия тестирования и выбор тестов

Этот навык отвечает на вопрос «Какие тесты нужны здесь, сейчас и для чего?» —
систематически, а не наугад. Он предоставляет логику принятия решений; полный
каталог всех видов тестирования, методов и определений находится в
`testarten-katalog.md` в той же папке (для подробных вопросов обращайтесь туда).

---

## 1. Структура: мыслить в трёх измерениях

Прежде чем планировать или писать тесты, расположите задачу по трём осям (ISTQB).
Кто ведёт только «один список тестов», смешивает оси и планирует с пробелами:

| Ось | Вопрос | Варианты |
|---|---|---|
| **Уровень тестирования** | На каком уровне? | Модульный → интеграционный → системный → приёмочный |
| **Вид тестирования** | Какое свойство? | функциональное / нефункциональное / структурное / связанное с изменениями |
| **Метод тестирования** | Как возникают тест-кейсы? | Black-Box / White-Box / основанный на опыте |

Поперёк них: **статическое** (ревью, статический анализ — без выполнения, самое раннее
и дешёвое обнаружение ошибок) и **динамическое** (код выполняется).

## 2. Маршрутизатор ситуаций: что имеется?

Выберите точку входа по конкретной ситуации:

| Ситуация | Действие |
|---|---|
| **Разработка новой функции** | Уточнить критерии приёмки ДО кода (мышление ATDD/BDD). Модульные тесты параллельно с реализацией (классы эквивалентности + граничные значения). Интеграционный тест для новых интерфейсов. Один E2E-сценарий «happy path», не больше. |
| **Исправление ошибки** | Сначала тест, воспроизводящий ошибку (красный), затем исправление (зелёный) = **повторное тестирование**. Затем **регрессия** окружения. Диагностика сама по себе → `bugfix-protocol`. |
| **Рефакторинг** | НЕ добавлять новые тесты функций — существующий набор является страховочной сеткой. Сначала проверить, покрывает ли набор поведение на самом деле (при необходимости дописать характеризующие тесты). Покрытие/мутационное тестирование как индикатор пробелов. |
| **Унаследованный код без тестов** | Не начинать с модульных тестов каждой функции. Сначала характеризующие тесты на уровне системы/API вокруг текущего поведения, затем при изменении отдельных частей — дописывать модульные тесты. |
| **API / микросервисы** | Упор на API-тесты на уровне сервиса (средний уровень пирамиды). При разделённых командах/развёртываниях: **контрактное тестирование** (например, Pact) вместо общих интеграционных тестов на staging. |
| **Подготовка релиза** | Порядок: смоук (сборка стабильна?) → полная регрессия → нефункциональные тесты (нагрузка, безопасность) → UAT/приёмка → смоук на релиз-кандидате. |
| **Беспокойство о производительности** | Сначала определить измеримую цель (например, «P95 < 300 мс при 1 000 пользователях»), иначе ни один тест не поддаётся оценке. Нагрузочный тест = нормальная нагрузка, стресс-тест = точка отказа и восстановление. Обязательна среда, приближенная к продуктивной. |
| **Настройка тестового конвейера** | Реализовать шлюзы CI/CD из раздела 4; начать с модульных тестов и линтера при каждом коммите, затем постепенно расширять. |
| **Написание стратегии/концепции тестирования** | Структура по трём измерениям + сопоставление с фазами (раздел 4) + приоритизация на основе рисков (раздел 6, пункт 10). |

## 3. Уровни тестирования: объект, цель, момент

| Уровень | Проверяет | Когда | Эмпирическое правило |
|---|---|---|---|
| **Модульный/компонентный** | Отдельная функция/класс изолированно (моки/заглушки) | Во время реализации, каждый коммит | Широкая основа пирамиды; быстрый (< секунд), детерминированный |
| **Интеграция** | Взаимодействие, интерфейсы, подключение к БД | После модульных тестов, при каждом слиянии | Интегрировать инкрементально (сверху вниз/снизу вверх), никогда не «большим взрывом» в крупных системах |
| **Система** | Всю систему относительно технических требований | Как только существует интегрированная сборка | Функционально И нефункционально; ценны независимые тестировщики |
| **Приёмка** | Ожидания бизнеса, реальное использование | Последний уровень перед запуском | UAT силами профильного подразделения; не забыть эксплуатацию (резервное копирование/развёртывание/мониторинг); при необходимости Alpha/Beta |

**Пирамида тестирования** как соотношение объёмов: много модульных, целевые интеграционные/API,
мало E2E-тестов (ориентир ~70/20/10 как отправная точка — корректировать по фактическому
происхождению ошибок). Перевёрнутая пирамида (много UI-тестов) = медленно + нестабильно → избегать.

## 4. Сопоставление с фазами: когда что проверять?

### Шлюзы CI/CD (современное стандартное сопоставление)

| Этап конвейера | Шлюз |
|---|---|
| Каждый коммит | Модульные тесты, линтеры, статический анализ (секунды–минуты) |
| Pull Request | Ревью кода, SAST/SCA, целевые компонентные тесты |
| Слияние | Интеграционные/API/контрактные тесты, смоук на тестовом окружении |
| Ночью / перед релизом | Полная регрессия, E2E, тесты производительности/нагрузки, DAST |
| Релиз-кандидат | Смоук на staging, UAT, приёмка |
| Продуктив (Shift-Right) | Мониторинг/наблюдаемость, Canary/Blue-Green, feature flags, при необходимости Chaos-эксперименты |

**Временные бюджеты и правила блокировки (ориентиры из практики):**

- **Время от коммита до обратной связи < 10 минут** для быстрого пути (линтер + модульные +
  критические интеграционные тесты); весь конвейер до staging **< 30–45 минут**; полная
  регрессия ночью или перед релизом. Контур, который работает медленнее, начнут обходить.
- **Блокирующие и информирующие:** модульные, интеграционные и смоук-шлюзы ВСЕГДА блокируют
  (при красном результате нет слияния/развёртывания). Ночные этапы (регрессия, нагрузка, DAST)
  сообщают через тикет/исправление, но не блокируют каждый коммит. После развёртывания в продуктив:
  смоук + мониторинг — при красном результате откат + инцидент.
- **Точка передачи:** коммит (git push) разделяет внутренний цикл (локально: TDD, модульные,
  быстрая итерация) и внешний цикл (общий конвейер с шлюзами). То, что можно перенести во
  внутренний цикл, там ловится дешевле всего (Shift-Left).

### Классика (V-модель): тесты проектируются при спецификации

Требования↔приёмочный тест · Проектирование системы↔системный тест · Архитектура↔интеграционный
тест · Код↔модульный тест. Основная идея: тесты одного уровня проектируются **при создании
соответствующей спецификации** — не только в конце. Ревью требований/проектов (статическое
тестирование) — самое раннее обнаружение ошибок вообще.

### Квадранты гибкого тестирования (Agile Testing Quadrants) как сетка планирования спринтов

Q1 Модульные/TDD и Q2 story-тесты/BDD работают непрерывно и **предотвращают** ошибки;
Q3 исследовательское/юзабилити/UAT и Q4 производительность/безопасность **оценивают** продукт,
как только существует достаточно продукта. Подробности в каталоге.

## 5. Выбор методов разработки тестов

| Если тестовая база … | … тогда метод |
|---|---|
| содержит диапазоны входных значений/множества значений | **Классы эквивалентности** (один представитель на класс) + **анализ граничных значений** (на границе и сразу за каждой границей: для 5–50 тестировать 4, 5, 50, 51) — базовый набор почти для любого модульного теста |
| содержит сложные бизнес-правила/комбинации условий | **Тестирование таблиц решений** |
| описывает состояния и переходы (workflow, сессия, устройство) | **Тестирование переходов состояний** (проверять и запрещённые переходы) |
| описывает сценарии пользователя | **Тестирование по вариантам использования/сценариям** с путями ошибок и исключений |
| содержит код и покрытие должно измеряться | **Покрытие операторов/ветвей** — как индикатор пробелов, а не как цель (100 % покрытия ≠ корректность) |
| неясна или неполна, либо мало времени | **Исследовательское тестирование** (сессии с ограничением по времени и charter) + **угадывание ошибок** (ноль, пустая строка, спецсимволы, часовые пояса, гонки) |

Сначала систематические методы, опытные — сознательно **дополнительно**: они находят то,
что скрипты пропускают.

## 6. Лучшие практики (чек-лист при планировании/ревью тестов)

1. **Shift-Left:** ревью + статический анализ начиная с фазы требований — чем позже найдена
   ошибка, тем дороже (распространённое эмпирическое правило по Boehm; направление
   бесспорно, точные коэффициенты спорны).
2. **Соблюдать пирамиду тестирования** — E2E-тесты экономно, модульная основа широкая.
3. **Автоматизировать то, что повторяется** (смоук, регрессия, API, модульные) и закрепить
   в шлюзах CI/CD; ручные ресурсы оставить для исследовательского тестирования и юзабилити.
4. **Проектировать тест-кейсы систематически** (раздел 5), а не ad hoc.
5. **Делать нефункциональные требования измеримыми** — без числовой цели нет поддающегося
   оценке теста производительности/нагрузки.
6. **Повторное тестирование ≠ регрессия:** сначала подтвердить исправление, затем побочные
   эффекты. Порядок: смоук → санити/повторное тестирование → регрессия.
7. **Нестабильные тесты обрабатывать немедленно** — поместить в карантин, устранить причину
   или удалить; нестабильные наборы разрушают доверие к конвейеру.
8. **Управлять тестовыми данными и окружениями:** воспроизводимость (контейнеры/IaC), близость
   к продуктиву, анонимизированные или синтетические данные.
9. **Измерять качество самих тестов:** покрытие как индикатор пробелов; **мутационное
   тестирование** там, где цифры покрытия могут вводить в заблуждение.
10. **Приоритизировать по рискам:** глубина тестирования по последствиям отказа ×
    вероятности ошибки — а не равномерно.
11. **Качество — задача команды** (подход «вся команда»): тестировщики подключаются к
    требованиям рано; BDD/ATDD как общий инструмент с профильным подразделением.
12. **Не забывать Shift-Right:** мониторинг, Canary, feature flags; Chaos Engineering — только
    при зрелой наблюдаемости.

## 7. Современные методы — когда дополнительно применять

| Метод | Применять, если … |
|---|---|
| **Контрактное тестирование** (Pact) | Микросервисы с раздельными развёртываниями/командами |
| **Мутационное тестирование** (Stryker, PIT, mutmut) | Нужно оценить качество существующего набора тестов |
| **Property-Based Testing** (Hypothesis, fast-check) | Существуют инварианты («сортировка идемпотентна») и опасаются граничных случаев |
| **Фаззинг** | Парсеры, десериализация, критичные к безопасности входные данные |
| **Chaos Engineering** | Распределённые системы + зрелая наблюдаемость + отлаженные откаты |

## Смежные навыки (не дублировать)

- **`superpowers:test-driven-development`** — конкретный цикл Red-Green-Refactor при написании кода.
- **`bugfix-protocol`** — 6-фазная диагностика конкретной ошибки.
- **`bugsweep`** — систематический проход по поиску ошибок в кодовой базе.
- **`dev-cycle`** — 8-фазный полный цикл (начиная с версии 1.2.0: тесты проектируются в
  фазах 1/3/5, пишутся в фазе 6 и выполняются в фазе 7; данный навык определяет, КАКИЕ тесты
  где должны выполняться).
