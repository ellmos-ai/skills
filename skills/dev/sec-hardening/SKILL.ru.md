# sec-hardening - структурно, а не по частям

Когда находки одного класса повторяются, причина обычно лежит в структуре (нет центральной валидации, непроверенная граница доверия, секреты в коде). Этот навык предлагает изменения на этом уровне. Контракт: `sec-scan/references/contract.md` (находки §1/§2, правило 4 секреты, правило 5 стоимость).

## Вход

`findings.json` (в идеале `validated` и выше), отчёты об инцидентах, оценки, `threatmodel.md` и знание кода. Без предложений без подтверждённого доказательствами входа; допущения помечать как таковые.

## Процедура

1. **Объединить первопричины:** группировать находки по корню, а не по файлу: например, «каждый маршрут сам строит SQL», «проверка доступа повторяется в каждом обработчике», «конфигурация содержит секреты». Назвать id находок для каждой группы.
2. **Набросать текущую архитектуру** как ASCII-картину: границы доверия, поток данных, где проверка сегодня выполняется (или нет).
3. **Варианты для каждой причины** (не менее двух, включая «только отдельные патчи»): описание, **трудозатраты**, **риск внедрения** (регрессии, миграция), **эффект** (какой класс находок исчезает, какой остаётся), зависимости. В виде таблицы.
4. **Рекомендация** для каждой причины с обоснованием и **целевой картиной** (ASCII) рядом с текущей.
5. **Порядок:** что сначала, потому что закрывает сразу несколько находок или является предпосылкой; что может подождать. Промежуточные шаги, которые можно поставлять отдельно.
6. **Доказательства для каждого предложения:** id находок, расположения в коде (`path:line`), измерения. Предложение без доказательств помечается как гипотеза. Без выдуманных оценок трудозатрат во времени; только относительные (small/medium/large) или заданные пользователем.

## Результат

Один документ (например, `hardening.md` в каталоге сканирования или в чате), разделы: исходная точка, причины, текущая/целевая картины, варианты, рекомендация, порядок, открытые вопросы. **Не меняет код**, не создаёт патчей и ничего не коммитит (правило 3); отдельные шаги выполняются через `sec-fix` или обычную разработку. Без секретных значений в документе (правило 4).
