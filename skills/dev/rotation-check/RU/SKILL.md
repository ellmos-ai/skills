# Rotation-Check — Одна цель на запуск, честное покрытие, память

## Обзор и назначение

Любой, кто хочет периодически проверять конвейер (pipeline) с множеством проектов (источники, стиль, работоспособность, безопасность, переводы, …), сталкивается с проблемой распределения: проверять все проекты за один запуск слишком дорого; без памяти каждый запуск случайно проверяет одно и то же. Шаблон ротации решает обе проблемы: **ровно одна цель на запуск, выбор по принципу «дольше всего не проверялась», реестр в качестве памяти.** Таким образом, даже редкий такт (ежедневно/еженедельно) за несколько недель доказуемо и без дублирования работы покрывает весь конвейер.

Зарекомендовал себя как основа развитой системы продуктовых автоматизаций для нескольких проектных конвейеров.

## Компоненты

### 1. Два файла на конвейер (создаются один раз)

| Файл | Содержимое | Характер |
| --- | --- | --- |
| `CHECKED-REGISTRY.md` | Одна компактная строка на проверку: цель, дата, тип проверки, результат, следующий шаг | Обзор состояния — читается ПЕРЕД каждым выбором цели |
| `CHECKS-LOG.txt` | Короткая запись истории за запуск с деталями/доказательствами | Журнал — только дозапись (append-only) |

Оба файла располагаются в корне конвейера (не в отдельном проекте), чтобы запуск мог прочитать их за одно чтение. Формат строки реестра:

```text
| <ziel> | <YYYY-MM-DD> | <checktyp> | <ok|befund|übersprungen> | <nächster schritt> |
```

### 2. Правило выбора

1. Прочитать реестр и журнал (обязательно, ПЕРЕД выбором — иначе дублирующая проверка).
2. Кандидаты: цели, которые для ДАННОГО типа проверки никогда не проверялись или проверялись дольше всего назад.
3. Обход/пропуск: если цель недавно затрагивалась **тесно связанной** проверкой (например, проверка цитирования сразу после проверки источников не имеет смысла) или заблокирована/находится в активной разработке (соблюдать блокировки).
   **Период охлаждения сородичей (Sibling Cooldown):** Если несколько связанных проверок работают над одним и тем же набором целей (например, разработка, поиск багов и ревью одного конвейера), согласуйте период ожидания (эмпирическое значение: ~24 ч), в течение которого цель, обработанная смежной проверкой, не выбирается повторно — предотвращает коллизии и противоречивые параллельные изменения.
4. Продвигать вне очереди только при наличии веской причины (например, крупная переработка со времени последней проверки) — указать причину в журнале.

### 3. Выполнение проверки — с выходом в режиме read-only

Применить саму проверку (произвольно определяемую: проверка источников, проверка стиля, аудит безопасности, …) к ОДНОЙ выбранной цели. Два допустимых исхода:

- **Находка (Befund):** исправить то, что входит в рамки (scope); более крупные задачи записать как последующие в локальный файл TODO/AUFGABEN проекта (проверка не должна решать всё сама).
- **Нечего делать (Nothing to do):** кратко задокументировать и завершить. Холостой запуск — это результат, а не провал; ни в коем случае не расширять рамки только для того, чтобы «что-то найти».

### 4. Документирование

- Дополнить строку реестра (компактно), написать запись в журнал (детали/доказательства).
- **Гигиена журнала:** если реестр/журнал становятся громоздкими (эмпирическое значение: несколько сотен строк), переместить старое состояние в `_archiv/`, создать чистый файл и сослаться в заголовке на предшественника (путь + дата).
- **Дрейф путей (Path Drift):** если ожидаемый путь ведет в никуда (цель перемещена/переименована), НЕ создавать заново — скорректировать через авторитетный файл состояния/реестр конвейера и зафиксировать ошибочный путь в журнале ошибок (failure log).

### 5. Такт (частота)

Связать частоту со скоростью изменений проверяемого объекта: ротационные проверки стабильных ресурсов хорошо работают еженедельно (одна цель на запуск ≈ весь конвейер за квартал при ~12 целях); быстрыми проверками (например, активной работы) — ежедневно. Практический опыт: изначально почасовые проверки почти все были сокращены до ежедневных/еженедельных — покрытие сохранилось, затраты снизились.

## Шаблон промпта (для планировщика/автоматизации)

```text
VORBEREITUNG: Lies <PIPELINE_ROOT>/<POLICY-DOKUMENTE> sowie <REGISTRY> und <LOG>.

AUFGABE: Wähle genau ein Ziel aus <ZIELMENGE>. Bevorzuge Ziele, die für den Check
"<CHECKTYP>" noch nie oder am längsten nicht geprüft wurden. Wurde ein Ziel kürzlich
von diesem oder einem eng verwandten Check geprüft oder ist es gesperrt: ausweichen
oder read-only mit Logeintrag enden.

CHECK: <konkrete Prüf-/Pflegeaufgabe und was bei Befund zu tun ist; Folgearbeiten in
die projektlokale TODO-Datei>.

Wenn keine Arbeit anfällt: kurz dokumentieren, Lauf beenden.

DOKUMENTATION: Registry-Zeile in <REGISTRY> (Ziel, Datum, Checktyp, Ergebnis, nächster
Schritt) + Verlaufseintrag in <LOG>. Bei Überlänge: alten Stand nach _archiv/ und
frische Datei mit Verweis.

ABSCHLUSS: Kurzbericht (Ziel | getan | Ergebnis | Folgeaufgaben).
```

## Красные флаги (Red Flags)

| Мысль | Реальность |
| --- | --- |
| «Я просто выберу интересный проект» | Выбор только через реестр — иначе возникнет предвзятость к любимым проектам и слепые зоны. |
| «Я прочитаю реестр после проверки» | Сначала. Реестр — это критерий выбора, а не просто протокол. |
| «Несколько целей за один запуск сделают больше» | Одна цель сохраняет запуски короткими, идемпотентными и отменяемыми; объем достигается за счет ротации. |
| «Холостой запуск был бесполезен» | Задокументированный холостой запуск обновляет память — в этом заключается половина ценности системы. |
