# Human-Loop-Audit

> **`reissverschluss-merge` と混同しないこと:** 名称は「ジッパー」のイメージを共有しているが、`reissverschluss-merge` は **Git のマージ手順**（セクションごとに2つのコードブランチを統合する）である。`human-loop-audit` はGitとは無関係で、**ユーザーとのテスト/監査の流れ**である。どちらのスキルも、ジッパーを「2本の列を歯ごとに噛み合わせる」という同じ基本発想としてのみ用い、1本ずつ順番に進めるものではない。

## 目的と役割分担

ユーザーの時間が**直列のボトルネック**である。実際にアプリをライブで操作し、数秒で「しっくりくるか」を判断できるのはユーザーだけだ。それ以外のすべて（対象を開く、フィードバックを構造化して記録する、修復を開始する）はエージェントが担い、それも**ユーザーが次の対象を見ている間に**行う。後から行うのではない。エージェントは操縦者であると同時に評価者でもある。

**核心は順序そのものではなく重なり合いにある:** 「アプリを開く → 待つ → 評価する → 次のアプリを開く」という純粋な逐次処理は、ユーザーがテストしている待ち時間を無駄にする。Human-Loop-Audit はまさにこの時間帯を活用する。

## 手順

1. ユーザーから **「start」** を受け取る → エージェントは**最初**の検査対象を開く。対象のプロセスを起動するだけで十分である（例: `Start-Process <exe>`、または対象に対応する起動コマンド）。**デスクトップの乗っ取りは不要**で、操作はユーザー自身が行う。開いたことを短く確認する。
2. **ユーザーがテストし、フィードバックをチャットに書く** — 短い箇条書きで十分である。意味が変わるような言い換えはしない。
3. **フィードバックが届いたら、2つの作業を逐次ではなく並行して行う:**
   - エージェントは**ただちに次の検査対象を開き**、ユーザーが待たずにテストを続けられるようにする。
   - **同時に**、エージェントは受け取ったフィードバックを評価する。対象ごとの発見事項を構造化して記録する（**機能する** / **欠陥** / **要望**。短い説明付き）。欠陥または明確な要望があれば、**ただちにWorkerへ修復依頼を委任する**（まとめて保留し「あとで」依頼するのではない。ユーザーが次の対象をテストしている間に修復が進むようにするためだ）。
4. すべての対象が終わるまで**繰り返す**（以降の各対象について手順2/3へ戻る）。
5. **完了:** 発見事項リスト（対象ごとに機能する/欠陥/要望）と、開始した修復の一覧（Worker/依頼内容/状態）をユーザーに提示する。

## 発見事項の構造（検査対象ごと）

| 対象 | 状態 | 発見事項 | 修復の委任先 |
|---|---|---|---|
| `<App/Objekt-Name>` | 機能する / 欠陥 / 要望 | ユーザーの原文を変えない短い箇条書き | 委任した場合はWorker名/セッション |

1つの対象に複数の行を割り当ててよい（複数の発見事項がある場合）。何も黙って要約しないこと。完了報告はこの表から読み取るのであって、記憶に頼らない。

## 関連スキルとの区別

- **`reissverschluss-merge`**（上記の注記を参照） — 純粋な Git マージ手順。同じ名称のイメージを持つが、内容的な重なりはない。
- より狭い範囲の、プロジェクト固有の波（ウェーブ）単位のテスト/ストア提出サイクルが存在し、固定された追加フェーズ（アセットレビュー、提出シート、ID の書き戻し）を持ち、**逐次的**な実装（「対応項目の実装は別途行う」）となっている。`human-loop-audit` は意図的に**汎用的な**手順であり、**任意の**アプリ/GUIシリーズに用い、修復を別の後工程としてではなく**即時かつ並行して**委任する。
- **`bugsweep` / `bugfix-protocol`** — 実際の修復作業であり、`human-loop-audit` がここへ委任する。本スキル自体は修復を行わない。

## 落とし穴

- **次の対象を開く前に評価の完了を待たない** — 「待ってから評価し、それから次を開く」という純粋な逐次処理は、このスキルの核心である重なり合いを失わせる。
- **フィードバックはチャット履歴に溜めず、すぐに構造化して記録する** — セッションが途切れると失われるため。
- **既知の不安定な対象をそのまま起動しない** — ユーザーがライブで待機する前に、起動可能かを簡単に確認する。
- **委任は最後にまとめてではなく即時に行う** — さもないと、ユーザーのテストが終わった後にようやく修復が始まり、本手順の時間的利点が失われる。
