# Human-Loop-Audit

> **Не путать с `reissverschluss-merge`:** название использует тот же образ «молнии»,
> но `reissverschluss-merge` — это **процедура слияния Git** (поочерёдное объединение двух веток кода
> по участкам). `human-loop-audit` здесь не имеет никакого отношения к Git — это **процедура
> тестирования/аудита совместно с пользователем**. Оба навыка используют молнию лишь как общую
> основную идею: два потока соединяются зубец за зубцом, а не поток за потоком.

## Назначение и распределение ролей

Время пользователя — это **последовательное узкое место**: только он может по-настоящему
работать с приложением в реальном времени и за секунды сказать, правильно ли оно ощущается.
Всё остальное — открытие объектов, структурированная фиксация обратной связи, запуск
исправлений — берёт на себя агент, и делает это **во время**, а не после того, как
пользователь уже перешёл к следующему объекту. Агент одновременно оператор кабины и аналитик.

**Суть в перекрытии, а не в самом порядке:** чисто последовательное «открыть приложение →
ждать → проанализировать → открыть следующее» тратит время ожидания, в течение которого
пользователь тестирует. Human-Loop-Audit использует именно это окно.

## Ход работы

1. **«start»** / **«старт»** от пользователя → агент открывает **первый** объект проверки. Достаточно
   запустить процесс (например, `Start-Process <exe>` или соответствующую команду запуска объекта) —
   **перехват рабочего стола не нужен**, пользователь работает сам. Кратко подтвердить, что
   объект открыт.
2. **Пользователь тестирует и пишет обратную связь в чат** — достаточно коротких пунктов,
   ничего не переформулировать, если это меняет смысл.
3. **Как только обратная связь поступила, два действия идут параллельно, а не одно за другим:**
   - Агент **сразу открывает следующий объект проверки**, чтобы пользователь мог продолжить
     тестирование без задержки.
   - **Одновременно** агент анализирует полученную обратную связь: фиксирует вывод по каждому
     объекту в структурированном виде (**Работает** / **Дефект** / **Пожелание** с кратким
     описанием), а при дефекте или явном пожелании **немедленно передаёт задачу на исправление
     воркеру** (не копить и не поручать «позже» — исправление должно выполняться, пока
     пользователь продолжает тестировать).
4. **Повторять**, пока не пройдены все объекты (возврат к шагам 2/3 для каждого следующего
   объекта).
5. **Завершение:** представить пользователю список выводов (по каждому объекту
   Работает/Дефект/Пожелание) и список запущенных исправлений (воркер/задача/статус).

## Структура выводов (по каждому объекту проверки)

| Объект | Статус | Вывод | Исправление передано | 
|---|---|---|---|
| `<App/Objekt-Name>` | Работает / Дефект / Пожелание | краткий пункт, без изменения формулировки пользователя | имя/сессия воркера, если передано |

Одному объекту может соответствовать несколько строк (несколько выводов). Ничего не
сворачивается молча — итог строится по этой таблице, а не по памяти.

## Разграничение со смежными навыками

- **`reissverschluss-merge`** (см. примечание выше) — чисто процедура слияния Git, без
  содержательного пересечения, несмотря на одинаковый образ в названии.
- Смежные, но более узкие циклы тестирования волн/подачи в магазины с жёстко заданными
  дополнительными фазами (проверка ресурсов, таблицы подачи, обратная запись ID) и
  **последовательной** реализацией («выполнение пунктов идёт отдельно») существуют как
  процедуры, привязанные к конкретному проекту. `human-loop-audit` — намеренно **общий**
  процесс для **любых** серий приложений/GUI, который передаёт исправления **сразу и
  параллельно**, а не как отдельный последующий шаг.
- **`bugsweep` / `bugfix-protocol`** — собственно работа по исправлению, которую
  делегирует `human-loop-audit`; сам этот навык ничего не исправляет.

## Подводные камни

- **Не ждать анализа, прежде чем открыть следующий объект** — чисто последовательное
  «ждать, затем анализировать, затем открыть следующий» упускает именно то перекрытие,
  ради которого существует этот навык.
- **Фиксировать обратную связь сразу в структурированном виде**, а не копить в истории чата —
  при обрыве сессии она бы пропала.
- **Не запускать объекты вслепую**, если известно, что объект нестабилен, — заранее проверить,
  что он запускается, прежде чем пользователь начнёт тестировать вживую.
- **Передавать задачи сразу, а не копить до конца** — иначе исправление начнётся тогда, когда
  пользователь давно закончил тестирование, и выигрыш по времени будет потерян.

## Примеры запуска

- «human-loop-audit»
- «Давай протестируем приложения в режиме молнии.»
- «Я тестирую, ты анализируешь и исправляешь.»
- «start» / «старт» (после предварительного объявления Human-Loop-Audit, как сигнал запуска для шага 1)
