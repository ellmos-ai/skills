# sec-diff-scan

Как `sec-scan`, но область - **изменение**. Контракт, форматы файлов и правила: `sec-scan/references/contract.md`; схемы и валидатор - в `sec-scan/schemas/` и `sec-scan/scripts/`. Preflight (принадлежность, проверка блокировки, egress, стоимость), построение кандидатов (`id` через `secfind.py id`, маскирование секретов) и валидация работают так же, как в `sec-scan` > Процедура. Здесь перечислены только отличия.

## Определить область

Один из этих источников, всегда с точной точкой сравнения:

- PR: base- и head-коммит PR (локально `git diff <base>...<head>` или получить PR через `gh`; учитывать egress).
- Коммит(ы) или ветка: `git diff <base>...<branch>`.
- Рабочее дерево: `git diff` и `git diff --staged` плюс неотслеживаемые файлы.

`findings.json` > `target.ref` = head-коммит (или `working-tree`), `target.scope` = файлы diff. Если diff пуст, прервать и сообщить об этом.

## Процедура (вместо шагов 3-5 sec-scan)

1. **Прочитать diff**, а не только hunks: каждый изменённый файл - в контексте затронутой функции.
2. **Подтянуть контекст:** вызывающий код изменённых функций (кто подаёт входные данные?), вызываемый код (куда текут данные?), конфигурацию и тесты, документирующие допущения. Использовать `threatmodel.md`, если он есть; иначе самостоятельно кратко определить только затронутые границы доверия (полная модель не нужна; это `sec-threat-model`).
3. **Вопросы ревью для изменений:**
   - Новые точки входа или новые sink'и (shell, SQL, файловая система, десериализация, HTTP-клиент)?
   - Удалена, ослаблена или обойдена ли проверка (декоратор auth, валидация, экранирование, проверка прав)?
   - Регрессия известных шаблонов: тот же класс ошибок, что в прежних находках или в других местах репозитория (значения `rule` из существующего `findings.json`, если он есть).
   - Новая зависимость или изменённая версия в манифесте/lockfile; секреты или токены в изменении; дальнейшее ослабление конфигурации (CORS, debug, права)?
4. **Сообщать о находке, только если путь действительно достигает изменённого или затронутого места.** Ранее существовавшие дефекты в контексте, не связанные с изменением: записать с их реальной серьёзностью по контракту 3 и указать в `description` «существовал ранее, не внесён этим изменением» (не понижать до `info`) или, если не проверены, указать только в `coverage.limits`; предметом diff они не являются.

## Покрытие

`coverage.json`: `scanned` = файлы diff (глубина обычно `read`) **и** дополнительно прочитанные файлы контекста, `notScanned` = файлы diff, которые не были прочитаны (бинарные, сгенерированные, слишком большие), с причиной. В `limits` указывается: «только изменение, остальная часть репозитория не сканировалась». `complete` определяется по контракту 5. Чистое сканирование diff ничего не говорит о репозитории.

## Границы области

Без сканирования всего репозитория (`sec-scan`), без проверки во время выполнения (`sec-validate`), без исправления. Результат: `findings.json`, `coverage.json`, код возврата `secfind.py validate`.
