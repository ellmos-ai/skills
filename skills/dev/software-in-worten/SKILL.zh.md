# 以文字表达软件

## 基本思路

人类是**以视觉方式**进行设计的：*我希望如何操作它？* 智能体则**阅读文本**。
只要两者分开产生，它们就会逐渐偏离：界面能做到的事，技能可能并不知道；反之亦然。

然而两者本质相同，只是处于不同的形态。存在一种翻译关系，掌握它的人就能在两个方向上工作：

> **从文字生成界面。再把界面还原为文字。**

---

## 翻译对照表

| 在界面中 | 其含义 | 在文本中 |
|---|---|---|
| **鼠标指针** | *我可以选择* —— 可能性的空间 | 此处可选项的集合 |
| **标记选中** | *我想要这个* | 一个选择，一个值 |
| **点击** | *我做出决定，我要去那里* | **提示词** —— 用户的回答 |
| **字段、开关、设置项** | 一个会被保留的决定 | **Config** |
| **整个软件的设置** | 处处生效的决定 | **Policies** |
| **表单、输入界面** | 一组相关决定的集合 | **Template** |
| **启动某件事的按钮** | *现在将发生某些事* | 触发 **Skill** 或 **Workflow** |
| **随后运行的内容** | 步骤顺序 | 技能中的指令 —— 或一个 **脚本** |
| **进度条** | *正在运行，进行到哪一步* | 流程中的状态消息 |
| **成功提示、结果视图** | *得到了这个结果* | 返回值 —— 在界面中只是呈现得更美观 |
| **项目** | 一个有边界的工作状态 | 一个**文件夹** —— 并且因为它本身位于某个文件夹中，所以属于该软件的一部分 |
| **视图、标签页、区域** | 当前所处的一种状态 | 流程树中的一个步骤 |

**核心一行是点击。** 点击无非就是用户在对话中会说的话，只是更快。**点击就是提示词。**
而提示词之后会有反应：一个新的问题、一个新的视图、一种新的状态。

## 流程是一棵树

每个应用程序都是一系列决定，决定之间会发生某些事情：

```
Voraussetzungen geklärt?   →  Referenzen · Kandidatenliste · Nummern · Reihenfolge
        ↓
Einverständnis des Nutzers →  START
        ↓
Will er mitlesen?          →  ja: Mitleseansicht öffnen
Will er Zwischenmeldungen? →  ja: bei jedem Ereignis melden (durch, abgelehnt, Status)
        ↓
        [ AUSFÜHRUNG — oft ausgelagert an andere Software ]
        ↓
Rückgabe kommt zurück      →  auswerten
        ↓
Was will er wissen?        →  das Ergebnis in seinen Begriffen:
                              „bestellt bei X, 40 Minuten, 30 Euro"
```

**三个部分，始终相同：**

1. **决定** —— 条件判断，直到所需的一切都齐备
2. **执行** —— 通常根本不在自己的工具中进行，而是被外包出去
3. **反馈** —— 结果以人的语言返回给人

第三部分在设计时最常被低估。**沟通通过感官进行** —— 文字、图像、声音。界面负责把这些呈现出来；技能则描述*反馈什么*以及*何时反馈*。

## 中间层：蓝图

在“已描述”与“已构建”之间缺少一个阶段。它叫作**蓝图（Blueprint）**，是**排列方式与图像相符的文本** —— 一个可以阅读的屏幕：

```
 Worauf hast du Hunger?   [ Burger                        ]
 Wohin liefern?           [ Dorfstraße 1, 16321 Bernau    ]
 Höchstbetrag             [ 35 ] €   ⓘ Endbetrag an der Haustür
 Modus                    (•) Lieferung  ( ) Tisch  ( ) Abholung

 Kandidaten (ziehen zum Umsortieren)            ↻ neu suchen
 ┌────────────────────────────────────────────────────┐
 │ ≡ 1  Burger House Dorfstadt      ★ Favorit   offen │
 │ ≡ 2  Pizzeria Roma                            offen │
 └────────────────────────────────────────────────────┘

 [ Trockenlauf ansehen ]   [ Wirklich anrufen → 4 Anrufe, ~0,20 € ]
```

**这一阶段为何如此有价值：**

蓝图**既可阅读，也可查看**。人能看到自己的画面，智能体能看到字段、类型与顺序。它只需几分钟，没有成本，而且可以在对话中修改 —— 这与已构建的界面不同。

**而从蓝图出发，技能几乎会自然而然地产生：**

> **智能体需要能够做什么、知道什么、并按什么顺序去做，才能填完这个蓝图？**

每个字段都变成一个问题。排列顺序变成执行顺序。已预填的内容不再询问。显示为按钮的内容变成一个步骤。之后再补充智能体还需要了解的内容 —— 专业知识、边界与容易踩的坑。

**因此有三个阶段：** 描述 → **蓝图** → 技能 *（并且同样可以从那里生成一个已构建的界面）*。

### 空字段是一个问题 —— 而问题有其目的

`[ 35 ] €` 看起来像一个数字。但它其实是**向人发出的数据请求**，并且它有一个通常不会说出口的原因：

> **我们需要这个上限金额，因为它是决定是否下单的条件。**

因此这个字段同时承载三件事：**应填入什么**、**为何需要**，以及**它之后在哪里起作用**。在界面中，这些体现在布局和帮助文本中。而在文本中，必须把它明确写出来 —— 否则就会丢失。

**因此，每个蓝图下方都应附一份字段图例：**

| | |
|---|---|
| **问题** | 人会如何被询问 |
| **类型** | 数字、文本、选择、列表、有序列表、日期…… |
| **目的** | 该值之后用于什么 —— *“级联中的终止条件”* |
| **前置条件** | 必须具备什么，该字段才有意义 |
| **后置条件** | 填写之后成立什么 |
| **为空时** | 静默接受 · 设置默认值 · 追问 · 阻止 |
| **错误时** | 提示、追问、修正建议 |

**最后两行是最容易被遗漏的，** 也是运行时最容易引发麻烦的。*“价格无所谓”* 是一个有效的回答，必须被设计为有效，而不是错误。

### 字段是开放的 —— 问题起限定作用

空字段是**一切，也是无物**，就像一个空的上下文窗口：它邀请人们填入任何东西。但填什么呢？

**限定并非来自字段本身，而是来自它周围的内容** —— 通常是前面、上方或旁边的相关文字：

> *“最多希望花多少钱？”*

这个问题在**语义与语用上**都起到限定作用。字段本身仍然接受一切；而一旦有人充分利用这份自由，它就失去了用途。因此字段约束会介入：*只允许数字*。不是因为“三十五”难以理解，而是因为它更难处理，也更费时输入。

**由此得出工作方向：字段规则应从问题中推导，而不是反过来。** 如果先确定了数据类型，就等于已经忘记了问题本身。

而问题通常也承载**目的**，因此人们的界面上常会在旁边放一个信息图标：

> *“如果报价高于此价格，我们不接受。”*

这并非礼貌用语，而是字段真正的含义：**用户的一个偏好，之后会作为硬性门槛起作用。**

### 控制边界 —— 以及为何一切都必须随身携带

从一个字段出发，会形成一条链：

```
Feld „Höchstbetrag"
   → der Wert wird später gebraucht        (Zweck)
   → für eine Prüfung                       (Gate)
   → also muss der Gegenwert erhoben werden (neue Frage, an anderer Stelle)
   → diese Frage stellt niemand von uns     (sie steht im Prompt)
```

**决定性的界线就在这里：提示词一旦发出，就离开了我们的控制层。** 之后再也无法访问 —— 无法跟进、无法干预、没有第二次机会。

因此，凡是对方需要的一切都必须一并携带：

- **值本身** —— 35 欧元
- **获取对应数值的指令** —— 询问价格
- **若价格更高时怎么办** —— 拒绝、致谢、礼貌结束
- **若对方没有给出价格时怎么办** —— 不要估算，直接拒绝
- **若对方不想与机器交谈时怎么办** —— 请求人工回电，并将电话号码作为值返回

最后一点揭示了设计时最少被想到的方向：**即使是例外情况，也必须返回一个值**，否则人这边除了“没有成功”之外什么也收不到。

### 提示词就是一个即时生成的技能

由此可以明确，提示词究竟是什么：

> **提示词是界面刚刚组装出来的一个技能** —— 由这一次运行中的决定、点击与值拼成。它是个性化的，针对目的量身定制，并且被迫把所有想要的内容**用语言**表达出来。

一个固定写好的技能说明的是我们*总是*如何做。而一个提示词说明的是*这一次*应如何进行。两者形式相同 —— 一个持续存在，另一个在当下产生，用完即逝。

**实际意味着：** 若把提示词构建当作拼凑文本片段，就会写出糟糕的提示词。若把它当作*技能的生成*来对待 —— 包含目的、规则、边界、例外与返回值 —— 才能写出好的提示词。

### 等待并非无所事事，而是不知情

发送之后，人已经交出了控制权。此时他需要的不是耐心，而是**信息**：*现在发生了什么？进行到哪一步了？*

智能体本来就能获得这些信息 —— 它会查询进度。**但只要没有人把它翻译出来，人就什么也看不到。** 进度条、滚动日志和状态行正是为此而存在：它们不是装饰，而是把数据流翻译成等待者能够忍受的形式。

### 反馈是一个回传的提示词

成功消息不是结束，而是一次**交还**：

> *“这是你的任务的结果。”*

只有这样，人才能评估并继续行动。正因如此，它必须完整：*“已下单 —— 但是三份披萨而不是一份。好在回电号码就在这里，我自己打电话。”*

**没有可用的返回值，任何人都无法继续处理。** 只说“成功了”的消息，并没有闭合这个循环。

### 字段与问题分析

对于蓝图中的**每一个**元素 —— 字段、按钮、选择、显示 —— 都提出相同的问题：

| | |
|---|---|
| **想要什么，为什么？** | 该元素背后的意图 |
| **提交时会发生什么？** | 立即处理，还是先保存？ |
| **该值何时何地再次被需要？** | 它发生作用的位置 |
| **需要保留多久？** | 超出一次点击？超出一次运行？ |
| **对它必须做什么？** | 检查、携带、显示、丢弃 |

例如，上限金额**并非立即**被需要。它会被保存、携带，并且只在对话中才发挥作用 —— 因此需要一个存放它的位置，以及一个让它进入提示词的地方。

### 分支决定提问算法

一个选择很少只是一个值。它常常是一个**分支开关**，会改变之后的整个流程：

| 模式 | 对话中的第一个问题 | 取消什么 | 新增什么 |
|---|---|---|---|
| **配送** | *“请问送到这里吗？”* —— 回答否，立即结束通话 | — | 配送地址 |
| **自取** | 取消 | 配送问题 | 取餐时间 |
| **订座** | *“你们营业吗？X 点是否有空桌？”* | 整个价格检查 | 人数、儿童、座位需求、时间段 |

**对话中的顺序遵循排除力，而非好奇心。** 不配送的，就不必再询问餐食相关的问题 —— 最严格的条件最先提出，因为它能最快引向下一个候选项。

而且：**许多东西在各分支之间保持不变。** 上限金额无论是配送还是自取都适用，候选列表也是一样。变化的只是提问算法。

### 循环

```
Problem  →  Use Case  →  Wille        „Ich bin auf dem Land und habe Hunger"
   ↓
was ich will, wird zu Bedingungen     5 Personen · 19 Uhr · Italiener · nicht der eine
   ↓
Bedingungen brauchen Daten            → daraus ergeben sich die FELDER
   ↓
Felder + Entscheidungen               → daraus wird der PROMPT (der erzeugte Skill)
   ↓
                [ Ausführung jenseits der Kontrollgrenze ]
   ↓
Rückgabe empfangen und speichern      → nur, was vorher mitgegeben wurde, kommt zurück
   ↓
übersetzen in Sicht- und Hörbares     → MELDUNG an den Menschen
   ↓
er bewertet und entscheidet neu       → zurück nach oben
```

**用例为数据提供依据，数据为字段提供依据。** 从字段开始，就是凭空设计表单；从意图开始，表单则会自然得出。

### 两个蓝图之间是因果关系

蓝图是一种**静态排列**。若干蓝图依次排列，仍然构成不了流程 —— 中间会发生某些事，**而这个“中间”才是真正的逻辑**：这里一点击会发生什么？会运行哪项检查？会保存什么？会触发什么？

使这一时间层面可见的三种方式：

1. **图中的标注** —— 蓝图之间的箭头与简短注释
2. **前后对照** —— 同一片段的两种状态，“点击前”与“点击后”
3. **文字化** —— 图下方以文字写出前置条件与后置条件

第三种方式作用最广，因为它是可执行的。前两种则主要帮助人理解。

### 数据模型由字段产生

描述一个“添加联系人”字段时，就已经决定了存在收件人、他们会被保存，以及包含哪些信息。**数据表应依据字段来确定，而不是反过来。**

因此，在设计任何模式之前，把字段图例写完整是值得的：每个带有类型与目的的字段是一列，每个可重复的组是一张表，字段之间的每个关系是一个引用。

## 方向一：从文字到界面

**当流程首先被描述时。**

1. **收集决定。** 任何需要确定某事的地方。并进行分类：
   - **必填** —— 没有它就无法继续 → **必填字段**
   - **可推导** —— 可以来自上下文或已有数据 → 带可更正选项的**预填字段**
   - **可选** —— 能改善结果 → **折叠区域**
   - **关卡** —— 不可逆、花钱、会触达他人 → **确认步骤**
2. **将相关内容归组** → 一个界面、一个模板。
3. **把流程树切分为视图。** 一种状态 = 一个视图。
4. **设计反馈。** 何时反馈什么？进度、中间状态、结果。
5. **把始终有效的内容一次性确定下来** —— 颜色、排版、版式、动效。这些就是界面的策略。

**收获：** 从对话流程生成的表单，几乎总比凭空设计的更精简。在表述过程中，人会注意到哪个问题是多余的。

## 方向二：从界面到文字

**当应用程序已经存在或已被描述时。**

1. **把每次点击表述为一个问题。** 这个按钮究竟在问用户什么？
2. **把每个字段写成一条 Config 项** —— 包含默认值、类型与帮助文本。
3. **把每个视图写成流程中的一个步骤。**
4. **把每条消息写成一次返回** —— 报告什么，用什么文字？
5. **检查界面隐含知道的内容** —— 顺序、锁定、依赖关系，它们并不写在任何地方，只存在于布局之中。**正是这部分在翻译时最容易丢失。**

### 为何这个方向更难，以及如何仍然做到

方向一较容易，方向二感觉更吃力。原因如下：

> **技能是时间。屏幕是平面。**
> 先这个，再那个 —— 而屏幕上一切同时可见。

因此，你不是逐行翻译，而是**把一个流程切成若干平面**。切割的边界始终相同：

**屏幕产生于流程在此等待一个人的地方。**

两个等待点之间的一切都会自动运行 —— 那不会成为屏幕，最多是一个进度指示。为每一步都建一个视图，就是造了一座点击的牢笼。

**那么 if-then 链呢？** 并不是所有分支都会变得可见。四种情况：

| 条件的类型 | 它变成什么 |
|---|---|
| **人来设定**（“最多 35 欧元”） | 一个**字段** —— 在开始之前 |
| **系统来检查**（“价格超出上限”） | 一个**结果** —— 之后给出，并附理由 |
| **它改变了人所看到的内容**（“没有匹配项”） | 同一屏幕的一个**状态**，而不是新屏幕 |
| **它纯属机制**（重试、超时、格式校验） | **什么都不是** —— 它保持不可见 |

**第四种情况最为常见。** 脚本中的大多数分支根本不应出现在屏幕上。如果仍然展示它们，就是把流程图与界面混为一谈了。

**实践上可分四步：**

1. **标出等待点** —— 每个人需要做决定、确认或输入的位置。这些就是屏幕，而且数量通常出人意料地少。
2. **向回收集（回溯）** —— 在这个等待点之前，必须已知什么？这些值就是该屏幕的字段。
3. **向前收集（推演）** —— 之后会发生什么，其中哪些必须让人知道？这就是反馈。
4. **舍弃其余** —— 凡既非输入也非反馈的内容，都保持不可见。

## 梯度：技能 ↔ 脚本

```
weit von der Software                                    nah an der Software
   Skill trägt alles                                    Skript trägt alles
        │                                                       │
   ausführlicher Text          ────────────►         knappe Bedienungsanleitung
   jeder Schritt erklärt                             „ruf dies auf, dann jenes"
   funktioniert ohne Werkzeug                        funktioniert nur mit Werkzeug
```

**一个流程越自动化，技能需要解释的就越少。** 它会变得更简短、更具体 —— 最终几乎只剩下对脚本的一份操作说明：*什么时候用这个工具，输入什么，如何判断它是否成功。*

两条在日常中很有帮助的反向推论：

- **技能变得太长，说明缺一个脚本。** 长度是一个信号：凡是重复且机械的部分，都应该自动化。
- **脚本变得难以理解，说明缺一个技能。** 一个没有说明文字的工具，只对构建它的人可用。

## 共同的货币

**每个设置都以三种形式存在** —— 作为 Config 值、作为技能中的问题、作为界面中的字段。为了不让它们互相偏离，关于其呈现方式的描述只写**一次**，并由这三者共同读取：

```yaml
field: sample.method
label: "Ziehungsverfahren"                       # Oberfläche
question: "Wie soll gezogen werden — zufällig, geschichtet oder alle?"   # Skill
type: choice
options: [random, stratified, census]
default: random
help: "Geschichtet nur, wenn die Merkmale in der Grundlage stehen."
locked: false        # true = nicht abschaltbar, erscheint in keiner Oberfläche
```

**凡是 `locked`，都不会作为选项出现在任何地方。** 有些东西并不是设置，而是框架的一部分。

## 何时这份技能有帮助

- 正在设计一个应用程序，而流程尚不清楚 → **方向一**
- 一个现有工具需要供智能体使用 → **方向二**
- 界面与智能体访问方式出现偏离 → 引入**共同的货币**
- 技能变得过长而无人知道原因 → 检查**梯度**
- 一次设计对话需要在消失之前记录下来 → 表格 + 树
