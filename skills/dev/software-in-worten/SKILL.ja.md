# 言葉でつくるソフトウェア

## 考え方

人は**視覚的に**設計します。*これをどう操作したいか？* エージェントは**テキスト**を読みます。
両者が別々に作られると、互いにずれていきます。インターフェースにはできてもスキルには
知られていないことがあり、その逆もあります。

しかし、どちらも同じものが異なる状態で存在しているにすぎません。両者のあいだには
翻訳が成り立ち、それを知っている人は両方向に作業できます。

> **言葉からインターフェースを設計する。そして、インターフェースを言葉へ戻す。**

---

## 翻訳表

| インターフェース上の要素 | 意味すること | テキストでは |
|---|---|---|
| **マウスカーソル** | *選択できる* — 可能性の領域 | その地点でのオプションの集合 |
| **選択（マーキング）** | *これがほしい* | 選択、値 |
| **クリック** | *決めた、そこへ行きたい* | **プロンプト** — ユーザーの回答 |
| **フィールド、スイッチ、設定** | 残り続ける決定 | **Config** |
| **ソフトウェア全体の設定** | どこでも有効な決定 | **Policies** |
| **フォーム、入力マスク** | 関連する決定の集まり | **Template** |
| **何かを開始するボタン** | *今まさに何かが起きる* | **Skill** または **Workflow** が起動される |
| **その後に実行されること** | 手順の流れ | スキル内の指示 — または **スクリプト** |
| **進捗表示** | *実行中であり、どこまで進んだか* | 処理中のステータスメッセージ |
| **成功メッセージ、結果表示** | *この結果が出た* | 戻り値 — インターフェースでは見た目が整えられるだけ |
| **プロジェクト** | 区切られた作業状態 | **フォルダ** — それ自体がフォルダ内にあるため、ソフトウェアの一部 |
| **ビュー、タブ、領域** | 今いる状態 | 処理ツリー内の一つのステップ |

**中心となる行はクリックです。** クリックは、ユーザーが会話で言うであろうことを、
より速く表現したものにすぎません。**クリックはプロンプトです。** そしてプロンプトには
反応が続きます：新しい質問、新しいビュー、新しい状態。

## 処理は木構造である

あらゆるアプリケーションは、その間に何かが起こる一連の決定です：

```
Voraussetzungen geklärt?   →  Referenzen · Kandidatenliste · Nummern · Reihenfolge
        ↓
Einverständnis des Nutzers →  START
        ↓
Will er mitlesen?          →  ja: Mitleseansicht öffnen
Will er Zwischenmeldungen? →  ja: bei jedem Ereignis melden (durch, abgelehnt, Status)
        ↓
        [ AUSFÜHRUNG — oft ausgelagert an andere Software ]
        ↓
Rückgabe kommt zurück      →  auswerten
        ↓
Was will er wissen?        →  das Ergebnis in seinen Begriffen:
                              „bestellt bei X, 40 Minuten, 30 Euro"
```

**常に同じ三つの部分：**

1. **決定** — もし〜ならば、必要なものがそろうまで
2. **実行** — 多くの場合、自前のツールではなく外部に委託される
3. **フィードバック** — 結果を人に、その人の言葉で返す

設計時に最も過小評価されやすいのが三つ目です。**コミュニケーションは感覚を通じて行われます**
— テキストとして、画像として、音として。インターフェースはそれを形づくり、スキルは
*何を*、*いつ*フィードバックするかを記述します。

## 中間段階：ブループリント

「記述された」と「作られた」のあいだには、欠けている段階があります。それが**ブループリント**
です。これは**配置が画像に対応したテキスト** — 読むことのできる画面です：

```
 Worauf hast du Hunger?   [ Burger                        ]
 Wohin liefern?           [ Dorfstraße 1, 16321 Bernau    ]
 Höchstbetrag             [ 35 ] €   ⓘ Endbetrag an der Haustür
 Modus                    (•) Lieferung  ( ) Tisch  ( ) Abholung

 Kandidaten (ziehen zum Umsortieren)            ↻ neu suchen
 ┌────────────────────────────────────────────────────┐
 │ ≡ 1  Burger House Dorfstadt      ★ Favorit   offen │
 │ ≡ 2  Pizzeria Roma                            offen │
 └────────────────────────────────────────────────────┘

 [ Trockenlauf ansehen ]   [ Wirklich anrufen → 4 Anrufe, ~0,20 € ]
```

**この段階がこれほど有用な理由：**

ブループリントは**読むことも見ることもできます**。人は自分のイメージを見直せ、エージェントは
フィールド、型、順序を見ることができます。数分で作れ、コストもかからず、会話の中で修正できます
— 作り込まれたインターフェースとは異なります。

**そしてブループリントからは、スキルがほぼ自然に導かれます：**

> **このブループリントを埋めるために、エージェントは何を できて、何を知り、何を行う必要があるか
> — どの順序で？**

各フィールドが一つの質問になります。配置が順序になります。すでに入っている値は尋ねません。
ボタンとして置かれたものはステップになります。その後、エージェントが追加で知る必要のあること
— 専門知識、制限、落とし穴 — を補っていきます。

**つまり三段階です：** 記述 → **ブループリント** → スキル *（そしてそこから同じく容易に
作り込まれたインターフェースへ）*。

### 空のフィールドは問いであり、その問いには目的がある

`[ 35 ] €` は数値のように見えます。しかしそれは**人への データ照会**であり、その理由は
たいてい語られません：

> **この上限額が必要なのは、それが注文が行われる条件そのものだからだ。**

つまりフィールドは三つのものを同時に担っています：**何を**入れるべきか、**なぜ**必要か、
そして**後でどこで効くか**。インターフェースでは、それはレイアウトやヘルプテキストに
含まれています。テキストでは、それを書き下さなければなりません — さもないと失われます。

**そのため、すべてのブループリントの下にはフィールド凡例が必要です：**

| | |
|---|---|
| **問い** | 人に実際に尋ねるとしたらどう聞くか |
| **型** | 数値、テキスト、選択、リスト、順序付きリスト、日付 … |
| **目的** | 値が後で何に使われるか — *「カスケード内の打ち切り条件」* |
| **前提条件** | フィールドが意味を持つために、先に存在していなければならないもの |
| **事後条件** | 入力された後に成立すること |
| **空の場合** | 黙って受け入れる · 既定値を設定 · 問い返す · ブロックする |
| **不正な場合** | メッセージ、問い返し、修正案 |

**最後の二行は最も忘れられやすく**、運用中に最も多くのトラブルを生みます。*「価格は問わない」*
は有効な回答であり、エラーとしてではなく、そのようなものとして想定されていなければなりません。

### フィールドは開いている — 問いが絞り込む

空のフィールドは**すべてであり、同時に何でもない**ものです。空のコンテキストウィンドウと同じく、
何でも書き込んでよいという招待です。しかし何を？

**絞り込まれるのはフィールド自体ではなく、その周囲にあるもの** — たいていは直前、直上、
直側にある、つながったテキストです：

> *「せいぜい、いくらまでなら払えますか？」*

この問いは**意味的にも語用論的にも**絞り込みます。フィールド自体は依然としてすべてを許容します —
そして誰かがその自由を使うと、フィールドはその目的を失います。そこでフィールドの条件が介入します：
*数字のみ*。「三十五」が理解不能だからではなく、処理しにくく、書くのに手間がかかるからです。

**ここから作業の方向が決まります：問いからフィールドのルールが導かれるのであって、その逆ではありません。**
先にデータ型を決めてしまう人は、すでに問いを忘れています。

また、問いはたいてい**目的**も担っています。そのため人間の場合、横に情報マークが付くことが多いのです：

> *「この価格を超える見積もりは受け付けません。」*

これは丁寧さではなく、フィールドの本来の意味です：**ユーザーの好みであり、後で厳格なゲートとして
働くもの。**

### 制御の境界 — そしてなぜすべてを渡さなければならないか

フィールドからは一連の流れが続きます：

```
Feld „Höchstbetrag"
   → der Wert wird später gebraucht        (Zweck)
   → für eine Prüfung                       (Gate)
   → also muss der Gegenwert erhoben werden (neue Frage, an anderer Stelle)
   → diese Frage stellt niemand von uns     (sie steht im Prompt)
```

**そして決定的な境界線がここにあります：プロンプトとともに、それは私たちの制御層を離れます。**
その後はもうアクセスはありません — 追いかけることも、介入することも、二度目のチャンスもありません。

そのため、向こう側で必要になるものは**すべて**渡さなければなりません：

- **値そのもの** — 35 €
- **対価を取得する指示** — 価格を尋ねる
- **それが高かった場合に何が成り立つか** — 断る、礼を言う、丁寧に終える
- **誰も言わなかった場合に何が成り立つか** — 推測せず、断る
- **相手が機械と話したくない場合に何が成り立つか** — 担当者からの折り返しを頼み、番号を戻り値として返す

最後の点は、設計時に最も考えられにくい方向を示しています：**例外のケースでも値を返さなければ
ならない**のです。さもないと、人に届くのは「うまくいかなかった」だけになります。

### プロンプトは生成されたスキルである

これで、プロンプトとは本来何であるかが明らかになります：

> **プロンプトとは、インターフェースがたった今組み立てた一つのスキルである** — この一回の実行における
> 決定、クリック、値から。個人向けに調整され、目的に合わせられ、望まれたことすべてを**言葉で**
> 表現するよう強いられている。

固定的に書かれたスキルは、*いつも*どうやるかを述べます。プロンプトは、*今回*どう進めるべきかを述べます。
両者は同じ形式であり、一方は残り、もう一方はその瞬間に生まれて、その後は消えます。

**実践的な意味：** プロンプトの組み立てをテキスト部品の寄せ集めとして扱う人は、悪いプロンプトを作ります。
それを*スキルの生成*として扱う人 — 目的、ルール、制限、例外、戻り値を備えて — は、良いプロンプトを作ります。

### 待つことは何もしないことではなく、情報がないこと

送信後、人は制御を手放しています。そこで必要なのは忍耐ではなく、**情報**です：*今何が起きている？
どこまで進んだ？*

エージェントはそれをすでに受け取っています — 進捗を問い合わせるからです。**しかし人は、
誰かがそれを翻訳しない限り、何も見えません。** まさにそのために、進捗バー、並走するログ、
ステータス行が存在します。それらは装飾ではなく、データの流れを待つ人が耐えられる形へと
翻訳したものです。

### フィードバックは逆方向のプロンプトである

成功メッセージは締めくくりではなく、**返却の受け渡し**です：

> *「これがあなたの依頼の結果です。」*

そうして初めて、人は評価して次の行動に移れます。だからこそそれは完全でなければなりません：
*「注文は完了 — ただしピザが一枚ではなく三枚になっています。折り返し番号が書いてあって助かります、
自分で電話します。」*

**使える戻り値がなければ、誰も次の処理をできません。** 「うまくいった」としか言わないメッセージでは、
円は閉じていないのです。

### 質問とフィールドの分析

ブループリントの**すべての**要素 — フィールド、ボタン、選択、表示 — について、同じ問いを立てます：

| | |
|---|---|
| **何が望まれ、それは何のためか？** | その要素の背後にある意図 |
| **送信時に何が起きるか？** | すぐに処理されるか、まず保存されるか？ |
| **値はどこで、いつ再び必要になるか？** | その値が効く場所 |
| **どれくらいの期間保持しなければならないか？** | クリックを超えて？実行を超えて？ |
| **それをどうしなければならないか？** | 検証、受け渡し、表示、破棄 |

たとえば上限額は**すぐには**必要ありません。保存され、持ち運ばれ、会話の中で初めて効きます —
つまり、それが置かれる場所と、プロンプトへ移される箇所が必要です。

### モードの分岐が質問のアルゴリズムを決める

選択肢はめったに単なる値ではありません。多くの場合、その後の流れ全体を切り替える**分岐**です：

| モード | 会話での最初の質問 | 省略されるもの | 追加されるもの |
|---|---|---|---|
| **配達** | *「こちらへの配達をお願いできますか？」* — いいえで即通話終了 | — | 配達先住所 |
| **受け取り** | 省略 | 配達の質問 | 受け取り時刻 |
| **席の予約** | *「営業していて、Xの時刻に空席はありますか？」* | 価格確認全体 | 人数、子どもの有無、座席の希望、期間 |

**会話の順序は好奇心ではなく、排除力に従います。** 配達しない店には、料理について尋ねる必要はありません —
最も厳しい条件を最初に出すのは、次の候補へ最も速く導くからです。

そして、**分岐をまたいでも変わらないものが多くあります。** 上限額は配達でも受け取りでも変わらず、
候補リストも同様です。変わるのは質問のアルゴリズムだけです。

### 円環

```
Problem  →  Use Case  →  Wille        „Ich bin auf dem Land und habe Hunger"
   ↓
was ich will, wird zu Bedingungen     5 Personen · 19 Uhr · Italiener · nicht der eine
   ↓
Bedingungen brauchen Daten            → daraus ergeben sich die FELDER
   ↓
Felder + Entscheidungen               → daraus wird der PROMPT (der erzeugte Skill)
   ↓
                [ Ausführung jenseits der Kontrollgrenze ]
   ↓
Rückgabe empfangen und speichern      → nur, was vorher mitgegeben wurde, kommt zurück
   ↓
übersetzen in Sicht- und Hörbares     → MELDUNG an den Menschen
   ↓
er bewertet und entscheidet neu       → zurück nach oben
```

**ユースケースがデータを正当化し、データがフィールドを正当化します。** フィールドから始める人は
フォームを発明します。意図から始める人は、それを手に入れます。

### 二つのブループリントのあいだには因果関係がある

ブループリントは**静的な配置**です。いくつか並んでも、まだ流れにはなりません — そのあいだに何かが
起きており、**その「あいだ」こそが本当のロジック**です：ここでクリックされると何が起きるか？
どのチェックが走るか？何が保存されるか？何がトリガーされるか？

この時間的な層を可視化する三つの方法があります：

1. **画像内の注記** — ブループリントのあいだの矢印と短いメモ
2. **前後の対** — 同じ切り取りを二つの状態で、「クリック前」と「クリック後」
3. **文章化** — 画像の下に、事前条件と事後条件をテキストで書く

三つ目の方法が最も遠くまで届きます。実行可能だからです。最初の二つは、人が理解する助けになります。

### フィールドからデータモデルが生まれる

「連絡先を追加」というフィールドを記述した人は、すでに、宛先が存在すること、それが保存されること、
どの情報がそれに属するかを決めています。**データテーブルはフィールドに従うのであって、その逆ではありません。**

そのため、どのスキーマを設計する前にも、フィールド凡例を完全にしておく価値があります：型と目的を
持つ各フィールドは一つの列になり、繰り返されるグループは一つのテーブルになり、フィールド同士の
関係はそれぞれ参照になります。

## 方向1：言葉からインターフェースへ

**最初にフローが記述されている場合。**

1. **決定を集める。** 何かが定められるすべての箇所。その際に分類する：
   - **必須** — これがなければ先へ進めない → **必須フィールド**
   - **導出可能** — 文脈や既存データから得られる → 修正可能な**既定値付きフィールド**
   - **任意** — 結果を改善する → **折りたたみ領域**
   - **ゲート** — 取り消せない、費用がかかる、人に届く → **確認ステップ**
2. **関連するものをまとめる** → 一つのマスク、一つのテンプレート。
3. **木構造をビューに切り分ける。** 一つの状態 = 一つのビュー。
4. **フィードバックを設計する。** 何を、いつ知らせるか？進捗、中間結果、最終結果。
5. **全体を通じて変わらないものを一度決める** — 色、タイポグラフィ、レイアウト、動き。
   これらがインターフェースのポリシーです。

**利点：** 会話の流れから生まれたフォームは、製図台で作られたものよりほぼ常に簡潔になります。
言語化する中で、どの質問が不要かが分かるからです。

## 方向2：インターフェースから言葉へ

**アプリケーションがすでに存在する、または記述されている場合。**

1. **すべてのクリックを質問として言語化する。** このボタンは実際にユーザーに何を尋ねているのか？
2. **すべてのフィールドを Config の項目にする** — 既定値、型、ヘルプテキストとともに。
3. **すべてのビューを流れのステップにする。**
4. **すべてのメッセージを戻り値にする** — 何が、どのような言葉で報告されるか？
5. **インターフェースが暗黙のうちに知っていることを確認する** — どこにも書かれず、レイアウトの中にだけ
   潜んでいる、順序、ロック、依存関係。**これは、翻訳時に最も失われやすい部分です。**

### なぜこちらの方向は難しく、それでもどう進めるか

方向1は容易で、方向2はぎこちなく感じられます。理由があります：

> **スキルは時間であり、スクリーンは面である。**
> これが先で、あれが後 — すべてを同時に見渡せる形で。

つまり、一行ずつ翻訳するのではなく、**流れを面へと切り分けます**。その切断線は常に同じです：

**スクリーンは、流れが人を待つ場所に生まれる。**

二つの待機点のあいだのすべては自動的に進みます — それはスクリーンにはならず、せいぜい進捗表示に
なるだけです。すべてのステップにビューを作れば、クリックの牢獄ができあがります。

**では、if-then の連鎖は？** すべてが目に見えるわけではありません。四つのケースがあります：

| 条件の種類 | そこから生まれるもの |
|---|---|
| **人が定める**（「せいぜい35 €」） | **フィールド** — 開始前に |
| **システムが検査する**（「価格が上限超過」） | **結果** — その後、理由付きで |
| **人が見るものを変える**（「該当なし」） | 同じスクリーンの**状態**、新しいスクリーンではない |
| **純粋な仕組み**（再試行、タイムアウト、形式チェック） | **何もない** — 見えないままにする |

**四番目のケースが最も多い。** スクリプトの分岐のほとんどは、画面に載ることは決してありません。
それでも表示する人は、フローチャートとインターフェースを取り違えています。

**実践的な四つのステップ：**

1. **待機点をマークする** — 人が判断し、確認し、入力するすべての箇所。これらがスクリーンであり、
   たいてい驚くほど少ない。
2. **逆向きに集める** — この待機点の前に、何が既知でなければならないか？その値がスクリーンのフィールドになる。
3. **順方向に集める** — その後何が起き、そのうち人が知る必要があるのは何か？それがフィードバックになる。
4. **残りを省く** — 入力でも通知でもないものはすべて、見えないままにする。

## グラデーション：スキル ↔ スクリプト

```
weit von der Software                                    nah an der Software
   Skill trägt alles                                    Skript trägt alles
        │                                                       │
   ausführlicher Text          ────────────►         knappe Bedienungsanleitung
   jeder Schritt erklärt                             „ruf dies auf, dann jenes"
   funktioniert ohne Werkzeug                        funktioniert nur mit Werkzeug
```

**処理が自動化されるほど、スキルが説明すべきことは減ります。** スキルは短く具体的になり、
やがてスクリプトの操作説明に近いものになります：*いつこのツールを使うか、何を入れるか、
うまくいったことをどう判断するか。*

日常で役立つ二つの逆の推論があります：

- **スキルが長くなりすぎたら、スクリプトが足りない。** 長さは信号です：繰り返され、機械的なものは
  自動化すべきです。
- **スクリプトが分かりにくくなったら、スキルが足りない。** 説明文のないツールは、作った本人にしか使えません。

## 共通通貨

**あらゆる設定は三重に存在します** — Config の値として、スキル内の問いとして、インターフェース上の
フィールドとして。ばらばらにならないよう、その表現は**一度だけ**記述され、三者すべてがそれを読みます：

```yaml
field: sample.method
label: "Ziehungsverfahren"                       # Oberfläche
question: "Wie soll gezogen werden — zufällig, geschichtet oder alle?"   # Skill
type: choice
options: [random, stratified, census]
default: random
help: "Geschichtet nur, wenn die Merkmale in der Grundlage stehen."
locked: false        # true = nicht abschaltbar, erscheint in keiner Oberfläche
```

**`locked` であるものは、選択肢としてどこにも現れません。** 設定ではなく、足場の一部であるものもあります。

## このスキルが役立つとき

- アプリケーションを設計していて、流れがまだ不明確 → **方向1**
- 既存のツールをエージェントが使えるようにしたい → **方向2**
- インターフェースとエージェントからのアクセスが乖離している → **共通通貨**を導入する
- スキルが長くなりすぎて理由が分からない → **グラデーション**を確認する
- 設計の会話が消えてしまう前に記録したい → 表 + 木構造

## 関連

`condition` は、条件、時点、順序を検証可能なゲートへと翻訳します
（`/if`、`/when`、`/after`、`/and`、`/or`）
— 同じ動きを、フローの制御という特別なケースに適用したものです。
`skill-extractor` は会話の経過からスキルを獲得します。`plugin-system` は自作のスクリプトを見つけやすくします。
